*Saison 1 — Démarrer · Épisode 3 (final de saison)*

> **Précédemment.** Nous avons construit un monde jetable : une base, un stockage, une boîte mail qui n'écrit à personne. Tout compile, tout s'affiche. Et nous avons appris que c'est précisément là que le danger commence.

## Le fichier fantôme

Faisons une expérience. Elle tient en une ligne d'arborescence, et chacun peut la reproduire.

Next.js propose un fichier spécial, `proxy.ts`, qui s'exécute avant chaque requête : l'endroit rêvé pour vérifier qu'un visiteur a le droit d'entrer. Écrivons-le. Posons-le dans `apps/web/`, à la racine de l'application, là où il semble naturel qu'il vive. Redémarrons. Pas d'erreur, pas d'avertissement.

Il ne s'exécute jamais.

Next ne cherche ses fichiers de convention (`proxy.ts`, `instrumentation.ts`…) qu'à un endroit précis : **à côté du dossier `app`**. Le nôtre vit dans `apps/web/src/app`. Un `proxy.ts` posé un étage plus haut est un fichier comme un autre : Next l'ignore poliment, et la porte reste sans gardien.

TypeScript n'a rien vu : le code était juste. Next n'a rien dit : il n'avait aucune raison de chercher là. Et en testant connectés, nous ne remarquerions rien non plus.

C'est cela, une **erreur silencieuse** : du code correct, au mauvais endroit ou au mauvais moment, et aucun outil pour le signaler. Une erreur de compilation est une bonne nouvelle : elle s'affiche, désigne une ligne, bloque. Celles qui coûtent cher sont les autres.

« Ça compile » ne suffit pas. Il nous faut des vérifications qui cherchent précisément ce que les outils ne voient pas.

## La sentinelle

Toutes les vérifications du projet tiennent dans une commande, lancée à la racine :

```bash
pnpm check
```

Elle enchaîne cinq étapes, et s'arrête à la première qui échoue :

Regardons la première ligne : le fichier fantôme y est devenu un script. Les deux scripts maison sont courts, et c'est voulu : chacun traque **une seule** erreur silencieuse, et l'explique en français quand il la trouve.

C'est la réponse que nous donnerons, encore et encore : quand une erreur silencieuse nous a mordus, nous n'écrivons pas « faire attention » sur un post-it. Nous écrivons une vérification.

<Callout type="warning">
`pnpm clean` supprime le dossier `.next` alors que `pnpm dev` s'en sert peut-être. Après un `pnpm check`, si une modification n'apparaît pas dans le navigateur, arrêtons `pnpm dev` (Ctrl+C) et relançons-le : ce n'est pas le code qui est en cause.
</Callout>

## Le code qui marchait trop bien

TypeScript vérifie les types ; il ne sait rien de React. ESLint, avec les règles `react-hooks`, connaît les règles de React, et elles se sont durcies avec React 19 et son compilateur.

```bash
pnpm lint
```

Le carrousel de la page d'accueil gardait l'état « lecture ou pause » dans une `ref`, pour que sa boucle d'animation puisse le lire à chaque image :

```tsx
const playingRef = useRef(playing);
playingRef.current = playing; // écrit PENDANT le rendu
```

Le code marchait. Il marchait depuis des mois. ESLint le refuse pourtant : « Cannot update ref during render ».

Pourquoi ? Parce qu'un rendu React doit être une fonction pure. React se réserve le droit de le lancer deux fois, de l'interrompre au milieu, de le jeter pour en recommencer un autre. Écrire dans une `ref` pendant le rendu, c'est parier que React ne fera jamais rien de tout cela. Le pari était gagné hier. Il le serait peut-être encore demain. La correction le supprime en déplaçant l'écriture après le rendu :

```tsx
const playingRef = useRef(playing);
useEffect(() => {
  playingRef.current = playing; // écrit APRÈS le rendu
}, [playing]);
```

La boucle d'animation ne lit la `ref` que hors rendu : le comportement est identique, et le pari a disparu.

<Callout type="tip">
Une règle de lint qui se déclenche sur du code « qui marche » n'est pas une fausse alerte. C'est presque toujours un pari sur le comportement de React, gagné aujourd'hui, et perdu le jour où React change sa façon de rendre.
</Callout>

## Petits pas

Un commit est une marche qui tient debout toute seule : `pnpm check` passe avant et après. Nous n'enregistrons jamais un état intermédiaire « pour ne pas le perdre » ; une branche sert à ça.

Quand une fonctionnalité touche le backend et le front, nous la coupons en deux : d'abord le backend (le modèle, la procédure, ses vérifications), puis le front qui l'utilise. Si la seconde moitié révèle un problème dans la première, nous savons exactement où regarder.

Les messages suivent la forme `type(portée): résumé`, en français, avec un corps qui dit **pourquoi** :

```text
feat(rgpd): formulaire de droit à l'image — téléchargement, dépôt admin, aperçu membre
fix(carousel): erreurs react-hooks/refs et react-hooks/immutability
style(header): logo encore agrandi, barre de même hauteur
```

## Le contrat invisible

Le site embarque des tutoriels qui guident un utilisateur pas à pas sur la vraie page, en ne laissant actif que l'élément de l'étape en cours. Chaque étape désigne son élément par un nom :

```tsx
<input
  value={title}
  onChange={(e) => setTitle(e.target.value)}
  data-tour="posts.form.title"
/>
```

Cet attribut ne change rien à l'affichage. Un développeur qui fait le ménage pourrait le supprimer sans hésiter. Et pourtant, c'est un **contrat** : le composant promet que l'élément existe sous ce nom, et un tutoriel (dans `apps/web/src/features/tours/definitions/`) compte dessus. Rompez-le, et un administrateur, quelque part, verra son tutoriel se figer au milieu d'une étape, sans comprendre pourquoi.

C'est encore une erreur silencieuse. Elle a donc, elle aussi, sa vérification : si un `data-tour` utilisé disparaît, `pnpm check` échoue et nomme le tutoriel concerné. Nous mettons alors à jour l'un ou l'autre, dans le même commit.

<Callout type="info">
Un `data-tour` ne se supprime pas « parce qu'il ne sert à rien visuellement ». Cherchons d'abord son nom dans `features/tours/definitions/` : s'il y apparaît, un tutoriel en dépend.
</Callout>

## Écrire la suite de la série

La documentation vit dans `apps/web/content/docs`, en trois dossiers qui sont aussi les trois espaces du site : `guide` pour les visiteurs et les membres, `admin` pour les administrateurs (réservé côté serveur), `dev` pour nous. Le premier dossier d'une page décide de son espace ; son en-tête (`title`, `description`, `section`, `order`) décide de sa place dans la barre latérale.

Dans l'espace développeur, quelques règles tiennent le ton. Nous écrivons avec « nous ». Chaque épisode part d'un problème réel avant d'en venir à la solution, et se termine en ouvrant sur le suivant. Les points à retenir vont dans un `Callout`. La prose porte le raisonnement ; les listes ne servent qu'aux énumérations courtes.

Une contrainte technique, enfin, a déjà coûté des heures (et c'est, devinez quoi, une erreur silencieuse). Le compilateur MDX supprime sans prévenir les expressions JavaScript dans les attributs et les chaînes d'attribut sur plusieurs lignes : le tableau s'affiche vide, sans une erreur. Le composant `DocsTable` reçoit donc ses colonnes et ses lignes en JSON, entre apostrophes simples, **sur une seule ligne**, et toute apostrophe du contenu devient une apostrophe typographique (’) :

```mdx
<DocsTable columnsJson='["Colonne A","Colonne B"]' rowsJson='[["L’exemple","oui"],["Autre","non"]]' />
```

<Callout type="tip">
Le fil de la saison tient en une phrase : **nous rendons visibles les erreurs silencieuses avant qu'elles ne partent en production**. `pnpm check` en est l'outil, le petit commit la discipline, le contrat `data-tour` un exemple. La bonne réponse à une nouvelle erreur silencieuse est rarement « faire attention » : c'est une vérification de plus.
</Callout>

## Fin de saison

Nous avons tout ce qu'il faut. Un environnement jetable. Une sentinelle avant chaque commit. Un fichier fantôme démasqué, un pari sur React annulé, un contrat protégé.

Nous pourrions nous croire à l'abri.

Mais le fichier fantôme n'était que la moitié de l'histoire. Le vrai `proxy.ts` du projet est au bon étage, à côté du dossier `app`. La sentinelle le confirme à chaque commit. Il s'exécute. Et pourtant, un jour, par acquit de conscience, nous avons ouvert une fenêtre de navigation privée, sans aucune session, et tapé l'adresse du tableau de bord.

Il s'est affiché.

Le gardien était à son poste. Il était bien réveillé. Et il regardait passer tout le monde.
