## Une vitrine et un outil dans la même application

L'Association Kung Fu Chambéry enseigne plusieurs arts martiaux dans les locaux de la MJC de Chambéry. Son application répond à deux besoins.

Le premier est une **vitrine** : un visiteur arrive sur `akfc.fr` et veut savoir quelles disciplines sont enseignées, à quelle heure, par qui, et quand aura lieu le prochain stage.

Le second est un **outil** : les administrateurs publient des actualités, rangent des photos, tiennent la liste des membres, leur transmettent des documents et répondent à leurs demandes ; les membres consultent leurs documents et partagent des fichiers dans les espaces de leurs groupes.

Les deux vivent dans **une seule application**, qui partage la base, les médias et l'authentification. Ce choix permet qu'une photo validée dans la bibliothèque apparaisse dans une galerie publique sans être copiée, qu'un compte serve aussi bien sur le site que dans le tableau de bord, et qu'une correction de modèle profite aux deux côtés à la fois.

Il a une conséquence que nous retrouverons dans chaque partie : dans une même arborescence cohabitent des pages que tout internet peut lire et des pages qui contiennent des données personnelles. Savoir où passe la frontière entre les deux, et qui la garde, est une compétence centrale sur ce projet.

<Callout type="info">
L'idée directrice : **une seule source de vérité**, servie à deux publics. Chaque fois qu'une donnée existe en double dans le projet, c'est une exception, et un commentaire la justifie.
</Callout>

## Comment lire cette documentation

Cette documentation s'adresse d'abord à un développeur qui débute. Elle ne suppose pas que nous maîtrisons déjà les sujets qu'elle traite : chaque notion est définie au moment où elle sert pour la première fois, avec ce qu'elle est **dans ce projet**.

Ses parties suivent l'ordre dans lequel on **construirait** le projet, pas celui de ses dossiers. On ne bâtit pas tout à la fois : on installe le socle, on ouvre une vitrine publique, on permet d'écrire des données, on reconnaît qui se connecte, on administre le contenu et ses fichiers, on met en ligne, puis on accueille les membres. Un même sujet peut donc revenir plusieurs fois, quand le projet en a de nouveau besoin : « Qualité (1) » vérifie le code dès qu'on en écrit, « Qualité (2) » ajoute les tests quand un besoin que la relecture ne peut pas couvrir apparaît. Ces **reprises** sont voulues : elles montrent dans quel ordre les décisions se prennent.

Il arrive qu'une partie ait besoin d'un sujet traité plus loin. Quand quelques lignes suffisent pour suivre, elle les donne, dans un encadré comme celui-ci, avec le chapitre qui l'approfondit :

<Promesse vers="dev/api/pourquoi-trpc">
**tRPC** permet au navigateur d'appeler une fonction du serveur par son nom, avec des types vérifiés des deux côtés, sans écrire d'adresse d'API à la main. C'est tout ce qu'il faut savoir pour lire la suite de ce chapitre.
</Promesse>

Le numéro du chapitre visé est calculé : il reste juste quand la documentation évolue. Et un chapitre ne s'interrompt pour traiter d'abord un autre sujet que lorsque c'est indispensable pour le comprendre ; il le dit alors explicitement.

Les mots techniques, eux, sont définis une fois, là où ils servent pour la première fois, puis réunis dans le **glossaire**, en fin de documentation. Partout ailleurs, un terme du glossaire est souligné en pointillés : le survoler (ou le toucher une fois) affiche sa définition courte et le chapitre qui le définit ; cliquer dessus ouvre son entrée, qui liste toutes les pages qui l’emploient, et dont le bouton « Retour » ramène exactement là où l’on lisait.

Chaque chapitre part d'un besoin concret, présente le choix retenu et ce qu'il permet, puis montre le code qui l'implémente. Les encadrés résument ce qu'il faut retenir ; la fin de chaque chapitre annonce la question que traite le suivant.

Le code montré est celui du dépôt. Quand un extrait est raccourci, il le dit.

<Callout type="tip">
Gardons le dépôt ouvert à côté. Chaque chemin cité s'ouvre dans l'éditeur : c'est la meilleure façon de vérifier que nous avons compris.
</Callout>

Une règle découpe ce territoire : **`apps/web` affiche, `packages/backend` décide**. Le front ne parle jamais à la base ; il appelle une procédure tRPC, et c'est le backend qui vérifie les droits, valide l'entrée, lit ou écrit. Les types qui circulent entre les deux vivent dans `packages/contracts`. Ce découpage permet qu'un changement d'un côté casse la compilation de l'autre, et donc qu'une incompatibilité soit détectée sur notre machine plutôt que devant un membre.

## Le trajet d'une action

Suivons ce qui se passe quand un administrateur publie une actualité. Ce trajet reviendra dans presque chaque partie.

1. Le formulaire vit dans `apps/web`. À l'envoi, il appelle `trpc.post.create` : un appel de fonction typé, pas une URL écrite à la main.
2. La requête arrive au routeur `post` de `packages/backend`. Le middleware `isAdmin` vérifie la session ; Zod valide le type du titre et du contenu.
3. Prisma écrit l'article dans PostgreSQL, dans une transaction qui enregistre aussi les médias qu'il référence.
4. Le front invalide son cache : la liste des actualités se recharge d'elle-même.

Ce trajet emploie déjà plusieurs mots que la suite définira en détail. Pour le lire aujourd'hui, une phrase chacun suffit :

<Promesse vers="dev/api/la-carte-du-systeme">
Le trajet complet d'une procédure, du clic à la base et retour, a sa partie : « API ». Nous y suivrons chacun de ces maillons dans le code.
</Promesse>

Les fichiers prennent un autre chemin, détaillé dans la partie « Stockage et médias ». Un fichier lourd ne transite pas par notre API : le backend délivre une autorisation signée, et le navigateur envoie le fichier directement au stockage compatible S3 (Cloudflare R2 en production, SeaweedFS sur notre machine). Le serveur n'a ainsi jamais à tenir un fichier de plusieurs dizaines de mégaoctets en mémoire.

<Callout type="info">
Deux circuits : les **données** passent par tRPC et Prisma, les **fichiers** vont directement au stockage avec une autorisation signée. Il n'y a pas d'upload dans les routeurs tRPC.
</Callout>

Le point le plus souvent mal compris : un **cours** n'a pas de date. C'est « le mardi à 20 h ». Une séance précise n'existe que pour un stage ou un événement.

## Trois environnements, une règle

Le projet tourne à trois endroits.

La **production** vit sur un serveur Hetzner, dans des conteneurs Docker, et sert `akfc.fr`. Ses données sont celles de vrais membres. La **sandbox recruteurs** est une copie autonome, lancée par `docker-compose.sandbox.yml`, avec des comptes et des contenus de démonstration. Le **développement** se fait sur notre machine, avec sa propre base, son propre stockage et sa propre boîte mail.

Cette séparation est stricte. Elle permet d'essayer une migration, de lancer un script de nettoyage ou de réinitialiser des mots de passe de démonstration sans qu'aucune de ces opérations puisse atteindre un membre réel. Elle permet aussi de détruire et reconstruire l'environnement de développement à volonté.

<Callout type="warning">
**Le développement ne touche jamais aux données de production.** Notre base locale part de zéro, se remplit de données de démonstration, et peut être détruite à tout moment. Si une commande demande l'adresse du serveur de production, nous sommes au mauvais endroit.
</Callout>

## À suivre

Nous savons ce que fait le projet, comment il est rangé et ce qu'il ne doit jamais toucher. Reste à le faire tourner.

Un `pnpm install` suivi de `pnpm dev` ne suffit pas : dès la première page, l'application interroge une base de données, demande son logo à un stockage S3, et s'attend à pouvoir envoyer des e-mails. Aucun de ces services n'existe encore sur notre machine.

</Callout>
