## Le package.json de la racine

Le `package.json` créé par `pnpm init` devient celui du projet entier :

```json
// package.json (extrait)
{
  "name": "akfc_2",
  "version": "0.1.0",
  "private": true,
  "type": "module",
```

`private: true` interdit toute publication sur le registre npm. `type: module` fait des fichiers `.js` et `.mjs` de la racine (les scripts de `scripts/`, les tests) des modules ES. Les scripts, eux, deviennent la seule porte d’entrée des commandes courantes : `pnpm dev`, `pnpm check`, `pnpm dev:infra`, `pnpm db:migrate`… Le chapitre « Le package.json et le monorepo » les détaille un par un.

À côté, deux petits fichiers figent l’environnement : `.nvmrc` (une ligne, `22`) pour Node.js, et le champ `packageManager` pour pnpm, rempli par `corepack use pnpm@10.24.0`, empreinte comprise.

## Des paquets qui se nomment et s’importent

Les `package.json` des paquets reçoivent un nom de portée, `@akfc/…`, et deux champs qui décident comment on les importe :

```json
// packages/backend/package.json (extrait)
{
  "name": "@akfc/backend",
  "private": true,
  "type": "module",
  "imports": {
    "#*": "./src/*"
  },
  "exports": {
    "./*": "./src/*"
  },
```

- `imports` : à l’intérieur du paquet, `#modules/tickets/router.ts` désigne `./src/modules/tickets/router.ts`.
- `exports` : depuis un autre paquet, `@akfc/backend/modules/tickets/router.ts` désigne le même fichier, à condition que l’importeur déclare la dépendance `"@akfc/backend": "workspace:*"`.

`create-next-app` avait posé un alias de `tsconfig`, `@/*`. Il est retiré : un seul mécanisme vaut pour tous les paquets, et c’est un standard de Node que TypeScript, webpack et Turbopack lisent tous. Le chapitre « Le package.json et le monorepo » le reprend.

## Une configuration TypeScript commune

Chaque paquet avait, ou aurait eu, son `tsconfig.json` complet. Les options communes montent dans `tsconfig.base.json`, à la racine, et chaque paquet l’**étend** :

```json
// apps/web/tsconfig.json (extrait)
{
  "extends": "../../tsconfig.base.json",
```

Deux options y sont ajoutées à la main par rapport à celles de `create-next-app` : `allowImportingTsExtensions`, qui permet d’écrire `.ts` ou `.tsx` dans un import (les champs `imports` et `exports` l’exigent), et `noEmit`, que cette option impose. Le chapitre « TypeScript et ses tsconfig » montre le fichier entier.

## Deux fichiers d’environnement

`prisma init` avait écrit un `.env` avec une valeur d’exemple. Le projet sépare ce qui se partage de ce qui ne se partage pas :

- `.env.example`, versionné : **toutes** les variables, avec des valeurs bidon et un commentaire chacune ;
- `.env.dev.example`, versionné : les valeurs du développement local, prêtes à copier, qui ne valent que pour les services de `docker-compose.dev.yml` ;
- `.env` et `apps/web/.env.local`, jamais versionnés (`.gitignore` ignore `.env*`, sauf les modèles) : les copies réelles, sur chaque machine.

Pourquoi deux copies sur la machine, et lequel des deux fichiers lit qui : c’est l’objet de la section « La configuration : deux fichiers, deux lecteurs » de la mise en route.

## Ce qui est venu ensuite

Le reste de la structure n’est pas né d’un générateur : il a été écrit au fil des besoins, et chaque partie de cette documentation raconte le sien. `docker-compose.dev.yml` et le `Dockerfile` ont leur partie ; `scripts/` et `e2e/` appartiennent à la qualité ; `packages/finder-core` et `packages/config` sont nés quand du code a dû être partagé.

<Callout type="concept">
**Une règle pour toute nouvelle pièce du dépôt.** Avant d’ajouter un fichier de configuration, chercher s’il peut étendre ou rejoindre un fichier existant (un tsconfig qui étend la base, une variable dans les modèles d’environnement, un script dans le package.json racine). Une configuration de plus est une configuration de plus à tenir à jour.
</Callout>
