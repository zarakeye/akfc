> **Précédemment.** Une seule application sert la vitrine du club et son outil de gestion. Le front affiche, le backend décide. Et le développement ne touche jamais aux données de production.

## Ce dont l'application a besoin

Dès sa première page, l'application lit ses réglages dans une base PostgreSQL, charge son logo depuis un stockage compatible S3, et doit pouvoir envoyer des e-mails (réinitialisation de mot de passe, notifications de tickets).

En production, ces services sont réels : PostgreSQL sur le serveur, Cloudflare R2 pour les fichiers, la messagerie OVH pour les e-mails. Sur notre machine, trois conteneurs les remplacent en parlant **exactement les mêmes protocoles**. L'application ne fait pas la différence : seule la configuration change. Le code testé en local est donc celui qui tournera en production, sans branche « si développement » à maintenir.

### Windows : travailler dans WSL 2

Le projet ne se développe pas dans PowerShell ni dans l'invite de commandes de Windows. Sous Windows, nous travaillons dans **WSL 2** (Windows Subsystem for Linux) : un vrai Linux, Ubuntu, qui tourne à côté de Windows. Tous les outils s'installent dans ce Linux, le dépôt y est cloné, et les commandes de cette documentation s'y tapent telles qu'elles sont données pour Linux.

WSL s'installe une seule fois, depuis une invite de commandes Windows ouverte en administrateur ; c'est la seule commande Windows de ce chapitre :

```bash
wsl --install
```

Après le redémarrage, Ubuntu s'ouvre et demande un nom d'utilisateur et un mot de passe Linux. À partir de là, tout se passe dans son terminal.

<Callout type="warning">
Dans WSL, le dépôt se clone dans le dossier personnel Linux (`~/akfc`), pas sous `/mnt/c/…` : les fichiers de Windows vus depuis Linux sont plusieurs fois plus lents, et `pnpm install` comme le rechargement de Next.js en souffriraient.
</Callout>

### Node.js, par nvm

Node.js ne s'installe pas depuis le site de Node, mais avec **nvm** (Node Version Manager). nvm installe une version de Node dans le dossier personnel, sans droits d'administrateur, et passe d'une version à l'autre d'un dossier à l'autre. La version du projet est écrite dans le fichier `.nvmrc` de la racine, qui ne contient qu'une ligne : `22`.

nvm s'installe de la même façon sur macOS, Linux et WSL. Le script d'installation ajoute nvm au fichier de démarrage du terminal (`~/.zshrc` sur macOS, `~/.bashrc` sur Linux) : il faut ensuite **ouvrir un nouveau terminal**.

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh | bash
```

Puis, dans un nouveau terminal, à la racine du dépôt une fois cloné (`nvm install` lit `.nvmrc`), ou n'importe où en précisant la version :

```bash
nvm install 22
node --version
```

`node --version` doit afficher `v22.…`. La même version est utilisée par l'image de production : `.nvmrc` et `NODE_VERSION` dans le `Dockerfile` doivent changer ensemble.

### Docker

<OsTabs>
<Os name="mac">

Sur macOS, Docker tourne dans **Docker Desktop**, une application qui démarre une petite machine virtuelle Linux. Avec Homebrew :

```bash
brew install --cask docker-desktop
```

Sans Homebrew, on télécharge Docker Desktop sur docker.com (version Apple Silicon ou Intel selon le Mac). Il faut ensuite **lancer l'application une fois** et accepter ses conditions : tant qu'elle ne tourne pas, la commande `docker` ne répond pas.

```bash
docker version
docker compose version
```

</Os>
<Os name="linux">

Sur Linux, on installe **Docker Engine**, sans interface graphique. Le script officiel de Docker ajoute son dépôt de paquets et l'installe :

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
```

Pour lancer `docker` sans `sudo`, notre utilisateur rejoint le groupe `docker`, puis on se déconnecte et se reconnecte (ou on ouvre un nouveau terminal de session) :

```bash
sudo usermod -aG docker $USER
docker run --rm hello-world
docker compose version
```

</Os>
<Os name="windows">

Sous Windows, on installe **Docker Desktop pour Windows** (docker.com). Dans ses réglages : **General** → « Use the WSL 2 based engine » coché, puis **Resources → WSL integration** → activer l'intégration avec Ubuntu.

Docker Desktop doit être lancé. Les commandes `docker` se tapent ensuite dans le terminal Ubuntu, comme sous Linux :

```bash
docker run --rm hello-world
docker compose version
```

</Os>
</OsTabs>

`docker compose` (avec une espace) est le module Compose v2, fourni avec Docker Desktop et avec Docker Engine. L'ancienne commande `docker-compose` (avec un tiret) n'est plus utilisée par le projet.

### pnpm, par corepack

pnpm ne s'installe pas à la main. Node.js 22 fournit **corepack**, un outil qui procure le bon gestionnaire de paquets à chaque projet. On l'active **une fois par machine**, avant la toute première installation :

```bash
corepack enable
```

Cette commande n'est écrite dans aucun fichier du dépôt pour le poste de développement, et `pnpm install` ne peut pas la lancer lui-même : tant qu'elle n'a pas été tapée, la commande `pnpm` n'existe pas. Elle installe, à côté de `node`, un petit lanceur nommé `pnpm`.

<Callout type="info">
À partir de Node.js 25, corepack n'est plus fourni avec Node. Le projet est sur Node 22, qui le fournit encore ; sur une version plus récente, on l'installe d'abord à part avec `npm install -g corepack`, puis `corepack enable` s'utilise de la même façon.
</Callout>

Ce lanceur, à chaque appel, lit le champ `packageManager` du `package.json` le plus proche :

```json
// package.json (extrait)
"packageManager": "pnpm@10.24.0+sha512.01ff8ae71b4419903b65c60fb2dc9d34cf8bb6e06d03bde112ef38f7a34d6904c424ba66bea5cdcf12890230bf39f9580473140ed9c946fef328b6e5238a345a"
```

La première fois, il télécharge cette version exacte de pnpm, vérifie qu'elle correspond à l'empreinte qui suit `+sha512.`, puis l'exécute ; les fois suivantes, il la reprend dans son cache. Le champ ne s'écrit pas à la main : `corepack use pnpm@<version>` le remplit, empreinte comprise. C'est ainsi qu'on change de version de pnpm pour tout le monde : un commit qui modifie cette ligne.

L'image de production procède de la même façon, au tout début de sa construction :

```dockerfile
# Dockerfile (extrait)
RUN corepack enable
```

Épingler la version garantit que tous les développeurs et le serveur produisent le même `pnpm-lock.yaml` pour les mêmes dépendances, et donc installent exactement les mêmes paquets.

## La base, le stockage et la boîte mail

```bash
pnpm dev:infra
```

Comme toutes les commandes `pnpm <nom>` de ce chapitre, c'est un **script** du `package.json` de la racine : un raccourci vers une commande plus longue, le même pour tout le monde.

```json
// package.json (extrait)
"dev:infra": "docker compose -f docker-compose.dev.yml up -d",
"dev:infra:stop": "docker compose -f docker-compose.dev.yml stop",
```

Docker télécharge les images au premier lancement, puis démarre :

Les ports ne sont pas les ports habituels (5432 pour Postgres, 9000 pour MinIO) : ils coexistent ainsi avec un Postgres déjà installé ou avec la sandbox lancée en parallèle. Tout écoute sur `127.0.0.1` seulement, donc rien n'est exposé au réseau.

Les données survivent à un redémarrage, dans des volumes Docker. `pnpm dev:infra:stop` arrête les conteneurs sans rien effacer.

**Mailpit** accepte tous les e-mails que l'application lui confie et les affiche dans une page web, sans jamais les transmettre. Nous pouvons donc tester une réinitialisation de mot de passe ou une notification de ticket de bout en bout, en lisant le message réellement produit, sans aucun risque d'écrire à quelqu'un.

<Callout type="info">
L'envoi d'e-mails réels n'est pas évité par prudence : il est **impossible** en développement. Ce principe, rendre l'erreur impossible plutôt que compter sur l'attention, revient souvent dans le projet.
</Callout>

## La configuration : deux fichiers, deux lecteurs

L'application lit les adresses et mots de passe de ces services dans des variables d'environnement. Le dépôt fournit `.env.dev.example`, aligné sur `docker-compose.dev.yml`. Nous le copions à deux endroits :

```bash
cp .env.dev.example .env
cp .env.dev.example apps/web/.env.local
```

Deux programmes différents lisent la configuration, chacun dans son dossier :

- la CLI Prisma (migrations, seed) se lance à la racine du dépôt ; son fichier `prisma.config.ts` commence par `import 'dotenv/config'` et charge le `.env` **de la racine**, où il trouve l'adresse de la base :

```ts
// prisma.config.ts (extrait)
import 'dotenv/config'
import { defineConfig } from 'prisma/config'

export default defineConfig({
  schema: 'prisma/schema.prisma',
  datasource: {
    url: process.env.DATABASE_URL!,
    directUrl: process.env.DIRECT_DATABASE_URL,
  },
```


- Next.js s'exécute dans `apps/web` et charge les fichiers `.env*` **de son propre dossier**, `.env.local` en priorité.

<Callout type="warning">
Aucun de ces deux fichiers n'est versionné : le `.gitignore` les exclut, et seuls les modèles `.env.example` et `.env.dev.example` sont suivis. Un vrai secret n'a rien à faire dans le dépôt, même dans une branche : l'historique Git le garderait pour toujours.
</Callout>

Le modèle complet, avec un commentaire par variable, est `.env.example`. Celui de développement n'en garde que l'indispensable ; la relève automatique des réponses aux tickets (`TICKET_IMAP_*`), par exemple, reste éteinte tant que sa variable n'est pas définie.

### Une garde contre la production

Ces deux fichiers sont le seul lien entre notre machine et une base. Il suffit d'y recopier l'adresse du serveur — pour vérifier une donnée, pour aller vite — et tout ce que nous lançons écrit dans la production : `pnpm db:migrate` migre la base des membres hors de l'ordre de déploiement, `pnpm dev` y écrit dès son démarrage (le fichier `instrumentation.ts` garantit dossiers, groupes et segments de stockage), puis à chaque clic dans le site local. Rien ne prévient : l'adresse est valide, la connexion réussit.

Une garde regarde donc **où mène** l'adresse, avant toute écriture. Elle accepte la machine elle-même (`127.0.0.1`, `localhost`) et les noms sans point (`postgres`, `pgbouncer`) : ce sont des services du réseau Docker, ceux du serveur, de la sandbox ou des tests. Tout le reste — une adresse IP, un nom de domaine — est refusé :

```js
// prisma/db-target.mjs (extrait)
function isLocalHost(host) {
  const h = host.replace(/^\[|\]$/g, "").toLowerCase();
  if (h === "localhost" || h === "::1" || /^127\.\d+\.\d+\.\d+$/.test(h)) return true;
  return !h.includes(".") && !h.includes(":") && h !== "";
}
```

Elle est appelée à trois endroits, chacun devant une porte vers la base :

</Callout>

## Les tables

Les **migrations** de `prisma/migrations` décrivent, dans l'ordre, chaque transformation du schéma depuis le début du projet. Les appliquer toutes reconstruit la base telle qu'elle est en production, sans aucune donnée.

```bash
pnpm db:migrate
```

```json
// package.json (extrait)
"db:migrate": "prisma migrate deploy",
```

`prisma migrate deploy` applique les migrations manquantes et n'en crée aucune. C'est la commande utilisée en production : notre base se construit exactement de la même façon que celle du serveur.

`prisma migrate dev`, elle, compare le schéma à la base et **écrit une nouvelle migration**. Nous l'utiliserons dans la partie « Données », quand nous modifierons le schéma.

## Les données de démonstration

Le script de démonstration crée deux comptes, le groupe Administrateurs, la catégorie « Cours » et quatre disciplines :

```bash
pnpm db:seed:dev
```

```json
// package.json (extrait)
"db:seed:dev": "node --env-file=.env prisma/db-target.mjs && node --env-file=.env prisma/seed.sandbox.mjs",
```

Le script n'importe pas `dotenv` : c'est Node lui-même qui charge le `.env` de la racine, grâce à l'option `--env-file`.

C'est le script de la sandbox recruteurs, `prisma/seed.sandbox.mjs`. Il est **idempotent** : le relancer ne crée pas de doublons et remet les mots de passe à leur valeur de démonstration. Nous pouvons donc le relancer à tout moment pour retrouver un état connu. C'est la séparation des bases qui rend ce geste sans danger.

## Lancer l'application

```bash
pnpm dev
```

Le script de la racine ne lance pas Next.js lui-même : il délègue au paquet `web` (`apps/web`), dont le propre `package.json` a son script `dev`. L'option `--filter` de pnpm désigne le paquet visé par son nom.

```json
// package.json (extrait)
"dev": "pnpm --filter web dev",
```

```json
// apps/web/package.json (extrait)
"dev": "next dev",
```

L'application répond sur `http://localhost:3000`. Au démarrage, `apps/web/src/instrumentation.ts` crée les dossiers racines de la bibliothèque, s'assure que le groupe Administrateurs existe, prépare l'espace de chaque groupe collaboratif et les catégories de tickets. Une base neuve est ainsi utilisable sans aucune manipulation.

Vérifions chaque service séparément :

1. Connectons-nous avec `admin@akfc.demo`. Le menu du compte propose « Dashboard » : la **base** et l'authentification répondent.
2. Ouvrons la bibliothèque du tableau de bord et déposons une image. Elle apparaît dans la console MinIO (`http://localhost:9201`), bucket `akfc-dev` : le **stockage** répond.
3. Déconnectons-nous et demandons « Mot de passe oublié » pour `membre@akfc.demo`. Le message arrive dans Mailpit (`http://localhost:8026`) : les **e-mails** fonctionnent.

<Callout type="info">
Trois services, trois vérifications : si l'une échoue, nous savons immédiatement quel service regarder.
</Callout>
