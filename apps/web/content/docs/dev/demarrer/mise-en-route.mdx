## Ce dont une application a besoin pour démarrer

Cloner le dépôt et lancer `pnpm dev` ne suffit pas. L'application démarrerait, puis tomberait à la première page : elle cherche une base de données pour lire ses réglages, un stockage pour afficher son logo, et un serveur d'e-mails pour envoyer un lien de réinitialisation de mot de passe.

En production, ces trois services sont réels : PostgreSQL sur le serveur, Cloudflare R2 pour les fichiers, la messagerie OVH pour les e-mails. Sur notre machine, nous allons les remplacer par trois conteneurs qui parlent exactement les mêmes protocoles. L'application ne fait pas la différence ; seule la configuration change.

Le fichier `docker-compose.dev.yml`, à la racine du dépôt, décrit ces trois services. Nous allons l'utiliser dans un instant. Commençons par les outils.

pnpm n'a pas besoin d'être installé à la main. Node.js embarque corepack, qui lit le champ `packageManager` du `package.json` et fournit la bonne version :

```bash
corepack enable
```

<Callout type="tip">
Pourquoi épingler la version de pnpm ? Parce que deux versions différentes peuvent produire deux `pnpm-lock.yaml` différents pour les mêmes dépendances. Avec corepack, tous les développeurs et le serveur de production utilisent exactement le même pnpm.
</Callout>

## Récupérer le code et ses dépendances

```bash
git clone <adresse-du-dépôt> akfc
cd akfc
pnpm install
```

L'installation prend quelques minutes la première fois. À la fin, pnpm lance de lui-même `prisma generate` (c'est le script `postinstall` du `package.json`) : Prisma lit `prisma/schema.prisma` et fabrique un client TypeScript qui connaît chacun des 47 modèles. Sans cette étape, le moindre `prisma.post.findMany()` serait une erreur de compilation.

## Démarrer la base, le stockage et la boîte mail

```bash
pnpm dev:infra
```

Ce script lance `docker compose -f docker-compose.dev.yml up -d`. Docker télécharge les images au premier lancement, puis démarre quatre conteneurs :

<DocsTable columnsJson='["Service","Rôle","Adresse sur notre machine"]' rowsJson='[["db","PostgreSQL 17, la base de données","127.0.0.1:5435 (utilisateur akfc, mot de passe akfc-dev, base akfc_db)"],["storage","MinIO, un stockage compatible S3 qui joue le rôle de Cloudflare R2","API : 127.0.0.1:9200 · console : http://localhost:9201 (akfc-dev / akfc-dev-secret)"],["storage-init","Crée le bucket akfc-dev au premier démarrage, puis s’arrête","—"],["mail","Mailpit : capture tous les e-mails envoyés par l’application","SMTP : 127.0.0.1:1026 · boîte web : http://localhost:8026"]]' />

Les ports ne sont pas les ports habituels (5432 pour Postgres, 9000 pour MinIO) : un Postgres déjà installé sur la machine, ou la sandbox recruteurs lancée en parallèle, ne gênera pas. Tout écoute sur `127.0.0.1` seulement, donc rien n'est exposé au réseau.

Les données survivent à un redémarrage : elles vivent dans des volumes Docker. `pnpm dev:infra:stop` arrête les conteneurs sans rien effacer.

<Callout type="info">
Mailpit mérite qu'on s'y arrête. En développement, aucun e-mail ne doit partir sur internet : un test de réinitialisation de mot de passe ne doit pas écrire à un vrai membre. Mailpit accepte tous les messages et les affiche dans sa page web, sans jamais les transmettre.
</Callout>

## Configurer : deux fichiers, deux lecteurs

Les adresses et les mots de passe de ces services, l'application les lit dans des variables d'environnement. Le dépôt en fournit une version prête à l'emploi, `.env.dev.example`, alignée sur `docker-compose.dev.yml`. Nous la copions deux fois :

```bash
cp .env.dev.example .env
cp .env.dev.example apps/web/.env.local
```

Pourquoi deux copies ? Parce que deux programmes différents lisent la configuration, chacun à un endroit différent.

La CLI Prisma (migrations, seed) se lance à la racine du dépôt. Son fichier de configuration, `prisma.config.ts`, commence par `import 'dotenv/config'` : il charge le fichier `.env` **de la racine**.

Next.js, lui, s'exécute dans `apps/web`. Il charge les fichiers `.env*` **de son propre dossier**, et `.env.local` en priorité.

<Callout type="warning">
Aucun de ces deux fichiers n'est versionné : le `.gitignore` les exclut, et seuls les modèles `.env.example` et `.env.dev.example` sont suivis par Git. Un vrai secret (celui de la production, par exemple) n'a rien à faire dans le dépôt, même dans une branche, même pour un instant : l'historique Git le garderait pour toujours.
</Callout>

Le modèle complet, avec un commentaire par variable, est `.env.example`. Celui de développement n'en garde que ce qu'il faut pour démarrer ; la relève automatique des réponses aux tickets (`TICKET_IMAP_*`), par exemple, reste désactivée tant que sa variable n'est pas définie.

## Créer les tables

La base existe, mais elle est vide. Les **migrations** de `prisma/migrations` décrivent, dans l'ordre, chaque transformation qu'a subie le schéma depuis le début du projet. Les appliquer toutes, c'est reconstruire la base telle qu'elle est en production, sans une seule donnée.

```bash
pnpm db:migrate
```

Ce script lance `prisma migrate deploy`, qui applique les migrations pas encore appliquées et n'en crée aucune. C'est la commande de la production, et c'est volontaire : notre base locale se construit exactement comme celle du serveur.

Sa cousine, `prisma migrate dev`, sert à autre chose : elle compare le schéma à la base et **écrit une nouvelle migration**. Nous la retrouverons dans la partie « Données », le jour où nous modifierons le schéma.

## Remplir la base de données de démonstration

Une base vide ne permet même pas de se connecter : il n'existe aucun compte. Le script de démonstration en crée deux, ainsi que le groupe Administrateurs, la catégorie « Cours » et quatre disciplines.

```bash
pnpm db:seed:dev
```

Ce script est celui de la sandbox recruteurs, `prisma/seed.sandbox.mjs`. Il est **idempotent** : le relancer ne crée pas de doublons, il remet simplement les mots de passe à leur valeur de démonstration. Ses identifiants sont publics par nature, et n'existent que dans notre base locale.

## Lancer l'application

```bash
pnpm dev
```

L'application répond sur `http://localhost:3000`. Au démarrage, le fichier `apps/web/src/instrumentation.ts` lance une série de vérifications : il crée les dossiers racines de la bibliothèque, s'assure que le groupe Administrateurs existe, prépare l'espace de chaque groupe collaboratif et les catégories de tickets. Sur une base neuve, c'est ce qui rend la bibliothèque utilisable sans aucune manipulation.

Vérifions que tout fonctionne, service par service :

1. Connectons-nous avec `admin@akfc.demo`. Le menu du compte, en haut à droite, propose « Dashboard » : la **base** répond et l'authentification aussi.
2. Ouvrons la bibliothèque du tableau de bord et déposons une image. Elle apparaît dans la console MinIO (`http://localhost:9201`), dans le bucket `akfc-dev` : le **stockage** répond.
3. Déconnectons-nous, puis demandons « Mot de passe oublié » pour `membre@akfc.demo`. Le message arrive dans Mailpit (`http://localhost:8026`) : les **e-mails** partent, et ne vont nulle part ailleurs.

<Callout type="info">
Trois services, trois vérifications. Si l'une échoue, nous savons immédiatement lequel regarder, au lieu de chercher une erreur au milieu d'un écran blanc.
</Callout>

Pour repartir d'une page blanche, base et fichiers compris :

```bash
docker compose -f docker-compose.dev.yml down -v
pnpm dev:infra
pnpm db:migrate
pnpm db:seed:dev
```

L'option `-v` supprime les volumes, donc toutes les données de développement. Elle n'a aucun effet en dehors de notre machine.

<Callout type="tip">
Nous avons maintenant un environnement complet, isolé, et jetable. C'est précisément cette dernière qualité qui nous rend libres d'expérimenter : une base que l'on peut reconstruire en quatre commandes est une base que l'on n'a pas peur de casser.
</Callout>
