*Saison 1 — Démarrer · Épisode 2*

> **Précédemment.** Un club, une vitrine, un outil, une seule application. Une base de développement qui était, pendant trop longtemps, celle des vrais membres. Et une règle gravée depuis : le développement ne touche jamais à la production.

## L'écran blanc

Le dépôt est cloné. `pnpm dev` affiche `Ready`. Nous ouvrons `http://localhost:3000`.

Erreur. La page d'accueil veut lire le titre du site dans la base : il n'y a pas de base. Le header veut afficher le logo, rangé dans un stockage S3 : il n'y a pas de stockage. Et si nous allions jusqu'à « Mot de passe oublié », l'application chercherait un serveur d'e-mails qui n'existe pas davantage.

En production, ces trois services sont réels : PostgreSQL sur le serveur, Cloudflare R2 pour les fichiers, la messagerie OVH pour les e-mails. Nous n'en voulons aucun ici : l'épisode précédent nous a appris pourquoi.

Nous allons donc construire un monde de remplacement. Trois conteneurs qui parlent **exactement les mêmes protocoles** que les services réels. L'application ne verra pas la différence. Seule la configuration changera.

## Les outils du voyage

pnpm ne s'installe pas à la main. Node.js embarque corepack, qui lit le champ `packageManager` du `package.json` et fournit la bonne version :

```bash
corepack enable
```

Pourquoi cette précision d'horloger ? Parce que deux versions de pnpm peuvent écrire deux `pnpm-lock.yaml` différents pour les mêmes dépendances. Le jour où le serveur de production installe autre chose que ce que nous avons testé, le bug ne se reproduit plus chez nous. Avec corepack, tout le monde, serveur compris, utilise le même pnpm.

## Le code et ses dépendances

```bash
git clone <adresse-du-dépôt> akfc
cd akfc
pnpm install
```

À la fin de l'installation, pnpm lance de lui-même `prisma generate` (le script `postinstall` du `package.json`). Prisma lit `prisma/schema.prisma` et fabrique un client TypeScript qui connaît chacun des 47 modèles. Sans lui, le moindre `prisma.post.findMany()` serait une erreur de compilation.

## Trois conteneurs

```bash
pnpm dev:infra
```

Ce script lance `docker compose -f docker-compose.dev.yml up -d`. Docker télécharge les images au premier lancement, puis démarre :

<DocsTable columnsJson='["Service","Rôle","Adresse sur notre machine"]' rowsJson='[["db","PostgreSQL 17, la base de données","127.0.0.1:5435 (utilisateur akfc, mot de passe akfc-dev, base akfc_db)"],["storage","MinIO, un stockage compatible S3 qui joue le rôle de Cloudflare R2","API : 127.0.0.1:9200 · console : http://localhost:9201 (akfc-dev / akfc-dev-secret)"],["storage-init","Crée le bucket akfc-dev au premier démarrage, puis s’arrête","—"],["mail","Mailpit : capture tous les e-mails envoyés par l’application","SMTP : 127.0.0.1:1026 · boîte web : http://localhost:8026"]]' />

Les ports ne sont pas les ports habituels (5432 pour Postgres, 9000 pour MinIO) : un Postgres déjà installé, ou la sandbox lancée en parallèle, ne se battra pas pour la même place. Tout écoute sur `127.0.0.1` seulement : rien n'est exposé au réseau.

Les données survivent à un redémarrage, dans des volumes Docker. `pnpm dev:infra:stop` arrête les conteneurs sans rien effacer.

Arrêtons-nous un instant sur le troisième conteneur, parce qu'il est le plus étrange. **Mailpit est une boîte aux lettres qui ne poste jamais rien.** Il accepte chaque e-mail que l'application lui confie, l'affiche dans une page web, et le garde. Un test de réinitialisation de mot de passe ne doit pas écrire à un vrai membre ; avec Mailpit, il ne le peut tout simplement pas.

<Callout type="info">
Nous ne comptons pas sur la prudence pour ne pas envoyer d'e-mails : nous rendons l'envoi **impossible**. C'est une idée qui reviendra souvent.
</Callout>

## Deux fichiers pour un seul réglage

L'application lit les adresses et mots de passe de ces services dans des variables d'environnement. Le dépôt en fournit une version prête à l'emploi, `.env.dev.example`, alignée sur `docker-compose.dev.yml`. Et nous allons la copier… deux fois :

```bash
cp .env.dev.example .env
cp .env.dev.example apps/web/.env.local
```

Ce doublon ressemble à une erreur. C'est une énigme, et sa solution dit quelque chose d'important sur le monorepo : **deux programmes différents lisent la configuration, chacun à un endroit différent.**

La CLI Prisma (migrations, seed) se lance à la racine du dépôt. Son fichier de configuration, `prisma.config.ts`, commence par `import 'dotenv/config'` : il charge le `.env` **de la racine**.

Next.js, lui, s'exécute dans `apps/web`. Il charge les fichiers `.env*` **de son propre dossier**, et `.env.local` en priorité.

Un seul fichier, et l'un des deux programmes travaillerait à l'aveugle.

<Callout type="warning">
Aucun de ces deux fichiers n'est versionné : le `.gitignore` les exclut, et seuls les modèles `.env.example` et `.env.dev.example` sont suivis. Un vrai secret n'a rien à faire dans le dépôt, même dans une branche, même une minute : l'historique Git le garderait pour toujours.
</Callout>

Le modèle complet, avec un commentaire par variable, est `.env.example`. Celui de développement n'en garde que l'indispensable ; la relève automatique des réponses aux tickets (`TICKET_IMAP_*`), par exemple, reste éteinte tant que sa variable n'est pas définie.

## Rejouer l'histoire de la base

La base existe, mais elle est vide. Les **migrations** de `prisma/migrations` racontent, dans l'ordre, chaque transformation qu'a subie le schéma depuis le premier jour. Les appliquer toutes, c'est rejouer cette histoire et obtenir la base telle qu'elle est en production, sans une seule donnée.

```bash
pnpm db:migrate
```

Ce script lance `prisma migrate deploy`, qui applique les migrations manquantes et n'en crée aucune. C'est la commande de la production, et c'est voulu : notre base se construit exactement comme celle du serveur.

Sa cousine, `prisma migrate dev`, est d'une autre trempe : elle compare le schéma à la base et **écrit une nouvelle migration**. Puissante, et donc dangereuse au mauvais endroit. Nous la croiserons dans la saison « Données », le jour où nous toucherons au schéma.

## Les premiers habitants

Une base vide ne laisse même pas se connecter : il n'existe aucun compte. Le script de démonstration crée deux habitants, ainsi que le groupe Administrateurs, la catégorie « Cours » et quatre disciplines.

```bash
pnpm db:seed:dev
```

<DocsTable columnsJson='["Compte","Mot de passe","Rôle"]' rowsJson='[["admin@akfc.demo","sandbox-demo","administrateur (membre du groupe Administrateurs)"],["membre@akfc.demo","sandbox-demo","simple membre"]]' />

C'est le script de la sandbox recruteurs, `prisma/seed.sandbox.mjs`. Il est **idempotent** : le relancer ne crée pas de doublons, il remet les mots de passe à leur valeur de démonstration.

Relisons cette phrase en pensant à l'épisode précédent. *Il remet les mots de passe à leur valeur de démonstration.* Lancé sur notre base locale, c'est un confort. Lancé sur une base partagée avec la production, c'eût été une catastrophe. Voilà, très concrètement, ce que la séparation des bases nous a épargné.

## Allumer

```bash
pnpm dev
```

L'application répond sur `http://localhost:3000`. Au démarrage, `apps/web/src/instrumentation.ts` déroule une série de vérifications : il crée les dossiers racines de la bibliothèque, s'assure que le groupe Administrateurs existe, prépare l'espace de chaque groupe collaboratif et les catégories de tickets. Sur une base neuve, c'est ce qui rend la bibliothèque utilisable sans la moindre manipulation.

Maintenant, mettons notre monde à l'épreuve, un service à la fois :

1. Connectons-nous avec `admin@akfc.demo`. Le menu du compte, en haut à droite, propose « Dashboard » : la **base** répond, l'authentification aussi.
2. Ouvrons la bibliothèque du tableau de bord et déposons une image. Elle apparaît dans la console MinIO (`http://localhost:9201`), bucket `akfc-dev` : le **stockage** répond.
3. Déconnectons-nous, demandons « Mot de passe oublié » pour `membre@akfc.demo`. Le message arrive dans Mailpit (`http://localhost:8026`) : les **e-mails** partent, et ne vont nulle part ailleurs.

<Callout type="info">
Trois services, trois vérifications. Si l'une échoue, nous savons immédiatement lequel regarder, au lieu de chercher une erreur au milieu d'un écran blanc.
</Callout>

## Quand le monde résiste

Et pour tout raser et repartir d'une page blanche, base et fichiers compris :

```bash
docker compose -f docker-compose.dev.yml down -v
pnpm dev:infra
pnpm db:migrate
pnpm db:seed:dev
```

L'option `-v` supprime les volumes, donc toutes les données de développement. Elle n'a aucun effet hors de notre machine.

<Callout type="tip">
Nous avons un environnement complet, isolé, et **jetable**. C'est cette dernière qualité qui nous rend libres : une base que l'on reconstruit en quatre commandes est une base que l'on n'a pas peur de casser.
</Callout>

## Fin de l'épisode

Tout fonctionne. Nous nous connectons, nous déposons des images, nous recevons des e-mails qui n'existent pas. Le projet compile. Les pages s'affichent.

C'est exactement le moment où le danger commence.

Car une application qui compile et qui s'affiche peut parfaitement être cassée. Ce projet l'a été, plus longtemps qu'on ne l'aimerait, sans qu'aucun outil ne proteste : une protection qui ne protégeait rien, du code « qui marche » que React s'apprêtait à briser, et des fichiers que Next sait ignorer sans un mot.

Les erreurs bruyantes, nous savons les corriger. Ce sont les silencieuses qui nous intéressent maintenant.
