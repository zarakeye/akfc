> **Précédemment.** Un fichier est envoyé directement au stockage grâce à une URL présignée, puis enregistré dans `MediaAsset` sous une clé calculée par le serveur, comme `AKFC/courses/tchoy-lee-fut/salut-final.jpg`. Il naît en attente, et il est servi par des routes qui vérifient les droits. Reste à le retrouver, le ranger et le valider.

## Les parcours du chapitre

Deux cas d'utilisation traversent ce chapitre : parcourir la bibliothèque, et y ranger un fichier. Chaque onglet en déroule les étapes et ce qu'elles lisent ou écrivent en base, relevé dans le code ; chaque étape mène à son explication plus bas, ou à la carte des entités, rejouée à cette étape.

## Ce que l'explorateur doit montrer

Le stockage ne connaît que des clés. L'administrateur, lui, attend un explorateur de fichiers : des dossiers qu'on ouvre, un fil d'Ariane, des fichiers qu'on renomme, déplace, valide ou jette. Entre les deux, il faut ajouter ce que le stockage ignore :

- le **nom lisible** d'un fichier (la clé est un slug, `salut-final-2025.jpg`, le nom d'origine est en base) ;
- son **statut** (en attente ou validé), son expéditeur ;
- des **libellés** de dossiers en français (`courses` s'affiche « Cours », `personal-space` « Espace personnel ») ;
- des dossiers qui doivent apparaître **même vides** (un espace de groupe tout juste créé n'a encore aucun fichier, donc aucune clé) ;
- et seulement ce que l'utilisateur a **le droit** de voir.

Le Finder répartit ce travail en trois couches.

## Trois couches

Le contrat entre le composant et l'adaptateur est une interface de `packages/contracts` :

```ts
// packages/contracts/src/finder/adapter.ts (extrait)
export interface FileAdapter {
  list(options: ListOptions): Promise<ListResult>;
  getTree?(options: GetTreeOptions): Promise<GetTreeResult>;
  getNode?(path: string): Promise<FinderNode | null>;
  getMetadata?(path: string): Promise<FinderNodeMetadata | null>;
  moveItems?(options: MoveOptions): Promise<void>;
  delete?(path: string): Promise<void>;
}
```

Seule `list` est obligatoire. Un adaptateur en lecture seule n'implémente ni `moveItems` ni `delete`, et le composant masque les actions correspondantes.

Ce découpage permet d'utiliser **le même composant à trois endroits** :

- la **bibliothèque** du tableau de bord (`<Finder adapter={finderStorageAdapter} rootPath={APP_ROOT} />`), qui parle aux procédures `storage.*` ;
- la page **Mes espaces** des membres, avec `memberFinder.adapter.ts`, dont la racine est virtuelle (`__mes-espaces__`) et ne liste que les espaces de groupe accessibles au membre ;
- le **sélecteur de médias** (`MediaPicker`), qui monte le Finder en mode sélection pour choisir les images d'une page ou d'une galerie.

Le panier du sélecteur vit dans `packages/finder-core` (`usePickerCartStore`), un paquet sans aucun code d'affichage : il pourra être repris tel quel par la future application mobile.

<Callout type="info">
Le composant ne connaît qu'un **contrat** ; chaque usage fournit son adaptateur. Ajouter un nouvel explorateur (un espace documentaire, une version mobile) revient à écrire un adaptateur, pas un nouveau Finder.
</Callout>

## Lister un stockage sans dossiers

Un stockage S3 sait répondre à une question précise : « donne-moi les clés qui commencent par ce préfixe, et regroupe ce qui suit le prochain `/` ». C'est l'option `Delimiter` de `ListObjectsV2` :

```ts
// packages/backend/src/modules/storage/adapters/r2/r2StorageAdapter.ts (extrait)
const response = await s3.send(
  new ListObjectsV2Command({
    Bucket,
    Prefix,          // ex. "AKFC/courses/"
    Delimiter: "/",
    MaxKeys: 1000,
  })
);
```

La réponse contient deux listes : `Contents`, les objets situés directement sous le préfixe (les **fichiers**), et `CommonPrefixes`, les préfixes plus longs regroupés jusqu'au `/` suivant (les **sous-dossiers**). Un dossier n'existe donc que s'il contient au moins un objet.

`getTree` répète cette lecture sur plusieurs niveaux (`buildSubTree`, récursif jusqu'à la profondeur demandée). Le contrat distingue trois états pour les enfants d'un dossier :

## Ce que le backend ajoute au stockage

La procédure `storage.getTree` ne se contente pas de relayer le stockage. Elle vérifie le droit de lecture, lit, puis complète le résultat en plusieurs passes :

```ts
// packages/backend/src/modules/storage/router.ts (extrait, simplifié)
await assertCanReadPath({ prisma: ctx.prisma, userId: ctx.user.id, path: input.path });

const result = await reader.getTree({ path: readPath, depth: input.depth });
stripBinSubtree(result.root, `${ctx.appRoot}/bin`);
await enrichTreeWithStatus(ctx.prisma, ctx.appRoot, result.root);
result.root = await mergeGroupSpaceFoldersIntoTree({ root: result.root, /* … */ });
if (input.path === ctx.appRoot) {
  result.root = await ensureContentRootsInTree(result.root, ctx.prisma, ctx.appRoot);
  result.root = scopePersoSpaceInTree(result.root, ctx.appRoot, ctx.user.id);
}
return { ...result, root: await applyGroupSpaceNamesToTree(result.root, ctx.prisma) };
```

L'enrichissement est **groupé** : une seule requête `findMany` sur toutes les clés du dossier, puis une seule pour les noms des expéditeurs, au lieu d'une requête par fichier. Un dossier de 200 photos coûte deux requêtes, pas 400.

Les libellés des dossiers suivent le même principe de découplage que les noms de fichiers : la clé physique ne change jamais, et une table `FolderLabel` associe un chemin à un nom d'affichage. Le fil d'Ariane et l'arbre lisent ces libellés (`storage.folderLabels`).

<Callout type="tip">
Partout dans le Finder, deux notions cohabitent : l'**identité** d'un nœud (sa clé, stable, qui sert aux opérations et aux jointures avec `MediaAsset.fullPath`) et son **nom affiché** (nom d'origine, `displayName` ou `FolderLabel`). Une opération ne reconstruit jamais un chemin à partir d'un nom affiché.
</Callout>

## Côté navigateur : un cache par dossier

Le composant garde son état dans un store Zustand (`useFinderStore`) : dossier courant, contenu, sélection, tri, mode d'affichage. Le hook `useFinderData` charge le contenu du dossier courant par l'adaptateur et le range dans un **cache par chemin** :

- revenir dans un dossier déjà visité l'affiche immédiatement, sans requête ni indicateur de chargement ;
- après une modification (envoi, déplacement, renommage), `reloadFolderContent()` vide le cache et force une relecture.

Le tri suit la convention des explorateurs de fichiers : les dossiers d'abord, puis les fichiers, avec une comparaison qui respecte les accents et les nombres (`Intl.Collator` en français : « photo 2 » avant « photo 10 »).

## Modifier : quatre opérations

### Renommer

Renommer un **fichier** ne touche pas au stockage : la clé est un slug stable, et seul `MediaAsset.displayName` change. Il n'y a ni copie, ni risque de deviner une extension, ni référence à mettre à jour.

```ts
// packages/backend/src/modules/storage/router.ts (extrait)
if (input.type === "file") {
  const result = await ctx.prisma.mediaAsset.updateMany({
    where: {
      appRoot: ctx.appRoot,
      OR: [{ fullPath: input.path }, { fullPath: { startsWith: `${input.path}.` } }],
    },
    data: { displayName: cleanName },
  });
  // …
}
```

Renommer un **dossier** est un vrai déplacement (voir plus bas), après vérification qu'aucun élément ne porte déjà ce nom. Deux catégories de dossiers refusent le renommage physique : les **racines de contenu** (cours, stages, événements, espaces), dont l'action « Renommer » modifie le `FolderLabel` à la place, et les **dossiers-entités** (l'espace d'un groupe, d'un utilisateur, un dossier d'avatars), dont le chemin sert aux contrôles d'accès. Les renommer casserait le lien entre le dossier et ce qu'il représente.

### Déplacer

S3 n'a pas d'opération « renommer » : déplacer un objet, c'est le **copier** sous sa nouvelle clé, puis **supprimer** l'ancien. Déplacer un dossier, c'est le faire pour chaque objet qui commence par son préfixe. La base suit dans la même opération :

```ts
// packages/backend/src/modules/storage/adapters/r2/r2StorageAdapter.ts (extrait)
const oldPrefix = `${operation.source.path}/`;
const newPrefix = `${operation.target.path}/`;
await prisma.$executeRaw`
  UPDATE "MediaAsset"
  SET "fullPath" = ${newPrefix} || SUBSTRING("fullPath" FROM ${oldPrefix.length + 1}::int)
  WHERE "appRoot" = ${appRoot} AND "fullPath" LIKE ${oldPrefix + "%"};
`;
```

Une seule requête SQL réécrit le préfixe de toutes les lignes concernées ; Prisma n'offre pas de fonction de remplacement de sous-chaîne dans `updateMany`, d'où le SQL brut. Le `/` final du préfixe n'est pas décoratif : sans lui, déplacer `cours` déplacerait aussi `cours-avance`.

La procédure `storage.move` planifie d'abord toutes les opérations d'un geste (une sélection multiple en produit plusieurs), écarte celles qui ne déplacent rien, puis les exécute **une par une** : des déplacements simultanés sur des préfixes voisins pourraient se marcher dessus. Un déplacement ne change jamais le statut d'un fichier : c'est une réorganisation, pas une validation.

### Valider

Valider un fichier ou un dossier entier passe par `media.setStatus`, qui modifie la colonne `status` des lignes concernées. Avant toute modification, une garde refuse de remettre en attente un média qui est posé dans une page : ce serait le retirer du site sans prévenir. Le message d'erreur nomme les contenus qui l'utilisent.

### Mettre à la corbeille

La corbeille n'est pas un statut : c'est un rangement. `trash.trashToBin` déplace l'élément dans une zone cachée, `AKFC/bin/.trash/<identifiant>/`, et crée une ligne `TrashEntry` qui conserve son nom et son **chemin d'origine** :

L'identifiant unique dans le chemin évite toute collision : deux fichiers `photo.jpg` jetés depuis deux dossiers différents coexistent dans la corbeille. Dans le Finder, la corbeille apparaît comme une feuille de l'arbre, avec sa propre vue en liste plate.

La ligne `MediaAsset` d'un fichier jeté n'est pas modifiée : elle garde son chemin d'origine. Comme la restauration replace le fichier exactement à ce chemin, la ligne retrouve son objet, avec son statut, son nom et sa description intacts. Ce choix entraîne deux règles, réunies dans `trashedAssets.service.ts` :

- **on ne jette pas un fichier utilisé.** S'il est posé dans une page, dans une galerie, ou publié dans les documents des membres, la mise à la corbeille est refusée, avec un message qui nomme chaque fichier et ce qui l'utilise. Sans cette garde, le contenu afficherait un média cassé tant que le fichier est dans la corbeille ;
- **la suppression définitive efface les lignes.** Une fois les objets supprimés, les lignes restées sur le chemin d'origine n'ont plus de fichier : elles sont effacées. Sauf une : si un nouveau fichier a été déposé entre-temps au même chemin, l'enregistrement de cet envoi a repris la ligne (un `upsert` sur `fullPath`), et elle lui appartient désormais. La suppression vérifie donc dans le stockage qu'aucun objet n'existe plus à ce chemin avant d'effacer.

```ts
// packages/backend/src/modules/trash/services/trashedAssets.service.ts (extrait)
const prefix = item.kind === "file" ? previous : `${previous}/`;
const live = new Set((await r2ListByPrefix(prefix)).map((o) => o.key));
const orphanIds = rows.filter((r) => !live.has(r.fullPath)).map((r) => r.id);
```

<Callout type="warning">
Le stockage et la base doivent rester d'accord : un déplacement ou un renommage de dossier met à jour `MediaAsset.fullPath` dans la même procédure, et une suppression définitive efface les lignes devenues sans fichier. Une opération qui ne toucherait que l'un des deux laisserait des fichiers sans statut, ou des lignes qui pointent vers rien.
</Callout>

## À suivre

Les médias sont envoyés, rangés, validés. Un média validé n'est pourtant visible de personne tant qu'il n'est posé nulle part : la route publique exige qu'il soit **placé** dans une page ou une galerie publique.

Ce placement est le travail du constructeur de pages. Une page y est faite de blocs (texte riche, image et texte, galerie…), édités dans le tableau de bord et rendus côté serveur sur le site. Chaque enregistrement doit tenir à jour la liste des médias qu'une page utilise, pour que la route publique sache quoi servir, et pour qu'on ne puisse pas retirer un média encore affiché.

<Callout type="tip">
**Partie suivante : le contenu éditorial.** Le constructeur de pages : un format de blocs commun aux pages, aux actualités et aux fiches, son éditeur, son rendu serveur, et la synchronisation des références de médias qui relie une page à ce qu'elle affiche.
</Callout>
