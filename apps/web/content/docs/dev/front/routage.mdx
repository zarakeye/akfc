*Saison 2 — Les fondations du front · Épisode 1*

> **Précédemment.** Nous avons construit un monde jetable, appris à traquer les erreurs qui ne disent rien, posté une sentinelle avant chaque commit. Puis une fenêtre de navigation privée, sans session, a affiché le tableau de bord. Le gardien était à son poste. Il regardait passer tout le monde.

## La porte

Tout commence par une vérification de routine.

Le tableau de bord du club contient des noms, des adresses e-mail, des photos d'enfants, des documents d'assemblée générale. Il est réservé. Un fichier, `proxy.ts`, est censé se tenir devant sa porte : toute requête vers l'espace d'administration passe par lui, et sans jeton de session valide, elle est renvoyée à l'accueil.

Ce fichier existe. Il compile. Il est propre, commenté, testé à la main. Nous ouvrons une fenêtre de navigation privée, sans aucune session, et nous tapons l'adresse du tableau de bord.

Il s'affiche.

Pas de redirection. Pas d'erreur. Le gardien est à son poste, et il regarde passer tout le monde.

Pour comprendre comment une porte peut être fermée à clé et grande ouverte à la fois, il faut d'abord comprendre comment Next.js décide qu'une adresse correspond à un fichier. Remontons le fil.

## Un dossier, une route

Dans l'App Router de Next.js, l'arborescence de `apps/web/src/app` **est** la carte du site. Il n'existe nulle part de liste des routes : chaque dossier crée un segment d'URL, et quelques fichiers aux noms réservés disent ce que ce segment fait.

## Trois mondes qui ne se ressemblent pas

Pourquoi des parenthèses ? Parce que le projet abrite trois mondes qui n'ont presque rien en commun.

Le **site public** est fait de pages longues. L'accueil enchaîne un carrousel, un texte, des sections ; le document entier défile, comme sur n'importe quel site. Un visiteur arrive souvent par un moteur de recherche, et la page doit être complète dès le premier octet reçu.

Le **tableau de bord** est une application. Il occupe exactement la hauteur de l'écran : header fixe, barre latérale, et une zone de contenu qui défile seule. La bibliothèque de fichiers, elle, ne défile pas du tout : elle gère son propre défilement, comme le Finder d'un Mac.

La **documentation**, enfin, a sa propre barre latérale et pas de header du site.

Il faut donc des enveloppes différentes, des layouts différents. Le réflexe serait de créer deux dossiers, `public/` et `admin/`. Mais un dossier crée un segment d'URL : la page des disciplines deviendrait `/public/disciplines/…`, et chaque lien du site traînerait ce préfixe absurde.

Les **groupes de routes** existent pour ce cas précis. Un dossier entre parenthèses range des pages et peut porter son propre layout, mais **il n'apparaît pas dans l'URL** :

- `app/(public)/disciplines/[slug]/page.tsx` répond à `/disciplines/tchoy-lee-fut` ;
- `app/(public)/page.tsx` répond à `/` ;
- `app/(admin)/dashboard/posts/page.tsx` répond à `/dashboard/posts`.

Le groupe est invisible. C'est exactement ce que nous voulions.

Et c'est exactement ce qui nous a trahis.

## Le nom qui n'existait pas

Retournons devant la porte. Voici ce que contenait `proxy.ts`, à l'époque où le tableau de bord s'ouvrait à n'importe qui :

```ts
// apps/web/src/proxy.ts — version d'origine
export const config = {
  matcher: ["/(admin)/:path*"],
};
```

Le `matcher` dit au proxy quelles adresses surveiller. Celle-ci se lit : « toutes les adresses qui commencent par `/(admin)` ».

Seulement voilà : **aucune adresse ne commence par `/(admin)`**. Le groupe n'existe que dans l'arborescence des fichiers ; dans les URL, il s'évapore. Le tableau de bord vit à `/dashboard`. Le gardien attendait des visiteurs à une porte qui n'avait jamais été construite, pendant que tout le monde entrait par l'autre.

Aucune erreur, aucun avertissement. Le code était juste du point de vue de TypeScript, juste du point de vue de Next. Il était simplement faux.

La correction tient en une ligne :

```ts
// apps/web/src/proxy.ts (extrait)
export const config = {
  matcher: [
    "/dashboard/:path*",
    "/profil/:path*",
    "/test-finder/:path*",
    "/test-picker/:path*",
    "/simpleEditor/:path*",
  ],
};
```

Les deux premières lignes réparent la porte. Les trois suivantes ont leur propre histoire ; nous y viendrons avant la fin de l'épisode.

<Callout type="warning">
Un nom entre parenthèses n'existe que dans les fichiers. Partout où l'on raisonne en URL (le `matcher` du proxy, `robots.txt`, un lien, une redirection), on écrit le chemin **sans** le groupe : `/dashboard`, jamais `/(admin)/dashboard`.
</Callout>

La porte est réparée. Mais en la réparant, nous avons regardé de plus près ce que le proxy vérifie réellement. Et la réponse n'est pas rassurante.

## Ce que le gardien ne voit pas

Le proxy s'exécute avant les pages, dans un environnement volontairement léger. Il lit le cookie de session, vérifie que le jeton est **correctement signé**, et c'est tout :

```ts
// apps/web/src/proxy.ts (extrait)
const token = req.cookies.get(COOKIE_NAME)?.value;
if (!token || !JWT_SECRET) {
  return NextResponse.redirect(new URL("/", origin));
}
try {
  jwt.verify(token, JWT_SECRET);
  return NextResponse.next();
} catch {
  return NextResponse.redirect(new URL("/", origin));
}
```

Il ne consulte pas la base. Il ne sait donc pas si la session a été révoquée, ni si la personne est administrateur. Un membre ordinaire, connecté, avec un jeton parfaitement valide, passe.

Alors, qui protège vraiment les données ? Il faut descendre jusqu'au backend. Chaque procédure d'administration passe par un middleware tRPC, `isAdmin`, qui relit la session et refuse sans discuter :

```ts
// packages/backend/src/trpc/middleware.ts
export const isAdmin = t.middleware(({ ctx, next }) => {
  const user = ctx.sessionClient?.user;
  if (!user) {
    throw new TRPCError({ code: "UNAUTHORIZED", message: "Authentication required." });
  }
  if (!user.isAdmin) {
    throw new TRPCError({ code: "FORBIDDEN", message: "Administrator access required." });
  }
  return next();
});
```

Les données étaient donc à l'abri. Mais l'**interface**, elle, s'ouvrait à n'importe quel membre connecté : il voyait le squelette du tableau de bord, une barre latérale vide, des pages qui affichaient des erreurs de chargement. Pas une fuite, mais une porte entrouverte sur une pièce vide, ce qui n'est jamais bon signe.

Pourquoi le layout du tableau de bord ne vérifiait-il pas lui-même ? Pour le comprendre, il faut regarder comment chaque monde construit son enveloppe.

## L'enveloppe de tout le monde

`app/layout.tsx` enveloppe absolument tout : le site, le tableau de bord, la documentation. Chaque ligne qu'on y ajoute s'exécute pour chaque page de l'application. Il ne garde donc que l'universel, et il le fait côté serveur.

Il lit dans la base le titre et la description du site, que les administrateurs règlent dans les Réglages :

```tsx
// apps/web/src/app/layout.tsx (extrait)
export async function generateMetadata(): Promise<Metadata> {
  const settings = await prisma.siteSettings
    .findUnique({ where: { id: "site" }, select: { shortTitle: true, longTitle: true, tagline: true } })
    .catch(() => null);
  const shortTitle = settings?.shortTitle?.trim() || "AKFC";
  // …
}
```

Le `.catch(() => null)` est une décision, pas une paresse : si la base tombe, le site doit afficher un titre par défaut plutôt qu'une page d'erreur pour une simple balise `<title>`.

Il injecte aussi le **style réglable** du site, des variables CSS lues en base et sérialisées en `html:root{…}`. Ce sélecteur pèse plus lourd que `:root` : la surcharge gagne par sa spécificité, quel que soit l'ordre dans lequel Next assemble les feuilles. Il pose la classe `dark` si le cookie du visiteur le demande. Il monte les fournisseurs communs : tRPC, React Query, le moteur des tutoriels. Et il lit la session du visiteur, pour une raison que nous découvrirons à la fin de l'épisode, et qui n'est pas anodine.

Comme il lit la base et des cookies à chaque requête, il déclare `export const dynamic = 'force-dynamic'` : son rendu dépend du visiteur et du moment, il ne peut pas être figé au build.

## Le site public : servir avant qu'on demande

`app/(public)/layout.tsx` est lui aussi un composant serveur. Et ce choix change ce que voit le visiteur.

Le ruban d'actualité apparaît sur toutes les pages publiques. Nous aurions pu le charger dans le navigateur, avec une requête tRPC. Le visiteur aurait alors vu la page s'afficher, puis, une demi-seconde plus tard, un bandeau surgir en poussant tout le contenu vers le bas. Le layout fait l'inverse : il lit la base **avant** d'envoyer quoi que ce soit.

```tsx
// apps/web/src/app/(public)/layout.tsx (extrait)
export default async function PublicLayout({ children }: { children: React.ReactNode }) {
  const now = new Date();
  const activeNews = await prisma.breakingNews.findMany({
    where: {
      publicationDate: { not: null, lte: now },
      OR: [{ expiresAt: null }, { expiresAt: { gt: now } }],
    },
    orderBy: { publicationDate: "desc" },
    take: 20,
  });
  // … logo et nom du site, lus de la même façon
  return (
    <div className="flex min-h-dvh flex-col bg-background">
      <div className="sticky top-0 z-50 bg-background">
        <Header initialLogoUrl={initialLogoUrl} initialBrand={initialBrand} />
        <FirstLoginRedirect />
      </div>
      <BreakingNewsShell news={activeNews} />
      <main className="flex-1">{children}</main>
      <Footer />
      <DraftPageBadge />
    </div>
  );
}
```

Le logo suit la même règle : lu côté serveur, passé au `Header` comme **valeur initiale**, présent dès la première image. Le header le relit ensuite dans le navigateur, si bien qu'un nouveau logo déposé dans les Réglages apparaît sans recharger.

Le reste est de la mise en page qui sait ce qu'elle veut. Aucune hauteur fixe : le document défile. `min-h-dvh` garde le footer en bas d'une page courte. Le header est collant ; le ruban, placé sous le bloc collant, défile avec la page au lieu de manger de la hauteur en permanence.

<Callout type="tip">
Retenons le geste : **ce que le serveur peut savoir avant d'envoyer la page, il le met dans la page**. Le navigateur ne devrait jamais avoir à demander ce que le serveur connaissait déjà.
</Callout>

Gardons cette phrase en tête. Elle va nous revenir, au moment où nous nous y attendrons le moins.

## Le tableau de bord : une application dans une page

`app/(admin)/dashboard/layout.tsx` fait le choix inverse. Sa première ligne est `'use client'`.

Il le faut : ce layout gère un état (l'ouverture du tiroir de navigation sur téléphone) et réagit au clavier. Un composant serveur ne sait faire ni l'un ni l'autre. Mais ce choix a un prix : un composant client ne lit pas la base. **Voilà pourquoi le tableau de bord ne pouvait pas vérifier lui-même qui entrait.**

Sa mise en page renverse aussi celle du site. Hauteur ferme, `h-dvh`, exactement l'écran. Et c'est la zone de contenu qui défile :

```tsx
// apps/web/src/app/(admin)/dashboard/layout.tsx (extrait)
<main className="relative min-h-0 flex-1 overflow-y-auto p-4 lg:p-10">
  {children}
</main>
```

Ce `min-h-0` est un détail qui a coûté des heures. Par défaut, un élément flex refuse de devenir plus petit que son contenu. Sans lui, une liste de 300 membres agrandit le `<main>` au-delà de l'écran, et c'est la page entière qui défile, header compris. La bibliothèque de fichiers, elle, se borne elle-même (`h-full overflow-hidden`) au lieu de compliquer le layout. La règle, écrite dans le code : **le cas général défile, le cas spécial se borne.**

### Le tiroir qui restait ouvert

Sur téléphone, la barre latérale devient un tiroir. L'administrateur choisit une page ; le tiroir doit se fermer. Le réflexe :

```tsx
// Ce que nous n'avons PAS fait
useEffect(() => {
  setSidebarOpen(false);
}, [pathname]);
```

Un effet s'exécute **après** l'affichage. React montre d'abord la nouvelle page avec le tiroir encore ouvert, puis relance un rendu pour le fermer. Un clignement. Le layout ajuste plutôt l'état **pendant** le rendu :

```tsx
// apps/web/src/app/(admin)/dashboard/layout.tsx (extrait)
const [lastPath, setLastPath] = useState(pathname);
if (pathname !== lastPath) {
  setLastPath(pathname);
  setSidebarOpen(false);
}
```

Quand React croise un `setState` en plein rendu, il jette ce rendu et recommence aussitôt avec le nouvel état, avant d'afficher quoi que ce soit. Aucune image intermédiaire n'atteint l'écran.

## Le gardien qui manquait

Récapitulons ce que nous savons. Le proxy vérifie une signature, pas un rôle. Le layout du tableau de bord est un composant client et ne peut pas lire la base. tRPC protège les données, mais pas l'interface.

Il manque quelqu'un. Quelqu'un qui s'exécuterait **côté serveur**, **avant** le layout client, et qui aurait le droit de lire la base.

Les groupes de routes nous l'offrent. Le dossier `(admin)` n'avait pas de layout. Il en a désormais un, et il est serveur :

```tsx
// apps/web/src/app/(admin)/layout.tsx (extrait)
export default async function AdminZoneLayout({ children }: { children: ReactNode }) {
  const session = await getSessionFromRequest().catch(() => null);
  const user = session?.user;
  if (!user) redirect("/");

  if (!user.isAdmin) {
    const categories = await handledCategoryIds(prisma, user.id).catch(() => []);
    const handlesTickets = categories === null || categories.length > 0;
    if (!handlesTickets) redirect("/");
  }

  return children;
}
```

Il laisse passer deux profils : les administrateurs, et les membres qui traitent les demandes d'au moins une catégorie de tickets (ceux-là ont leur boîte de réception dans le tableau de bord). `handledCategoryIds` est la fonction même du module des tickets : la règle « qui traite quoi » n'est écrite qu'une fois. Tous les autres repartent vers l'accueil avant qu'une seule ligne du tableau de bord ne soit rendue.

<Callout type="info">
Un layout serveur au-dessus d'un layout client : **le serveur décide, le client affiche**. C'est le schéma à reprendre chaque fois qu'une zone interactive a besoin d'une vérification en base. Et la sécurité reste en profondeur : proxy, layout serveur, puis tRPC, qui a toujours le dernier mot sur les données.
</Callout>

## Deux pièces de plus dans la maison

Avant de refermer la porte, deux visites rapides.

**Les pages publiques et les pages du tableau de bord ne sont pas faites de la même matière.**

<DocsTable columnsJson='["Groupe","Pages","Dont « use client »","Pourquoi"]' rowsJson='[["(public)","19","5","Lecture seule, référencement, premier affichage complet. Les 5 pages client sont réservées aux membres connectés."],["(admin)/dashboard","58","28","Formulaires, mutations, listes à rafraîchir. Les autres sont de minces pages serveur qui montent un composant client."]]' />

Une page publique lit la base elle-même. Celle d'une discipline montre tout le schéma, et cache un piège :

```tsx
// apps/web/src/app/(public)/disciplines/[slug]/page.tsx (extrait)
export default async function PublicDisciplinePage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const discipline = await prisma.discipline.findUnique({ where: { slug }, /* … */ });

  if (!discipline) notFound();
  // Brouillon (ou publication programmée) : invisible du public.
  if (!discipline.publicationDate || discipline.publicationDate > new Date()) {
    notFound();
  }
  // …
}
```

`params` est une **promesse** depuis Next 15 : Next commence à rendre avant d'avoir résolu les paramètres. Oublier le `await`, c'est lire `slug` sur une promesse, et obtenir `undefined` en silence. Notons aussi qu'un brouillon répond **404**, exactement comme une page inexistante : personne ne doit pouvoir deviner qu'une discipline est en préparation.

**Toutes les procédures tRPC passent par une seule porte.** Un unique fichier de route les reçoit :

```ts
// apps/web/src/app/api/trpc/[trpc]/route.ts
const handler = async (req: NextRequest): Promise<Response> => {
  return fetchRequestHandler({
    endpoint: "/api/trpc",
    req,
    router: appRouter,
    createContext: async () => createTRPCContext({ req }),
  })
}
export { handler as GET, handler as POST }
```

Le segment `[trpc]` reçoit le nom de la procédure (`post.create`, `discipline.getAll`…) et l'aiguille vers le bon routeur de `packages/backend`. Le front n'écrit jamais une URL : il appelle des fonctions. La saison consacrée à l'API ouvrira cette boîte.

## Les pièces oubliées

Les trois lignes mystérieuses du `matcher`, maintenant.

`test-finder`, `test-picker` et `simpleEditor` sont des bancs d'essai : des pages qui montent un composant seul, le temps de le mettre au point. Aucune garde ne les couvrait. N'importe quel visiteur pouvait les ouvrir, en production. Elles ne donnaient accès à aucune donnée protégée (tRPC, encore), mais elles n'avaient rien à faire là.

Les supprimer aurait privé le développement d'outils utiles. Le proxy les intercepte désormais :

```ts
// apps/web/src/proxy.ts (extrait)
const DEV_ONLY = ["/test-finder", "/test-picker", "/simpleEditor"];

export async function proxy(req: NextRequest) {
  const { origin, pathname } = req.nextUrl;
  if (DEV_ONLY.some((p) => pathname === p || pathname.startsWith(`${p}/`))) {
    return process.env.NODE_ENV === "production"
      ? new NextResponse("Not Found", { status: 404 })
      : NextResponse.next();
  }
  // … vérification du jeton pour /dashboard et /profil
}
```

En développement, rien ne change. En production, ces pages n'existent plus.

## Le clignement

Il reste une dernière anomalie, et c'est la plus sournoise, parce qu'elle ne dure qu'une fraction de seconde.

Connectons-nous, puis rechargeons une page. Regardons le header, très attentivement. Pendant un battement de paupière, il affiche le formulaire de connexion. Puis il se reprend, et montre notre menu.

Le site doute, un instant, de qui nous sommes.

La cause est enfouie dans le store qui garde la session, un store Zustand. Ce store est un **module** : sur le serveur, il est partagé par toutes les requêtes de tous les visiteurs. Y ranger la session de l'un la ferait fuiter chez le suivant. Il reste donc vide pendant le rendu serveur, et le HTML envoyé décrit toujours un visiteur anonyme. La vraie session n'arrivait qu'après coup, par une requête lancée depuis le navigateur.

Souvenons-nous de la phrase : *ce que le serveur peut savoir avant d'envoyer la page, il le met dans la page.* Le serveur connaissait la session. Il ne la mettait pas dans la page.

Le layout racine la lit désormais lui-même, et la transmet par un **contexte React**, qui, lui, est propre à chaque requête :

```tsx
// apps/web/src/app/layout.tsx (extrait)
const initialSession = await getSessionFromRequest().catch(() => null);
// …
<SessionLoader initialSession={initialSession}>{children}</SessionLoader>
```

Un petit hook choisit la bonne source selon le moment :

```tsx
// apps/web/src/features/auth/InitialSession.tsx (extrait)
export function useCurrentUser() {
  const initial = useContext(InitialSessionContext);
  const status = useSessionStore((s) => s.status);
  const user = useSessionStore((s) => s.session?.user ?? null);
  return status === "idle" ? (initial?.user ?? null) : user;
}
```

Tant que le store n'est pas prêt (sur le serveur, et au tout premier rendu dans le navigateur), la valeur du serveur fait foi : le HTML et le premier rendu client sont identiques. Puis `SessionLoader` remplit le store avec cette même session, sans nouvelle requête, et le store reprend la main pour suivre connexions et déconnexions. Le header ne doute plus.

## Ce que cache une première ligne

Trois corrections, une même leçon. Le proxy ne voyait pas les rôles parce qu'il n'avait pas accès à la base. Le tableau de bord ne pouvait pas se garder parce qu'il était client. Le header clignait parce que la session vivait dans un store client, vide sur le serveur.

À chaque fois, le coupable était le même : une frontière. D'un côté, du code qui s'exécute sur le serveur, lit la base, connaît le visiteur. De l'autre, du code qui s'exécute dans le navigateur, réagit aux clics, mais ne sait rien que ce qu'on lui transmet.

Cette frontière traverse chaque fichier du projet. Elle se déclare d'un seul mot, en première ligne : `'use client'`. Et ce mot fait bien plus que ce qu'il laisse paraître.

Pourquoi un composant client ne peut-il jamais toucher à Prisma, même pour une lecture innocente ? Que se passe-t-il exactement quand une date, un objet, une fonction franchissent la frontière ? Pourquoi un composant serveur peut-il contenir un composant client, mais pas l'inverse, sauf par un tour de passe-passe que le projet utilise partout sans le dire ?

Et surtout : que se passe-t-il, exactement, quand un composant serveur tend un objet à un composant client ? Qui le relit, en chemin ? Et où atterrit-il ?

<Callout type="tip">
**Dans l'épisode suivant** : la frontière invisible. Nous allons la franchir dans les deux sens, regarder ce qui passe, ce qui se perd, et ce qui casse en silence. Et nous découvrirons pourquoi un seul objet passé en trop, une seule ligne d'apparence innocente, suffirait à glisser l'empreinte du mot de passe d'un membre dans le code source de la page, lisible par quiconque fait « Afficher la source ».
</Callout>
