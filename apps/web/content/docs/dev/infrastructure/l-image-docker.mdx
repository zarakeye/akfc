## Avant de commencer : les mots de cette partie

Les mots de Docker vus à la mise en route (image, conteneur, volume, port) suffisaient à lancer une base sur sa machine. Mettre un site en ligne en ajoute quelques-uns.

- Un **Dockerfile** est la recette d’une image : une suite d’instructions (partir de telle image, copier ces fichiers, lancer cette commande) que Docker exécute pour la construire.
- Une construction **en plusieurs étapes** (*multi-stage*) enchaîne plusieurs images dans un même Dockerfile : les premières installent et compilent, la dernière ne recopie que le résultat. Les outils de construction ne partent pas en production.
- **Docker Compose** décrit dans un fichier (`docker-compose.yml`) plusieurs conteneurs qui fonctionnent ensemble, appelés **services** : le site, la base, le stockage. Une commande les démarre tous, dans l’ordre.
- Un **déploiement** remplace la version du site qui tourne sur le serveur par une nouvelle, sans perdre de données.
- Le **migrateur** est un conteneur à part, lancé à chaque déploiement avant le site : il applique les migrations en attente, puis s’arrête.
- Un **serveur web** placé devant le site (ici, Caddy) reçoit les visiteurs, s’occupe du HTTPS, et transmet leurs requêtes au conteneur du site.
- Les **journaux** (*logs*) sont ce que le site écrit pendant qu’il tourne : les démarrages, les erreurs, les tâches de la nuit. Sur un serveur, c’est le seul moyen de savoir ce qui s’est passé.

## Une image, des étapes 🐳

Une image Docker est un système de fichiers figé : un Linux minimal, Node, l’application compilée, ce qu’il faut pour la lancer. Le serveur la construit à partir du dépôt, puis en démarre un **conteneur**. Le `Dockerfile` en est la recette, exécutée ligne à ligne ; chaque ligne produit une **couche**, que Docker garde en cache tant que ce dont elle dépend n’a pas changé.

<Callout type="tip">
**Ordonner les couches du plus stable au plus changeant.** Le système et les outils, puis les dépendances, puis le code. Une construction ne refait alors que ce qui a changé, et la suite : une ligne de code modifiée ne refait que les dernières couches.
</Callout>

## Ce que Docker ne reçoit pas

Avant de construire, Docker envoie au moteur le **contexte** : le dossier du dépôt, filtré par `.dockerignore`. Tout ce qui entre dans le contexte peut finir dans une couche, et une couche garde ce qu’on y a copié même si une étape suivante le supprime.

Aucun `.env` n’entre dans l’image : les secrets sont donnés au **conteneur**, au démarrage, par le serveur (partie « Configuration », chapitre « Les variables d’environnement »). Une image peut être partagée, poussée sur un registre, inspectée couche par couche ; elle ne contient rien qu’on ne puisse montrer.

La relecture a ajouté la construction des tests de bout en bout (`.next-e2e`, qui pèse plusieurs centaines de mégaoctets), les tests et leurs résultats, et les scripts `apply-*.sh` qu’on dépose à la racine du dépôt pour appliquer une modification : ils ne servent ni au build ni au site.
