Les contenus les plus importants du site, pourtant, ne sont pas des pages libres : ce sont les disciplines, les cours, les stages et les événements du club.

## Pourquoi commencer par le vocabulaire

Avant d'écrire un formulaire ou une requête, il faut savoir exactement ce que l'on modélise. « Le cours de Tchoy Lee Fut » peut désigner l'art martial lui-même, le créneau du mardi soir, ou la séance d'hier. Chacun de ces sens correspond à un modèle différent, avec des règles différentes. Confondre deux d'entre eux mène à des formulaires qui demandent des informations absurdes (une date pour un créneau hebdomadaire) ou qui n'en demandent pas assez.

Le modèle du club distingue **ce qui est enseigné** (les disciplines, rangées par catégorie, famille et origine), **quand on le pratique régulièrement** (les cours) et **ce qui se passe ponctuellement** (les stages et les événements, avec leurs séances datées).

<Callout type="warning">
Dans le code, un **stage** s'appelle `Seminar`. Le modèle s'appelait `Stage` ; il a été renommé pour suivre la convention du projet, qui nomme en anglais le code, les URL et les dossiers de stockage (`courses`, `seminars`, `events`). L'interface, elle, parle français et dit « stage ». La page publique d'un stage est donc `/seminars/[slug]`, et la migration `rename_stage_to_seminar` ne fait que renommer tables, colonnes et contraintes, sans toucher aux données.
</Callout>

## La discipline, au centre

La discipline est le cœur du modèle. Tout ce qui est enseigné ou organisé s'y rattache directement ou indirectement.

```prisma
// prisma/schema.prisma (extrait simplifié)
model Discipline {
  id              Int            @id @default(autoincrement())
  name            String
  type            DisciplineType           // MARTIAL_ART, CALLIGRAPHY…
  slug            String?        @unique
  publicationDate DateTime?
  familyId        Int?
  originId        Int?
  description     Json                     // page complète, au constructeur
  summary         Json                     // présentation courte pour l'accueil
  summaryMediaId  String?                  // image de la carte d'accueil
  categoryId      Int
  instructorId    String                   // instructeur principal

  @@unique([categoryId, name])
}
```

Plusieurs décisions sont visibles dans ce modèle.

**Un nom unique par catégorie, un slug unique tout court.** Deux catégories peuvent avoir une discipline du même nom ; l'URL publique, elle, doit être unique. Le slug est saisi par l'administrateur (pré-rempli à partir du nom), et ne change pas quand on renomme la discipline : les liens déjà partagés restent valides.

**Famille et origine sont des entités, pas du texte libre.** Un champ texte « Famille » aurait vite contenu « Kung-fu », « Kung Fu » et « kungfu » : trois entrées de menu pour la même famille. Une table, avec un sélecteur dans le formulaire, rend les doublons impossibles. L'origine porte en plus ses propres informations (pays, région, période historique) et sert aussi aux stages et aux événements.

**Deux contenus.** `description` est la page complète de la discipline, construite avec les blocs du constructeur de pages. `summary` et `summaryMediaId` forment la carte de la page d'accueil : une image puis un court texte, avec « Lire la suite ». Une discipline au résumé vide n'a pas de carte.

**La catégorie ne change pas après la création.** `discipline.update` refuse de modifier `categoryId` : le dossier des fichiers d'une discipline est rangé sous celui de sa catégorie (`AKFC/courses/tchoy-lee-fut/`). Déplacer la discipline casserait le lien avec ses fichiers.

**Une date de publication.** Sans date, la discipline est un brouillon ; avec une date future, sa publication est programmée. Le filtre est appliqué par toutes les lectures de l'API (voir le chapitre sur l'API, « l'histoire des brouillons »).

## Le cours : un créneau, pas une date

```prisma
// prisma/schema.prisma (extrait simplifié)
model Course {
  id           Int      @id @default(autoincrement())
  disciplineId Int
  audience     Audience  // KIDS, TEENAGERS, ADULTS, ALL_AGES
  day          Day       // MONDAY … SATURDAY
  beginTime    Int       // HHMM : 1830 = 18h30
  endTime      Int
  instructorId String?
  requisites   String[]
  content      Json

  @@unique([disciplineId, day, beginTime, audience])
}
```

Un cours n'a pas de date : c'est « le mardi à 18h30, pour les adultes ». Les vacances et les annulations ponctuelles ne font pas partie du modèle.

Les horaires sont des entiers au format HHMM (`1830`), pas des `DateTime`. Une heure de cours n'a ni jour ni fuseau ; un `DateTime` aurait obligé à inventer une date arbitraire et à gérer le changement d'heure. Un entier se compare et se trie directement, et la règle « la fin après le début » se vérifie d'une soustraction.

La contrainte d'unicité empêche de saisir deux fois le même créneau pour le même public. L'instructeur du cours est facultatif : à défaut, c'est l'instructeur principal de la discipline.

## Le stage et l'événement : des séances datées

Un stage et un événement ont la même structure temporelle : une fiche, et une liste de **séances** (`SeminarSession`, `EventSession`), chacune avec une date, des horaires au format HHMM, un lieu et des remarques. Un stage d'un week-end a deux séances ; un stage sur deux week-ends en a quatre. Les séances sont supprimées avec leur stage (`onDelete: Cascade`).

Ils diffèrent par leur rapport aux disciplines :

Le stage accepte une discipline **extérieure** sous forme de texte (`externalDisciplineLabel`) : le club accueille parfois un intervenant pour une pratique qu'il n'enseigne pas, comme la calligraphie chinoise. Créer une `Discipline` pour l'occasion la ferait apparaître dans le menu des disciplines enseignées. L'origine permet alors de classer le stage quand il n'a pas de discipline du club.

Comme les disciplines, stages et événements ont un `summary` et une image de carte, et une date de publication. Leurs lectures publiques sont filtrées ; les écrans d'administration utilisent des procédures séparées (`seminar.getAllAdmin`, `seminar.getByIdAdmin`), réservées aux administrateurs.

## L'agenda : deux modèles, une liste

Pour un visiteur, la différence entre un stage et un événement n'a pas d'importance : il veut savoir ce qui arrive. La page « Agenda » fond donc les deux dans une seule liste chronologique, triée sur la **prochaine séance à venir** de chacun.

```ts
// apps/web/src/app/(public)/agenda/page.tsx (extrait)
const publicFilter = { publicationDate: { not: null, lte: now } };
const nextSession = {
  where: { date: { gte: now } },
  orderBy: { date: "asc" as const },
  take: 1,
  select: { date: true },
};
const [seminars, events] = await Promise.all([
  prisma.seminar.findMany({
    where: { ...publicFilter, sessions: { some: { date: { gte: now } } } },
    select: { id: true, label: true, slug: true, summary: true, summaryMediaId: true, sessions: nextSession },
  }),
  prisma.event.findMany({ /* même requête */ }),
]);
```

Le tri est fait en mémoire, après les deux requêtes. La clé de tri, la prochaine séance, est calculée sur une relation filtrée : SQL ne saurait l'ordonner qu'avec une sous-requête, et les rendez-vous à venir d'un club se comptent en dizaines. Un stage commencé mais pas terminé reste dans l'agenda, avec sa prochaine date : on peut encore le rejoindre.

Le filtre de publication est **le même** que celui des fiches publiques : une seconde règle créerait deux vérités sur ce qui est public.

## Les personnes

Les instructeurs, animateurs et organisateurs ne sont pas des entités à part : ce sont des membres (`User`), reliés par des relations nommées (`DisciplineInstructor`, `CourseInstructor`, `SeminarPrimaryAnimator`, `SeminarAnimators`, `EventOrganizer`). Un instructeur se connecte avec son compte de membre et a son profil, sa photo, sa biographie.

Ces relations sont en `Restrict` : un membre qui est instructeur principal d'une discipline, animateur principal d'un stage ou organisateur d'un événement ne peut pas être supprimé tant qu'il l'est. Supprimer le compte d'un instructeur n'efface donc jamais une discipline par accident ; il faut d'abord la confier à quelqu'un d'autre.
