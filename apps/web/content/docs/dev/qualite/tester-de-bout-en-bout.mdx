> **Précédemment.** Les gardes maison, le typecheck et le lint lisent le code sans l’exécuter : ils ne voient ni une règle de droits mal appliquée, ni une page qui répond ce qu’elle ne devrait pas.

Un test **de bout en bout** se place là où se place un utilisateur : devant un navigateur. Il ouvre une page, remplit un formulaire, clique, et vérifie ce que l’écran affiche ou ce que le serveur répond. Entre les deux, tout s’exécute pour de vrai : le composant React, la procédure tRPC, la requête Prisma, la base, le stockage, l’envoi d’un e-mail. Rien n’est simulé ; c’est ce qui le rend lent, et c’est ce qui le rend probant.

Le projet utilise **Playwright**, qui pilote un vrai Chromium. Les tests vivent dans `e2e/` à la racine, et se lancent par une commande à part, `pnpm e2e` : quelques minutes, contre quelques secondes pour `pnpm check`, qui reste la vérification de chaque commit.

<Callout type="info">
Les tests de bout en bout ne remplacent pas les gardes du chapitre 1 : ils en sont le complément. Une garde statique dit « ce code est cohérent » ; un test de bout en bout dit « ce parcours, sur ce site, fait ce qu’il doit ». Le premier est rapide et exhaustif sur ce qu’il sait lire, le second est lent et ne vérifie que ce qu’on lui a écrit.
</Callout>

Chaque parcours vérifie une règle **décidée** pour le club (les brouillons réservés aux administrateurs, un avatar qui ne représente que son titulaire, des droits qui ne changent que pour des droits plus récents), plutôt qu’un détail d’affichage. Un test qui vérifie la couleur d’un bouton casse à chaque retouche et ne protège rien ; un test qui vérifie qu’un membre ne lit pas le document d’un autre protège ce qui compte.

Un membre connecté qui demande le document d’un autre reçoit **404**, comme pour un document qui n’existe pas : le site ne confirme même pas son existence (partie « Membres et collaboration »). Sans session, **401** : la question n’est pas encore de savoir à qui est le document, mais qui demande. Le test fixe les deux réponses ; une modification qui les échangerait le ferait échouer.

## Un test doit pouvoir échouer

Un test qui passe ne prouve rien tant qu’on ne l’a pas vu **échouer** pour la bonne raison. Une assertion qui ne regarde pas ce qu’on croit (un texte présent ailleurs sur la page, une réponse 200 d’une page d’erreur) passe toujours, et protège d’autant moins qu’elle rassure.

À l’écriture de ces tests, deux règles ont été cassées exprès, le temps d’un lancement :

<Callout type="tip">
Écrire le test d’une règle avant de la corriger, quand c’est possible, donne cette preuve gratuitement : le test échoue d’abord (la règle est fausse), puis passe (elle est corrigée).
</Callout>

## Ce que le premier lancement a trouvé

Les six premiers parcours sont passés au premier lancement complet. La sortie du serveur, elle, montrait une erreur à chaque ouverture de la fiche d’un membre : `ReferenceError: DOMMatrix is not defined`.

Le visionneur de PDF (react-pdf, sur pdf.js) utilise au chargement de son module une API du navigateur, `DOMMatrix`, que Node n’a pas. Importé directement, il faisait échouer le **rendu serveur** de chaque page qui le contient : la fiche d’un membre, le profil, la page des documents. Next rattrape l’erreur et laisse le navigateur rendre la page — elle s’affiche, le test passe — mais l’erreur se répète dans les journaux à chaque visite, et la page arrive sans son HTML. La vignette PDF du Finder avait déjà rencontré le problème ; le visionneur suit maintenant la même solution :

Le septième parcours, ajouté plus tard pour le moteur des tutoriels, a trouvé le problème inverse : un composant **serveur** envoyé au navigateur avec les formulaires d’administration. La partie « Étude de cas » le raconte.

<Callout type="info">
Un test qui passe n’est pas toute l’information d’un lancement. La sortie du serveur montre ce que l’écran cache : une erreur rattrapée, un e-mail qui n’est pas parti, une requête lente. Elle se lit à chaque lancement, comme le résultat des tests.
</Callout>

Les tests ne font pas partie de `pnpm check` : ils se lancent avant un déploiement, et après toute modification d’une règle qu’ils couvrent. Plus tard, une intégration continue (GitHub Actions) pourra les lancer à chaque envoi sur GitHub, sur une machine qui monte elle-même Postgres, MinIO et Mailpit.

<Callout type="warning">
Un test qui échoue « une fois sur dix » n’est pas un test capricieux : c’est un test qui dépend de quelque chose qu’il ne contrôle pas (l’ordre, l’heure, un état laissé par un autre). On cherche cette dépendance ; on n’ajoute pas de nouvel essai automatique pour la masquer.
</Callout>
