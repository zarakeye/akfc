Côté qualité, nous en étions restés à « Qualité (1) » : le typecheck vérifie la cohérence des types, le lint les règles de React et du langage. Tous deux appliquent des règles générales, écrites pour n’importe quel projet ; aucun ne voit une règle de droits mal appliquée.

Certaines erreurs n’appartiennent qu’à ce projet. Elles ont un point commun : **rien ne les signale**. Le code compile, le lint ne dit rien, la page s’affiche — et pourtant quelque chose ne fonctionne plus, ou la documentation ment. Pour chacune, le projet a écrit une garde : un script de quelques dizaines de lignes, lancé au début de `pnpm check`, qui cherche cette erreur-là et l’explique en français quand il la trouve.

## Les fichiers que Next lit en silence 🧭

Next reconnaît quelques fichiers à leur **nom** : `proxy.ts` (le filtre qui s’exécute avant chaque requête, ancien `middleware.ts`), `instrumentation.ts` (exécuté au démarrage du serveur). Il ne les cherche qu’à un endroit : le dossier qui contient `app/`. Ce projet range son application dans `apps/web/src/app` ; un `proxy.ts` posé dans `apps/web/` serait ignoré, sans un mot. Le filtre d’authentification du tableau de bord ne s’exécuterait plus, et rien ne le dirait.

Les tutoriels interactifs guident l’utilisateur pas à pas en mettant en valeur un élément de l’écran.

<Promesse vers="dev/etude-de-cas/un-tutoriel-en-donnees" section="Un contrat de nom entre le tuto et la page">

## La carte des procédures, toujours à jour

Les parcours de cette documentation montrent ce que fait chaque procédure : les entités qu’elle lit, crée, modifie ou supprime, les e-mails qu’elle envoie. Ces effets ne sont pas écrits à la main. `build-procedure-map.mjs` les relève dans le code du backend et les écrit dans un fichier JSON que la documentation lit.

Ce motif — **un fichier généré, versionné, et une vérification qu’il est à jour** — vaut pour tout fichier produit à partir du code. Le fichier généré se relit dans une revue (on voit dans le diff qu’une procédure supprime désormais des messages), et la vérification garantit qu’on ne commite pas un backend modifié avec une carte d’hier.

<Callout type="warning">
Supprimer une fonction exportée du backend la retire aussi de la carte. La revue de cette partie en donne un exemple : la suppression de `parsePathToDestination` (chapitre 1) a fait échouer cette garde jusqu’à la régénération de la carte. C’est le comportement voulu : le diff de la carte montre ce que la suppression a retiré.
</Callout>

## Les extraits de code, ancrés sur le texte

Un extrait de la documentation montre des lignes d’un fichier du projet. Longtemps, ces lignes ont été désignées par leurs numéros (`snippetRange="235-247"`). Le défaut est apparu d’un coup : quelques champs ajoutés en haut de `schema.prisma`, et soixante-dix extraits, dans vingt chapitres, montraient le code d’à côté. Sans erreur : un extrait décalé s’affiche très bien.

Un extrait désigne donc désormais son code par son **texte** : la première ligne (`snippetStart`), puis la dernière (`snippetEnd`), ou la fin du bloc qu’ouvre la première (`snippetEnd="(fin du bloc)"`). Des lignes ajoutées au-dessus ne le décalent plus ; des lignes ajoutées dedans l’allongent, et il les montre.

## Les renvois, les encadrés et le glossaire

La documentation se réorganise au fil du projet : des chapitres changent de partie, des sections changent de titre. Trois choses en dépendent sans que rien ne les relie pour TypeScript : les **promesses** (le composant `Promesse`, un renvoi vers le chapitre qui approfondit un sujet : son attribut `vers` désigne le chapitre, `section` une de ses sections), les **encadrés** (le composant `Callout`, dont l’attribut `type` choisit la couleur), et le **glossaire** (chaque terme renvoie au chapitre et à la section qui le définissent).

`check-doc-components.mjs` relit ces trois contrats à chaque `pnpm check` : une promesse vers un chapitre déplacé, un encadré d’un type que le composant ne connaît pas, un terme dont la définition a disparu ou une forme revendiquée par deux termes arrêtent la chaîne. Les types d’encadré ne sont pas recopiés dans la garde : elle les lit dans `Callout.tsx`, là où le composant les déclare.

<Callout type="info">
Le numéro affiché par une promesse (« Approfondi en 10.7 ») n’est écrit nulle part : le composant le calcule au rendu, à partir du menu. C’est ce qui permet de réordonner les parties sans réécrire les renvois ; la garde, elle, vérifie seulement que la cible existe.
</Callout>

<Promesse vers="dev/moteur-doc/du-code-cite-au-code-montre" section="Désigner un passage par son texte">
Ces trois gardes protègent le moteur de la documentation : des extraits lus sur le disque à chaque visite, des renvois dont le numéro se calcule, un glossaire repéré dans le texte. Le moteur lui-même est la seconde étude de cas, en fin de parcours.
</Promesse>

## À suivre

Les gardes, le typecheck et le lint lisent le code sans l’exécuter. Ce qui ne se voit qu’à l’exécution — une règle de droits, un brouillon montré à qui ne devrait pas le voir, un e-mail qui n’arrive pas — demande d’exécuter le site, dans un vrai navigateur.
