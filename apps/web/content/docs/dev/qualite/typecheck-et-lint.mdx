> **Précédemment.** Le site est utilisable au clavier et avec un lecteur d'écran. Toutes les fonctions sont en place ; reste à garantir qu'elles continuent de marcher après chaque modification.

Une erreur qu'un outil peut trouver ne devrait jamais attendre qu'un humain la croise. Ce chapitre présente les deux vérifications que `pnpm check` lance avant chaque commit : le **typecheck**, qui compare les types de tout le projet, et le **lint**, qui relit le code à la recherche de motifs que l'on sait fautifs. Il raconte aussi comment le lint a été ramené à zéro, parce que chaque correction enseigne une règle de React.

## Deux vérifications, deux questions

Le typecheck ne connaît que les types : un composant parfaitement typé peut quand même provoquer un rendu de trop, ou afficher une valeur périmée. Le lint connaît les **règles de React** : celles des hooks, et celles du **React Compiler**, qui optimise les composants du projet (mode strict). Les deux se complètent ; aucun ne remplace l'autre.

## Le lint dans pnpm check

Le lint s'exécute sur `apps/web`, à la fin de `pnpm check`, et n'accepte **aucun** avertissement :

```json
// apps/web/package.json (extrait)
"lint": "eslint . --max-warnings 0",
```

Un avertissement toléré en appelle d'autres : au bout de quelques mois, la liste en compte des dizaines, et plus personne ne la lit. Une règle qui ne convient pas au projet se désactive dans la configuration, avec un commentaire qui dit pourquoi ; elle ne reste pas affichée en jaune. Les fichiers qui ne sont pas notre code, comme le worker minifié de pdf.js servi depuis `public/`, sont exclus de la même façon.

Avant d'entrer dans `pnpm check`, le lint comptait **22 erreurs et 14 avertissements**. Ils se rangeaient en deux familles.

## Ce que le lint révèle : du code mort

La première famille paraît anodine ; elle ne l'est pas toujours. Le formulaire des disciplines acceptait une option `submitLabel`, et les pages de création et d'édition lui passaient « Créer » ou « Enregistrer ». Le lint signalait qu'elle n'était jamais lue : depuis l'arrivée des deux boutons « Enregistrer en brouillon » et « Publier », son libellé était écrit en dur. Une option qui ne fait rien trompe celui qui la lit ; elle a été retirée, avec ses usages.

De même, deux états de l'arborescence du Finder (« chargement », « erreur ») n'étaient jamais modifiés : l'indicateur de chargement qui en dépendait ne pouvait pas s'afficher. Le code qui ne s'exécute jamais ment sur ce que fait le programme.

## Les règles du React Compiler

Le React Compiler réécrit chaque composant pour éviter les calculs et les rendus inutiles, sans `useMemo` ni `useCallback` écrits à la main. Il ne peut le faire que si le composant respecte les règles de React : un rendu ne doit rien modifier hors de lui, un effet sert à se synchroniser avec l'extérieur, pas à recopier des données. Quand un composant s'en écarte, le Compiler **renonce à l'optimiser**, et la règle de lint correspondante le signale. Les seize cas du projet relevaient de six motifs.

### Ne pas recopier une donnée dans un état depuis un effet

Les Réglages du site remplissaient leur formulaire avec un `useEffect` : à l'arrivée des données, l'effet recopiait chaque valeur dans un état. Le formulaire s'affichait donc d'abord vide, puis React refaisait un rendu complet. La règle `react-hooks/set-state-in-effect` l'interdit.

Le remplissage se fait maintenant **pendant le rendu**, une seule fois, protégé par un drapeau :

```tsx
// apps/web/src/app/(admin)/dashboard/settings/page.tsx (extrait)
if (!initialized && settings.isSuccess) {
  const s = settings.data;
  setInitialized(true);
  setShortTitle(s?.shortTitle ?? "AKFC");
  setLongTitle(s?.longTitle ?? "Association de Kung Fu de Chambéry");
  setTagline(s?.tagline ?? "");
  setSupportEmail(s?.supportEmail ?? "");
}
```

React accepte qu'un composant modifie son propre état pendant le rendu, à condition qu'une condition l'empêche de recommencer : il refait alors immédiatement le rendu, avant d'afficher quoi que ce soit. Le formulaire apparaît directement rempli.

### Déduire « en cours » au lieu de le stocker

Les aperçus des blocs « image et texte » résolvaient leur média dans un effet qui commençait par remettre trois états à zéro (`media`, `loading`, l'erreur d'image), avant de lancer la requête. C'est encore un état modifié dans le corps de l'effet.

Le hook partagé `useResolvedPreviewMedia` garde un seul état, le **résultat**, étiqueté par la clé du média auquel il répond. L'effet ne le modifie qu'à l'arrivée de la réponse :

```ts
// apps/web/src/features/page-builder/components/useResolvedPreviewMedia.ts (extrait)
const [fetched, setFetched] = useState<Fetched | null>(null);

useEffect(() => {
  if (m == null || key === null) return;
  let cancelled = false;
  const done = (media: Fetched["media"], resolution: Fetched["resolution"]) => {
    if (!cancelled) setFetched({ key, media, resolution });
  };
```

« En cours » n'est plus stocké : il se **déduit**. S'il y a un média et pas encore de résultat pour lui, c'est qu'on l'attend.

```ts
// apps/web/src/features/page-builder/components/useResolvedPreviewMedia.ts (extrait)
if (m == null || key === null) return { media: null, resolution: "idle" };
if (fetched === null || fetched.key !== key) return { media: null, resolution: "loading" };
return {
  media: fetched.media ? { ...fetched.media, caption: m.caption } : null,
  resolution: fetched.resolution,
};
```

Le même raisonnement règle deux autres problèmes. Une réponse arrivée trop tard pour un ancien média est ignorée d'office, puisque sa clé ne correspond plus. Et la légende, prise dans le bloc à chaque rendu, se met à jour pendant la frappe sans relancer de requête, alors qu'avant elle restait figée jusqu'au changement de média. Les deux aperçus recopiaient la même logique ; ils partagent désormais le hook.

### Une saisie en cours : un brouillon, pas une copie

Le recadrage d'image associe à chaque curseur un champ numérique. Un effet recopiait la valeur du curseur dans le texte du champ à chaque changement. Le champ affiche maintenant la valeur du curseur, **sauf** pendant la saisie, où un brouillon prend le relais :

```tsx
// apps/web/src/features/gallery-crop/components/Cropper.tsx (extrait)
const [draft, setDraft] = useState<string | null>(null);
const text = draft ?? (decimals ? ctrl.value.toFixed(decimals) : String(Math.round(ctrl.value)));
const commitText = (raw: string) => {
  const n = Number(raw);
  if (!Number.isNaN(n)) ctrl.set(Math.min(max, Math.max(min, n)));
  setDraft(null);
};
```

### Une source extérieure : useSyncExternalStore

Le bandeau d'actualités compte les nouvelles publiées depuis la dernière ouverture du panneau, date gardée dans le `localStorage` du navigateur. Le serveur ne la connaît pas : il fallait la lire après le montage, et un effet la recopiait dans un état.

React a un hook fait pour lire une source extérieure : `useSyncExternalStore`. Il reçoit une fonction d'abonnement, une fonction de lecture, et la valeur à utiliser côté serveur :

```tsx
// apps/web/src/features/breaking-news/BreakingNewsShell.tsx (extrait)
const lastSeenRaw = useSyncExternalStore(subscribeLastSeen, readLastSeen, () => null);
const unseenCount = lastSeenRaw === null ? 0 : countUnseen(news, lastSeenRaw);
```

Côté serveur et pendant l'hydratation, la valeur vaut `null` : pas de badge, donc pas de différence entre le HTML du serveur et le premier rendu du navigateur. Ensuite le navigateur lit sa valeur, et React se réabonne aux changements, y compris ceux faits dans un autre onglet.

### Ne pas écrire un ref pendant le rendu

L'envoi de photos personnelles garde ses aperçus dans un ref, pour les libérer au démontage. Le ref était mis à jour pendant le rendu, ce que la règle `react-hooks/refs` interdit : React peut abandonner un rendu en cours, et le ref garderait alors une valeur qui n'a jamais été affichée. La mise à jour passe dans un effet, qui ne s'exécute qu'après un rendu effectivement affiché :

```tsx
// apps/web/src/features/admin/perso/PersoPhotoUploader.tsx (extrait)
const itemsRef = useRef<UploadItem[]>([]);
useEffect(() => {
  itemsRef.current = items;
}, [items]);
```

### Laisser le Compiler mémoïser

Trois mémoïsations écrites à la main (`useMemo`, `useCallback`) empêchaient le Compiler de travailler, parce qu'il ne pouvait pas garantir que leurs dépendances ne changeraient pas en douce. La plus simple : sur la page « Documents », un `useMemo` dépendait d'un tableau recréé à chaque rendu tant que la requête n'avait pas répondu, et ne mémoïsait donc rien. Il a été retiré : le Compiler mémoïse lui-même.

Dans le recadrage, le dessin de l'aperçu était un `useCallback` appelé avant d'être déclaré. Il est devenu un effet qui lit des constantes, et l'arrivée de l'image le relance par un état modifié dans le rappel `onload`, ce qui est permis : seul le corps de l'effet ne doit pas modifier d'état.

Sur la carte des entités, le placement des atomes, coûteux, est désormais gardé dans un cache de module, indexé par graphe et par ensemble d'atomes : la simulation est déterministe, le même ensemble donne toujours la même carte.

### Les bibliothèques : useWatch plutôt que watch

Les formulaires de galerie lisaient leurs champs avec `form.watch()` de react-hook-form. Cette fonction renvoie des valeurs que le Compiler ne sait pas suivre, et il renonçait à optimiser tout le composant (`react-hooks/incompatible-library`). La bibliothèque fournit un hook prévu pour cela, `useWatch` :

```tsx
// apps/web/src/features/admin/galleries/forms/UpdateGalleryForm.tsx (extrait)
const selectedCategoryId = useWatch({ control: form.control, name: "categoryId" });
const watchedSeminarId = useWatch({ control: form.control, name: "seminarId" });
const watchedEventId = useWatch({ control: form.control, name: "eventId" });
```

<Callout type="tip">
Les six motifs disent la même chose : **un état ne doit pas être la copie d'une autre donnée**. Ce qui se calcule à partir des props, d'un résultat de requête ou d'une source extérieure se calcule au rendu. Un état garde seulement ce que rien d'autre ne sait : ce que l'utilisateur a tapé, ce qu'une requête a renvoyé.
</Callout>

## Lire une erreur du lint

Une erreur du lint donne le fichier, la ligne, et le nom de la règle (`react-hooks/set-state-in-effect`). Le nom suffit pour retrouver la page de documentation de la règle, qui explique le motif attendu ; les règles du Compiler renvoient en plus à la page « You Might Not Need an Effect » de la documentation de React, la lecture la plus utile sur le sujet.

Désactiver une règle sur une ligne (`// eslint-disable-next-line`) reste possible, mais c'est une exception qui se justifie dans un commentaire. Le projet en garde une, connue : les aperçus relancent leur requête quand le **média** change, pas à chaque modification du bloc, ce que la règle des dépendances d'effet ne peut pas deviner.

## À suivre

Le typecheck et le lint trouvent les erreurs que l'on peut décrire à l'avance. Les autres se manifestent à l'exécution : une page blanche, une requête qui échoue, un membre qui ne voit pas un document. Il faut alors savoir où regarder, et dans quel ordre.
