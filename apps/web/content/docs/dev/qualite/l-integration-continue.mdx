> **Précédemment.** `pnpm check` tourne avant chaque commit ; les tests de bout en bout, eux, demandent Docker et un quart d’heure, et se lancent quand on y pense.

L’intégration continue fait tourner les deux **à chaque push**, sur une machine de GitHub, sans qu’on y pense. Un push qui casse quelque chose se voit avant le déploiement : une croix rouge sur le commit, et un e-mail de GitHub.

## Le workflow

Un seul fichier, `.github/workflows/ci.yml`. Il se déclenche à chaque push, sur une pull request, et à la main depuis l’onglet **Actions** du dépôt.

`permissions: contents: read` : le workflow lit le code, rien d’autre — il ne peut ni pousser, ni commenter, ni publier. `concurrency` annule une exécution devenue inutile : deux pushes rapprochés, seul le dernier va au bout.

### Les mêmes services que sur le Mac

Les tests de bout en bout parlent à des adresses fixes (`e2e/env.mjs`) : Postgres sur le port 5435, le stockage (SeaweedFS) sur 9200, Mailpit sur 1026. Le workflow ne les redéfinit pas : il démarre **le même** `docker-compose.dev.yml` que le Mac.

`--wait` rend la main quand la base et le stockage répondent à leur `healthcheck`, et que Mailpit tourne. Un changement de port ou d’image dans le compose vaut donc aussi pour la CI : il n’y a rien à maintenir en double.

### Ce que la machine neuve a trouvé

La toute première exécution a échoué en une demi-minute, avant le moindre test : `pull access denied for minio/minio`. MinIO, le stockage local de l’époque, avait retiré ses images de Docker Hub en septembre 2026. Le Mac ne s’en était pas aperçu : Docker ne télécharge une image que s’il ne l’a pas déjà, et la sienne était en cache depuis des mois. La machine de GitHub, elle, part de zéro à chaque exécution : elle voit ce que verrait un nouveau développeur, ou un recruteur qui lance la sandbox.

Le message parle de `docker login`, mais se connecter n’y aurait rien changé : Docker répond la même chose pour un dépôt privé et pour un dépôt qui n’existe plus. Le stockage local est passé à SeaweedFS, un logiciel libre, à une **version figée** (partie « Stockage et médias ») ; Mailpit, jusque-là en `latest`, a été figé dans la foulée. C’est le même principe que pour les actions de ce workflow : une dépendance ne change pas sans qu’on l’ait décidé. L’application ne parle que le S3 standard : en changer n’a touché que les fichiers compose, pas une ligne de code.

## Ce que la CI ne fait pas

<Callout type="warning">
**Aucun secret, aucun déploiement.** Tout l’environnement des tests est factice et local à la machine de GitHub ; `e2e/env.mjs` refuse d’ailleurs une adresse qui ne serait pas locale. Rien dans le workflow ne connaît la production : elle ne se touche que depuis le serveur, migration d’abord.
</Callout>

Le dépôt est destiné à être public (c’est aussi un portfolio) : n’importe qui pourra lire le workflow et voir ses exécutions. Il ne contient rien à protéger, et c’est voulu — un workflow sans secret ne peut pas en laisser fuir.

Les actions externes (`actions/checkout`, `pnpm/action-setup`…) sont **figées à un commit précis**, le numéro de version en commentaire. Une étiquette comme `v7` peut être déplacée par son auteur, ou par quelqu’un qui aurait pris son compte : la CI exécuterait alors un autre code que celui qu’on a lu. Un commit, lui, ne bouge pas. Monter de version devient un geste choisi : changer le commit et son commentaire.

## Le réflexe avant un déploiement

Avant le `git pull` sur le serveur, un coup d’œil à l’onglet **Actions** : une coche verte sur le dernier commit, on déploie ; une croix rouge, on lit l’étape en échec et on corrige d’abord.

<Callout type="info">
Pour l’instant, on pousse directement sur la branche principale : la CI prévient **après** le push. Si d’autres contribuent un jour, on passera par des pull requests, et GitHub pourra exiger que la CI passe avant de fusionner — un réglage du dépôt (« branch protection »), le workflow restant le même.
</Callout>
