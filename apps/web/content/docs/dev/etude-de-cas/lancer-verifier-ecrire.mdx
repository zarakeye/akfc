Dans une fiche, le bouton est affiché à tous ceux qui lisent la documentation. À un visiteur qui n’a pas le rôle requis, il ne propose pas un tuto qui échouerait sur une page refusée : il est désactivé, et dit pourquoi (« Réservé aux administrateurs connectés »). Un identifiant inconnu affiche « Tuto introuvable » — ce que la garde empêche désormais d’atteindre (chapitre 1).

## Ce que le test a trouvé

À son premier lancement, le test s’est arrêté à l’étape 2 : la page de création d’une actualité ne s’affichait pas du tout (« This page couldn’t load »). Ce lancement-là tournait sur la machine de la relecture, sans Docker, où la connexion à la base passait par un module de remplacement. La console du navigateur désignait ce module — le **backend** de connexion à la base, exécuté… dans le navigateur.

La chaîne était la suivante. Le formulaire d’actualité est un composant client ; il importe le constructeur de pages depuis l’entrée `@features/page-builder`. Cette entrée exportait aussi `PageRenderer`, le composant **serveur** qui affiche une page : il lit la base par Prisma et résout les médias. Importer l’entrée, c’était importer `PageRenderer`, donc le backend, dans le code envoyé au navigateur de chaque formulaire d’administration.

En production, et dans les tests lancés sur un poste avec Docker, le client Prisma dispose d’une version pour navigateur : elle se construit sans erreur, et ne lève une erreur qu’à la première requête, que personne ne fait. Rien ne cassait, rien ne se voyait — mais chaque formulaire chargeait du code serveur qui n’avait rien à y faire. Le module de remplacement, lui, n’avait pas de version pour navigateur : il a rendu visible ce qui était là depuis longtemps.

`import "server-only"` ne fait rien à l’exécution. Mais si un composant client l’importe, **le build échoue**, avec le nom du fichier fautif. La règle « ce composant ne part jamais au navigateur » n’est plus une convention à retenir : c’est le compilateur qui la tient.

<Callout type="info">
Un test de bout en bout trouve aussi ce qu’il ne cherche pas. Ce test vérifiait un tuto ; il a trouvé un composant serveur dans le code du navigateur — comme le premier lancement des tests de la partie « Qualité » avait trouvé le visionneur PDF qui faisait échouer le rendu serveur. Les deux problèmes étaient invisibles à l’écran.
</Callout>

<Callout type="tip">
Un tuto vieillit comme le code qu’il traverse. La garde surveille ses cibles ; le test, son déroulement. Une étape dont le texte ne correspond plus à l’écran (un bouton renommé « Enregistrer ») ne se voit qu’à la relecture : un tuto se relit quand sa page change.
</Callout>

## Fin du parcours

Cette étude de cas clôt la documentation du développeur. Le moteur des tutoriels a traversé presque toutes ses parties : des données typées et une union discriminée, un état hors de React lu sans écart d’hydratation, un composant serveur tenu hors du navigateur, l’accessibilité au clavier, une garde maison, un test de bout en bout. C’est la méthode de tout le projet, appliquée à une seule fonctionnalité : **décrire en données, vérifier par un outil, et ne pas croire qu’une chose marche avant de l’avoir vue marcher**.
