> **Précédemment.** Chaque procédure tRPC reçoit un contexte, et les procédures d'administration exigent un administrateur. Le chapitre sur le routage a montré trois niveaux de contrôle autour du tableau de bord. Il reste à voir d'où vient ce que tous ces contrôles consultent : la session.

## Les parcours du chapitre

Quatre cas d'utilisation traversent ce chapitre : se connecter et naviguer, retrouver un mot de passe oublié, en changer et se déconnecter, et ouvrir le tableau de bord en administrateur. Chaque onglet en déroule les étapes et ce qu'elles lisent ou écrivent en base, relevé dans le code ; chaque étape mène à son explication plus bas, ou à la carte des entités, rejouée à cette étape.

## Deux questions

Toute requête pose deux questions distinctes.

- **Qui est-ce ?** C'est l'**authentification** : relier une requête à un compte, de façon fiable, à chaque fois.
- **A-t-il le droit ?** C'est l'**autorisation** : décider, pour ce compte, si l'action demandée est permise.

Le projet traite la première avec un cookie et une session en base, la seconde avec des groupes de membres.

## Le choix : un jeton signé qui désigne une session en base

Deux approches classiques s'opposent. Un **jeton autoporteur** (JWT) contient l'identité de l'utilisateur et se vérifie sans base de données, mais il reste valide jusqu'à son expiration, même si l'on voudrait le révoquer. Une **session en base** se révoque instantanément, mais exige une lecture à chaque requête.

Le projet combine les deux. Le cookie contient un JWT signé, et ce JWT ne contient qu'une chose : l'identifiant d'une ligne `Session` en base.

```ts
// packages/backend/src/lib/session/session.server.ts (extrait)
const session = await prisma.session.create({
  data: { userId: user.id, expiresAt },
});

const payload: SessionJwtPayload = { sessionId: session.id };
const token = jwt.sign(payload, JWT_SECRET!, { expiresIn: "7d" });

const cookieStore = await cookies();
cookieStore.set(COOKIE_NAME, token, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax",
  expires: expiresAt,
  path: "/",
});
```

Ce choix permet deux choses à la fois :

- **une vérification rapide là où la base n'est pas disponible.** Le proxy, qui s'exécute avant chaque page protégée, vérifie la signature du jeton sans requête : un jeton falsifié ou expiré est écarté immédiatement ;
- **une révocation immédiate.** Supprimer la ligne `Session` suffit à déconnecter un appareil, même si son jeton est encore bien signé. C'est ce que font la déconnexion, le changement et la réinitialisation de mot de passe.

Le jeton ne contient ni nom, ni rôle, ni droit. Ces informations sont relues en base à chaque requête : un changement de droits prend effet tout de suite, sur toutes les sessions ouvertes.

## Se connecter

La procédure `auth.login` compare le mot de passe à son empreinte bcrypt, puis crée la session :

```ts
// packages/backend/src/modules/auth/services/auth.service.ts (extrait)
const user = await prisma.user.findUnique({ where: { email } });
if (!user) {
  throw new TRPCError({ code: "UNAUTHORIZED", message: "INVALID_CREDENTIALS" });
}
const valid = await bcrypt.compare(password, user.password);
if (!valid) {
  throw new TRPCError({ code: "UNAUTHORIZED", message: "INVALID_CREDENTIALS" });
}
await createSessionJWT(user);
```

Une adresse inconnue et un mauvais mot de passe produisent **la même erreur**. Un visiteur ne peut donc pas utiliser le formulaire de connexion pour savoir si une adresse a un compte au club.

À la connexion, `createSessionJWT` enregistre aussi la date de dernière connexion, par une requête SQL directe : passer par Prisma mettrait à jour `updatedAt`, qui signifie « dernière modification du profil ».

Côté navigateur, le formulaire appelle `auth.login`, puis `auth.getSession`, et remplit le store de session avant de rediriger. Les mots de passe font au moins 12 caractères ; ils sont stockés sous forme d'empreinte bcrypt de coût 12, jamais en clair.

## Lire la session à chaque requête

Tout ce qui a besoin de connaître le visiteur appelle `getSessionFromRequest` : le contexte tRPC, les layouts serveur, les routes de médias.

```ts
// packages/backend/src/modules/auth/getSessionFromRequest.ts (extrait)
const token = await readAuthToken(req);
if (!token) return null;

let payload: SessionJwtPayload;
try {
  payload = jwt.verify(token, JWT_SECRET) as SessionJwtPayload;
} catch {
  return null;
}

const sessionDB = await prisma.session.findUnique({
  where: { id: payload.sessionId },
  include: { user: true },
});
if (!sessionDB) return null;

if (sessionDB.expiresAt < new Date()) {
  await prisma.session.deleteMany({ where: { id: sessionDB.id } });
  return null;
}
```

Le jeton est lu dans l'en-tête de la requête quand elle est fournie (routes API, tRPC), sinon dans `cookies()` (composants serveur). La session et l'utilisateur arrivent en une seule requête (`include`). Une session expirée est supprimée au passage.

La fonction renvoie un `SessionClient`, et non la ligne `User` complète :

```ts
// packages/backend/src/modules/auth/getSessionFromRequest.ts (extrait)
user: {
  id: session.user.id,
  email: session.user.email,
  firstName: session.user.firstName,
  lastName: session.user.lastName,
  pseudo: session.user.pseudo,
  avatar: session.user.avatar,
  isFirstLogin: session.user.isFirstLogin,
  isAdmin,
},
```

Cette liste explicite de champs est essentielle. La session est transmise au navigateur, et la ligne `User` contient l'empreinte du mot de passe : la recopier entière l'enverrait dans chaque page.

<Callout type="warning">
Ce qui part vers le navigateur se choisit **champ par champ**. Une ligne de base de données n'est jamais transmise telle quelle à un composant client ni renvoyée par une procédure publique.
</Callout>

`getSessionFromRequest` supprime une session expirée quand il la rencontre. Pour celles des appareils qui ne reviennent jamais, une purge quotidienne, lancée au démarrage par `instrumentation.ts` (`startRetentionSchedule`, chaque nuit à 3 h), supprime les sessions expirées et les liens de réinitialisation périmés, avec les autres données dont la durée de conservation est écoulée.

## Le contexte tRPC et les procédures

Le contexte de chaque requête tRPC contient la session :

```ts
// packages/backend/src/trpc/core.ts (extrait)
export async function createTRPCContext({
  req,
}: {
  req: Request | NextRequest;
}): Promise<TRPCContext> {
  const sessionClient = await getSessionFromRequest(req);

  return {
    sessionClient,
    prisma,
    requestIp: getIpFromRequest(req),
    userAgent: req.headers.get("user-agent"),
    appRoot: APP_ROOT,
  };
}
```

## Se déconnecter et changer de mot de passe

La déconnexion supprime la ligne `Session` désignée par le cookie, puis le cookie.

Le changement de mot de passe vérifie l'ancien, refuse un nouveau mot de passe identique, puis, **dans une même transaction**, enregistre la nouvelle empreinte et supprime toutes les autres sessions de l'utilisateur :

```ts
// packages/backend/src/modules/auth/router.ts (extrait)
await ctx.prisma.$transaction(async (tx) => {
  await tx.user.update({
    where: { id: userId },
    data: { password: hashed },
  });
  await tx.session.deleteMany({
    where: {
      userId,
      ...(currentSessionId ? { NOT: { id: currentSessionId } } : {}),
    },
  });
});
```

Quelqu'un qui change son mot de passe parce qu'il le croit compromis déconnecte ainsi tous les autres appareils, tout en restant connecté sur celui qu'il utilise.

## Le mot de passe oublié

La réinitialisation repose sur un jeton à usage unique, envoyé par e-mail :

```ts
// packages/backend/src/modules/auth/services/passwordReset.service.ts (extrait)
export const RESET_TOKEN_TTL_MS = 1000 * 60 * 30; // 30 min
export const RESET_TOKEN_COOLDOWN_MS = 1000 * 60 * 2; // 2 min

export function createPasswordResetToken(): { token: string; tokenHash: string } {
  const token = crypto.randomBytes(32).toString("hex");
  const tokenHash = hashResetToken(token);
  return { token, tokenHash };
}
```

## La création d'un compte

Il n'y a pas d'inscription libre : un administrateur crée le compte (`user.create`), avec au moins un groupe. Le mot de passe est **généré par le serveur** et envoyé par e-mail au seul membre ; l'administrateur ne le voit jamais. Le compte naît avec `isFirstLogin` à vrai : à sa première connexion, le composant `FirstLoginRedirect` envoie le membre vers `/profil/edit` pour compléter son profil (voir le chapitre « Le profil et la première connexion »). Les comptes de démonstration (`@akfc.demo`) ne reçoivent pas d'e-mail.

## Les droits : des groupes

Les droits ne reposent pas sur un rôle attaché à l'utilisateur, mais sur ses **groupes**. Un membre peut appartenir à plusieurs groupes, et chaque appartenance a un niveau :

<DocsTable columnsJson='["Notion","Modèle","Signification"]' rowsJson='[["Groupe","MemberGroup","Un ensemble de membres. S’il est collaboratif (isCollaborative), il a un espace de fichiers."],["Appartenance","MemberGroupMembership","Un membre dans un groupe, avec un niveau d’accès : VIEWER (consulter) ou EDITOR (consulter et déposer)."],["Hiérarchie","MemberGroup.parentGroupId","Un groupe peut avoir un groupe parent ; les membres du parent ont accès aux espaces des descendants."],["Administrateurs","MemberGroup.isAdminGroup","Un groupe unique, créé au démarrage s’il n’existe pas (ensureAdminGroup). Ses membres sont les administrateurs."]]' />

Ce modèle permet de répondre aux besoins du club sans nouvelle notion : un groupe « Bureau » qui reçoit certains documents, un groupe par cours avec son espace partagé, des encadrants qui voient les espaces de tous les cours d'une discipline par l'héritage.

**Être administrateur, c'est appartenir au groupe Administrateurs.** `getSessionFromRequest` le calcule à chaque requête, et le pose dans `SessionClient.isAdmin`. Les services qui n'ont pas la session sous la main utilisent la même règle :

```ts
// packages/backend/src/modules/memberGroups/isAdminByGroup.service.ts (extrait)
const membership = await prisma.memberGroupMembership.findFirst({
  where: { userId, group: { isAdminGroup: true } },
  select: { id: true },
});
return membership !== null;
```

**L'accès à l'espace d'un groupe** se calcule en remontant la hiérarchie : on lit l'appartenance au groupe visé, puis à son parent, et ainsi de suite, et l'on garde le meilleur niveau.

```ts
// packages/backend/src/modules/memberGroups/resolveGroupAccessForUser.service.ts (extrait)
while (cursor && !seen.has(cursor)) {
  seen.add(cursor);
  const membership = await prisma.memberGroupMembership.findUnique({
    where: { groupId_userId: { groupId: cursor, userId } },
    select: { access: true },
  });
  if (membership?.access === "EDITOR") return "EDITOR";
  if (membership?.access === "VIEWER") best = "VIEWER";
  const group = await prisma.memberGroup.findUnique({ where: { id: cursor }, select: { parentGroupId: true } });
  cursor = group?.parentGroupId ?? null;
}
return best;
```

L'ensemble `seen` protège contre une boucle dans la hiérarchie : un groupe qui serait par erreur son propre ancêtre ne bloque pas la requête.

## Les pages en construction

Une dernière forme d'autorisation concerne les pages éditoriales (accueil, association, contacts). Tant qu'un administrateur ne les a pas publiées, elles affichent « Page en construction » aux visiteurs, et leur vrai contenu aux administrateurs, qui peuvent ainsi les préparer et les relire en conditions réelles :

```ts
// apps/web/src/features/editorial/editorialGate.tsx (extrait)
export async function isEditorialPageGated(key: string): Promise<boolean> {
  const vis = await prisma.pageVisibility.findUnique({ where: { key } });
  if (vis?.published === true) return false;
  const session = await getSessionFromRequest();
  const isAdmin = (session?.user?.isAdmin ?? false);
  return !isAdmin;
}
```
