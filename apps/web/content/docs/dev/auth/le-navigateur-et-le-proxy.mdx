## Mouvement 3 — Autour de la session

Nous avons construit la naissance d’une session (Mouvement 1), puis sa vie complète à travers tout le backend (Mouvement 2).

Mais l’authentification n’est jamais purement backend. Elle touche au navigateur, qui doit savoir « qui suis-je » pour afficher la bonne interface. Elle touche à l’entrée du site, où un premier filtre peut écarter une requête sans jeton avant même qu’une page ne soit rendue. ## Le navigateur : la session dès le premier affichage

Côté navigateur, la question « qui est connecté ? » se pose dès le premier affichage. Le header doit montrer, tout de suite, soit le bouton « Se connecter », soit l’avatar du membre. Une réponse qui arrive après coup se voit : le header affiche « visiteur », puis bascule sur « connecté » une fraction de seconde plus tard.

La première version du projet avait exactement ce défaut. Un composant, `SessionLoader`, appelait `getSession` après le montage de l’application, et le header attendait la réponse. Le projet lit désormais la session **côté serveur**, dans le layout racine, et la transmet au navigateur avec la page :

```tsx
// apps/web/src/app/layout.tsx (extrait)
  // Session lue ici, côté serveur : le header s'affiche d'emblée connecté ou non (voir
  // SessionLoader / useCurrentUser). Base indisponible → visiteur anonyme, pas d'erreur.
  const initialSession = await getSessionFromRequest().catch(() => null);
```

```tsx
// apps/web/src/app/layout.tsx (extrait)
        <AppProviders>
          <SessionLoader initialSession={initialSession}>{children}</SessionLoader>
        </AppProviders>
```

`getSessionFromRequest`, sans requête en argument, lit le cookie avec `cookies()` de Next (chapitre 5). Le `.catch(() => null)` dit ce qui se passe si la base ne répond pas : le visiteur est traité comme anonyme, et le site s’affiche quand même.

La session lue part ensuite dans `SessionLoader`, qui alimente deux endroits à la fois :

## Pourquoi deux endroits : un contexte et un store

`SessionLoader` range la session dans un **store Zustand** (`useSessionStore`), et la confie aussi à un **contexte React** (`InitialSessionProvider`). Ce doublon apparent répond à une contrainte précise du rendu serveur :

Le commentaire de tête le dit : un store Zustand est un **module**. Sur le serveur, ce module est partagé par toutes les requêtes de tous les visiteurs. Y ranger la session d’un membre pendant le rendu serveur, ce serait risquer de l’afficher à quelqu’un d’autre. Le store reste donc vide pendant le rendu serveur, et n’est rempli qu’une fois dans le navigateur, par l’effet de `SessionLoader`.

Un contexte React, lui, est propre à **chaque rendu** : il peut porter la session du visiteur dès le HTML, sans risque de mélange. `useCurrentUser` combine les deux : la valeur du contexte tant que le store n’est pas initialisé (statut `idle`), puis celle du store, qui suit ensuite les connexions et les déconnexions.

---

## 🔭 Pour aller plus loin — pourquoi Zustand plutôt qu’un contexte pour la suite ?

Si le contexte peut porter la session, pourquoi ne pas s’en servir partout ?

Le contexte React a une limite : **chaque changement de sa valeur fait se réafficher tous ses consommateurs**, même ceux que le changement ne concerne pas. Zustand permet des **sélecteurs fins** : un composant s’abonne à la seule partie qu’il lit (`useSessionStore((s) => s.session?.user?.avatar)`). Quand l’avatar change, seuls les composants qui lisent l’avatar se réaffichent.

La session est lue par une trentaine de composants — header, menus, cloches de notification, finder, formulaires. Pour la valeur vivante, le store est le bon outil ; pour la valeur initiale, propre à la requête, le contexte. Chacun fait ce qu’il sait faire.

Le store a d’ailleurs été allégé pendant l’écriture de cette partie. Il portait un indicateur `loading`, une fonction `resetStatus` et deux états d’animation (`justLoggedIn`, `justLoggedOut`) remis à zéro par des minuteries de trois secondes — rien de tout cela n’était lu par aucun composant. Il reste trois états (`idle`, `guest`, `authenticated`) et les actions réellement utilisées.

## 🔭 Pour aller plus loin — pourquoi ne pas renvoyer la session directement depuis login ?

Cette séparation pourrait sembler redondante à première vue.

`login` pourrait renvoyer le `SessionClient` directement dans sa réponse. Cela économiserait un aller-retour réseau. Alors pourquoi ne pas le faire ?

Parce que cela mélangerait **deux responsabilités distinctes** :

- `login` répond à : *« est-ce que ça a marché ? »* (succès, ou la raison de l’échec)
- `getSession` répond à : *« qui es-tu ? »* (le `SessionClient` complet)

En les séparant :

- `getSession` reste **réutilisable indépendamment** de la connexion : après une modification du profil (`fetchSession`), ou chaque fois que le front a besoin de relire la vérité du serveur ;
- `login` reste **focalisé sur sa seule responsabilité** — authentifier, pas projeter ;
- le contrat de retour de `login` reste **minimal et stable** : si `SessionClient` évolue, la signature de `login` ne change pas.

Le coût d’un aller-retour supplémentaire est négligeable, une fois par connexion, à côté de la clarté gagnée.

---

<Callout type="tip">
Le navigateur reflète la discipline du backend.

Deux appels, deux responsabilités. Le coût est imperceptible pour le membre ; la clarté pour le développeur est réelle.
</Callout>

## 🔭 Pour aller plus loin — un proxy qui ne tournait jamais

Le commentaire du `matcher` raconte une erreur instructive. Les pages du tableau de bord vivent dans `app/(admin)/dashboard/…`. Le dossier `(admin)` est un **groupe de routes** : ses parenthèses disent à Next de l’ignorer dans les adresses. La page est servie à `/dashboard/…`, pas à `/(admin)/dashboard/…`.

L’ancien `matcher` visait pourtant `"/(admin)/:path*"`. Aucune adresse ne commençant par `/(admin)`, le proxy ne s’exécutait **jamais**. Rien ne le signalait : aucune erreur, aucune page cassée. Un visiteur sans jeton qui ouvrait `/dashboard` n’était pas renvoyé à l’accueil par le proxy — il passait.

Ce qui a évité le pire, c’est que le proxy n’était pas seul : chaque procédure d’administration exige `isAdmin`. Le visiteur voyait au mieux le squelette du tableau de bord, dont aucune donnée ne se chargeait. Depuis, le `matcher` vise les vraies adresses, et un layout serveur garde aussi l’interface du tableau de bord (chapitre 9).

C’est la meilleure démonstration du principe de la section suivante : la protection qui compte vit **plus bas**, là où elle ne dépend pas d’une configuration qu’on ne voit pas fonctionner.

## 🔭 Pour aller plus loin — proxy.ts en Next.js 16

Next.js 16 a renommé l’ancienne convention `middleware.ts` en `proxy.ts`. Le renommage n’est pas cosmétique.

Le terme « middleware » prêtait à confusion avec Express, où un middleware porte volontiers de la logique applicative. Dans Next, ce fichier vit à la **frontière** — entre le navigateur et l’application — et n’est pas fait pour porter la logique métier. Le nom « proxy » rend cette intention explicite.

Le changement fait aussi écho à un incident réel : en mars 2025, une vulnérabilité critique (**CVE-2025-29927**) permettait de contourner entièrement le middleware de Next, en ajoutant à la requête un en-tête HTTP `x-middleware-subrequest`. Elle touchait les versions 11.1.4 à 15.2.2. Toute application qui faisait reposer ses autorisations sur le middleware seul était ouverte.

L’enseignement est central : **un proxy ne doit jamais être la seule couche de sécurité**. Il filtre, il écarte tôt, il évite de rendre une page pour rien — mais la vérification qui fait foi vit plus bas.

---

## Le rôle exact du proxy dans la chaîne

`proxy.ts` fait deux choses, pas plus :

- il vérifie la **présence** du cookie de session ;
- il vérifie la **signature** du jeton (et son algorithme, et sa date).

Il ne fait pas :

- de recherche en base (la session a pu être révoquée depuis) ;
- de lecture des droits (ce n’est pas son rôle) ;
- de chargement du membre (c’est la responsabilité du backend).

Et il ne s’exécute **que** devant les pages listées dans son `matcher` : `/dashboard`, `/profil` et les bancs d’essai. Il ne voit jamais `/api/trpc`, ni les routes de fichiers.

---

👉 **En cas d’échec**, le proxy renvoie à l’accueil. Pas d’erreur, pas de page d’explication : comme le portier d’un club, il ne discute pas.

👉 **En cas de succès**, il laisse passer. Mais ce succès n’est qu’un feu vert préliminaire : un jeton bien signé peut désigner une session supprimée.
