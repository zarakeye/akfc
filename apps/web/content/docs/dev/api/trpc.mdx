> **Précédemment.** Le schéma Prisma décrit les données du club, et le client généré les lit et les écrit en TypeScript, côté serveur. Le navigateur, lui, n'a pas accès à la base. Il lui faut une API.

## Le besoin : des appels typés de bout en bout

Une API REST classique sépare deux mondes. Le serveur expose des URL (`POST /api/disciplines`), le client les appelle avec `fetch`, et les types des deux côtés sont écrits deux fois : une fois pour la route, une fois pour le client. Rien ne garantit qu'ils restent d'accord. Un champ renommé côté serveur casse l'application en production, pas à la compilation.

Le projet utilise **tRPC**. Le backend déclare des **procédures**, des fonctions avec une entrée validée et une sortie typée. Le front les appelle comme des fonctions :

```ts
const created = await createMutation.mutateAsync(input); // trpc.discipline.create
```

Les types de l'entrée et de la sortie sont **inférés** du code du backend. Il n'y a ni URL à écrire, ni type à dupliquer, ni client à générer. Renommer un champ dans une procédure fait échouer `pnpm check` partout où le front l'utilise.

Le lien entre les deux côtés tient en une ligne, côté navigateur :

```ts
// apps/web/src/core/trpc/trpcClient.ts (extrait)
import type { AppRouter } from "@backend/modules"
```

C'est un `import type` : il est effacé à la compilation. Le navigateur reçoit les **types** du routeur, jamais son code ni celui de Prisma.

<Callout type="info">
tRPC convient ici parce que le front et le back vivent dans le même dépôt, en TypeScript, et sont déployés ensemble. Une API destinée à des clients tiers, ou écrite dans d'autres langages, appellerait plutôt REST ou GraphQL.
</Callout>

## Un routeur par domaine

Chaque domaine du projet a son dossier dans `packages/backend/src/modules`, avec son routeur. Le routeur de l'application les assemble :

```ts
// packages/backend/src/modules/index.ts (extrait)
export const appRouter = router({
  auth: authRouter,
  user: userRouter,
  discipline: disciplineRouter,
  seminar: seminarRouter,
  event: eventRouter,
  post: postRouter,
  storage: storageRouter,
  media: mediaRouter,
  trash: trashRouter,
  memberGroup: memberGroupRouter,
  memberDocument: memberDocumentRouter,
  ticket: ticketRouter,
  // … une trentaine de domaines au total
});

export type AppRouter = typeof appRouter;
```

Le nom de la clé devient l'espace de noms côté client : `trpc.discipline.create`, `trpc.storage.getTree`. Ajouter un domaine, c'est créer son routeur et l'ajouter ici ; son API est aussitôt disponible et typée dans le front.

Toutes les procédures arrivent par une seule route HTTP, `app/api/trpc/[trpc]/route.ts`, décrite au chapitre sur le routage : le segment `[trpc]` reçoit le nom de la procédure, et `fetchRequestHandler` la fait exécuter avec le contexte de la requête.

## Le contexte et les niveaux de procédure

Chaque requête construit un **contexte** (`createTRPCContext`) que toutes les procédures reçoivent : la session du visiteur, le client Prisma, son adresse IP, son navigateur, la racine de stockage. Trois niveaux de procédures s'appuient dessus :

Le chapitre sur l'authentification détaille d'où vient la session et ce que signifie « administrateur ». Ici, retenons que la garde est **déclarée sur la procédure** : une procédure d'administration ne peut pas oublier de vérifier les droits, puisque la vérification fait partie de sa définition.

Un même routeur mélange souvent les niveaux. Celui des disciplines expose ses lectures publiquement (le site public en a besoin) et réserve ses écritures aux administrateurs.

### Le piège des lectures publiques : l'histoire des brouillons

Une discipline n'est publique qu'à partir de sa date de publication : sans date, c'est un brouillon ; avec une date future, une publication programmée. Les administrateurs préparent ainsi une nouvelle discipline à leur rythme, et la page publique `/disciplines/[slug]` répond 404 tant qu'elle n'est pas publiée.

Pendant longtemps, pourtant, les brouillons n'étaient pas secrets. Les lectures `discipline.getAll` et `discipline.getById` étaient des `publicProcedure` sans filtre : le tableau de bord en avait besoin pour lister et éditer toutes les disciplines, et seuls les écrans d'administration les appelaient. La page publique, elle, filtrait correctement. Tout semblait juste.

Mais une procédure publique n'est pas publique « pour les écrans qui l'utilisent » : elle l'est pour quiconque connaît son nom. N'importe quel visiteur pouvait ouvrir `/api/trpc/discipline.getAll` dans son navigateur et lire la liste complète, brouillons compris, avec leur nom, leur description et leur date de publication prévue. Aucune page n'affichait ces informations ; l'API les donnait.

La règle de visibilité vit désormais **dans les procédures**, en un seul endroit :

```ts
// packages/backend/src/modules/disciplines/router.ts (extrait)
function visibleTo(ctx: { sessionClient: { user?: { isAdmin?: boolean } | null } | null }): Prisma.DisciplineWhereInput {
  if (ctx.sessionClient?.user?.isAdmin) return {};
  return { publicationDate: { not: null, lte: new Date() } };
}

getAll: publicProcedure.query(async ({ ctx }) => {
  return ctx.prisma.discipline.findMany({
    where: visibleTo(ctx),
    orderBy: [{ categoryId: "asc" }, { name: "asc" }],
  });
}),
```

Toutes les lectures du routeur (`getAll`, `getAllByCategory`, `getAllForMenu`, `getById`, `getBySlug`) appliquent ce filtre. Un administrateur voit tout ; un membre ou un visiteur ne voit que ce qui est publié, et un brouillon demandé par son identifiant répond « introuvable », exactement comme la page publique.

Les stages et les événements résolvent le même problème autrement : une lecture publique filtrée (`seminar.getAll`) et une lecture séparée réservée aux administrateurs (`seminar.getAllAdmin`). Pour les disciplines, le filtre selon l'appelant a été préféré parce que la même liste sert aussi aux formulaires des membres (le dépôt de fichiers propose les disciplines) : ils reçoivent désormais les seules disciplines publiées, sans qu'aucun écran ait eu à changer.

<Callout type="warning">
Une `publicProcedure` est une URL publique. La question à se poser n'est pas « quelle page l'utilise ? » mais « que verrait un inconnu qui l'appelle directement ? ». Ce qui ne doit pas sortir est filtré **dans la procédure** ; masquer une information dans l'interface ne la protège pas.
</Callout>

## Anatomie d'une procédure

`discipline.create` montre toutes les étapes d'une écriture.

**1. L'entrée est validée par Zod.** Le schéma décrit chaque champ, et tRPC refuse la requête avant même d'exécuter la procédure si l'entrée ne le respecte pas. Le type TypeScript de l'entrée est déduit du schéma : une seule déclaration sert de validation et de type.

```ts
// packages/backend/src/modules/disciplines/router.ts (extrait)
const createInput = z.object({
  name: z.string().trim().min(1).max(120),
  slug: slugSchema,
  type: disciplineTypeEnum,
  familyId: z.number().int().positive().nullable().optional(),
  description: pageContentSchemaV1,
  categoryId: z.number().int().positive(),
  instructorId: z.string().trim().min(1),
  publicationDate: z.coerce.date().nullable().optional(),
  // …
});
```

**2. Les références sont vérifiées.** Une catégorie, un instructeur, une famille ou une origine inexistants produisent une erreur `BAD_REQUEST` explicite, plutôt qu'une violation de clé étrangère incompréhensible.

**3. L'écriture et ses conséquences forment une transaction.** Créer une discipline, c'est aussi enregistrer les médias que sa description utilise, pour que la route publique accepte de les servir et que personne ne puisse les retirer :

```ts
// packages/backend/src/modules/disciplines/router.ts (extrait)
return await ctx.prisma.$transaction(async (tx) => {
  let created;
  try {
    created = await tx.discipline.create({ data: { /* … */ } });
  } catch (err) {
    if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2002") {
      const t = err.meta?.target;
      const onSlug = Array.isArray(t) ? t.includes("slug") : String(t ?? "").includes("slug");
      throw new TRPCError({
        code: "CONFLICT",
        message: onSlug
          ? "This slug is already used. Choose a different one."
          : "A discipline with this name already exists in this category.",
      });
    }
    throw err;
  }

  await syncPageMediaReferences(tx, {
    pageType: "DISCIPLINE",
    pageId: String(created.id),
    newContent: { version: 1, blocks: [...input.description.blocks, ...(input.summary?.blocks ?? [])] },
    extraMediaIds: input.summaryMediaId ? [input.summaryMediaId] : [],
  });

  return created;
});
```

Si la synchronisation échoue (par exemple parce que la description utilise un média encore en attente), la création est annulée : il n'existe jamais de discipline enregistrée dont les médias ne le seraient pas.

**4. Les erreurs de la base deviennent des erreurs lisibles.** L'unicité du slug et celle du nom dans une catégorie sont garanties par la base. Plutôt que de vérifier avant d'écrire (ce qui laisserait une fenêtre où deux requêtes simultanées passeraient toutes les deux), la procédure écrit, et traduit l'erreur Prisma `P2002` en `CONFLICT` en précisant quelle contrainte a sauté.

## Les erreurs

Une procédure signale un refus en levant une `TRPCError` avec un code :

<DocsTable columnsJson='["Code","HTTP","Quand"]' rowsJson='[["BAD_REQUEST","400","Entrée invalide ou référence inexistante."],["UNAUTHORIZED","401","Aucune session."],["FORBIDDEN","403","Session valide, droit insuffisant."],["NOT_FOUND","404","L’élément visé n’existe pas."],["CONFLICT","409","Doublon, ou écrasement non confirmé."]]' />

Le message accompagne l'erreur jusqu'au client, où le composant peut l'afficher. Les messages destinés à l'utilisateur sont donc rédigés pour lui.

Certaines issues ne sont pas des erreurs mais des résultats attendus. La connexion, par exemple, renvoie `{ success: false, error: "INVALID_CREDENTIALS" }` plutôt que de lever une exception : un mauvais mot de passe fait partie du fonctionnement normal du formulaire, et le front choisit le message à afficher selon le code reçu.

## superjson : des dates qui restent des dates

JSON ne connaît que les chaînes, les nombres, les booléens, les tableaux et les objets. Une `Date` envoyée telle quelle arriverait comme une chaîne, et `discipline.publicationDate.getTime()` planterait côté client.

Le serveur et le client déclarent le même **transformateur**, `superjson`, qui encode les types que JSON ignore et les reconstruit à l'arrivée :

```ts
// packages/backend/src/trpc/core.ts (extrait)
export const t = initTRPC.context<TRPCContext>().create({
  transformer: superjson,
});
```

Une `Date` du serveur arrive en `Date` dans le navigateur, et le type inféré le dit.

## Côté navigateur : deux clients

Le front dispose de deux clients, déclarés dans le même fichier :

```ts
// apps/web/src/core/trpc/trpcClient.ts (extrait)
export const trpc = createTRPCReact<AppRouter>()

export const trpcClient = createTRPCClient<AppRouter>({
  links: [
    httpBatchLink({
      url: "/api/trpc",
      transformer: superjson,
      fetch(url, options) {
        return fetch(url, { ...options, credentials: "include" })
      },
    }),
  ],
})
```

`httpBatchLink` **regroupe** les appels lancés au même moment en une seule requête HTTP : une page qui charge la liste des disciplines, des familles et des origines n'envoie qu'une requête. `credentials: "include"` joint le cookie de session.

### Lire, écrire, rafraîchir

Une lecture passe par `useQuery`, qui met le résultat en cache sous une clé dérivée de la procédure et de son entrée. Une écriture passe par `useMutation`. Après une écriture, le composant **invalide** les lectures concernées :

```tsx
// apps/web/src/app/(admin)/dashboard/disciplines/create/page.tsx (extrait)
const utils = trpc.useUtils();
const createMutation = trpc.discipline.create.useMutation();

const handleSubmit = async (input: DisciplineFormInput): Promise<void> => {
  const created = await createMutation.mutateAsync(input);
  await utils.discipline.getAll.invalidate();
  setCreatedId(created.id);
};
```

`invalidate()` marque la liste comme périmée : tout composant qui l'affiche la recharge de lui-même. Le composant qui crée n'a pas à savoir qui affiche la liste.

### Et côté serveur ?

Les composants serveur n'appellent pas tRPC : ils lisent la base directement avec Prisma (chapitre sur le routage), ce qui évite une requête HTTP vers soi-même. tRPC est l'API **du navigateur**. Pour un script ou un test qui doit passer par les procédures, `createTRPCCaller` (`packages/backend/src/trpc/trpcCaller.ts`) construit un appelant à partir d'une requête.
