> **Précédemment.** Une requête se lit en deux dimensions : le contexte (dans quel cadre) et la procédure (quelle intention). Le routeur regroupe les procédures d’un domaine, et `appRouter` assemble les domaines.

## Mouvement 2 — Composer une procédure

Savoir que l’environnement et l’intention sont deux choses distinctes, c’est un début. Mais dans un backend réel, une procédure n’est jamais seule : elle vit au milieu d’autres couches, chacune avec son rôle. Ce mouvement est celui de la composition — apprendre qui fait quoi, et dans quel ordre.

Voici les deux étapes que nous allons traverser :

- **Ce chapitre** — Nous ouvrons un vrai routeur métier et nous clarifions une ambiguïté qui piège beaucoup de débutants : d’où vient réellement `ctx` ? Puis nous sortons la logique de la procédure pour la placer dans un service, nous déplaçons la sécurité dans des gardes, et nous voyons ce que tRPC apporte vraiment — et ce qu’il n’apporte pas.
- **Chapitre 5** — Nous apprenons à fabriquer une procédure concrète, dans le bon ordre, avec les bonnes contraintes, pour qu’elle se lise d’un seul regard.

À la fin de ce mouvement, nous saurons non seulement *comprendre* une procédure existante, mais aussi en *écrire* une nouvelle, dans un backend réel, sans mélanger les responsabilités.

## Le router métier (là où l’intention devient action)

Maintenant que le contexte est clarifié, nous pouvons enfin ouvrir un vrai router métier.

Mais avant d’aller plus loin, un point doit être verrouillé.

Parce que c’est le point où la plupart des développeurs débutants se perdent.

---

## 🧠 D’où vient réellement `ctx` ?

En lisant une procédure pour la première fois, nous pourrions croire que `ctx` est créé ici.

Ce n’est pas le cas.

👉 `ctx` est produit **en amont** par `createTRPCContext`.

Et surtout :

👉 il n’est jamais appelé manuellement dans le router.

Il serait même impossible de l’appeler manuellement : le router n’a pas accès à la requête HTTP. La requête vit à un niveau supérieur, dans la route App Router. Le router ne connaît que le résultat — l’objet `ctx` déjà construit, qui lui est remis.

Une dernière procédure de ce routeur mérite un regard, plus bas dans le fichier : `getSession`.

```ts
// packages/backend/src/modules/auth/router.ts (extrait)
  getSession: publicProcedure.query(async ({ ctx }) => {
    return ctx.sessionClient;
  }),
```

Elle est publique — pas besoin d’être connecté pour l’appeler — et pourtant elle lit le contexte, où `sessionClient` peut être `null`. Le client obtient toujours une réponse : la session, ou rien. C’est la procédure que le front appelle pour savoir « qui suis-je, maintenant ? ». Elle tient en une ligne parce que tout le travail a été fait avant elle, par `createTRPCContext`.

## 2) Le contexte est déjà prêt

Quand la procédure s’exécute :

👉 `ctx` est déjà disponible

Donc nous pouvons directement :

- accéder à Prisma via `ctx.prisma`  
- lire l’utilisateur via `ctx.sessionClient.user`  
- appliquer la logique métier  

---

👉 Nous ne faisons pas :

- lire les cookies  
- reconstruire la session  
- deviner l’utilisateur  

Toute cette plomberie a été faite en amont par le middleware et `createTRPCContext`. Si nous nous retrouvions à écrire `req.headers.get("cookie")` dans une procédure, ce serait le signe d’une fuite architecturale — quelque chose devrait vivre dans `core.ts`, pas ici.

---

## 3) Prisma termine le flux

Prisma n’est pas le début.

👉 c’est la fin logique du flux

- contexte construit  
- intention définie  
- action exécutée  

Dans notre architecture, Prisma est toujours le dernier maillon. Quand nous voyons `ctx.prisma.user.create(...)`, c’est que toutes les étapes précédentes ont réussi : authentification, validation, autorisation. Si l’une d’elles avait échoué, nous ne serions jamais arrivés ici.

## 🧠 Le problème d’un router “trop intelligent”

Si nous écrivons :

<CodeSnippet
  language="ts"
  title="Logique métier directement dans la procédure"
  kind="anti-pattern"
  codeJson='"protectedProcedure.mutation(({ ctx, input }) => {\n  return ctx.prisma.user.create({ data: input })\n})"'
/>

👉 nous mélangeons plusieurs responsabilités :

- intention (procédure)  
- logique métier  
- accès base de données  

---

💥 Résultat :

- duplication quand plusieurs procédures font la même chose  
- code difficile à tester parce que dépendant de tRPC  
- logique dispersée dans les routers  

Et surtout, un effet pernicieux : quand une règle métier change — disons, “nous devons désormais envoyer un e-mail de bienvenue lors de la création d’un membre” — nous devons la répliquer partout où un membre est créé. Y compris dans les scripts de seed, les tâches CRON, les tests. Et si nous en oublions un endroit, l’incohérence s’installe silencieusement.

---

## 🔥 La séparation des responsabilités

Dans un backend propre, nous introduisons une séparation explicite :

- **procédure** → intention  
- **guard / middleware** → autorisation  
- **service** → logique métier  
- **Prisma** → accès aux données  

Chaque couche a un rôle unique. Et chaque couche peut changer sans affecter les autres.

## 1) Le service : la vraie logique métier

Nous extrayons la logique dans un fichier séparé :

<CodeSnippet
  language="ts"
  title="Service métier"
  kind="pattern"
  codeJson='"export const userService = {\n  async createUser(ctx, input) {\n    return ctx.prisma.user.create({ data: input })\n  }\n}"'
/>

---

👉 Le service :

- contient la logique métier, isolée  
- peut être testé sans tRPC  
- peut être réutilisé par plusieurs procédures, des scripts, des jobs  

Regardons un vrai service du projet, celui qui vérifie un identifiant et un mot de passe :

Ce service fait un travail précis : il cherche le membre par son adresse, compare le mot de passe saisi à l’empreinte enregistrée (bcrypt) — à une empreinte factice si l’adresse n’a pas de compte, pour que la réponse prenne le même temps —, puis crée la session — une ligne en base et un jeton signé dans un cookie, que la partie suivante ouvrira en détail. Aucune trace de requête HTTP, aucun cookie lu, aucune procédure : il reçoit deux chaînes et fait son travail.

Une seule trace de tRPC subsiste : l’erreur qu’il lève est une `TRPCError`. Un service tout à fait indépendant lèverait sa propre erreur, que la procédure traduirait. Le projet accepte ce raccourci, parce que ses services ne servent que ses procédures ; il faut seulement savoir qu’il existe.

C’est cette indépendance qui le rend testable, réutilisable, et maintenable.

## 2) La procédure devient simple

<CodeSnippet
  language="ts"
  title="Procédure orchestratrice"
  kind="pattern"
  codeJson='"protectedProcedure.mutation(({ ctx, input }) => {\n  return userService.createUser(ctx, input)\n})"'
/>

---

👉 Elle :

- reçoit l’intention  
- délègue au service approprié  
- ne contient plus de logique lourde  

Cette légèreté n’est pas une perte — c’est un gain. Quand nous lisons un router, nous devons pouvoir embrasser en un coup d’œil toutes les intentions qu’il expose. Si chaque procédure fait trente lignes de logique métier, la carte du système devient illisible.

---

## 3) Les guards : sécuriser le flux

Avant, nous écrivions peut-être ceci :

<CodeSnippet
  language="ts"
  title="Vérification manuelle"
  kind="anti-pattern"
  codeJson='"if (!ctx.session.user) {\n  throw new Error(\u0027Unauthorized\u0027)\n}"'
/>

---

Dans chaque procédure. À chaque fois. Avec le risque d’oublier une fois sur cent.

Avec tRPC :

👉 cette logique est déplacée dans :

- `protectedProcedure` (un middleware attaché globalement)  
- ou un middleware spécialisé (`isAdmin`, réservé aux administrateurs)  

---

<Callout type="info">
La sécurité ne doit pas être répétée dans chaque procédure.

Elle doit être centralisée.
</Callout>

---

## 🔥 Le rôle de protectedProcedure

👉 `protectedProcedure` fait deux choses :

- bloque l’accès si l’utilisateur n’est pas authentifié (jette `UNAUTHORIZED`)  
- garantit que `ctx.sessionClient.user` existe (requalification TypeScript)  

---

💡 Donc dans le service appelé par une `protectedProcedure` :

👉 nous pouvons supposer que l’utilisateur est présent, sans vérifier

TypeScript le garantit. Le middleware `isAuthed` a requalifié `ctx.sessionClient` de `SessionClient | null` vers `AuthenticatedSessionClient`. Quand le service lit `ctx.sessionClient.user.id`, aucun `?` n’est nécessaire. La garantie est portée par les types.

## 🧭 Ce que fait réellement le projet

Il serait faux de dire que chaque procédure du projet délègue à un service. Beaucoup portent leur logique elles-mêmes, et ce n’est pas un défaut en soi. La règle suivie est plus simple : **une logique utilisée à un seul endroit reste dans sa procédure ; dès qu’elle sert à deux endroits, elle descend dans un service**.

Les services vivent à côté du routeur de leur domaine, dans un dossier `services/` (`modules/media/services/syncPageMediaReferences.service.ts`, `modules/auth/services/auth.service.ts`…). Ils reçoivent ce dont ils ont besoin en paramètres — le client Prisma, ou la transaction en cours — plutôt que le contexte tRPC tout entier.

Le routeur des disciplines en donne un exemple récent. La création et la modification d’une discipline vérifiaient chacune, ligne à ligne, que la catégorie, l’instructeur, la famille et l’origine existaient : une cinquantaine de lignes, écrites deux fois, déjà légèrement différentes (la catégorie, non modifiable, n’est vérifiée qu’à la création). Ces vérifications sont désormais un service :

## 💥 Ce que tRPC apporte vraiment

Il faut être précis ici, parce qu’il y a souvent une incompréhension.

👉 tRPC ne remplace pas le backend

tRPC ne contient pas notre logique métier. Il ne gère pas nos règles d’autorisation complexes. Il ne persiste pas nos données.

👉 Il organise :

- le flux (comment une requête traverse le système)  
- le typage (comment les types circulent sans rupture)  
- l’injection du contexte (comment chaque procédure hérite d’un environnement)  

tRPC est une couche d’**orchestration**. Comme un chef d’orchestre, il ne joue pas lui-même les instruments. Il s’assure que chaque musicien entre au bon moment, dans la bonne tonalité.

---

<Callout type="tip">
tRPC est une couche d’orchestration.

Le cœur métier reste dans les services.
</Callout>
