> **Précédemment.** Zod garde l’entrée : une donnée invalide est refusée avant toute logique, et le service travaille sur des données fiables.

Nous avons maintenant un système propre.

Une entrée validée, un contexte fiable, une sécurité centralisée, une logique déléguée.

Mais ce système est encore décrit dans son "happy path".

Et un backend réel ne vit pas uniquement dans le cas favorable.

---

## 🧠 La vraie question

Que se passe-t-il quand quelque chose échoue ?

---

Sans cadre clair, les dérives sont prévisibles.

Des `try/catch` apparaissent partout.  
Des `return { success: false }` remplacent de vraies erreurs.  
Chaque couche formate les messages à sa façon.  
Le client reçoit des réponses incohérentes selon où l’erreur s’est produite.

---

💥 Le flux devient illisible.

Pas parce que ça casse — parce que ça ne casse plus de façon prévisible. Une erreur identifiable est une ressource, pas un problème. Un échec silencieux, ou masqué, ou déformé, est bien pire : il se propage sans être remarqué, jusqu’à provoquer un effet inattendu loin de sa cause.

---

## 🔥 Le principe fondamental

Une erreur doit être :

- **lancée au bon endroit**, par la couche qui sait pourquoi elle échoue  
- **expressive**, avec un code et un message exploitables  
- **propagée sans être déformée**  

---

Et surtout : elle ne doit pas être transformée en pseudo-succès.

---

## 1) Ne pas transformer une erreur en résultat

<CodeSnippet
  language="ts"
  title="Anti-pattern : masquer l'erreur"
  kind="anti-pattern"
  codeJson='"try {\n  const user = await service.createUser(ctx, input)\n  return { success: true, user }\n} catch (e) {\n  return { success: false, message: \"Une erreur est survenue\" }\n}"'
/>

---

En retournant `{ success: false }`, nous perdons :

- la cause réelle de l’erreur  
- le code HTTP approprié  
- la possibilité pour le client de distinguer une erreur métier d’une erreur réseau  

---

👉 Le client ne peut plus réagir intelligemment.  
👉 Il sait juste que "ça a échoué".

Et "ça a échoué" n’est pas une information exploitable. Le client ne peut pas distinguer "l’utilisateur n’a pas les droits" de "le serveur est tombé" de "les données sont invalides". Les trois méritent pourtant des réactions UX très différentes.

---

## 2) Le projet avait ce motif, à un endroit précis

La connexion renvoie un résultat plutôt que de lever une erreur quand le mot de passe est faux : `{ success: false, error: "INVALID_CREDENTIALS" }`. C’est un choix délibéré, et il est juste. Un mauvais mot de passe n’est pas un incident : il fait partie du fonctionnement normal du formulaire, qui choisit le message à afficher selon le code reçu.

Mais la première version allait plus loin. Toute autre erreur — la base injoignable, un bug dans le service — devenait elle aussi un résultat : `{ success: false, error: "LOGIN_FAILED" }`. Le formulaire affichait « Connexion impossible », le serveur ne journalisait rien, et la cause disparaissait. Exactement le contre-exemple ci-dessus, en plus discret.

## 4) Les codes d’erreur tRPC ne sont pas arbitraires

<DocsTable
  title="Codes d’erreur et leur sémantique"
  columnsJson='["Code","HTTP","Signification","Lancé par"]'
  rowsJson='[["BAD_REQUEST","400","Entrée invalide, ou référence inexistante","Zod (automatiquement), la procédure, un service"],["UNAUTHORIZED","401","Aucune session","isAuthed (protectedProcedure), isAdmin"],["FORBIDDEN","403","Session valide, droit insuffisant","isAdmin, une garde d’espace, une règle métier"],["NOT_FOUND","404","L’élément visé n’existe pas (ou n’est pas visible)","la procédure"],["CONFLICT","409","Doublon, ou état incompatible","la procédure, souvent en traduisant P2002"],["INTERNAL_SERVER_ERROR","500","Tout ce qui n’est pas une TRPCError","tRPC lui-même, qui emballe l’erreur imprévue"]]'
/>

---

Chaque couche a ses codes.

Zod lève `BAD_REQUEST` automatiquement si `.input()` échoue.  
`isAuthed` lève `UNAUTHORIZED`.  
`isAdmin` lève `FORBIDDEN`.  
La procédure, ou le service qu’elle appelle, lève `NOT_FOUND`, `CONFLICT` ou `BAD_REQUEST` selon la règle violée.  
Et tout ce que personne n’a levé volontairement devient `INTERNAL_SERVER_ERROR`.

---

👉 Le flux d’erreur suit exactement le flux d’exécution.

Le message accompagne l’erreur jusqu’au client, où le composant peut l’afficher. Les messages des erreurs voulues sont donc rédigés pour l’utilisateur, en français : « Un membre utilise déjà cette adresse e-mail. », « Action réservée aux administrateurs. ».

---

## 🔭 Pour aller plus loin — pourquoi ces codes sont des codes HTTP

Les codes que tRPC utilise (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, etc.) correspondent à des codes HTTP standardisés. Ce n’est pas une coïncidence.

tRPC transporte ses erreurs via HTTP. Quand le serveur lève `TRPCError({ code: "NOT_FOUND" })`, la réponse HTTP est bien un 404. Cela signifie que les outils standards du web — devtools, logs de proxy, outils de monitoring — voient les erreurs comme des codes HTTP conventionnels.

C’est une bonne pratique : s’intégrer aux conventions existantes plutôt que réinventer un vocabulaire propriétaire. Un développeur qui connaît HTTP peut lire un log d’erreur tRPC sans formation supplémentaire.

---

👉 Le code d’erreur est le même que celui de `isAdmin`.  
👉 La cause est différente.

C’est intentionnel.

Le client ne voit pas « qui » a levé l’erreur.  
Il voit « quelle erreur s’est produite », et un message qui l’explique.  
Et c’est tout ce dont il a besoin pour réagir correctement.

## 6) Ce que le navigateur reçoit d’une erreur imprévue

Reste un cas que rien de ce qui précède ne couvre : l’erreur que personne n’a levée volontairement. Une requête Prisma qui échoue, une colonne absente après une migration oubliée, un `undefined` lu par mégarde. tRPC l’emballe dans une `TRPCError` de code `INTERNAL_SERVER_ERROR`, et le message qui part vers le navigateur est… celui de l’erreur d’origine.

Pour une erreur Prisma, ce message contient le nom de la méthode appelée, parfois des noms de tables et de colonnes, parfois un extrait de la requête. C’est ce que le projet envoyait, en production, à n’importe quel visiteur qui provoquait une erreur. Et dans le même temps, côté serveur, rien n’était écrit : la route `/api/trpc` ne journalisait pas les erreurs. Le visiteur en savait plus que l’administrateur.

Pour une erreur interne en production, il remplace le message par une phrase neutre ; les erreurs voulues (`FORBIDDEN`, `CONFLICT`…) gardent le leur, rédigé pour l’utilisateur. En développement, rien ne change : le développeur voit le vrai message, et la pile d’appels, que tRPC n’envoie qu’en dehors de la production.

`onError` est appelé pour chaque erreur, sur le serveur. Seules les erreurs internes sont écrites : un refus est un fonctionnement normal, et journaliser chaque mot de passe erroné noierait les vraies pannes. L’entrée de la procédure n’est jamais écrite, parce qu’elle peut contenir un mot de passe. Les journaux du conteneur (`docker logs`) montrent désormais la procédure en cause et l’erreur complète.

<Callout type="warning">
Un message d’erreur est une donnée qui sort. Les messages écrits pour l’utilisateur (« Ce slug est déjà utilisé ») peuvent sortir ; les messages écrits par une bibliothèque pour un développeur ne le doivent pas. La règle se pose une fois, à l’endroit où toutes les erreurs passent — pas procédure par procédure.
</Callout>

## 🚀 Conclusion

Nous ne masquons plus les erreurs.  
Nous ne les dispersons plus.

---

👉 Chaque couche lance ce qu’elle sait lancer.  
👉 tRPC se charge du reste.

---

La dernière question reste entière.

Le système produit des erreurs propres.  
Mais que renvoie-t-il quand tout se passe bien ?

---

## À suivre

Les erreurs ne sont plus des accidents à étouffer : elles sont levées avec un code, transportées par tRPC, et seules celles écrites pour l’utilisateur sortent telles quelles. Reste le dernier maillon : ce que le backend renvoie quand tout se passe bien.

<Callout type="tip">
**Chapitre suivant : maîtriser la sortie.** Ne jamais renvoyer une ligne complète, `select` et `omit`, le DTO partagé avec le front, et `satisfies`, qui vérifie sans élargir.
</Callout>
