## 🧠 Que renvoyons-nous réellement au client ?

---

Sans réflexion, le réflexe naturel est de faire ceci :

<CodeSnippet
  language="ts"
  title="Retour direct du modèle Prisma (anti-pattern)"
  kind="anti-pattern"
  codeJson='"return ctx.prisma.user.findMany()"'
/>

---

Cela fonctionne.

Mais quelque chose pose un problème silencieux.

Nous exposons directement :

- tous les champs du modèle — y compris `password`  
- des relations parfois non voulues  
- une structure intimement liée à la base  

---

💥 Le client devient dépendant de la structure interne du backend.

Et le jour où Prisma évolue — un champ renommé, une relation ajoutée — le frontend peut casser sans que le backend ait "changé" du point de vue métier.

Plus grave : des données sensibles peuvent fuir. Le hash du mot de passe, des métadonnées d’audit, des identifiants internes — tout ce qui vit dans le modèle Prisma traverse silencieusement la frontière.

Ce n’est pas un risque théorique. La suppression d’un membre (`user.delete`) se terminait ainsi :

<CodeSnippet
  language="ts"
  title="Avant : la ligne complète renvoyée"
  kind="anti-pattern"
  codeJson='"return tx.user.delete({\n  where: { id: input.id },\n});"'
/>

`delete` renvoie la ligne supprimée, et la procédure la renvoyait au navigateur : à chaque suppression, l’empreinte bcrypt du mot de passe du membre partait vers l’écran de l’administrateur, visible dans l’onglet Réseau des outils du navigateur. Aucune page ne l’affichait ; l’API la donnait. L’écran, lui, n’utilisait même pas la réponse.

La correction tient en une ligne : ne demander à Prisma que ce qui doit sortir.

<CodeSnippet
  language="ts"
  title="Après : seul l’identifiant sort"
  kind="pattern"
  codeJson='"return tx.user.delete({\n  where: { id: input.id },\n  select: { id: true },\n});"'
/>

Une empreinte n’est pas un mot de passe, mais elle permet de le chercher hors ligne, sans limite d’essais. Elle n’a rien à faire hors du serveur, même chez un administrateur.

---

## 🔥 Le principe fondamental

Le backend ne doit jamais exposer directement ses modèles internes.

Il doit exposer :

👉 une **forme contrôlée, stable, pensée pour le client**

Pour une donnée exposée largement, `select` est le choix prudent ; `omit` convient à un écran d’administration qui a réellement besoin de presque tout.

---

## 🔭 Pour aller plus loin — le sens du sigle DTO

DTO signifie *Data Transfer Object*. Le terme est ancien — il vient des architectures Java d’entreprise — mais l’idée est intemporelle.

Un DTO est un objet conçu **uniquement pour le transport**. Il ne contient pas de logique. Il ne persiste pas. Il sert d’intermédiaire entre deux couches.

Dans notre cas, le DTO est la forme que prend la donnée quand elle sort du backend vers le frontend. Il est distinct du modèle de base (ce que Prisma manipule) et de la vue (ce que React affiche). Il est la forme du contrat.

Cette distinction porte un nom en architecture : le **pattern Boundary**. La donnée change de forme aux frontières du système, et chaque forme est adaptée à son contexte.

<Callout type="info">
`satisfies` ne ment pas au compilateur.

Il lui demande de vérifier que ce que nous produisons respecte ce que nous avons promis.

C’est la différence entre un cast aveugle et un contrat honnête.
</Callout>

Le projet a vérifié cette différence à ses dépens, au moment même où cette fonction a été écrite. Sa première version annotait le type de retour : `function toUserProfile(…): UserProfile`. Tout compilait côté serveur. Mais deux écrans du front (la page de profil et la fiche d’un membre) ont aussitôt cessé de compiler : `id` y était devenu `string | null`, parce que le contrat `UserProfile`, plus large que la réalité, admet un identifiant nul. L’annotation avait **élargi** le type ; `satisfies` le vérifie sans y toucher, et le front a retrouvé `id: string`.

---

## 🔭 Pour aller plus loin — satisfies vs as vs type annotation

TypeScript offre trois façons différentes de déclarer le type d’une valeur, et `satisfies` est le plus récent (TS 4.9).

- `const x = value as Type` → **cast aveugle**. TypeScript fait confiance, ne vérifie pas. Dangereux.
- `const x: Type = value` → **annotation**. TypeScript vérifie que `value` respecte `Type`, mais perd le type concret de `value` : `x` aura le type `Type`, pas la forme réelle de `value`.
- `const x = value satisfies Type` → **vérification avec préservation**. TypeScript vérifie la conformité, et garde le type concret de `value`.

Dans le cas du DTO, `satisfies` est le bon choix. Nous voulons vérifier que la projection respecte `UserProfile`, mais nous voulons aussi garder le type exact pour l’inférence côté client (tRPC remonte le type concret jusqu’au frontend).

## 🔥 Le vrai bénéfice

Avant :

- le frontend lit directement la structure de la base  
- chaque évolution du schéma Prisma peut casser l’interface  
- des données sensibles peuvent fuir sans que personne le remarque  

---

Après :

- le frontend consomme un contrat stable  
- Prisma peut évoluer sans impacter le client si le DTO reste compatible  
- la sortie est maîtrisée dès la procédure

## 🚀 Conclusion

Nous ne renvoyons plus les modèles internes.

Nous exposons des **contrats stables**, pensés pour le consommateur.

---

Nous avons maintenant un système complet :

- entrée validée (Zod, inline ou partagé)  
- contexte fiable (createTRPCContext)  
- intention claire (procédure)  
- sécurité dans la chaîne (`protectedProcedure`, `isAdmin`) et règles métier dans la procédure  
- logique métier isolée (service)  
- erreurs structurées (TRPCError)  
- sortie maîtrisée (select, DTO, satisfies)  

---

👉 Le flux est désormais cohérent de bout en bout.

Pas seulement dans sa mécanique — dans sa lisibilité.

Chaque couche dit ce qu’elle fait.  
Chaque erreur dit ce qui a échoué.  
Chaque réponse dit exactement ce qu’elle promet.

---

🎯 C’est ce qui transforme un backend fonctionnel en backend **compréhensible**.

---

👉 **Où nous en sommes :** le DTO ferme le flux — la sortie est filtrée, structurée, ancrée à un contrat que le frontend peut consommer sans trembler. Chaque couche du backend a désormais sa propre façon d’être stricte. Reste à prendre du recul et à regarder le système dans son ensemble — parce qu’un backend ne se comprend vraiment qu’une fois que toutes ses couches fonctionnent ensemble.

## Ce que nous venons de construire dans le Mouvement 3

Nous avons durci chaque articulation du flux. Quatre idées en sont ressorties :

- **La sécurité est centralisée, pas dispersée.** `protectedProcedure` et `isAdmin` : les règles d’accès vivent dans des middlewares composables, déclarés dans la chaîne de chaque procédure. Les règles métier qui dépendent de l’entrée vivent dans la procédure, et jamais seulement dans l’interface. Le reste du code peut faire confiance aux types, parce que les vérifications ont déjà eu lieu — et TypeScript requalifie le contexte pour le prouver.
- **Zod est la frontière du backend.** Toute donnée qui entre passe par un schéma explicite, dont la portée dépend de l’usage : local à la procédure, ou hissé dans `packages/contracts` pour être partagé avec le frontend. Entre la requête et la logique métier, il y a toujours ce seuil — et le service peut travailler sans défiance.
- **`TRPCError` est un signal, pas un incident à cacher.** Chaque couche lève ce qu’elle sait lever, avec le bon code, et laisse tRPC transformer ce signal en réponse HTTP cohérente. Le *happy path* et le chemin d’erreur coexistent sans que la lisibilité du code en souffre.
- **Le DTO contrôle ce qui sort.** `select` filtre à la source, le mapping transforme, `satisfies` relie le service à un contrat vérifiable. La sortie n’est plus le reflet brut du modèle Prisma — c’est une forme choisie, stable, et partageable.
