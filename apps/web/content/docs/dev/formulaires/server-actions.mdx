> **Précédemment.** `useActionState` relie une fonction métier à un `<form>` réel : le navigateur soumet, React orchestre, l’interface lit un état. Mais la fonction métier appelait encore `fetch` : le serveur restait « derrière une URL ».

## 5 — Le changement de paradigme : du Pages Router à l’App Router

C’est ici que l’App Router change la donne. Dans un modèle React classique, et dans Next.js avec le **Pages Router** (l’organisation d’origine de Next.js, où chaque fichier du dossier `pages/` était une page, et où le serveur s’atteignait par des routes d’API écrites à part, `pages/api/…`), le client reste responsable de l’orchestration :

- il déclenche l’évènement ;
- il construit la requête ;
- il appelle une API (`fetch`) ;
- il interprète la réponse.

Le serveur est toujours « derrière une URL ».

### Le problème réel

Même dans un monorepo, où frontend et backend sont proches et partagent du code, le pont reste HTTP : le `<form>` ne peut pas appeler directement une fonction serveur, il doit passer par une route d’API.

### Le vrai changement de l’App Router

Avec l’App Router, le formulaire n’appelle plus une URL : il appelle une **fonction serveur**. La chaîne devient `<form>` → `formAction` → server action → Prisma, sans `fetch` écrit à la main, sans route intermédiaire obligatoire, sans duplication entre client et serveur.

Concrètement, avant :

1. le `<form>` déclenche `onSubmit` ;
2. JavaScript fait un `fetch` ;
3. le `fetch` atteint une route d’API ;
4. la route exécute la logique métier.

Maintenant :

1. le formulaire porte `<form action={formAction}>` ;
2. React appelle la server action ;
3. la server action exécute la logique métier.

Le pont est intégré au framework.

`useActionState` change de statut au passage. Avec le Pages Router, il organisait mieux le code, mais reposait toujours sur `fetch`. Avec l’App Router, il devient un vrai pont, où chacun a son étape : le DOM déclenche, React orchestre, le serveur exécute, et l’interface lit l’état de retour. La répartition des rôles est claire :

- React Hook Form : l’expérience (les champs, la validation locale) ;
- la server action : la logique métier et la validation réelle ;
- `useActionState` : l’orchestration du cycle ;
- Prisma : la source de vérité.

Rien de cela n’est possible avec le Pages Router : sans server actions, pas d’appel direct au serveur, `fetch` est obligatoire et le client reste le coordinateur principal. L’App Router ne nous ramène pas au web pur : il fait mieux. Le `<form>` redevient central, le serveur redevient accessible directement, et React n’intercepte plus tout : il orchestre.

<Callout type="info">
Le vrai changement ne vient pas de `useActionState` seul, mais du couple server actions et App Router. Ensemble, ils suppriment le `fetch` écrit à la main, reconnectent le formulaire au serveur, et nous laissent construire avec le web plutôt que de le contourner.
</Callout>

Prenons-la dans l'ordre.

**`'use server'`, première ligne.** C'est elle qui fait de ce fichier un module d'actions serveur. Le composant client importe `saveCategoryFormAction` comme une fonction ordinaire ; au build, Next.js remplace cet import par une **référence** : un identifiant, et le moyen de l'appeler. Le code de l'action ne part jamais dans le navigateur, et pas davantage `prisma` qu'elle importe.

**La signature `(prevState, formData)`.** C'est le contrat de `useActionState` vu au chapitre précédent : l'état précédent, puis le `FormData` brut que le navigateur a construit à partir des champs `name`. La valeur renvoyée devient le nouvel état du composant.

**Le contrôle des droits, avant tout le reste.** Nous y revenons juste après : c'est la ligne la plus importante du fichier.

**La validation par le schéma.** Le `FormData` est converti en objet, puis passé au **même** schéma que celui du résolveur côté client, mais complet cette fois (`id` compris). Le `?? undefined` n'est pas un détail : nous verrons au chapitre 6 ce qu'il évite.

**Les règles que seul le serveur connaît.** La catégorie se choisit dans une liste fixe (`course`, `seminar`, `event`), et ne change plus une fois choisie : le formulaire ne la propose plus, mais une requête fabriquée le pourrait, alors l'action le refuse. L'unicité de la clé et du libellé ne peut pas non plus être vérifiée dans le navigateur : il faudrait connaître toutes les catégories existantes. C'est le serveur, avec Prisma, qui la vérifie, en s'excluant lui-même en édition.

**L'écriture**, création ou mise à jour selon la présence d'`id`, dans une transaction. À la création, la catégorie reçoit son **segment de stockage** (le nom de son dossier, `courses` pour « Cours »), figé une fois pour toutes : la renommer ne change ensuite que le libellé que le finder affiche, jamais le dossier où vivent ses fichiers. L'état de retour donne l'identifiant de la catégorie : le composant s'en sert pour rediriger vers sa fiche.

<Promesse vers="dev/domaine/un-modele-qui-s-ouvre" section="Le nom affiché n’est pas une identité">
Un libellé est fait pour être lu et renommé ; un dossier de fichiers doit rester où il est. Dériver l’un de l’autre déplacerait les fichiers à chaque renommage : d’où un segment calculé une fois, à la création.
</Promesse>

**Les erreurs.** La vérification préalable de l'unicité donne un message clair dans le cas courant ; si deux enregistrements simultanés la passent tous les deux, c'est la contrainte de la base qui tranche (`P2002`), avec le même message. Toute autre erreur est **journalisée** avant de renvoyer un message générique : un `catch` muet cacherait une base injoignable derrière « Enregistrement impossible ».

## Une server action est une porte ouverte

C’est la conséquence la moins visible du modèle, et la plus dangereuse à oublier. Une server action n’est pas une fonction privée de la page qui l’utilise : Next.js lui attribue un identifiant, et l’expose comme un **point d’accès HTTP**. N’importe quel navigateur peut l’appeler en `POST`, qu’il ait affiché le formulaire ou non ; les identifiants figurent dans le JavaScript envoyé au navigateur, il suffit de les lire. Masquer le formulaire aux non-administrateurs ne protège donc rien.

Les actions d’administration vérifient les droits **à leur première ligne**, avant même de lire le formulaire. La vérification est partagée :

L’action du profil suit la même règle avec une exigence différente : il suffit d’être connecté, mais elle ne modifie **que** le compte de l’appelant, dont l’identifiant vient de la session, jamais du formulaire.

Si l'identifiant venait d'un champ caché, n'importe quel membre connecté pourrait le remplacer par celui d'un autre et modifier son profil.

<Callout type="warning">
Une procédure tRPC déclare ses droits par son type (`protectedProcedure`, `.use(isAdmin)`) : l'oublier est visible dans le code. Une server action n'a pas ce garde-fou : **rien** ne la protège si elle ne vérifie pas elle-même. Toute nouvelle action commence par sa vérification de droits.
</Callout>

## Le retour de l’action : un état, pas une exception

Une server action ne lève pas d’erreur pour un refus attendu (catégorie déjà existante, champ invalide, droits insuffisants) : elle **renvoie** un état que le composant affiche. Une exception, elle, interromprait le rendu et finirait dans la page d’erreur de Next.js, sans message utile pour l’utilisateur.

Trois états possibles, que TypeScript distingue par `status` : rien n'a encore été envoyé, l'envoi a réussi, ou il a échoué. En cas d'échec, `fieldErrors` peut associer un message à chaque champ : le formulaire de profil s'en sert pour afficher, sous chaque champ, l'erreur trouvée par le serveur (plus loin, chapitre 6). Les formulaires plus anciens (catégorie, origine, famille, galerie) utilisent une forme plus simple, `{ success, error }`, comme `SaveCategoryFormState` plus haut.

Un piège propre aux fichiers `"use server"` : ils ne peuvent exporter **que des fonctions asynchrones**, puisque chaque export devient un point d'accès. Une constante, même un simple état initial, y provoque une erreur au premier envoi. L'état initial du formulaire de profil vit donc dans un fichier de types à part, sans la directive :

## À suivre

L’App Router a redonné au serveur son statut : il n’est plus derrière une URL à construire, mais directement au bout du `<form>`. Avec `useActionState`, le `fetch` écrit à la main disparaît, et le formulaire retrouve le modèle natif du web, en version augmentée. Le modèle tient sur le papier, et sur un vrai formulaire du projet. Reste à le confronter à ce qui ne dépend pas de nous : une API externe, un backend séparé, et nos propres raccourcis.

<Callout type="tip">
**Chapitre suivant : le modèle hybride face au réel.** Quand `fetch` redevient nécessaire, ce qu’un contrat partagé garantit (et ce qu’il ne garantit pas), la hiérarchie de vérité, et un contre-exemple tiré du projet.
</Callout>
