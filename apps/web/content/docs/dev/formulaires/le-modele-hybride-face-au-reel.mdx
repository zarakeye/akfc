> **Précédemment.** Avec l’App Router, le formulaire appelle directement une fonction serveur. Une action du projet vérifie ses droits, valide avec le schéma partagé, écrit avec Prisma et renvoie un état. Le modèle tient, dans le contexte qui l’a vu naître.

## 6 — RHF, useActionState et server actions : renouer avec le modèle d’origine du web

Jusqu’ici, nous avons remonté le fil de l’histoire :

- le modèle HTML d’origine ;
- la rupture introduite par React ;
- la tentative de réparation côté client, avec React Hook Form ;
- puis l’apparition de `useActionState`, et des server actions.

Toutes les pièces sont là. Il reste à les voir fonctionner **ensemble**, dans un formulaire réel du projet.

Et surtout, le serveur n’est plus distant. Au premier chapitre, nous l’avons vu s’éloigner derrière une URL, souvent sur un autre domaine, avec son cortège de `fetch`, de JSON et de types écrits deux fois. Avec l’App Router, il revient dans le même système que l’interface : le formulaire appelle une fonction, les types sont les mêmes des deux côtés, et un seul schéma décrit la règle.

👉 le serveur n’est plus une destination lointaine atteinte par `fetch`  
👉 il redevient un acteur direct du cycle du formulaire

À partir de là, nous ne cherchons plus seulement à rendre le client plus confortable. Nous réorganisons le système complet :

- le client garde l’expérience utilisateur ;
- le serveur reprend la logique métier ;
- `useActionState` devient le pont entre les deux.

Autrement dit, nous ne collons plus un formulaire React sur une API distante : nous reconnectons le formulaire à une logique serveur qui vit déjà dans le même système.

<Callout type="info">
C’est ici que le modèle hybride atteint sa forme mature :

- React Hook Form garde la responsabilité de l’expérience utilisateur ;
- la server action reprend la logique métier ;
- `useActionState` orchestre le cycle entre les deux.

👉 le client n’imite plus le serveur  
👉 il coopère avec lui
</Callout>

### 6.1 — Le contrat : définir la forme de la vérité

Avant même de parler de server action ou de composant, il faut comprendre une chose essentielle :

👉 un formulaire mature ne commence pas par son JSX  
👉 il commence par son **contrat**

Dans le modèle hybride, trois mondes doivent s’aligner :

- le client (React Hook Form) manipule des valeurs typées ;
- le serveur (la server action) traite un `FormData` brut ;
- le retour renvoie un état structuré vers l’interface.

S’ils ne parlent pas la même langue, les erreurs deviennent difficiles à ranger sous le bon champ, les comportements imprévisibles, et l’expérience se dégrade. Le fichier `updateMeForm.types.ts`, celui du formulaire « Mon profil », fixe cette langue commune :

- côté client, par le résolveur de React Hook Form, mais en partie seulement : `.pick({ key: true, type: true })` ne garde que les deux champs saisis, car `id` vient d’un champ caché que l’utilisateur ne saisit pas ;

#### Sans contrat, avec contrat


Sans contrat : des types flous, des erreurs difficiles à tracer, des comportements imprévisibles. Avec contrat : une langue commune, des erreurs maîtrisées, un système fiable.

### 6.2 — La server action concentre la vérité métier

À ce stade, une bascule importante se produit. Jusqu’ici, le client portait encore une partie de la logique du formulaire ; avec la server action, cette logique est replacée au bon endroit.

👉 le serveur ne se contente plus de répondre  
👉 il devient le point de décision du système

Nous avons lu une action ligne par ligne au chapitre précédent, celle de la catégorie. Elle vérifie les droits, valide avec le schéma partagé, applique les règles que seul le serveur connaît, écrit avec Prisma et renvoie un état. La logique métier n’est plus atteinte par `fetch` : elle est exécutée là où elle doit vivre.

👉 ce n’est pas une étape technique de plus  
👉 c’est un changement d’autorité

#### Quand le formulaire n’est pas la seule entrée

Le projet ajoute une contrainte que le modèle doit absorber : une application mobile est prévue. Elle n’aura pas de server actions ; elle appellera les procédures tRPC. Une même opération, changer son mot de passe par exemple, a donc **deux entrées** : la procédure `auth.changePassword` et la server action du formulaire de la page profil.

Écrire la logique deux fois, ce serait recréer la duplication que ce chapitre combat. Elle descend donc d’un étage, dans un **service** : une fonction du backend, `changePassword`, que les deux entrées appellent.

Mais ni l’une ni l’autre ne contient de règle : vérifier le mot de passe actuel, refuser un mot de passe identique, fermer les autres sessions, tout cela est dans le service. La server action reste le point d’entrée du formulaire ; elle n’est plus le seul lieu de la vérité, elle en est la porte.

### 6.3 — Le composant client se recentre sur l’interface

Une fois la logique métier déplacée côté serveur, le rôle du composant client change profondément. Il ne disparaît pas, mais il cesse de porter des responsabilités qui ne lui appartenaient pas.

👉 il ne décide plus  
👉 il orchestre

Il garde :

- la gestion locale des champs ;
- l’hydratation du formulaire ;
- l’affichage des erreurs ;
- la réaction au cycle de l’action (en cours, succès, erreur).

### 6.4 — Le nouveau flux complet

À ce stade, le fonctionnement du formulaire n’a plus grand-chose à voir avec le modèle React classique. Ce qui change n’est pas seulement la syntaxe : c’est la manière dont les responsabilités sont distribuées.

**Côté client**

1. l’utilisateur modifie les champs ;
2. React Hook Form gère les valeurs, et valide avec le schéma partagé ;
3. le `<form>` déclenche `formAction`.

**Le pont**

4. `formAction` appelle la server action.

**Côté serveur**

5. lecture du `FormData` ;
6. vérification des droits ;
7. normalisation et validation ;
8. logique métier, dans l’action ou dans son service ;
9. persistance.

**Le retour**

10. un état structuré ;
11. la mise à jour de l’interface ;
12. la resynchronisation, s’il le faut.

Ce flux est plus long à lire que l’ancien modèle, mais beaucoup plus simple à comprendre : chaque étape a une responsabilité claire.

- le client guide l’utilisateur ;
- le serveur décide ;
- le formulaire relie les deux.

/>

<Callout type="info">
Dans ce modèle :

- le formulaire redevient un point de passage naturel ;
- le serveur redevient le lieu de décision ;
- le client redevient une interface.

👉 chacun retrouve son rôle
</Callout>

### 6.5 — Pourquoi ce modèle est supérieur

Pour le mesurer, revenons à ce que faisait le client auparavant. Dans un modèle React classique, le composant devait :

- gérer les champs ;
- valider ;
- construire une requête ;
- appeler `fetch` ;
- gérer la réponse HTTP ;
- interpréter les erreurs ;
- les ranger dans l’interface ;
- maintenir les états de soumission.

👉 il imitait un backend, sans en avoir les garanties

Avec le modèle hybride, cette charge est répartie :

- React Hook Form garde l’expérience utilisateur ;
- la server action reprend la logique métier, ou la confie à un service quand plusieurs entrées la partagent ;
- `useActionState` orchestre le cycle.

Le résultat n’est pas seulement plus confortable : il est plus juste. Le client ne prend plus de décisions métier, le serveur n’est plus contourné, le formulaire redevient un passage structuré. Ce n’est pas une amélioration de plus : c’est un réalignement du système avec le web lui-même.

<Callout type="info">
Nous n’inventons pas un nouveau modèle. Nous en retrouvons un, avec de meilleurs outils.
</Callout>

### 6.6 — Le modèle face au réel

Nous avons construit quelque chose de solide. Mais, pour être honnêtes, il reste une zone floue : nous avons présenté un modèle sans l’avoir confronté au réel. Nous pourrions dire « voilà le bon modèle » ; ce serait mentir un peu, car ce modèle **n’est pas universel**.

#### Le cas réel : quand notre architecture nous contraint

Jusqu’ici, nous avons travaillé dans un contexte particulier :

- un monorepo ;
- un backend accessible ;
- des server actions possibles.

Nous pouvions donc mettre la logique métier côté serveur, accéder directement à Prisma, et n’écrire aucun `fetch`. Mais si nous n’avions **pas** ce luxe ?

Dans beaucoup de projets, le backend est externe, l’API est publique, et le frontend est découplé : une API REST fournie par un service tiers, ou un backend maintenu par une autre équipe. Nous ne pouvons alors **pas** appeler une server action interne : nous **devons** passer par HTTP. `fetch` redevient normal, et nécessaire.

<Callout type="info">
Le problème n’a jamais été `fetch`. Le problème commence quand le client devient une autorité métier.
</Callout>

#### Le coût de l’existant

Une autre contrainte, la plus fréquente, ne vient pas de la technique mais de l’histoire du projet. Un front et un back déjà séparés, deux équipes, une API dont d’autres applications dépendent : atteindre ce modèle demande alors un changement d’approche radical. Rapprocher les deux bases de code, revoir les déploiements, réécrire les formulaires un à un : c’est coûteux, et ce n’est pas toujours possible, ni même raisonnable.

Les bénéfices sont pourtant réels, et flagrants une fois le pas franchi. Le projet l’a vécu en convertissant ses formulaires : chaque logique descendue dans un service, chaque règle écrite une seule fois, des messages identiques dans le navigateur et sur le serveur. Même ici, la conversion n’est pas totale : les éditeurs riches et le dépôt de fichiers restent sur tRPC, pour des raisons que le chapitre 7 détaille.

👉 le modèle hybride est une cible, pas un prérequis  
👉 on s’en rapproche par étapes, en sachant ce que chaque étape coûte et rapporte

#### Mauvais modèle ou modèle contraint

Il faut être précis ici : tout n’est pas « mauvais » ou « bon ».

Le **mauvais modèle**, celui que nous avons tous écrit au début, est un client qui :

- valide des règles métier ;
- décide de ce qui est correct ou non ;
- reconstruit la vérité ;
- interprète lui-même les erreurs du serveur.

Autrement dit, un backend déguisé en frontend.

Le **modèle contraint**, propre, accepte la contrainte d’une API publique et répartit les rôles :

- le client envoie les données (`fetch`) et affiche le résultat ;
- le serveur valide, décide et enregistre.

Le client reste un **consommateur**. Le problème n’est pas l’outil, c’est la répartition des responsabilités.

### 6.7 — Réduire la casse (ce que nous ferions dans la vraie vie)

Quand les server actions sont impossibles, nous ne cherchons pas la perfection, mais à **limiter la divergence** entre le client et le serveur. Trois moyens existent.

#### 1 — Partager un contrat

<CodeSnippet
  language="ts"
  title="Contrat partagé (Zod + TS)"
  filename="@acme/contracts/user.ts"
  codeJson='"import { z } from \"zod\"\n\nexport const LoginSchema = z.object({\n  email: z.string().email(),\n  password: z.string().min(8),\n})\n\nexport type LoginInput = z.infer<typeof LoginSchema>"'
/>

Frontend et backend parlent alors la même langue. Mais soyons lucides : ce contrat n’exécute rien, et ne valide rien côté serveur. C’est une **projection** de la règle, pas la règle appliquée.

#### Dans le projet : `packages/contracts`

Ce contrat partagé, le projet l’a, même s’il utilise des server actions : c’est le schéma de la catégorie vu en 6.1. La remarque précédente vaut pour lui aussi : ce fichier n’exécute rien, et n’empêche rien tant que l’action ne l’appelle pas. Sa seule garantie est que, **quand** les deux côtés l’utilisent, ils appliquent la même règle.

#### 2 — Générer les types avec OpenAPI

**OpenAPI** est un format standard qui décrit une API REST (ses adresses, ce qu’elles reçoivent, ce qu’elles renvoient) dans un fichier. Des outils en tirent automatiquement des types et un client pour le navigateur :

<CodeSnippet
  language="yaml"
  title="Extrait OpenAPI"
  filename="openapi.yaml"
  codeJson='"paths:\n  /login:\n    post:\n      requestBody:\n        content:\n          application/json:\n            schema:\n              $ref: \"#/components/schemas/LoginInput\""'
/>

Le transport est automatisé et sécurisé ; mais, encore une fois, cela ne remplace pas la logique du serveur.

#### 3 — Utiliser un SDK du backend

Un **SDK** (*Software Development Kit*) est ici un petit paquet, publié par l’équipe du backend, qui offre des fonctions toutes prêtes pour appeler son API (un client npm, des fonctions typées, le `fetch` caché à l’intérieur), au lieu d’écrire chaque `fetch` à la main. La **DX** (*developer experience*), le confort du développeur qui l’utilise, s’en trouve meilleure ; la contrainte fondamentale reste la même.

### 6.8 — Hiérarchie de vérité (le vrai déclic)

Selon le contexte, la vérité ne vit pas au même endroit.

Avec des **server actions** (le cas idéal) :

- Prisma est la vérité ;
- la server action est le point d’entrée ;
- le client est l’interface.

Avec une **API publique** (le cas contraint) :

- le backend est la vérité ;
- le contrat partagé en est une projection ;
- le client est un consommateur.

Avec **deux entrées** (le cas du projet, server actions pour le site et tRPC pour l’application mobile) :

- Prisma est la vérité ;
- le service porte la logique métier ;
- la server action et la procédure sont deux portes vers lui ;
- chaque client est une interface.

<Callout type="info">
Le client ne doit jamais être la source de vérité métier : il consomme une vérité définie ailleurs.
</Callout>

Et une troisième fois dans `packages/contracts`, dans un schéma `authSchema` prévu pour être partagé… que personne n’importait. La procédure de réinitialisation, la page « Mot de passe oublié » et la page du nouveau mot de passe avaient chacune leur copie, de la règle des 12 caractères ou de celle de l’adresse e-mail.

Le schéma partagé existait, il était juste, et il ne servait à rien : c’est la remarque de la section 6.7 (« ce contrat n’exécute rien ») prise sur le fait. Le jour où la longueur minimale serait passée à 14 caractères, il aurait fallu penser à six fichiers. Un seul oubli, et deux scénarios étaient possibles :

- le formulaire exige 12, la procédure 14 : l’utilisateur voit un formulaire « valide » refusé par le serveur, avec un message qu’il n’a jamais vu ;
- le formulaire exige 14, la procédure 12 : rien ne casse, mais la règle affichée n’est plus celle du système.

Chaque copie avait été écrite de bonne foi, à un moment différent. C’est ainsi qu’une duplication s’installe : jamais d’un coup.

## Ce que nous gardons

Ce n’est ni React, ni `fetch` qui posent problème : le vrai problème, c’est **où vit la vérité**.

Quand nous le pouvons (server actions, logique côté serveur, modèle centralisé), nous le faisons. Quand nous ne le pouvons pas (API publique, backend séparé), nous structurons : un contrat partagé, une validation côté serveur, un client passif.

<Callout type="info">
Un bon système ne dépend pas des outils, mais de la bonne répartition des responsabilités. La question n’est pas « comment envoyer un formulaire », mais **qui a le droit de décider**.
</Callout>

## Ce que nous venons de construire dans le Mouvement 2

Nous avons réparé la fracture. Trois idées en sont ressorties :

- **`useActionState` est un pont, pas une destination.** Il ne remplace pas le contrat natif du web, il l’augmente — en permettant à une fonction métier de se brancher à un `<form>` sans reconstruire à la main tout ce que le navigateur faisait déjà. C’est le chaînon qui manquait pour reconnecter React au modèle ancien sans renoncer à ses forces.
- **App Router change la nature du serveur dans le code.** Les Server Actions transforment le serveur d’une « URL à appeler » en une fonction directement référencée depuis le formulaire. Le fetch manuel disparaît, le formulaire retrouve sa cible naturelle, et la plomberie réseau sort du code applicatif.
- **Le modèle hybride redistribue les responsabilités clairement.** RHF tient l’UX et la validation instantanée ; `useActionState` tient la traduction vers le `<form>` ; la Server Action tient la logique métier et revalide tout ce qui vient du client. Chacun fait ce qu’il fait le mieux — et surtout, plus rien ne fait ce qu’il ne devrait pas.

Le Mouvement 3 va maintenant regarder ce modèle sous un autre angle : celui de ses limites. Parce qu’un pattern vraiment mature ne se juge pas sur ce qu’il permet de faire, mais sur ce qu’il nous interdit de faire mal — et sur ce qu’il ne peut pas du tout faire.

## À suivre

Le modèle hybride a résisté : chaque pièce est à sa place, et il a supporté la confrontation aux contraintes du réel. Mais un modèle qui fonctionne toujours n’apprend rien sur ses propres limites. C’est justement le moment de changer de posture : un modèle qui donne confiance cache ses pièges les plus dangereux là où il semble le plus solide.

<Callout type="tip">
**Chapitre suivant : les pièges du modèle hybride.** La fausse sécurité du client, `useActionState` détourné, le `FormData` qui ment, l’interface qui affiche une vérité périmée, et la duplication qu’il faut garder.
</Callout>
