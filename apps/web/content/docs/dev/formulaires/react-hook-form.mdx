## 3 — Remettre de l’ordre : l’essor des bibliothèques de formulaires

Face à cette complexité, une évidence s’est imposée : gérer un formulaire entièrement à la main devient vite ingérable. Chaque implémentation répétait les mêmes gestes : suivre les champs, synchroniser les valeurs, valider, afficher les erreurs, contrôler l’envoi. Des bibliothèques sont apparues pour simplifier ce travail, et React Hook Form s’est imposée parmi elles.

### Le rôle réel de React Hook Form

Son objectif : redonner de la structure aux formulaires côté client. Les champs sont enregistrés automatiquement, leurs valeurs suivies sans nouveaux calculs d’affichage inutiles, la validation peut être centralisée (souvent avec Zod), et les erreurs arrivent sous une forme structurée. Nous ne manipulons plus chaque champ : nous en déléguons la gestion à un système pensé pour cela. React Hook Form ne simplifie pas seulement le code, il structure le **comportement du formulaire côté client**.

### Dans le projet : React Hook Form et un résolveur Zod

Le tableau de bord du club s’appuie sur React Hook Form dans la plupart de ses formulaires simples. Celui d’une catégorie (choisie parmi « Cours », « Stage », « Évènement », avec son libellé) en est le plus petit exemple :

Trois réglages, trois décisions :

- `resolver: zodResolver(...)` branche un **schéma Zod** sur React Hook Form. Les règles ne sont plus écrites champ par champ (`register("email", { required: "Email requis" })`), mais dans un schéma, une seule fois ;
- ce schéma, `saveCategoryFormSchema`, n’est pas défini dans le composant : il est importé de `packages/contracts`, le paquet que partagent le navigateur et le serveur. Nous y reviendrons au chapitre 5 ;
- `mode: "onBlur"` vérifie un champ quand l’utilisateur le quitte, plutôt qu’à chaque frappe : l’erreur apparaît au bon moment, sans clignoter pendant la saisie.

C’est React Hook Form utilisé à son meilleur. Et pourtant, tout ce qui suit s’applique ici aussi : ce résolveur ne protège rien. Il filtre ce que l’utilisateur honnête tape dans un navigateur ordinaire ; il ne voit pas le reste.

## Le problème fondamental reste entier

C’est ici que beaucoup de développeurs se trompent : même avec React Hook Form, le modèle fondamental ne change pas. Le client reste responsable de la validation locale, de la construction de la requête, de l’appel réseau (`fetch`) et de la gestion des réponses du serveur. React Hook Form améliore l’expérience ; il ne répare pas l’architecture.

### Le piège : une illusion de sécurité

Validation propre, erreurs bien gérées, code structuré : React Hook Form donne une impression de solidité. Mais cette solidité est locale. Elle ne garantit **rien** côté serveur, ni vis-à-vis du modèle Prisma, la vraie source de vérité du projet. Avec React Hook Form seul, les types, les validations et les structures peuvent encore évoluer chacun de son côté : le système reste potentiellement incohérent.

<Callout type="warning">
React Hook Form structure le client, mais ne garantit pas la cohérence avec le serveur : le modèle Prisma n’y est pas impliqué, la validation doit être refaite côté serveur, et les règles métier y restent. Il améliore l’expérience, sans restaurer le contrat du système.
</Callout>

### Le bon positionnement

Il faut donc remettre React Hook Form à sa place : ce n’est pas une solution complète, mais une **couche d’expérience côté client**. Son rôle est de capturer les saisies, de les organiser et d’améliorer l’expérience ; il ne décide pas, ne valide pas réellement, et ne garantit rien. Le serveur reste la source de vérité, et ce serveur s’appuie sur Prisma.

<Callout type="info">
React Hook Form est un excellent outil, à condition de ne pas lui donner un rôle qu’il n’a pas : il gère l’expérience, le serveur applique les règles métier, Prisma définit la structure réelle des données. Chaque couche a sa responsabilité.
</Callout>

## Ce que nous venons de construire dans le Mouvement 1

Nous avons fait un détour historique, et trois idées en sont ressorties :

- **Le contrat natif n’était pas naïf, il était juste.** Un `<form action>` et une méthode suffisaient à faire parler le navigateur et le serveur dans une langue commune, où chacun tenait son rôle. Nous avons perdu cette clarté, pas parce qu’elle était fausse, mais parce qu’elle ne répondait plus aux besoins d’expérience utilisateur que React allait permettre.
- **React a gagné en flexibilité, mais il a fracturé l’architecture.** En interceptant le submit, il s’est rendu responsable de tout ce que le navigateur faisait silencieusement — transport, validation, orchestration — sans toujours mesurer ce qu’il prenait en charge. Le formulaire n’est plus un mécanisme, c’est devenu un pattern fragile.
- **Les form libraries ont soigné le symptôme, pas la cause.** RHF a remis de l’ordre dans le chaos local du client, mais la fracture avec le serveur est restée entière. Nous avons gagné en confort ce que nous continuions de perdre en cohérence.

Le Mouvement 2 va maintenant reconstruire le pont — en passant par `useActionState`, puis par App Router et les Server Actions, puis par un modèle hybride où chaque couche retrouve enfin sa place.

## À suivre

React Hook Form a fait un travail honnête côté client : champs, validation locale, erreurs. Le confort est revenu ; la cohérence, non : le serveur reste contourné, et la validation métier reste à refaire ailleurs. Il manque un pont qui rebranche une fonction métier sur un vrai `<form>`, sans que nous jouions nous-mêmes le rôle du navigateur.
