## 3 — Remettre de l’ordre : l’essor des bibliothèques de formulaires

Face à cette complexité croissante, une évidence s’est imposée :

👉 gérer un formulaire entièrement à la main devient vite ingérable.

Chaque implémentation répétait les mêmes patterns :

- gestion des inputs  
- synchronisation des valeurs  
- validation  
- affichage des erreurs  
- contrôle du submit  

Très vite, des bibliothèques sont apparues pour simplifier ce travail.

Parmi elles, React Hook Form s’est imposée comme une solution particulièrement efficace.

---

### 🧩 Le rôle réel de React Hook Form

Son objectif est clair :

👉 redonner de la structure à la gestion des formulaires côté client

Avec React Hook Form, une grande partie de la mécanique est abstraite :

- les champs sont enregistrés automatiquement  
- les valeurs sont suivies sans re-render excessif  
- la validation peut être centralisée (souvent avec Zod)  
- les erreurs sont gérées de manière structurée  

Nous ne manipulons plus directement chaque input.  
Nous déléguons leur gestion à un système pensé pour ça.

👉 RHF ne simplifie pas seulement le code : il structure le **comportement du formulaire côté client**

Là où un formulaire React « vanilla » (écrit à la main, sans bibliothèque) devient rapidement verbeux et fragile, React Hook Form apporte :

- moins de boilerplate  
- moins de bugs liés aux états  
- meilleure performance  
- structure plus claire  

👉 côté développeur, c’est un énorme gain

### 🔎 Dans le projet : React Hook Form et un résolveur Zod

Le tableau de bord du club s'appuie sur React Hook Form dans la plupart de ses formulaires simples. Celui d'une catégorie (choisie parmi « Cours », « Stage », « Évènement », avec son libellé) en est le plus petit exemple :

Trois réglages, trois décisions :

- `resolver: zodResolver(...)` branche un **schéma Zod** sur React Hook Form. Les règles ne sont plus écrites champ par champ (`register("email", { required: "Email requis" })`), mais dans un schéma, une seule fois ;
- ce schéma, `saveCategoryFormSchema`, n'est pas défini dans le composant : il est importé de `packages/contracts`, le paquet que partagent le navigateur et le serveur. Nous y reviendrons au chapitre 5 ;
- `mode: "onSubmit"` et `reValidateMode: "onChange"` : les erreurs apparaissent au premier envoi, puis s'effacent au fil de la frappe, dès que la saisie est corrigée. React Hook Form sait qu'un envoi a eu lieu parce que c'est lui qui l'a conduit, par son `handleSubmit` : nous le verrons avec `useActionState`.

Ce dernier réglage a une histoire. Le formulaire vérifiait d'abord un champ quand l'utilisateur le quittait (`mode: "onBlur"`) : l'erreur semblait arriver au bon moment, sans clignoter pendant la saisie. Jusqu'à ce qu'un test le prenne en défaut, sur le formulaire du nouveau mot de passe. Corriger un champ signalé, puis cliquer aussitôt sur le bouton d'envoi : le clic fait d'abord quitter le champ, le message disparaît, le bouton remonte sous le pointeur… et le clic tombe à côté. Rien ne part. Selon la hauteur du message et la place du bouton, le clic tombe parfois encore dessus, parfois non : c'est le pire des défauts, celui qu'on ne reproduit pas à chaque fois. Tous les formulaires du projet ont donc changé de réglage. Le confort d'un réglage se juge aussi à l'usage réel, souris en main.

C'est React Hook Form utilisé à son meilleur. Et pourtant, tout ce que la suite de cette section décrit s'applique ici aussi : ce résolveur ne protège rien. Il filtre ce que l'utilisateur honnête tape dans un navigateur ordinaire. Il ne voit pas le reste.

### ⚠️ Mais le problème fondamental reste entier

Et c’est ici que beaucoup de développeurs se trompent.

Il faut être lucide. Même avec React Hook Form :

👉 le modèle fondamental **ne change pas**. Nous sommes toujours dans un monde où le client doit tout gérer.

Le client reste responsable de :

- la validation côté client  
- la construction de la requête  
- l’appel réseau (`fetch`)  
- la gestion des réponses serveur  

Autrement dit :

👉 RHF améliore l’expérience  
👉 mais ne répare pas l’architecture

👉 *React Hook Form ne répare pas la rupture introduite par React. Il la rend simplement plus confortable.*

<Callout type="info">
React Hook Form améliore fortement l’expérience côté client :

- moins de code pour gérer les inputs
- validation plus simple à organiser
- meilleures performances (moins de re-renders)

Mais :

- le client reste responsable du flux complet
- le contrat natif du `<form>` n’est pas restauré
- la logique métier reste découplée du serveur

👉 RHF simplifie l’implémentation…  
👉 mais ne change pas le modèle.
</Callout>

---

### 🧨 Le piège : une illusion de sécurité

RHF donne une impression de solidité :

- validation propre  
- erreurs bien gérées  
- code structuré  

Mais cette solidité est locale.

👉 Elle ne garantit **rien** côté serveur

👉 Elle ne garantit **rien** vis-à-vis du modèle Prisma

Dans notre projet :

👉 la source de vérité est le `schema.prisma`

Mais avec RHF seul :

- les types peuvent diverger  
- les validations peuvent différer  
- les structures peuvent évoluer indépendamment  

👉 Nous restons dans un système potentiellement incohérent

<Callout type="warning">
React Hook Form structure le client…

mais ne garantit pas la cohérence avec le serveur.

- ❌ le modèle Prisma n’est pas directement impliqué  
- ❌ la validation doit être dupliquée  
- ❌ les règles métier restent côté serveur  

👉 RHF améliore l’UX  
👉 mais ne restaure pas le contrat du système
</Callout>

### 🧠 Le bon positionnement mental

Pour comprendre correctement RHF, il faut le remettre à sa place.

👉 ce n’est pas une solution complète  
👉 c’est une couche spécialisée

👉 RHF est une **couche UX client**

Son rôle :

- capturer les inputs  
- organiser les données  
- améliorer l’expérience utilisateur  

Mais :

👉 il ne décide pas  
👉 il ne valide pas réellement  
👉 il ne garantit rien  

👉 le serveur reste la source de vérité

👉 et ce serveur s’appuie sur Prisma

<Callout type="info">
React Hook Form est un excellent outil…

👉 à condition de ne pas lui donner un rôle qu’il n’a pas

- RHF gère l’expérience utilisateur  
- le serveur applique les règles métier  
- Prisma définit la structure réelle des données  

👉 chaque couche a une responsabilité précise
</Callout>

👉 **Où nous en sommes :** React Hook Form a fait un travail honnête côté client — gestion des champs, validation locale, affichage des erreurs. Mais il n’a pas touché la fracture originale : le serveur reste contourné, la validation métier reste à refaire ailleurs, et le contrat entre le formulaire et le backend reste à réécrire à la main. Le confort est revenu ; la cohérence, non. Reste à trouver le pont qui réconcilie enfin ces deux mondes — et c’est là que commence le vrai mouvement.

## Ce que nous venons de construire dans le Mouvement 1

Nous avons fait un détour historique, et trois idées en sont ressorties :

- **Le contrat natif n’était pas naïf, il était juste.** Un `<form action>` et une méthode suffisaient à faire parler le navigateur et le serveur dans une langue commune, où chacun tenait son rôle. Nous avons perdu cette clarté, pas parce qu’elle était fausse, mais parce qu’elle ne répondait plus aux besoins d’expérience utilisateur que React allait permettre.
- **React a gagné en flexibilité, mais il a fracturé l’architecture.** En interceptant le submit, il s’est rendu responsable de tout ce que le navigateur faisait silencieusement — transport, validation, orchestration — sans toujours mesurer ce qu’il prenait en charge. Le formulaire n’est plus un mécanisme, c’est devenu un pattern fragile.
- **Les form libraries ont soigné le symptôme, pas la cause.** RHF a remis de l’ordre dans le chaos local du client, mais la fracture avec le serveur est restée entière. Nous avons gagné en confort ce que nous continuions de perdre en cohérence.

Le Mouvement 2 va maintenant reconstruire le pont — en passant par `useActionState`, puis par App Router et les Server Actions, puis par un modèle hybride où chaque couche retrouve enfin sa place.

## À suivre

Le confort est revenu ; la cohérence, non. Il manque un pont qui rebranche une fonction métier sur un vrai `<form>`, sans que nous jouions nous-mêmes le rôle du navigateur.
