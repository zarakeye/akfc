> **Précédemment.** Le modèle hybride est assemblé, et il tient face au réel : les server actions quand nous le pouvons, un contrat et un client passif quand nous ne le pouvons pas. Et la question centrale n’est plus « comment envoyer », mais « qui a le droit de décider ».

## Mouvement 3 — Les limites du modèle

Jusqu’ici, nous avons construit. Ce mouvement change de posture : nous ne cherchons plus à faire tenir le modèle, nous cherchons à comprendre où il ne tient plus. Un modèle que nous appliquons partout perd son sens ; seul un modèle que nous savons situer reste un bon modèle.

Voici les deux étapes que nous allons traverser :

- **Section 7** (ce chapitre) : les pièges réels du modèle hybride, c’est-à-dire les détournements confortables, les fausses sécurités, les moments où l’interface ment à l’utilisateur. Tout ce qui donne l’impression que ça marche… jusqu’à ce que ça casse ;
- **Section 8** (chapitre suivant) : situer le modèle, savoir quand il est le bon choix et quand il ne l’est pas, et distinguer un pattern utilisé à bon escient d’un pattern appliqué par réflexe.

À la fin de ce mouvement, nous ne saurons plus seulement utiliser React Hook Form, `useActionState` et les server actions : nous saurons aussi dire, avec lucidité, quand ne pas les utiliser.

## 7 — Là où le modèle casse : les pièges réels du modèle hybride

Jusqu’ici, tout tenait, et c’est justement ce qui est dangereux. Le modèle hybride ne casse pas immédiatement : il fonctionne, il donne confiance, il donne même une sensation de maîtrise. C’est exactement là que les erreurs commencent.

Changeons donc de posture : au lieu de construire, observons **comment ça casse dans la vraie vie**. Pas en théorie : dans des situations qui arrivent réellement, chacune confrontée au code du projet.

### 7.1 — Le faux sentiment de sécurité (le piège le plus dangereux)

Nous construisons un formulaire :

- React Hook Form valide ;
- les erreurs s’affichent ;
- le bouton se désactive ;
- tout semble propre.

Et nous nous disons : « mes données sont propres ». Imaginons maintenant qu’un utilisateur contourne le client, qu’une requête soit rejouée, ou qu’une valeur soit modifiée en route. Le serveur reçoit quelque chose d’invalide, et deux issues sont possibles :

- soit il l’accepte : c’est un bug métier ;
- soit il le refuse : l’interface devient incohérente, car elle avait dit « c’est bon ».

Ce moment arrive toujours. Et quand il arrive, nous réalisons que le client n’a jamais été une barrière, seulement un filtre pour l’expérience de saisie.

<Callout type="warning">
Le client rassure ; le serveur protège.
</Callout>

### 7.2 — Le piège confortable : détourner `useActionState`

Nous découvrons `useActionState`, et très vite nous nous disons : « je peux tout faire avec ça ». Alors nous commençons à :

- stocker des données dedans ;
- synchroniser des écrans avec ;
- y centraliser des appels au serveur.

Et ça marche… au début. Puis un jour :

- deux composants dépendent du même état ;
- une action modifie autre chose ailleurs ;
- un rechargement de la page efface tout.

Nous comprenons alors que `useActionState` n’est ni un gestionnaire d’état global (*state manager*), ni une couche d’accès aux données (*data layer*) : c’est un outil **local, contextuel, éphémère**, qui vit le temps d’une interaction avec un formulaire.

<Callout type="warning">
`useActionState` ne structure pas notre application : il structure une interaction.
</Callout>

### 7.3 — Le piège silencieux : `FormData`

C’est ici que les bugs les plus vicieux apparaissent. Le serveur reçoit :

<CodeSnippet
  language="ts"
  title="Entrée brute"
  filename="server.action.ts"
  codeJson='"formData: FormData"'
/>

Ce que cela veut dire en réalité :

- tout est chaîne de caractères (*string*) ;
- rien n’est garanti ;
- certaines valeurs peuvent être `null` (un champ absent du formulaire).

Imaginons que nous écrivions :

<CodeSnippet
  language="ts"
  title="Bug silencieux"
  filename="server.action.ts"
  codeJson='"const age = Number(formData.get("age"))"'
/>

Si le champ `age` est absent, `formData.get("age")` renvoie `null`, et `Number(null)` vaut `0`. Nous venons d’introduire un bug sans aucune erreur. C’est cela, le danger : pas un plantage, mais une dérive silencieuse, un âge de 0 enregistré comme s’il avait été saisi.

### Le vrai pipeline

Le bon ordre est toujours le même :

1. lire la valeur brute ;
2. traduire l’absence en `undefined` (« non renseigné »), sans l’inventer en `0` ou en chaîne vide ;
3. laisser le schéma décider.

<CodeSnippet
  language="ts"
  title="Pipeline sûr"
  filename="server.action.ts"
  codeJson='"const raw = formData.get("age")

const age = raw ? Number(raw) : undefined

const parsed = schema.safeParse({ age })"'
/>

<Callout type="info">
`FormData` n’est pas une donnée : c’est une matière première, qu’il faut transformer avant de lui faire confiance.
</Callout>

#### Dans le projet : deux façons de traiter la matière première

L’action du profil applique ce pipeline à la lettre, en trois temps :

  filepath="apps/web/src/features/admin/users/forms/update-me/updateMeForm.action.ts"
  filename="updateMeForm.action.ts"
  snippetStart="const raw = {"
  snippetEnd="const parsed = updateMeFormSchema.safeParse(input);"
  snippetHighlight="2,13,19"
  snippetTitle="Lire, nettoyer, puis valider"
  fullFileTitle="Voir le fichier complet"
/>

- **`raw`** : chaque valeur est extraite et forcée en chaîne. `formData.get` renvoie `null` pour un champ absent, et `?? ""` en fait une chaîne vide plutôt que la chaîne `"null"` que produirait `String(null)` ;
- **`input`** : les chaînes sont nettoyées (`trim`), et un champ facultatif laissé vide devient `undefined`, c’est-à-dire « non renseigné » pour le schéma, et non « renseigné avec une chaîne vide » ;
- **`safeParse`** : seulement maintenant, le schéma décide.

L’action de la catégorie, plus courte, contient le même soin en une seule ligne :

<CodeExample
  language="ts"
  filepath="apps/web/src/features/admin/categories/actions/saveCategoryForm.action.ts"
  filename="saveCategoryForm.action.ts"
  snippetStart="// `id` absent en création"
  snippetLines="5"
  snippetHighlight="3"
  snippetTitle="Une absence qui reste une absence"
  fullFileTitle="Voir le fichier complet"
/>

En création, il n’y a pas de champ `id` : `formData.get("id")` renvoie `null`. Or le schéma déclare `id: z.coerce.number().int().positive().optional()`. Sans `?? undefined`, `z.coerce.number()` convertirait `null` en `0` (exactement le `Number(null)` de plus haut), et `.positive()` refuserait ce zéro : **aucune catégorie ne pourrait être créée**, avec un message d’erreur sur un champ que l’utilisateur ne voit même pas. Avec `?? undefined`, l’absence reste une absence, et `.optional()` l’accepte.

### 7.4 — Le moment où l’interface ment

Une scène réelle, en trois temps. D’abord, nous modifions notre profil :

- le formulaire valide ;
- la requête passe ;
- nous mettons à jour un état local (*state*) avec ce que nous avons envoyé ;
- tout semble correct.

Puis nous rafraîchissons la page, et les données ne correspondent pas. Pourquoi ? Parce que le serveur a pu :

- normaliser une valeur (enlever des espaces, changer la casse) ;
- en modifier une autre (une règle métier) ;
- en rejeter une partie.

Notre client, lui, ne le sait pas : il affiche ce qu’il croit avoir envoyé. L’interface ment.

<Callout type="warning">
Un état local n’est jamais une vérité : c’est une projection temporaire.
</Callout>

#### Dans le projet : relire après avoir écrit

Le projet ne met jamais à jour un état local « à la main » après un enregistrement : il redemande la vérité au serveur.

Après la création ou la modification d’une catégorie, le formulaire invalide les lectures tRPC qui l’affichent ailleurs, puis redirige vers la fiche :

Le formulaire de profil va plus loin, parce que les données modifiées vivent à deux endroits :

C’est exactement « l’interface qui ment » : chaque morceau d’interface aurait cru sa propre copie.

### 7.5 — La duplication inévitable (et saine)

Oui, nous validons deux fois, et non, ce n’est pas un problème. Le problème serait de croire que ces deux validations doivent être identiques. Elles ont la même forme et la même intention, mais pas le même rôle :

- la validation du client sert l’expérience de saisie ;
- la validation du serveur garantit la vérité.

Le piège est de vouloir « une seule validation ». Le résultat est alors l’un ou l’autre :

- soit l’expérience se dégrade (toutes les erreurs n’apparaissent qu’après un aller-retour au serveur) ;
- soit la sécurité devient fragile (la seule validation est celle du client, que l’on peut contourner).

#### Dans le projet : deux validations, deux rôles

Le formulaire de changement de mot de passe montre une validation client **plus riche** que celle du serveur, sans contradiction :

Le schéma partagé `changePasswordSchema` (mot de passe actuel, nouveau mot de passe d’au moins 12 caractères) est celui que la procédure applique. Le schéma du formulaire l’**étend** avec une confirmation, et vérifie que les deux saisies sont identiques (`refine`). La confirmation n’intéresse que l’utilisateur, qui pourrait faire une faute de frappe dans un champ masqué : le formulaire et sa server action la vérifient, mais le service qui change le mot de passe ne la reçoit jamais. Le serveur, lui, garde ses propres vérifications, que le navigateur ne peut pas faire : l’ancien mot de passe correspond-il au compte ?

Le formulaire de profil fait le choix inverse : **aucun** résolveur côté client. Toute la validation est faite par l’action, qui renvoie une erreur par champ :

Le prix de ce choix : un aller-retour serveur pour découvrir une erreur qu’un résolveur aurait signalée tout de suite. Pour un formulaire qu’on remplit rarement, c’est un prix acceptable.

### 7.6 — Le piège de l’excès d’application

Nous découvrons un modèle puissant, alors nous voulons tout faire avec. Nous commençons à l’utiliser pour :

- des tableaux de bord ;
- du temps réel ;
- de l’interrogation régulière du serveur (*polling*) ;
- du cache.

C’est une erreur. Ce modèle est optimisé pour **une action ponctuelle** (un envoi, une réponse), pas pour **un flux continu** de données. Chaque outil a son terrain ; le chapitre suivant trace ces frontières.

### 7.7 — Le vrai piège (le plus subtil)

Ce modèle ne casse pas quand nous faisons une erreur : il casse quand nous faisons quelque chose qui **semble correct**, par exemple :

- mettre à jour un état local après un envoi ;
- faire confiance à la validation de React Hook Form ;
- convertir un `FormData` directement.

Tout fonctionne, jusqu’au jour où ça ne fonctionne plus. Et ce jour-là, le bug est difficile à comprendre, parce qu’il ne vient pas d’une ligne fausse, mais d’une **hypothèse fausse**.

## Le point clé (celui que nous gardons vraiment)

<Callout type="info">
Le modèle hybride fonctionne uniquement si nous respectons la hiérarchie : le client fait l’interface, le serveur détient la vérité, le formulaire n’est qu’un passage.
</Callout>

## Conclusion

Un développeur qui débute cherche à faire fonctionner ; avec l’expérience, il cherche à optimiser ; plus tard encore, il cherche à comprendre où ça casse, et pourquoi. C’est cette dernière question que ce chapitre a posée : nous ne voulons pas seulement utiliser ce modèle, nous voulons savoir **quand il devient dangereux**.

Le modèle hybride ne casse pas en hurlant : il casse discrètement, dans les moments où il donne l’impression de tenir. Les pièges les plus dangereux ne sont pas ceux qui produisent des bugs visibles, mais ceux qui installent une fausse sécurité : un détournement ici, un raccourci là, une interface qui ment à l’utilisateur sans que personne ne s’en aperçoive. Reste l’étape suivante : savoir situer le modèle, et pas seulement le faire marcher.
