## Pourquoi les formulaires deviennent un problème… dès que le système devient sérieux

Un monde structuré existe déjà côté serveur : un modèle, des entités, des relations, un système cohérent porté par Prisma. Il est correct, typé, cohérent, mais encore fermé : aucun utilisateur ne peut agir sur lui. C’est là que les formulaires entrent en jeu.

## Avant de commencer : les mots de cette partie

Les formulaires sont le point où le navigateur, React et le serveur se rencontrent : chacun apporte ses mots. Les voici, une fois pour toutes, avant le détour historique.

### Le formulaire, côté navigateur

- Un **formulaire** (`<form>`) regroupe des champs de saisie (`<input>`, `<select>`, `<textarea>`). Chaque champ porte un attribut **`name`** : le nom sous lequel sa valeur sera envoyée.
- **Soumettre** le formulaire (cliquer sur le bouton `type="submit"`, ou appuyer sur Entrée dans un champ) déclenche l’**évènement `submit`**. Sans JavaScript, le navigateur rassemble alors les valeurs, les **sérialise** (les met à plat en texte : `email=a%40b.fr&password=…`) et les envoie au serveur dans une requête `POST`, à l’adresse que donne l’attribut `action`. Le serveur répond par une nouvelle page.
- **`FormData`** est l’objet qui contient ces valeurs côté JavaScript : on y lit un champ par son nom (`formData.get("email")`). Toutes ses valeurs sont des chaînes de caractères (ou des fichiers) : un nombre, une date ou une case cochée doivent être reconvertis.
- Le **DOM** (*Document Object Model*) est la page telle que le navigateur la tient en mémoire : un arbre d’éléments (le formulaire, ses champs, ses boutons) que JavaScript peut lire et modifier, et qui émet des évènements.
- **`preventDefault()`** empêche le comportement par défaut d’un évènement. Appelé sur `submit`, il arrête l’envoi natif : c’est JavaScript qui reprend la main, et tout ce que faisait le navigateur est désormais à sa charge.

### Ce que React ajoute

- Un **hook** est une fonction de React dont le nom commence par `use` (`useState`, `useActionState`, `useForm`) et qui donne une capacité à un composant : garder une valeur, réagir à un évènement, suivre un envoi.
- Un **état** (*state*, créé par `useState`) est une valeur qu’un composant garde d’un affichage à l’autre ; la modifier provoque un nouveau calcul de l’affichage, un **re-render**.
- Un champ **contrôlé** affiche une valeur gardée dans un état React et mise à jour à chaque frappe ; un formulaire en **état contrôlé** tient ainsi toute sa saisie dans React. L’autre façon de faire laisse la valeur dans le champ du navigateur et ne la lit qu’au besoin : c’est celle de React Hook Form.

### Ce que le serveur reprend

- Une **server action** est une fonction d’un fichier marqué `"use server"`. Elle s’exécute sur le serveur, mais un formulaire peut l’appeler directement (`<form action={…}>`) : Next.js fabrique la requête à notre place.
- Une **mutation** est une opération qui modifie des données côté serveur : créer, modifier, supprimer. Le contraire d’une lecture.
- Un **schéma partagé** est un schéma Zod écrit une fois dans `packages/contracts`, le paquet que se partagent le navigateur et le serveur, et importé des deux côtés : par le formulaire pour prévenir, par le serveur pour décider.

## Une frontière, pas une couche d’interface

Un formulaire n’est pas une couche d’interface : c’est un **point de passage**, l’endroit où une intention humaine (écrire une adresse, modifier un profil, créer une ressource) tente d’entrer dans un système structuré. Ce passage n’est pas neutre. Ce que l’utilisateur envoie n’est ni fiable, ni typé, ni validé, alors que le système construit avec Prisma est strict, contraint et typé. Le formulaire est une zone de friction entre deux mondes qui ne parlent pas la même langue : le navigateur (interaction, expérience, évènements) et le serveur (logique métier, validation, persistance). Surtout, c’est la frontière entre **l’intention de l’utilisateur** et **le modèle Prisma**.

### Le problème réel des formulaires modernes

Avec React, nous avons gagné du contrôle : intercepter les évènements, gérer des états, envoyer les requêtes nous-mêmes. En échange, la complexité s’est déplacée. Chaque formulaire est devenu une gestion de champs, une validation côté client, une logique réseau, une gestion d’erreurs et une synchronisation de l’interface, et surtout une **duplication implicite du modèle serveur** : le frontend définit ses propres types, le backend valide de son côté, les règles divergent. Le problème est invisible au début ; il grandit avec le temps.

Le vrai enjeu n’est donc pas de « collecter des données », mais de transformer une intention en une structure conforme au modèle du système, et ce modèle existe déjà : il vient de Prisma.

### Ce que change l’App Router

Avec les server actions, nous ne simulons plus un envoi au serveur avec un `fetch` : nous reconnectons le formulaire au serveur. Cela ne supprime pas le problème, cela le rend visible, et une question devient centrale : **qui est responsable de quoi ?** Le client gère-t-il la validation ? Le serveur doit-il tout vérifier ? Où vivent les erreurs, où s’applique le typage ?

Cette série organise les réponses autour de quatre outils : React Hook Form pour l’expérience de saisie, Zod pour valider les données côté serveur, les server actions pour porter la logique métier, `useActionState` pour relier le serveur à l’interface. Mais l’objectif est surtout de comprendre pourquoi ils existent, et pourquoi ils vont ensemble. Le but n’est pas un formulaire qui fonctionne : c’est un formulaire qui respecte le système, un point d’entrée fiable dans un modèle déjà structuré.

<Callout type="info">
Un formulaire moderne n’est pas un composant : c’est une interface entre une intention humaine et un modèle typé, défini par Prisma. Tout l’enjeu est que ce passage ne casse pas la cohérence du système.
</Callout>

## Ce que nous allons traverser

Beaucoup de problèmes actuels viennent de ce que nous ne savons plus comment le web fonctionnait à l’origine. Plutôt que d’apprendre simplement à écrire un formulaire, nous allons reconstruire son histoire dans React, et voir pourquoi le modèle que nous construirons est une réconciliation avec quelque chose de plus ancien. Trois mouvements, répartis sur sept chapitres, puis une ouverture :

- **Mouvement 1 — La rupture** (ce chapitre et le suivant). Nous revenons au point de départ — le contrat natif entre le formulaire et le serveur —, puis nous regardons ce que React a cassé en le réinterprétant, et comment les bibliothèques ont tenté de soigner le symptôme sans toucher la cause.
- **Mouvement 2 — La réconciliation** (chapitres 3 à 5). Nous découvrons le pont que `useActionState` construit, puis comment App Router en fait une vraie route retour au serveur via les server actions, et enfin comment ces pièces se combinent avec React Hook Form dans un modèle hybride qui tient.
- **Mouvement 3 — Les limites du modèle** (chapitres 6 et 7). Nous regardons où ce modèle casse, où son confort devient dangereux, et comment choisir lucidement quand l’utiliser — et quand aller chercher autre chose.

La **section 9**, à la fin du dernier chapitre, ouvrira ensuite la porte vers la suite du parcours — tRPC — en montrant pourquoi, malgré tout ce que nous venons de construire, un problème reste entier.

À chaque étape, le code du projet confronte le récit au réel : les formulaires du tableau de bord, du profil et de la connexion, tels qu’ils sont écrits aujourd’hui.

## Mouvement 1 — La rupture

Ce mouvement est un détour historique : la seule façon de voir ce qui a été perdu en route, et donc ce que nous cherchons à retrouver. Il compte trois sections :

- **Section 1** : l’origine, `<form action="...">`, et la façon dont le web avait déjà résolu le problème avant les frameworks ;
- **Section 2** : ce que React a fait de ce contrat : en interceptant l’envoi, il a gagné en souplesse mais déplacé des responsabilités qui n’auraient pas dû bouger ;
- **Section 3** (chapitre suivant) : la tentative de sauvetage par les bibliothèques de formulaires, React Hook Form en tête, qui soignent le confort côté client sans toucher à la fracture côté serveur.

À la fin de ce mouvement, le formulaire ne sera plus un problème d’interface à résoudre, mais un contrat ancien qu’il faut réapprendre à honorer.

## 1 — À l’origine : `<form action>`

### Le web avait déjà résolu le problème

Le web n’a pas attendu les frameworks : dès HTML, un mécanisme complet faisait transiter des données du navigateur vers le serveur.

<CodeSnippet
  language="html"
  title="Formulaire HTML natif"
  filename="demo.html"
  kind="educational"
  highlightLines="1-5"
  codeJson='"<form action=\"/login\" method=\"POST\">\n  <input name=\"email\" />\n  <input name=\"password\" />\n  <button type=\"submit\">Login</button>\n</form>"'
 />

Quand l’utilisateur clique sur **Login**, le navigateur prend entièrement le relais, sans rien demander à JavaScript. Voici le cycle complet :

1. il lit l’attribut `action` : `/login`, la route du serveur ;
2. il collecte tous les champs qui ont un attribut `name` ;
3. il les sérialise (`application/x-www-form-urlencoded`, ou `multipart/form-data` quand il y a des fichiers) ;
4. il envoie la requête HTTP (`POST` ici) au serveur ;
5. il laisse le serveur répondre, par une nouvelle page.

Aucune logique côté client, aucune orchestration, aucun état complexe.

### Une séparation des responsabilités parfaite

Le navigateur capture, met à plat et transmet ; le serveur reçoit, valide et traite. Surtout, **le serveur reste la source de vérité**. Ce qu’il reçoit n’est pas « juste des données » : ce sont des données destinées à entrer dans un système structuré. Prisma n’existait pas, mais le principe était déjà là : le formulaire n’était qu’un point d’entrée vers un modèle côté serveur.

Dans beaucoup d’applications de cette époque, le serveur était à la fois serveur web (il produisait le HTML) et serveur de données (il exécutait la logique métier et accédait à la base). Rendu et logique vivaient ensemble, et le flux ne laissait aucune ambiguïté : une requête entrait, elle était traitée, une page complète sortait. Le navigateur n’avait rien à orchestrer.

Ce modèle était **structurellement cohérent** : une seule source de vérité, aucune logique dupliquée, aucune validation concurrente, un flux simple et prévisible. Il forçait naturellement le respect du modèle côté serveur.

<Callout type="info">
Dans le modèle HTML natif, le navigateur collecte et envoie les données, le serveur porte toute la logique métier, et le protocole HTTP sert de contrat entre les deux. Pas d’état client complexe, pas de validation en double, très peu de surface d’erreur.
</Callout>

Sa limite : très peu de contrôle sur l’interface. C’est ce que React va chercher à résoudre, en déplaçant au passage une partie des responsabilités.

## 2 — React intercepte le formulaire

Avec React, le formulaire n’est plus un mécanisme natif que l’on déclenche, mais un évènement que l’on intercepte. Au lieu de laisser le navigateur soumettre le formulaire, on empêche son comportement par défaut :

<CodeSnippet
  language="ts"
  title="React — interception du submit"
  filename="LoginForm.tsx"
  kind="anti-pattern"
  codeJson='"onSubmit={(e) => {\n  e.preventDefault()\n  // logique custom\n}}"'
/>

À partir de là, tout bascule.

### Le contrat est cassé

Le navigateur ne fait plus rien pour nous. C’est désormais JavaScript qui doit tout orchestrer :

- récupérer les valeurs des champs ;
- garder leur état ;
- valider les données ;
- envoyer une requête HTTP à la main (`fetch`) ;
- gérer les erreurs ;
- synchroniser l’interface.

Nous gagnons en contrôle, mais nous perdons le **lien direct avec le serveur**, donc avec le modèle Prisma. Le frontend commence à définir ses propres structures, la validation se fait deux fois, les règles peuvent diverger : le système n’est plus cohérent par construction.

Le changement n’est pas seulement technique, il est architectural. Le formulaire ne transporte plus une intention vers le modèle : il reconstruit une version locale de ce modèle. De là viennent les dérives (types dupliqués, validations incohérentes, logique dispersée, bugs difficiles à voir), et une illusion dangereuse : croire que le client peut garantir la validité des données, alors que seule la validation du serveur compte.

<Callout type="warning">
Avec React classique, le contrat natif est cassé : plus de soumission par le navigateur, un réseau géré à la main (`fetch`), une validation en double, et une divergence possible avec le modèle du serveur. Le formulaire devient une implémentation locale, potentiellement incohérente avec la réalité.
</Callout>

### Avant, après : ce qui change vraiment

Avec React classique, centré sur le client, un envoi enchaîne :

1. `onSubmit` ;
2. `preventDefault()` ;
3. la lecture des valeurs ;
4. la construction d’un `fetch` ;
5. la réponse HTTP ;
6. l’analyse des erreurs ;
7. la mise à jour de l’état.

Le client orchestre tout, y compris ce qui ne lui appartient pas.

Avec l’App Router et les server actions (le modèle hybride que construit cette série), il ne reste que :

1. `<form action={formAction}>` ;
2. React orchestre l’envoi ;
3. la server action s’exécute sur le serveur ;
4. une réponse structurée revient vers l’interface.

Le client déclenche, le serveur décide, et **le modèle reste la source de vérité**.

<Callout type="info">
Dans React classique, nous simulons le web ; avec l’App Router, nous recommençons à nous appuyer sur lui, et nous reconnectons le formulaire au modèle du serveur.
</Callout>

## À suivre

React a gagné quelque chose de réel, le contrôle fin de l’interface, mais il l’a payé en cassant un contrat silencieux : le `<form>` ne sait plus soumettre seul, et JavaScript doit tout orchestrer, y compris ce qu’il n’aurait jamais dû gérer. L’écosystème a répondu par des bibliothèques qui promettaient de remettre de l’ordre dans les formulaires. Ont-elles réparé la fracture, ou seulement rendu le symptôme plus supportable ?
