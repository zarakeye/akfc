Le header est la seule partie de l'interface présente sur toutes les pages publiques, et la seule qui change selon la personne qui regarde. Un visiteur y trouve la navigation et le formulaire de connexion. Un membre y trouve en plus son menu, ses documents à lire et la cloche de ses espaces. Un administrateur, la cloche de la bibliothèque et le tableau de bord. Trois questions organisent le composant `Header` : d'où vient la liste des liens, comment l'afficher sur un écran étroit, et comment savoir dès le premier affichage qui est connecté.

Une entrée est un **lien**, un **menu** à sous-liens, ou l'entrée spéciale **`activities`**. Cette dernière n'est pas une liste figée : « Nos disciplines » se construit à partir des familles et des disciplines enregistrées en base. C'est donc un composant (`OurActivitiesMenu`), pas des données. Le type `NavEntry` est une union discriminée par `kind` : le header traite chaque sorte d'entrée dans sa branche, et TypeScript signale une sorte oubliée.

Cette liste alimente **deux rendus**. À partir de 1 280 pixels de large (`xl`), une barre horizontale ; en dessous, un bouton « burger » qui ouvre un panneau plein écran. Les deux parcourent `NAV_ENTRIES` : un lien ajouté à la liste apparaît des deux côtés, sans risque de l'oublier dans l'un.

Le panneau n'existe pas seulement par manque de place. Le survol n'existe pas sur un écran tactile : dans la barre, les sous-menus y étaient inaccessibles. Le panneau les ouvre à l'appui. Les cloches, elles, restent hors du panneau : leur intérêt est d'être vues sans qu'on les cherche.

### Fermer le panneau quand on a choisi

Le panneau doit se fermer quand le visiteur touche un lien. Plutôt qu'un gestionnaire sur chaque lien (dont ceux de « Nos disciplines », qui vivent dans un autre composant), un seul gestionnaire écoute le panneau entier :

C'est la **délégation d'évènements** : un clic remonte du lien jusqu'au panneau, qui regarde s'il est parti d'un lien. Les boutons qui déroulent un sous-menu ne sont pas des liens : ils ne ferment pas le panneau, ce qui est voulu. Un menu ajouté plus tard en profite sans rien recevoir.

Le commentaire du code explique aussi ce qui a été écarté : un effet qui fermerait le panneau quand l'URL change. Un effet sert à synchroniser React avec un système extérieur ; la vraie question n'était pas « l'URL a changé », mais « le visiteur a touché un lien ». Cet évènement existait déjà.

Tant que le panneau est ouvert, le défilement de la page est bloqué (`document.body.style.overflow = "hidden"`), puis rétabli à la fermeture : sinon la page glisse sous le doigt pendant qu'on parcourt le menu.

## Qui est connecté, dès le premier affichage

Le header est un composant client : il réagit à la connexion et à la déconnexion. La session vit dans un store Zustand (voir « Authentification et droits »). Mais ce store est un module partagé : sur le serveur, il est commun à toutes les requêtes, et ne peut donc pas contenir la session d'un visiteur. Il est vide pendant le rendu serveur. Sans précaution, le HTML arrivait avec un header « non connecté », puis basculait une fois la session chargée.

Le layout racine lit donc la session côté serveur et la transmet par un contexte React, propre à chaque requête. Le header la lit par `useCurrentUser` :

La requête du navigateur ne fait ensuite que les rafraîchir.

## Des signaux qui ne parlent que pour dire quelque chose

À droite de la barre, plusieurs signaux indiquent ce qui attend la personne connectée. Ils partagent une règle : **pas de badge à zéro**. Un compteur toujours affiché devient du décor, et on cesse de le regarder.

Les compteurs viennent de requêtes tRPC (`useQuery`), donc du cache de React Query. Une action qui change un compteur (un dépôt, une validation, une lecture) invalide la requête correspondante, et la cloche se met à jour sans rien savoir de l'action. Une version antérieure faisait un seul appel au montage, rangé dans un `useState` : hors du cache, aucune invalidation ne pouvait l'atteindre, et il fallait recharger la page pour voir un compteur juste.

Tout membre y trouve son profil, ses documents et la déconnexion. Un membre non administrateur peut déposer des fichiers ; un administrateur accède au tableau de bord ; « Demandes reçues » n'apparaît qu'à qui peut en traiter. Comme pour les pages, ce menu n'est qu'une commodité : chaque destination vérifie elle-même les droits sur le serveur.

<Callout type="info">
Le header ne décide d'aucun droit. Il montre ou cache des entrées selon la session, pour que chacun voie ce qui le concerne ; les pages et les procédures qu'elles appellent refusent elles-mêmes ce qui n'est pas permis.
</Callout>
