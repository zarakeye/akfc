> **Précédemment.** Chaque partie s'est terminée, tôt ou tard, sur un formulaire : créer une discipline, déposer un fichier, changer de mot de passe, publier un document. Il est temps de regarder ce qu'ils ont en commun, et pourquoi ils ne sont pas tous construits de la même façon.

## Ce qu'un formulaire doit garantir

Quelle que soit sa technique, un formulaire du projet tient quatre promesses :

1. **une règle de validation n'est écrite qu'une fois**, dans un schéma Zod, et appliquée des deux côtés : dans le navigateur pour afficher l'erreur sous le champ, sur le serveur parce que le navigateur ne fait foi de rien ;
2. **le serveur a le dernier mot**, sur la validité comme sur les droits ;
3. **l'utilisateur voit l'état** : envoi en cours, erreur sous le champ concerné, message de réussite ;
4. **la donnée affichée ailleurs se met à jour** après l'enregistrement.

Trois techniques coexistent pour tenir ces promesses, chacune adaptée à un type de formulaire.

## Les schémas, côté serveur et côté client

Les schémas partagés vivent dans `packages/contracts/src/forms` :

```ts
// packages/contracts/src/forms/saveCategoryForm.schema.ts
export const saveCategoryFormSchema = z.object({
  id: z.coerce.number().int().positive().optional(),
  type: z.string().trim().min(1, "Le type est obligatoire."),
});
```

Le même schéma sert au navigateur, par le résolveur de React Hook Form, et au serveur, qui le réapplique à l'arrivée. Le client peut n'en utiliser qu'une partie : ici, il ne valide que `type` (`.pick({ type: true })`), car `id` vient d'un champ caché que l'utilisateur ne saisit pas. Le serveur, lui, valide toujours le schéma complet.

Les messages d'erreur sont écrits dans le schéma, en français, pour l'utilisateur final : ce sont eux qui s'affichent sous les champs.

## Technique 1 : React Hook Form et server action

Une **server action** est une fonction marquée `"use server"`, que React peut appeler directement depuis un formulaire : `<form action={formAction}>`. Le navigateur envoie le formulaire, Next exécute la fonction sur le serveur, et sa valeur de retour devient le nouvel état du composant, par `useActionState`.

```tsx
// apps/web/src/features/admin/categories/forms/CategoryForm.tsx (extrait)
const form = useForm<FormValues>({
  resolver: zodResolver(saveCategoryFormSchema.pick({ type: true })),
  defaultValues: { type: initial?.type ?? "" },
  mode: "onBlur",
});

const [state, formAction, isPending] = useActionState<SaveCategoryFormState, FormData>(
  saveCategoryFormAction,
  {} as SaveCategoryFormState,
);
```

Ce montage permet :

- **une validation immédiate** : React Hook Form vérifie chaque champ quand on le quitte (`mode: "onBlur"`) et affiche l'erreur sans aller-retour serveur ;
- **un état d'envoi gratuit** : `isPending` désactive le bouton pendant l'enregistrement ;
- **un même formulaire pour créer et modifier** : en édition, un champ caché `id` fait basculer l'action sur la mise à jour.

### Bloquer l'envoi tant que le formulaire est invalide

La validation de React Hook Form est **asynchrone** (`form.trigger()` renvoie une promesse). Or le formulaire part dès la fin du gestionnaire `onSubmit`, s'il n'a pas appelé `preventDefault()`. Un `preventDefault()` placé après un `await` arrive trop tard : l'action est déjà partie.

Le projet suspend donc **toujours** l'envoi, valide, puis relance l'action lui-même :

```tsx
// apps/web/src/features/admin/categories/forms/CategoryForm.tsx (extrait)
<form
  action={formAction}
  onSubmit={(e) => {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    void form.trigger().then((valid) => {
      if (valid) startTransition(() => formAction(formData));
    });
  }}
>
```

Le `FormData` est lu tout de suite, tant que l'événement est disponible. L'action est relancée dans une `startTransition`, ce qui garde `isPending` exact. L'attribut `action` reste en place : sans JavaScript, le formulaire s'envoie quand même, et le serveur valide.

<Callout type="warning">
Dans un gestionnaire d'événement, tout ce qui doit empêcher le comportement par défaut se fait **avant le premier `await`**. Après, l'événement est déjà traité.
</Callout>

### Le retour de l'action : un état, pas une exception

Une server action ne lève pas d'erreur pour un refus attendu : elle **renvoie** un état que le composant affiche. Le contrat est commun, dans `packages/contracts/src/forms/form-action.types.ts` :

```ts
// packages/contracts/src/forms/form-action.types.ts
export type FormActionState<T = undefined, F extends string = string> =
  | { status: "idle" }
  | { status: "success"; data?: T; message?: string }
  | { status: "error"; error: string; fieldErrors?: Partial<Record<F, string>> };
```

`fieldErrors` associe un message à un champ : le formulaire de profil reporte ainsi sous chaque champ l'erreur trouvée par le serveur. Les formulaires plus anciens (catégorie, origine, famille, galerie) utilisent une forme plus simple, `{ success, error }`.

Un piège propre aux server actions : un fichier `"use server"` ne peut exporter **que des fonctions asynchrones**. L'état initial d'un formulaire (`initialUpdateMeFormState`) vit donc dans un fichier de types à part, sans la directive.

### Une server action est une porte ouverte

Une server action n'est pas une fonction privée de la page qui l'utilise. Next lui attribue un identifiant, et l'expose comme un point d'accès HTTP : n'importe quel navigateur peut l'appeler en `POST`, qu'il ait affiché le formulaire ou non. Les identifiants figurent dans le JavaScript envoyé au navigateur.

Les actions d'administration vérifient donc les droits **à leur première ligne**, exactement comme une procédure `isAdmin` :

```ts
// apps/web/src/features/admin/categories/actions/saveCategoryForm.action.ts (extrait)
export const saveCategoryFormAction = async (
  prevState: SaveCategoryFormState,
  formData: FormData,
): Promise<SaveCategoryFormState> => {
  // Point d'accès public : les droits se vérifient ici, avant toute lecture du formulaire.
  if (!(await callerIsAdmin())) return { success: false, error: ADMIN_ONLY_MESSAGE };

  const parsed = saveCategoryFormSchema.safeParse({ /* … */ });
  // …
};
```

`callerIsAdmin` (`features/admin/common/actions/callerIsAdmin.ts`) lit la session comme le reste de l'application. L'action de profil, elle, exige simplement une session et ne modifie que le compte de l'appelant, dont l'identifiant vient de la session et jamais du formulaire.

<Callout type="warning">
Une procédure tRPC déclare ses droits par son type (`protectedProcedure`, `.use(isAdmin)`). Une server action n'a pas ce garde-fou : **rien** ne la protège si elle ne vérifie pas elle-même. Toute nouvelle action commence par sa vérification de droits.
</Callout>

## Technique 2 : React Hook Form et mutation tRPC

Quand le serveur est déjà une procédure tRPC, le formulaire l'appelle depuis le `handleSubmit` de React Hook Form, qui ne déclenche la fonction que si la validation passe :

```tsx
// apps/web/src/features/auth/ChangePasswordForm.tsx (extrait)
const { register, handleSubmit, reset, formState: { errors, isSubmitting } } = useForm<FormValues>({
  resolver: zodResolver(formSchema),
  defaultValues: { currentPassword: "", newPassword: "", confirmPassword: "" },
});

const changePassword = trpc.auth.changePassword.useMutation();

const onSubmit = handleSubmit(async (values) => {
  try {
    await changePassword.mutateAsync({ currentPassword: values.currentPassword, newPassword: values.newPassword });
    reset();
    setOkMsg("Mot de passe modifié. Les autres appareils ont été déconnectés.");
  } catch (e) {
    setErrMsg(e instanceof Error ? e.message : "Impossible de changer le mot de passe.");
  }
});
```

Le schéma du client peut être plus riche que celui de la procédure : la confirmation du mot de passe n'intéresse que le formulaire, et n'est pas envoyée. La procédure garde ses propres vérifications (ancien mot de passe correct, nouveau mot de passe différent), dont le message remonte dans le `catch`.

## Technique 3 : état contrôlé et mutation tRPC

Le formulaire d'une discipline contient deux éditeurs du constructeur de pages, des sélecteurs de famille, d'origine et d'instructeur, un sélecteur d'image, et **deux** boutons d'envoi : « Enregistrer en brouillon » et « Publier ». React Hook Form n'apporte plus grand-chose ici : les valeurs sont des objets (des contenus de blocs), pas des champs texte.

Le composant garde donc chaque valeur dans un état React, vérifie à l'envoi ce qui doit l'être, et transmet un objet complet à la page, qui appelle la procédure :

```tsx
// apps/web/src/features/admin/disciplines/forms/DisciplineForm.tsx (extrait)
const handleSubmit = async (publish: boolean) => {
  setSubmitError(null);
  if (name.trim() === "") {
    setSubmitError("Le nom est obligatoire.");
    return;
  }
  // … autres vérifications, dont la longueur de la présentation synthétique
  setIsSubmitting(true);
  try {
    await onSubmit({
      publicationDate: publish ? (initial?.publicationDate ?? new Date()) : null,
      name: name.trim(),
      slug: slug.trim(),
      description,
      summary,
      // …
    });
  } catch (err) {
    setSubmitError(err instanceof Error ? err.message : String(err)); // ex. « slug déjà utilisé »
  } finally {
    setIsSubmitting(false);
  }
};
```

Le choix entre brouillon et publication se fait **au bouton** : « Publier » pose la date de publication (ou garde celle qui existait), « Enregistrer en brouillon » la retire. C'est cette date que filtrent ensuite toutes les lectures publiques de l'API.

Le formulaire ne contient pas la logique d'enregistrement : il reçoit une fonction `onSubmit`. La page de création y appelle `discipline.create`, la page d'édition `discipline.update` ; chacune invalide ensuite les listes concernées. Le même composant sert aux deux.
