## Le schéma, source de vérité

`prisma/schema.prisma` décrit la base entière : 47 modèles et 18 énumérations. De ce seul fichier découlent :

- le **client TypeScript** (`prisma generate`, lancé automatiquement après `pnpm install`) : chaque modèle devient une API typée, `prisma.discipline.findMany(...)`, et chaque champ mal nommé est une erreur de compilation ;
- les **migrations** SQL qui font évoluer la base ;
- la **documentation** du modèle de données.

Ce dernier point est une convention du projet : chaque modèle et chaque champ porte un commentaire `///`, en français, qui dit ce qu'il représente et ce qui se passe quand on le supprime. Ces commentaires apparaissent dans l'autocomplétion de l'éditeur, au survol d'un champ.

```prisma
// prisma/schema.prisma (extrait)
/// Membre de l'association, et compte de connexion au site.
///
/// Création : par un administrateur (`user.create`), avec un mot de passe généré
/// côté serveur et envoyé par e-mail ; le membre est inscrit d'office dans un
/// groupe (accès EDITOR). Être administrateur ne dépend d'aucun champ de ce
/// modèle : c'est l'appartenance à un groupe marqué `MemberGroup.isAdminGroup`.
///
/// Suppression d'un membre (actions réelles en base) :
/// - BLOQUÉE (RESTRICT) tant qu'il est auteur de posts, commentaires, réactions
///   ou votes, instructeur principal d'une discipline, […] uploader d'un média […] ;
/// - EFFACE avec lui (CASCADE) : sessions, jetons de réinitialisation, adhésions
///   aux groupes, […]
model User {
```

Un commentaire signale aussi ce qui est inutilisé ou fragile (« ⚠ Code mort », « ⚠ Écrite, jamais relue ») : le schéma dit la vérité sur l'état du code, y compris ses dettes.

Le schéma est découpé en sections (`USER & AUTH`, domaine du club, contenus, médias…). Pour comprendre une fonctionnalité, on commence par lire ses modèles : la plupart des règles métier y sont déjà visibles.

## Lire un modèle : l'exemple de MediaAsset

```prisma
// prisma/schema.prisma (extrait simplifié : commentaires et champs secondaires retirés)
model MediaAsset {
  id               String   @id @default(cuid())
  fullPath         String   @unique
  mimeType         String
  originalFileName String
  displayName      String?
  bytes            Int
  appRoot          String
  status           String
  categoryId       Int?
  disciplineId     Int?
  uploaderUserId   String
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  category       Category?            @relation(fields: [categoryId], references: [id])
  discipline     Discipline?          @relation(fields: [disciplineId], references: [id])
  uploader       User                 @relation("UserMediaUploads", fields: [uploaderUserId], references: [id])
  pageReferences PageMediaReference[]
  galleryItems   GalleryItem[]
  memberDocument MemberDocument?

  @@index([status])
}
```

`status` est un `String`, pas une énumération : les valeurs autorisées (`pending`, `published`) sont garanties par le code (les schémas Zod des procédures), et le commentaire du champ le dit. Une énumération Prisma est préférée quand l'ensemble des valeurs est stable ; ici, il a évolué plusieurs fois.

## Choisir ce qui se passe à la suppression

Chaque relation décide de ce que devient la ligne liée quand on supprime sa cible. C'est l'une des décisions les plus importantes d'un schéma, et le projet en utilise trois :

<DocsTable columnsJson='["Règle","Effet","Exemple du projet"]' rowsJson='[["Cascade (25 relations)","La ligne liée est supprimée avec sa cible.","Supprimer un membre supprime ses sessions et ses adhésions aux groupes ; supprimer un fichier supprime sa présence dans les galeries."],["SetNull (11 relations)","La clé étrangère passe à NULL : la ligne survit, détachée.","Supprimer une discipline détache ses médias, qui restent dans la bibliothèque."],["Restrict (3 relations)","La suppression de la cible est refusée tant qu’une ligne liée existe.","Un média utilisé par une page (PageMediaReference) ne peut pas être supprimé."]]' />

```prisma
// prisma/schema.prisma (extrait)
model PageMediaReference {
  id           String             @id @default(cuid())
  mediaAssetId String
  pageType     PageReferencerKind
  pageId       String
  mediaAsset   MediaAsset         @relation(fields: [mediaAssetId], references: [id], onDelete: Restrict)

  @@unique([mediaAssetId, pageType, pageId])
}
```

Le critère de choix : **que perd-on si la ligne liée disparaît ?** Une session sans membre n'a aucun sens (Cascade). Un média sans discipline reste un média (SetNull). Une page sans son image serait cassée sous les yeux des visiteurs (Restrict) : la base refuse, et l'application affiche pourquoi.

Quand `onDelete` n'est pas écrit, Prisma applique sa valeur par défaut : `SetNull` pour une relation facultative, `Restrict` pour une relation obligatoire. C'est le cas des relations `category`, `discipline` et `uploader` de `MediaAsset` ; leur commentaire `///` rend la règle explicite.

`PageMediaReference.pageId` n'a **pas** de clé étrangère : selon `pageType`, il désigne une discipline, un stage, une actualité… Une clé étrangère ne peut viser qu'une seule table. L'intégrité de ce côté est donc tenue par le code (`syncPageMediaReferences`, appelé dans la même transaction que chaque enregistrement de contenu).

## Les contenus en JSON

Les contenus éditables au constructeur de pages (description d'une discipline, d'un stage, d'une page) sont stockés dans des colonnes `Json`. Leur structure, des blocs versionnés, est décrite par un schéma Zod de `packages/contracts` (`pageContentSchemaV1`), validé par chaque procédure qui écrit. PostgreSQL stocke le document sans en connaître la forme ; c'est Zod qui la garantit à l'entrée.

Ce choix permet d'ajouter un type de bloc sans migration, au prix d'une règle : on lit un contenu avec les fonctions de `packages/contracts/src/page` (`parseContent`, `extractMediaIds`…), qui connaissent ses versions, plutôt qu'en accédant directement aux propriétés du JSON.

## Le client : un singleton

```ts
// packages/backend/src/prisma.ts
const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    log: process.env.NODE_ENV === "development" ? ["error", "warn"] : ["error"],
  });

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```

Chaque `PrismaClient` ouvre son propre pool de connexions. En développement, le rechargement à chaud de Next réévalue les modules à chaque modification : sans ce rangement dans `globalThis`, chaque sauvegarde de fichier ouvrirait un nouveau pool, jusqu'à épuiser les connexions de PostgreSQL. En production, le module n'est évalué qu'une fois.

La connexion est configurée dans `prisma.config.ts`, qui charge le `.env` de la racine (chapitre « Mise en route ») et lit `DATABASE_URL`.

## Écrire de façon cohérente : les transactions

Une opération métier touche souvent plusieurs tables. Enregistrer une discipline, c'est écrire la discipline **et** recalculer les médias qu'elle utilise. Si la seconde étape échoue, la première ne doit pas rester à moitié faite :

```ts
// packages/backend/src/modules/disciplines/router.ts (extrait)
return await ctx.prisma.$transaction(async (tx) => {
  const created = await tx.discipline.create({ data: { /* … */ } });
  await syncPageMediaReferences(tx, { pageType: "DISCIPLINE", pageId: String(created.id), /* … */ });
  return created;
});
```

Dans la fonction passée à `$transaction`, toutes les requêtes passent par `tx`, et non par `prisma` : elles s'exécutent dans la même transaction PostgreSQL. Une exception annule l'ensemble. Une requête faite par erreur avec `prisma` dans ce bloc s'exécuterait **en dehors** de la transaction, et ne serait pas annulée.

<Callout type="warning">
Dans un bloc `$transaction(async (tx) => …)`, on n'utilise que `tx`. Les services appelés depuis une transaction reçoivent `tx` en paramètre (leur signature accepte `PrismaClient | Prisma.TransactionClient`).
</Callout>

## Quand Prisma ne suffit pas : le SQL brut

Prisma couvre l'immense majorité des besoins. Le projet descend en SQL dans deux types de cas, avec `$executeRaw` et ses gabarits (les valeurs interpolées sont transmises comme paramètres, jamais concaténées : pas d'injection SQL possible) :

- **une opération que l'API ne sait pas exprimer** : réécrire le début de `fullPath` pour tous les médias d'un dossier déplacé (`SUBSTRING` dans un `UPDATE`) ;
- **une écriture qui ne doit pas déclencher `@updatedAt`** : la date de dernière connexion, qui ne doit pas passer pour une modification du profil.

## Faire évoluer la base : les migrations

Une **migration** est un fichier SQL daté, dans `prisma/migrations/<date>_<nom>/migration.sql`. L'ensemble des migrations, appliquées dans l'ordre, reconstruit la base à l'identique. La première, `0_init`, contient l'état de départ ; les suivantes, chacune une évolution.

<DocsTable columnsJson='["Commande","Où","Effet"]' rowsJson='[["pnpm prisma migrate dev --create-only --name <nom>","machine de développement","Compare le schéma à la base locale et écrit le SQL de la migration, sans l’appliquer."],["pnpm db:migrate (prisma migrate deploy)","développement et production","Applique les migrations pas encore appliquées, dans l’ordre ; n’en crée jamais."]]' />

Le déroulé d'une évolution :

1. modifier `schema.prisma`, avec ses commentaires `///` ;
2. générer la migration (`migrate dev --create-only`), puis **la relire** : Prisma écrit le SQL qu'il croit juste, et un renommage de colonne, par exemple, peut devenir une suppression suivie d'une création, avec perte des données ;
3. ajouter en tête du fichier un commentaire qui explique l'évolution, comme dans les migrations existantes ;
4. l'appliquer en local (`pnpm db:migrate`), vérifier, enregistrer dans le même commit que le code qui l'utilise ;
5. en production, le déploiement lance `prisma migrate deploy`.

```sql
-- prisma/migrations/20261207000000_legal_contact/migration.sql (extrait)
-- Coordonnées légales de l'association (Informations légales) : siège, téléphone, e-mail, seules
-- utilisées par les documents à valeur légale. Distinctes des coordonnées publiques.
ALTER TABLE "SiteSettings" ADD COLUMN "legalAddress" TEXT;
ALTER TABLE "SiteSettings" ADD COLUMN "legalPhone" TEXT;
ALTER TABLE "SiteSettings" ADD COLUMN "legalEmail" TEXT;
```

`migrate dev` a besoin de créer une base temporaire (la « base fantôme ») pour calculer la différence. Le conteneur PostgreSQL de développement le permet ; l'utilisateur de la base de production, non : on n'y lance donc jamais que `migrate deploy`.

<Callout type="tip">
Une migration déjà appliquée ne se modifie plus : Prisma enregistre une empreinte de chaque migration appliquée, et `migrate dev` signale toute migration modifiée après coup en proposant de réinitialiser la base. On corrige par une nouvelle migration.
</Callout>
