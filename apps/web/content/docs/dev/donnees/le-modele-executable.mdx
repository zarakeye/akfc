> **Précédemment.** Les relations du modèle sont des décisions : ce que le système se permet, ce qu’il refuse, et ce qui arrive à la suppression. Mais le modèle reste une description.

## Mouvement 3 — Rendre le modèle vivant

Le schéma est précis, les relations sont pensées, la philosophie est en place, mais rien ne tourne encore. Ce mouvement, en une seule section, est celui du basculement : le moment où le déclaratif devient du code, où le modèle cesse d’être une intention pour devenir un outil que le backend manipule. Nous y voyons comment Prisma transforme le schéma en types générés et en client typé, pourquoi cette bascule fait disparaître la duplication entre les couches, et comment le typage devient structurel plutôt que décoratif.

À la fin de ce mouvement, le modèle ne vivra plus seulement dans un fichier, mais dans le code, garant de la cohérence jusqu’au bord du frontend. C’est ce qui permettra ensuite aux formulaires et à tRPC de s’appuyer sur lui sans jamais le redéfinir.

## 5 — Prisma, moteur du système

Jusqu’ici, Prisma nous aidait à **décrire le système** ; à partir de maintenant, il va nous permettre de **le faire vivre dans le code**.

### 5.1 — Le moment clé : transformer le schéma en code

Un point est souvent mal compris : modifier `schema.prisma` ne change rien immédiatement dans l’application. Ni le backend ni TypeScript ne « voient » encore les modèles. Le schéma doit d’abord être transformé :

<CodeSnippet
  language="bash"
  title="Prisma — génération du client et des types"
  filename="terminal.sh"
  kind="pattern"
  codeJson='"pnpm prisma generate"'
/>

Cette commande lit le schéma, ses relations et ses contraintes, et en produit un client et des types TypeScript. À partir de là, le modèle devient utilisable par le code.

### 5.2 — Ce que Prisma génère réellement (et pourquoi c’est décisif)

Dire que Prisma génère « un client » est réducteur : il fabrique un pont complet entre la base et TypeScript. Il produit :

- des méthodes (`findUnique`, `findMany`, `create`…) ;
- des types alignés sur les modèles (`User`, `MemberGroup`…) ;
- des types d’entrée (`UserCreateInput`…), qui décrivent ce qu’on a le droit d’écrire ;
- des structures relationnelles imbriquées (un membre **avec** ses adhésions) ;
- des contraintes directement exploitables (les clés uniques deviennent des clés de recherche).

Tout est dérivé du schéma : il n’y a plus d’interprétation humaine entre la base et le code.

### 5.3 — La fin d’un problème invisible : la duplication des types

Dans une architecture classique, la donnée est définie plusieurs fois : dans la base, dans le backend, dans le frontend, parfois dans les formulaires. Au début, tout semble cohérent. Puis le projet évolue : un champ est renommé, un type change, une relation évolue, et les couches divergent. Cette divergence se voit rarement tout de suite ; elle devient un bug plus tard.

Avec Prisma, ce problème disparaît presque entièrement, parce que le type vient du schéma, et que le schéma est unique.

### 5.5 — Le basculement : du typage décoratif au typage structurel

Dans beaucoup de projets, les types sont ajoutés après coup : ils documentent, aident l’autocomplétion, évitent certaines erreurs, mais ne sont pas la source de vérité. C’est un typage **décoratif**.

Avec Prisma, la logique s’inverse : les types ne sont pas ajoutés, ils sont produits par la structure du système. C’est un typage **structurel**. Une incohérence casse aussitôt la compilation, une modification du schéma se répercute dans toutes les couches, et une erreur ne peut plus rester silencieuse : le système devient cohérent par construction.

#### 🔎 Dans le projet : un type décoratif, remplacé par un type généré

Ce même fichier a longtemps contenu un exemple parfait de typage décoratif. Pour décrire « une session avec son membre », il écrivait le type à la main :

<CodeSnippet
  language="ts"
  title="Un type réécrit à la main"
  filename="getSessionFromRequest.ts (avant)"
  kind="anti-pattern"
  codeJson='"type SessionDB = Session & {\n  user: User | null;\n};\n\n// … puis, partout où le membre était lu :\nemail: session.user!.email,"'
/>

Ce type disait quelque chose de faux. Dans le schéma, `Session.user` est **obligatoire** : une session a toujours un membre. Mais le type écrit à la main le déclarait facultatif (`User | null`), si bien que le code devait ensuite rassurer TypeScript à chaque lecture avec un `!` (« fais-moi confiance, ce n’est pas null »), et vérifier un cas qui ne pouvait pas se produire. Le type était une opinion, posée au-dessus du système.

Le type est maintenant **déduit de la requête elle-même** :

### 5.6 — Pourquoi cela simplifie tout le reste

Nous n’avons plus besoin de redéfinir des types côté backend, de synchroniser des interfaces côté frontend, ni de maintenir à la main des DTO (des *Data Transfer Objects* : des types recopiés pour décrire ce qui voyage entre deux couches). Le modèle fait ce travail, et les formulaires, tRPC et l’authentification s’appuieront tous sur cette base unique.

#### 🔎 Là où le typage s’arrête : les contenus en JSON

Il existe un endroit où cette chaîne de types s’interrompt, et il faut le connaître.

Les contenus éditables au constructeur de pages (la description d’une discipline, d’un stage, d’une page) sont stockés dans des colonnes `Json`. Pour Prisma, et donc pour TypeScript, une telle colonne contient « du JSON », sans forme particulière. PostgreSQL stocke le document sans en connaître la structure.

Cette structure, des blocs versionnés, est donc garantie ailleurs : par un schéma Zod de `packages/contracts` (`pageContentSchemaV1`), que chaque procédure applique avant d’écrire. Dans le code qui enregistre une discipline, un `as Prisma.InputJsonValue` marque précisément ce passage : la donnée a été validée par Zod, puis remise à Prisma comme un JSON sans type.

<Promesse vers="dev/contenu/un-contenu-fait-de-blocs" section="Un seul format pour tous les contenus">
Un contenu de page est une liste de **blocs** (un texte, une galerie, une liste de documents…), rangée dans une enveloppe qui porte un numéro de version. Le domaine du club, juste après, en donne la forme ; la partie « Contenu éditorial » la construit bloc par bloc.
</Promesse>

Ce choix permet d’ajouter un type de bloc sans migration, au prix d’une règle : on lit un contenu avec les fonctions de `packages/contracts/src/page` (`parseContent`, `extractMediaIds`…), qui connaissent ses versions, plutôt qu’en accédant directement aux propriétés du JSON. Là où le schéma Prisma ne décrit plus la forme, c’est un schéma Zod qui prend le relais.

### 5.7 — Ce que cette section prépare

Le modèle vit maintenant dans le code, et deux questions pratiques apparaissent : comment écrire dans plusieurs tables sans laisser la base à moitié modifiée ? Comment faire évoluer le schéma quand la base de production contient déjà des données ?

Ces deux questions attendront un peu. Le site public n’écrit rien : il lit des disciplines, des cours, des stages, et les montre. Nous allons d’abord le construire, et revenir à l’écriture quand l’interface aura des données à enregistrer.

<Promesse vers="dev/donnees/ecrire-et-faire-evoluer">
Retenons pour l’instant qu’une écriture qui touche plusieurs tables passe par une **transaction**, et que le schéma n’évolue jamais sans une **migration**, relue avant d’être appliquée.
</Promesse>

## Ce que nous venons de construire dans le Mouvement 3

Nous avons franchi la frontière qui sépare le descriptif de l’exécutable. Avec du recul, un système complet apparaît :

1. PostgreSQL stocke la donnée ;
2. Prisma définit sa structure et en génère les types ;
3. TypeScript comprend ces types ;
4. le backend les utilise.

La donnée circule sans rupture. Quatre idées en sont ressorties :

- **`prisma generate` n’est pas un détail d’outillage, c’est un basculement.** Cette commande prend un schéma déclaratif et en produit un client typé, aligné sur les modèles et les relations. Dès lors, le backend ne manipule plus « des objets qui ressemblent à des membres » : il manipule des `User`, au sens strict du type.
- **Le typage devient structurel, pas décoratif.** Les types ne sont plus des annotations posées au-dessus du code pour rassurer l’éditeur : ils sont générés à partir de la source de vérité, et chaque évolution du schéma les met à jour. Le code compile ou ne compile pas selon ce que la base permet réellement.
- **Le projet devient typé de bout en bout.** C’est ce qu’on appelle, en anglais, un système *type-safe end-to-end* : de la base au navigateur, chaque couche manipule des types qui viennent du même schéma, et Prisma en est la fondation.
- **La cohérence devient une propriété de la chaîne, pas un effort individuel.** Tant que chaque couche consomme les types générés, il n’est plus nécessaire de vérifier à chaque étage que les structures correspondent. Les couches du dessus peuvent se concentrer sur ce qu’elles font : capturer une intention, transporter une donnée, sécuriser un accès.

La partie « Données (1) » s’arrête ici : nous savons lire le modèle, et le lire avec des types sûrs. C’est exactement ce dont le site public a besoin. Les quatre modèles du noyau disent comment le site connaît ses membres ; ils ne disent rien encore de ce qu’il montre. Un visiteur, lui, cherche un cours, un stage, un horaire.
