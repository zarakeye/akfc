## Mouvement 3 — Rendre le modèle vivant

Jusqu’ici, tout ce que nous avons construit reste statique. Le schéma est précis, les relations sont pensées, la philosophie est en place — mais rien ne tourne encore. Ce mouvement est celui du basculement : le moment où le déclaratif devient du code, où le modèle cesse d’être une intention pour devenir un outil que le backend peut manipuler.

Voici l’étape unique mais décisive que nous allons traverser :

- **Section 5** — Nous voyons comment Prisma transforme le schéma en types générés et en client typé, pourquoi cette bascule fait disparaître la duplication entre les couches, et comment le typage devient structurel plutôt que décoratif.

À la fin de ce mouvement, le modèle ne vivra plus seulement dans un fichier — il vivra dans le code, exploitable par le backend, garant de la cohérence jusqu’à la bordure du frontend. Et c’est ce qui permettra, dans la suite, aux formulaires et à tRPC de s’appuyer sur lui sans jamais avoir à le redéfinir.

## 5 — Quand le modèle devient exécutable : Prisma comme moteur du système

Jusqu’ici, nous avons construit quelque chose de solide.

Nous avons défini des entités.  
Nous avons structuré des relations.  
Nous avons pris des décisions d’architecture.

Mais à ce stade, tout cela reste… statique.

Le modèle existe.  
La base est prête.  
Le schéma est lisible.

👉 mais rien ne circule encore

Et c’est exactement ici que Prisma change de nature.

Jusqu’à maintenant, il nous aidait à **décrire le système**.  
À partir de maintenant, il va nous permettre de **le faire vivre dans le code**.

---

### 5.1 — Le moment clé : transformer le schéma en code

Un point est souvent mal compris.

Modifier `schema.prisma` ne change rien immédiatement dans l’application.

Le backend ne “voit” pas encore nos modèles.  
TypeScript non plus.

👉 le schéma n’est pas encore exploitable

👉 il doit être transformé

<CodeSnippet
  language="bash"
  title="Prisma — génération du client et des types"
  filename="terminal.sh"
  kind="pattern"
  codeJson='"pnpm prisma generate"'
/>

Cette commande marque un basculement.

Prisma va :

- lire notre schéma  
- comprendre nos relations  
- interpréter nos contraintes  
- générer un client  
- produire des types TypeScript  

Et à partir de là :

👉 notre modèle devient utilisable par le code

---

### 5.2 — Ce que Prisma génère réellement (et pourquoi c’est décisif)

Dire que Prisma génère “un client” est réducteur.

En réalité, il fabrique un pont complet entre la base et TypeScript.

Il génère :

- des méthodes (`findUnique`, `findMany`, `create`, etc.)  
- des types parfaitement alignés (`User`, `MemberGroup`, etc.)  
- des types d’input (`UserCreateInput`, etc.)  
- des structures relationnelles imbriquées  
- des contraintes directement exploitables  

👉 tout est dérivé du schéma

Cela signifie une chose très importante :

👉 il n’y a plus d’interprétation humaine entre la base et le code

---

### 5.3 — La fin d’un problème invisible : la duplication des types

Dans une architecture classique, la donnée est définie plusieurs fois :

- dans la base  
- dans le backend  
- dans le frontend  
- parfois dans les formulaires  

Au début, tout semble cohérent.

Puis le projet évolue.

Et très vite :

- un champ est renommé  
- un type change  
- une relation évolue  

👉 les couches divergent

Et cette divergence est rarement visible immédiatement.

👉 elle devient un bug plus tard

Avec Prisma, ce problème disparaît presque entièrement.

Parce que :

👉 le type vient du schéma  
👉 et le schéma est unique

### 5.4 — Lire une requête Prisma comme une projection du système

Regardons cette requête, celle que le serveur exécute à chaque requête d’un membre connecté pour retrouver sa session :

```ts
// packages/backend/src/modules/auth/getSessionFromRequest.ts (extrait)
  const sessionDB = await prisma.session.findUnique({
    where: { id: payload.sessionId },
    select: sessionSelect,
  });
```

`sessionSelect`, déclarée en tête du fichier, demande la session **avec** son membre — certains de ses champs seulement — et son éventuelle adhésion au groupe Administrateurs :

```ts
// packages/backend/src/modules/auth/getSessionFromRequest.ts (extrait)
const sessionSelect = {
  id: true,
  expiresAt: true,
  user: {
    select: {
      id: true,
      email: true,
      firstName: true,
      lastName: true,
      pseudo: true,
      avatar: true,
      isFirstLogin: true,
      memberGroupMemberships: {
        where: { group: { isAdminGroup: true } },
        select: { id: true },
        take: 1,
      },
    },
  },
} satisfies Prisma.SessionSelect;
```

Avec le réglage `relationJoins` vu au chapitre 2, Prisma lit le tout en une seule requête SQL, par des jointures. (Une première version faisait une seconde requête, à chaque requête du site, pour savoir si le membre était administrateur ; l’adhésion demandée ici la remplace.)

Ce code n’est pas qu’une requête.

Il est une projection directe du modèle :

- il reflète les relations  
- il reflète la structure des données  
- il définit la forme du résultat  

Et surtout :

👉 TypeScript connaît exactement ce que cette requête retourne

Pas parce que nous l’avons défini.

👉 parce que Prisma l’a généré

Dans ce modèle, un type incorrect n’est pas ignoré.

👉 il devient impossible à écrire

### 5.5 — Le basculement : du typage décoratif au typage structurel

Dans beaucoup de projets, les types sont ajoutés après coup.

Ils servent à :

- documenter  
- aider à l’auto-complétion  
- éviter certaines erreurs  

Mais ils ne sont pas la source de vérité.

👉 on parle de typage décoratif

Avec Prisma, nous changeons complètement de logique.

Les types ne sont pas ajoutés.

👉 ils sont produits par la structure du système

Nous passons à un typage structurel.

Et cela change tout.

Parce que maintenant :

- une incohérence casse immédiatement le code  
- une modification du schéma impacte toutes les couches  
- une erreur ne peut plus rester silencieuse  

👉 le système devient auto-cohérent

---

#### 🔎 Dans le projet : un type décoratif, remplacé par un type généré

Ce même fichier a longtemps contenu un exemple parfait de typage décoratif. Pour décrire « une session avec son membre », il écrivait le type à la main :

<CodeSnippet
  language="ts"
  title="Un type réécrit à la main"
  filename="getSessionFromRequest.ts (avant)"
  kind="anti-pattern"
  codeJson='"type SessionDB = Session & {\n  user: User | null;\n};\n\n// … puis, partout où le membre était lu :\nemail: session.user!.email,"'
/>

Ce type disait quelque chose de faux. Dans le schéma, `Session.user` est **obligatoire** : une session a toujours un membre. Mais le type écrit à la main le déclarait facultatif (`User | null`), si bien que le code devait ensuite rassurer TypeScript à chaque lecture avec un `!` (« fais-moi confiance, ce n’est pas null »), et vérifier un cas qui ne pouvait pas se produire. Le type était une opinion, posée au-dessus du système.

Le type est maintenant **déduit de la requête elle-même** :

```ts
// packages/backend/src/modules/auth/getSessionFromRequest.ts (extrait)
/** Une session lue avec son membre : type GÉNÉRÉ par Prisma à partir de la sélection elle-même. */
type SessionDB = Prisma.SessionGetPayload<{ select: typeof sessionSelect }>;
```

`Prisma.SessionGetPayload<…>` reçoit la sélection de la requête, et produit exactement le type de son résultat : une session, avec un `user` qui n’est pas `null` et qui n’a que les champs demandés. Les `!` ont disparu, et la vérification inutile aussi. Et comme la requête et le type partagent la même constante, `sessionSelect`, ils ne peuvent plus diverger : ajouter un champ à la sélection l’ajoute au type.

Le client généré fournit ainsi bien plus que des types de modèles :

- des types d’entrée, comme `Prisma.UserUpdateInput`, que l’action de profil utilise pour vérifier, sans rien changer à l’objet, que ce qu’elle s’apprête à écrire est bien acceptable par Prisma :

```ts
// apps/web/src/features/admin/users/forms/update-me/updateMeForm.action.ts (extrait)
  const updateData = {
    firstName: data.firstName,
    lastName: data.lastName,
    pseudo: data.pseudo ?? null,
    aboutMe: data.aboutMe ?? null,
    phone: data.phone ?? null,
    ...(birthDateLocked ? {} : { birthDate: data.birthDate ? new Date(data.birthDate) : null }),
    isFirstLogin: false,
  } satisfies Prisma.UserUpdateInput;
```

- des noms dérivés des contraintes : `@@unique([groupId, userId])`, vu au chapitre 3, devient dans le client une clé de recherche nommée `groupId_userId`, que la garde des espaces utilise pour trouver une adhésion précise :

```ts
// packages/backend/src/modules/memberGroups/resolveGroupAccessForUser.service.ts (extrait)
    const membership = await prisma.memberGroupMembership.findUnique({
      where: { groupId_userId: { groupId: cursor, userId } },
      select: { access: true },
    });
```

Ce nom n’est écrit nulle part à la main. Il existe parce que la contrainte existe, et il disparaîtrait avec elle : le code qui l’utilise cesserait alors de compiler, au lieu de chercher une ligne qui ne peut plus être unique.

### 5.6 — Pourquoi cela simplifie tout le reste

À ce stade, quelque chose devient évident.

Nous n’avons plus besoin de :

- redéfinir des types backend  
- synchroniser des interfaces frontend  
- maintenir des DTO manuellement (des *Data Transfer Objects* : des types recopiés à la main pour décrire ce qui voyage entre deux couches)  

👉 le modèle fait tout le travail

Et cela va avoir des conséquences directes :

- sur les formulaires  
- sur tRPC  
- sur l’authentification  

Parce que toutes ces couches vont s’appuyer sur cette base unique.

#### 🔎 Là où le typage s’arrête : les contenus en JSON

Il existe un endroit où cette chaîne de types s’interrompt, et il faut le connaître.

Les contenus éditables au constructeur de pages (la description d’une discipline, d’un stage, d’une page) sont stockés dans des colonnes `Json`. Pour Prisma, et donc pour TypeScript, une telle colonne contient « du JSON », sans forme particulière. PostgreSQL stocke le document sans en connaître la structure.

Cette structure, des blocs versionnés, est donc garantie ailleurs : par un schéma Zod de `packages/contracts` (`pageContentSchemaV1`), que chaque procédure applique avant d’écrire. Dans le code qui enregistre une discipline, un `as Prisma.InputJsonValue` marque précisément ce passage : la donnée a été validée par Zod, puis remise à Prisma comme un JSON sans type.

<Promesse vers="dev/contenu/un-contenu-fait-de-blocs" section="Un seul format pour tous les contenus">
Un contenu de page est une liste de **blocs** (un texte, une galerie, une liste de documents…), rangée dans une enveloppe qui porte un numéro de version. Le domaine du club, juste après, en donne la forme ; la partie « Contenu éditorial » la construit bloc par bloc.
</Promesse>

Ce choix permet d’ajouter un type de bloc sans migration, au prix d’une règle : on lit un contenu avec les fonctions de `packages/contracts/src/page` (`parseContent`, `extractMediaIds`…), qui connaissent ses versions, plutôt qu’en accédant directement aux propriétés du JSON.

👉 là où le schéma Prisma ne décrit plus la forme, c’est un schéma Zod qui prend le relais

## Ce que nous venons de construire dans le Mouvement 3

Nous avons franchi la frontière qui sépare le descriptif de l’exécutable. Trois idées en sont ressorties :

- **`prisma generate` n’est pas un détail d’outillage, c’est un basculement.** Cette commande prend un schéma déclaratif et en produit un client typé, parfaitement aligné avec les modèles et les relations. À partir de cet instant, le backend ne manipule plus « des objets qui ressemblent à des users » — il manipule des `User`, au sens strict du type.
- **Le typage devient structurel, pas décoratif.** Les types ne sont plus des annotations ajoutées au-dessus du code pour rassurer l’IDE — ils sont générés à partir de la source de vérité, et chaque évolution du schéma les met à jour. Le code compile ou ne compile pas selon ce que la base permet réellement.
- **La cohérence devient une propriété de la chaîne, pas un effort individuel.** Tant que tout le monde consomme les types générés par Prisma, il n’est plus nécessaire de vérifier à chaque couche que les structures correspondent. La fondation étant typée, les couches au-dessus peuvent se concentrer sur ce qu’elles font — capturer une intention, transporter une donnée, sécuriser un accès.

La partie « Données (1) » s’arrête ici : nous savons lire le modèle, et le lire avec des types sûrs. C’est exactement ce dont le site public a besoin.
