> **Précédemment.** `prisma generate` a fait du schéma un client typé : les types viennent du modèle, et une incohérence ne compile plus. Le système est cohérent en lecture.

Le modèle vit dans le code. Reste à l’écrire **correctement** : une opération métier touche souvent plusieurs tables, l’API de Prisma ne sait pas tout exprimer, et le schéma lui-même change au fil des mois. Ce chapitre traite ces trois questions avec le code du projet, puis ouvre sur la suite.

## Écrire de façon cohérente : les transactions

Une opération métier touche souvent plusieurs tables. Enregistrer une discipline, c’est écrire la discipline **et** recalculer les médias qu’elle utilise (la table `PageMediaReference` du chapitre 4, qui empêche de supprimer une image affichée). Si la seconde étape échoue, la première ne doit pas rester à moitié faite : une discipline enregistrée dont les images ne sont pas protégées est un piège pour plus tard.

```ts
// packages/backend/src/modules/disciplines/router.ts (extrait)
      return await ctx.prisma.$transaction(async (tx) => {
        let created;
        try {
          created = await tx.discipline.create({
            data: {
              name: input.name,
              slug: input.slug,
              type: input.type,
              familyId: input.familyId ?? null,
              school: input.school ?? null,
              classification: input.classification ?? null,
              originId: input.originId ?? null,
              description: input.description as Prisma.InputJsonValue,
              summary:
                input.summary === undefined
                  ? undefined
                  : (input.summary as Prisma.InputJsonValue),
              summaryMediaId: input.summaryMediaId ?? null,
              categoryId: input.categoryId,
              instructorId: input.instructorId,
              publicationDate: input.publicationDate ?? null,
            },
          });
        } catch (err) {
          if (
            err instanceof Prisma.PrismaClientKnownRequestError &&
            err.code === "P2002"
          ) {
            const t = err.meta?.target;
            const onSlug = Array.isArray(t)
              ? t.includes("slug")
              : String(t ?? "").includes("slug");
            throw new TRPCError({
              code: "CONFLICT",
              message: onSlug
                ? "Ce slug est déjà utilisé. Choisissez-en un autre."
                : "Une discipline de ce nom existe déjà dans cette catégorie.",
            });
          }
          throw err;
        }

        // UNION des deux composites. `syncPageMediaReferences` recalcule
        // l'ensemble COMPLET des références de la page : ne lui passer que la
        // description ferait passer les images du résumé pour orphelines.
        await syncPageMediaReferences(tx, {
          pageType: "DISCIPLINE",
          pageId: String(created.id),
          newContent: {
            version: 1,
            blocks: [
              ...input.description.blocks,
              ...(input.summary?.blocks ?? []),
            ],
          },
          // L'image de carte vit hors composite : sans cette ligne elle
          // échapperait au recensement et passerait pour orpheline.
          extraMediaIds: input.summaryMediaId ? [input.summaryMediaId] : [],
        });

        return created;
      });
```

Dans la fonction passée à `$transaction`, toutes les requêtes passent par `tx`, et non par `prisma` : elles s’exécutent dans la même transaction PostgreSQL. Si une exception sort de la fonction, PostgreSQL annule l’ensemble : la discipline n’est pas créée.

Deux détails de ce bloc valent d’être lus.

**L’erreur P2002.** Le `catch` qui entoure la création reconnaît une erreur précise de Prisma : `P2002`, une violation de contrainte d’unicité. Le schéma déclare le slug unique (`@unique`) ; plutôt que de vérifier l’unicité avant d’écrire (une vérification qu’une autre requête pourrait rendre fausse entre-temps), le code laisse la base refuser, puis traduit son refus en erreur lisible (`CONFLICT`). C’est la contrainte du schéma qui fait foi, pas le code.

**Le commentaire « UNION des deux composites ».** Une discipline a deux contenus (sa description et sa présentation synthétique) et une image de carte. `syncPageMediaReferences` recalcule la liste **complète** des médias utilisés : lui passer un seul des contenus ferait passer les images de l’autre pour orphelines. Le commentaire explique un bug avant qu’il n’arrive.

<Callout type="warning">
Dans un bloc `$transaction(async (tx) => …)`, on n’utilise que `tx`. Une requête faite par erreur avec `prisma` dans ce bloc s’exécuterait **en dehors** de la transaction, et ne serait pas annulée. Les services appelés depuis une transaction reçoivent `tx` en paramètre (leur signature accepte `PrismaClient | Prisma.TransactionClient`).
</Callout>

## Quand Prisma ne suffit pas : le SQL brut

Prisma couvre l’immense majorité des besoins. Le projet descend en SQL dans deux types de cas, avec `$executeRaw`.

**Une opération que l’API ne sait pas exprimer.** Déplacer un dossier dans le finder, c’est réécrire le début de `fullPath` pour tous les médias qu’il contient. `updateMany` sait donner la même valeur à plusieurs lignes, pas transformer la valeur de chacune :

```ts
// packages/backend/src/modules/storage/adapters/r2/r2StorageAdapter.ts (extrait)
      // Pour les folders : update tous les MediaAssets sous le préfixe.
      // On fait ça en SQL raw pour profiter du UPDATE...SET en une passe
      // (Prisma ne supporte pas REPLACE/SUBSTRING dans updateMany).
      const oldPrefix = `${operation.source.path}/`;
      const newPrefix = `${operation.target.path}/`;
      // Dans un LIKE, « _ » et « % » sont des jokers : un dossier « cours_2026 » correspondrait
      // aussi à « coursX2026 ». On les échappe (ainsi que l'échappement lui-même) pour que le
      // préfixe soit comparé littéralement ; seul le « % » final reste un joker. La barre oblique inverse est le
      // caractère d'échappement par défaut de LIKE dans PostgreSQL.
      const likePrefix = oldPrefix.replace(/[\\%_]/g, "\\$&");
      await prisma.$executeRaw`
        UPDATE "MediaAsset"
        SET "fullPath" = ${newPrefix} || SUBSTRING("fullPath" FROM ${oldPrefix.length + 1}::int)
        WHERE "appRoot" = ${appRoot} AND "fullPath" LIKE ${likePrefix + "%"};
      `;
```

Ce bloc montre aussi que le SQL brut demande plus d’attention que l’API. Dans un `LIKE`, `_` et `%` sont des **jokers** : `_` remplace n’importe quel caractère, `%` n’importe quelle suite. Un dossier nommé `cours_2026`, passé tel quel en préfixe, correspondait aussi à `coursX2026`, et un déplacement pouvait réécrire le chemin de fichiers qui n’étaient pas dans le dossier déplacé. Le préfixe est donc échappé avant d’être donné à `LIKE` : chaque `_`, `%` ou barre oblique inverse est précédé d’une barre oblique inverse, le caractère d’échappement par défaut de PostgreSQL. Seul le `%` ajouté à la fin reste un joker. Avec l’API de Prisma (`startsWith`), cet échappement est fait automatiquement : c’est le prix de la descente en SQL.

**Une écriture qui ne doit pas déclencher `@updatedAt`.** La date de dernière connexion ne doit pas passer pour une modification du profil :

```ts
// packages/backend/src/lib/session/session.server.ts (extrait)

  // Dernière connexion, en SQL direct pour ne pas modifier updatedAt (dernière modification du profil).
  await prisma.$executeRaw`UPDATE "User" SET "lastLoginAt" = NOW() WHERE "id" = ${userId}`.catch((err: unknown) => {
    console.error("[session] lastLoginAt non mis à jour :", err instanceof Error ? err.message : err);
```

Ces deux requêtes ressemblent à des chaînes de caractères, mais ce n’en sont pas. `$executeRaw` est un **gabarit étiqueté** : les valeurs écrites entre `${…}` ne sont pas collées dans le texte SQL, elles sont transmises à PostgreSQL comme des **paramètres**, à part. Un chemin de dossier contenant une apostrophe ou un fragment de SQL ne peut donc rien injecter. La règle qui en découle : ne jamais construire une requête SQL par concaténation, et ne jamais utiliser `$executeRawUnsafe` avec une valeur venue de l’extérieur.

<Callout type="info">
Le SQL brut sort du filet de Prisma : ni le type du résultat ni le nom des colonnes ne sont vérifiés à la compilation. Une colonne renommée dans le schéma casse ces requêtes sans que `pnpm typecheck` le voie. C’est pour cela qu’elles restent rares, courtes, et commentées.
</Callout>

## Faire évoluer la base : les migrations

Le schéma change : une colonne s’ajoute, un modèle se renomme, une table disparaît. Mais la base de production, elle, contient déjà des données. On ne la recrée pas : on la **fait évoluer**.

Une **migration** est un fichier SQL daté, dans `prisma/migrations/<date>_<nom>/migration.sql`. L’ensemble des migrations, appliquées dans l’ordre, reconstruit la base à l’identique. La première, `0_init`, contient l’état de départ ; les suivantes, chacune une évolution. Une table de la base, `_prisma_migrations`, garde la liste de celles déjà appliquées.

<DocsTable columnsJson='["Commande","Où","Effet"]' rowsJson='[["pnpm prisma migrate dev --create-only --name <nom>","machine de développement","Compare le schéma à la base locale et écrit le SQL de la migration, sans l’appliquer."],["pnpm db:migrate (prisma migrate deploy)","développement et production","Applique les migrations pas encore appliquées, dans l’ordre ; n’en crée jamais."]]' />

Le déroulé d’une évolution :

1. modifier `schema.prisma`, avec ses commentaires `///` ;
2. générer la migration (`migrate dev --create-only`), puis **la relire** ;
3. ajouter en tête du fichier un commentaire qui explique l’évolution, comme dans les migrations existantes ;
4. l’appliquer en local (`pnpm db:migrate`), vérifier, enregistrer dans le même commit que le code qui l’utilise ;
5. l’appliquer en production avant que le nouveau code ne tourne.

```sql
-- prisma/migrations/20261207000000_legal_contact/migration.sql (extrait)
-- Coordonnées légales de l'association (Informations légales) : siège, téléphone, e-mail, seules
-- utilisées par les documents à valeur légale. Distinctes des coordonnées publiques.
ALTER TABLE "SiteSettings" ADD COLUMN "legalAddress" TEXT;
ALTER TABLE "SiteSettings" ADD COLUMN "legalPhone" TEXT;
ALTER TABLE "SiteSettings" ADD COLUMN "legalEmail" TEXT;
```

### Relire la migration : l’exemple d’un renommage

L’étape 2 n’est pas une formalité. Prisma écrit le SQL qu’il **croit** juste, en comparant deux états du schéma. Quand un modèle change de nom, il voit un modèle qui disparaît et un autre qui apparaît : sa migration supprime l’ancienne table et crée la nouvelle, vide. Les données sont perdues.

Le renommage des stages en séminaires (`Stage` → `Seminar`) a été écrit à la main, pour cette raison :

```sql
-- prisma/migrations/20261111000000_rename_stage_to_seminar/migration.sql (extrait)
-- Renommage Stage → Seminar (métadonnée pure ; validé en transaction au préalable).
ALTER TABLE "Stage" RENAME TO "Seminar";
ALTER TABLE "StageSession" RENAME TO "SeminarSession";
ALTER TABLE "_StageAnimators" RENAME TO "_SeminarAnimators";
ALTER TABLE "SeminarSession" RENAME COLUMN "stageId" TO "seminarId";
ALTER TABLE "Gallery" RENAME COLUMN "stageId" TO "seminarId";
```

`RENAME TO`, `RENAME COLUMN` : les tables et les colonnes changent de nom, les lignes restent. La suite du fichier renomme aussi les séquences, les contraintes et les index, pour que la base corresponde exactement à ce que Prisma attend du nouveau schéma. Le commentaire de tête dit que l’opération a d’abord été « validée en transaction » : essayée, puis annulée, avant d’être écrite pour de bon.

### Une migration appliquée ne se modifie plus

Prisma enregistre une empreinte de chaque migration appliquée. Modifier un fichier déjà appliqué fait signaler la différence par `migrate dev`, qui propose de réinitialiser la base. On corrige donc par une **nouvelle** migration. Le dossier en garde un exemple, deux migrations à quelques heures d’intervalle :

```sql
-- prisma/migrations/20261101130000_drop_common_repository_label/migration.sql (fichier complet)
DROP TABLE IF EXISTS "CommonRepositoryLabel";
```

La table ajoutée par `20261101120000_add_common_repository_label` n’a pas servi ; plutôt que de réécrire l’histoire, une seconde migration la retire. Les deux restent : sur une base qui n’a vu que la première, la seconde fait le ménage.

`migrate dev` a besoin de créer une base temporaire (la « base fantôme ») pour calculer la différence. Le conteneur PostgreSQL de développement le permet ; l’utilisateur de la base de production, non : on n’y lance donc jamais que `migrate deploy`.

### Quand une migration manque en production

L’étape 5 est celle qui s’oublie, et le projet en a fait l’expérience.

Après une mise à jour, plus personne ne pouvait se connecter au site, et les contenus ne se chargeaient plus. Les journaux du conteneur disaient pourquoi : une colonne `User.birthDateVerified` n’existait pas. Le code venait d’être déployé, le client Prisma avait été généré avec le nouveau schéma, et chaque lecture d’un membre demandait cette colonne… à une base qui n’avait pas reçu la migration `20261209000000_image_consent_online`.

```sql
-- prisma/migrations/20261209000000_image_consent_online/migration.sql (extrait)
-- AlterTable
ALTER TABLE "User" ADD COLUMN     "birthDateVerified" BOOLEAN NOT NULL DEFAULT false,
```

Aucune donnée n’était perdue : la base était simplement en retard d’une migration. `prisma migrate deploy`, lancé contre la base de production, a rétabli le site.

La cause était dans l’outillage. Le Dockerfile prévoit une étape dédiée aux migrations :

```dockerfile
# Dockerfile (extrait)
# ─── Migrateur ────────────────────────────────────────────────────────────
FROM base AS migrator
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY prisma ./prisma
COPY prisma.config.ts package.json ./
CMD ["pnpm", "prisma", "migrate", "deploy"]
```

Mais le `docker-compose.yml` du serveur ne lançait pas de service construit sur cette étape. Les migrations ne s’appliquaient donc qu’à la main, et une mise à jour sans cette étape mettait en ligne un code qui attendait une base plus récente que la vraie. La partie « Infrastructure et déploiement » y reviendra.

<Callout type="warning">
Le code et la base doivent évoluer ensemble. Toute mise à jour qui contient un dossier dans `prisma/migrations/` exige un `prisma migrate deploy` en production **avant** que le nouveau code ne serve des requêtes. Le symptôme d’un oubli est toujours le même : une erreur Prisma qui parle d’une colonne ou d’une table qui « n’existe pas ».
</Callout>
