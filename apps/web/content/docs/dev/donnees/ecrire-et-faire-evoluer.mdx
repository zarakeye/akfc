> **Précédemment.** Le site public est en place : il **lit** le modèle, typé par `prisma generate`, et montre les disciplines, les cours, les stages et les événements du club, derrière un header commun. Il n’écrit encore rien. La partie « Données (1) » avait laissé deux questions en suspens pour ce moment : écrire dans plusieurs tables sans laisser la base à moitié modifiée, et faire évoluer le schéma quand la base contient déjà des données.

Nous reprenons donc le modèle là où nous l’avions laissé. Il vit dans le code ; reste à y écrire **correctement** : une opération métier touche souvent plusieurs tables, l’API de Prisma ne sait pas tout exprimer, et le schéma lui-même change au fil des mois. Ce chapitre traite ces trois questions avec le code du projet, puis ouvre sur la suite.

## Écrire de façon cohérente : les transactions

Une opération métier touche souvent plusieurs tables. Créer une discipline, c’est quatre écritures :

1. fixer le nom de son dossier de fichiers ;
2. écrire la discipline ;
3. recalculer les médias qu’elle utilise (la table `PageMediaReference` du chapitre « Les relations », qui empêche de supprimer une image affichée) ;
4. donner son libellé au dossier dans le finder.

Si une étape échoue, les précédentes ne doivent pas rester à moitié faites : une discipline enregistrée dont les images ne sont pas protégées est un piège pour plus tard.

Dans la fonction passée à `$transaction`, toutes les requêtes passent par `tx`, et non par `prisma` : elles s’exécutent dans la même transaction PostgreSQL. Si une exception sort de la fonction, PostgreSQL annule l’ensemble : la discipline n’est pas créée, et son dossier n’a pas de libellé.

Deux détails de ce bloc valent d’être lus.

**L’erreur P2002.** Le `catch` qui entoure la création reconnaît une erreur précise de Prisma : `P2002`, une violation de contrainte d’unicité. Le schéma déclare le slug unique (`@unique`) ; plutôt que de vérifier l’unicité avant d’écrire (une vérification qu’une autre requête pourrait rendre fausse entre-temps), le code laisse la base refuser, puis traduit son refus en erreur lisible (`CONFLICT`). C’est la contrainte du schéma qui fait foi, pas le code.

<Promesse vers="dev/api/gerer-les-erreurs" section="4) Les codes d’erreur tRPC ne sont pas arbitraires">
Ce code vit dans une **procédure** : une fonction du serveur que le tableau de bord appelle par son nom, et qui reçoit `ctx.prisma`, le client Prisma de la requête. `TRPCError` est la façon dont elle répond « non » ; son `code` (`CONFLICT`, `NOT_FOUND`…) dit à l’interface quel genre de refus c’est.
</Promesse>

**Le commentaire « UNION des deux composites ».** Une discipline a deux contenus (sa description et sa présentation synthétique) et une image de carte. `syncPageMediaReferences` recalcule la liste **complète** des médias utilisés : lui passer un seul des contenus ferait passer les images de l’autre pour orphelines. Le commentaire explique un bug avant qu’il n’arrive.

<Callout type="warning">
Dans un bloc `$transaction(async (tx) => …)`, on n’utilise que `tx`. Une requête faite par erreur avec `prisma` dans ce bloc s’exécuterait **en dehors** de la transaction, et ne serait pas annulée. Les services (les fonctions métier que plusieurs procédures se partagent) appelés depuis une transaction reçoivent `tx` en paramètre (leur signature accepte `PrismaClient | Prisma.TransactionClient`).
</Callout>

## Quand Prisma ne suffit pas : le SQL brut

Prisma couvre l’immense majorité des besoins. Le projet descend en SQL dans deux types de cas, avec `$executeRaw`.

**Une opération que l’API ne sait pas exprimer.** Déplacer un dossier dans le finder, c’est réécrire le début de `fullPath` pour tous les médias qu’il contient (`rewriteAssetPaths`, la seule fonction qui le fait, pour le déplacement comme pour la corbeille). `updateMany` sait donner la même valeur à plusieurs lignes, pas transformer la valeur de chacune :

<Promesse vers="dev/stockage/modifier-sans-casser" section="Déplacer, c’est copier puis supprimer">
Le **finder** est l’explorateur de fichiers du tableau de bord. Chaque fichier y a, en base, son chemin complet (`fullPath`, par exemple `AKFC/courses/tchoy-lee-fut/salut-final.jpg`) : déplacer un dossier oblige à réécrire le début du chemin de tous les fichiers qu’il contient. Seule la requête SQL compte ici ; le déplacement complet, fichiers compris, est raconté avec le stockage.
</Promesse>

Ce bloc montre aussi que le SQL brut demande plus d’attention que l’API. Dans un `LIKE`, `_` et `%` sont des **jokers** : `_` remplace n’importe quel caractère, `%` n’importe quelle suite. Un dossier nommé `cours_2026`, passé tel quel en préfixe, correspondait aussi à `coursX2026`, et un déplacement pouvait réécrire le chemin de fichiers qui n’étaient pas dans le dossier déplacé. Le préfixe est donc échappé avant d’être donné à `LIKE` : chaque `_`, `%` ou barre oblique inverse est précédé d’une barre oblique inverse, le caractère d’échappement par défaut de PostgreSQL. Seul le `%` ajouté à la fin reste un joker. Avec l’API de Prisma (`startsWith`), cet échappement est fait automatiquement : c’est le prix de la descente en SQL.

**Une écriture qui ne doit pas déclencher `@updatedAt`.** Un champ marqué `@updatedAt` dans le schéma est mis à jour par Prisma lui-même, à chaque écriture de la ligne : il dit quand la ligne a changé pour la dernière fois. Or la date de dernière connexion ne doit pas passer pour une modification du profil :

Ces deux requêtes ressemblent à des chaînes de caractères, mais ce n’en sont pas. `$executeRaw` est un **gabarit étiqueté** : les valeurs écrites entre `${…}` ne sont pas collées dans le texte SQL, elles sont transmises à PostgreSQL comme des **paramètres**, à part. Un chemin de dossier contenant une apostrophe ou un fragment de SQL ne peut donc rien **injecter**. Une **injection SQL**, c’est une valeur qui, collée telle quelle dans le texte d’une requête, en change le sens : `'; DROP TABLE "User"; --` termine la chaîne attendue et ajoute un ordre de son cru. La règle qui en découle : ne jamais construire une requête SQL par concaténation, et ne jamais utiliser `$executeRawUnsafe` avec une valeur venue de l’extérieur.

<Callout type="info">
Le SQL brut sort du filet de Prisma : ni le type du résultat ni le nom des colonnes ne sont vérifiés à la compilation. Une colonne renommée dans le schéma casse ces requêtes sans que `pnpm typecheck` le voie. C’est pour cela qu’elles restent rares, courtes, et commentées.
</Callout>

## Faire évoluer la base : les migrations

Le schéma change : une colonne s’ajoute, un modèle se renomme, une table disparaît. Mais la base de production, elle, contient déjà des données. On ne la recrée pas : on la **fait évoluer**.

Une **migration** est un fichier SQL daté, dans `prisma/migrations/<date>_<nom>/migration.sql`. L’ensemble des migrations, appliquées dans l’ordre, reconstruit la base à l’identique. La première, `0_init`, contient l’état de départ ; les suivantes, chacune une évolution. Une table de la base, `_prisma_migrations`, garde la liste de celles déjà appliquées.

<DocsTable columnsJson='["Commande","Où","Effet"]' rowsJson='[["pnpm prisma migrate dev --create-only --name <nom>","machine de développement","Compare le schéma à la base locale et écrit le SQL de la migration, sans l’appliquer."],["pnpm db:migrate (prisma migrate deploy)","développement et production","Applique les migrations pas encore appliquées, dans l’ordre ; n’en crée jamais."]]' />

Le déroulé d’une évolution :

1. modifier `schema.prisma`, avec ses commentaires `///` ;
2. générer la migration (`migrate dev --create-only`), puis **la relire** ;
3. ajouter en tête du fichier un commentaire qui explique l’évolution, comme dans les migrations existantes ;
4. l’appliquer en local (`pnpm db:migrate`), vérifier, enregistrer dans le même commit que le code qui l’utilise ;
5. l’appliquer en production avant que le nouveau code ne tourne.

### Relire la migration : l’exemple d’un renommage

L’étape 2 n’est pas une formalité. Prisma écrit le SQL qu’il **croit** juste, en comparant deux états du schéma. Quand un modèle change de nom, il voit un modèle qui disparaît et un autre qui apparaît : sa migration supprime l’ancienne table et crée la nouvelle, vide. Les données sont perdues.

### Une migration appliquée ne se modifie plus

Prisma enregistre une empreinte de chaque migration appliquée. Modifier un fichier déjà appliqué fait signaler la différence par `migrate dev`, qui propose de réinitialiser la base. On corrige donc par une **nouvelle** migration. Le dossier en garde un exemple, deux migrations à quelques heures d’intervalle :

La table ajoutée par `20261101120000_add_common_repository_label` n’a pas servi ; plutôt que de réécrire l’histoire, une seconde migration la retire. Les deux restent : sur une base qui n’a vu que la première, la seconde fait le ménage.

`migrate dev` a besoin de créer une base temporaire (la « base fantôme ») pour calculer la différence. Le conteneur PostgreSQL de développement le permet ; l’utilisateur de la base de production, non : on n’y lance donc jamais que `migrate deploy`.

### Quand une migration manque en production

L’étape 5 est celle qui s’oublie, et le projet en a fait l’expérience.

Après une mise à jour, plus personne ne pouvait se connecter au site, et les contenus ne se chargeaient plus. Les journaux du conteneur (ce que le site écrit pendant qu’il tourne : démarrages, erreurs) disaient pourquoi : une colonne `User.birthDateVerified` n’existait pas. Le code venait d’être déployé, le client Prisma avait été généré avec le nouveau schéma, et chaque lecture d’un membre demandait cette colonne… à une base qui n’avait pas reçu la migration `20261209000000_image_consent_online`.

Mais le `docker-compose.yml` du serveur, le fichier qui décrit les conteneurs à lancer et dans quel ordre, ne lançait pas de service construit sur cette étape. Les migrations ne s’appliquaient donc qu’à la main, et une mise à jour sans cette étape mettait en ligne un code qui attendait une base plus récente que la vraie. Le compose du serveur a depuis un service `akfc-migrator`, lancé avant le site à chaque déploiement.

<Promesse vers="dev/infrastructure/mettre-en-production" section="L’ordre d’un déploiement 🚀">
Un déploiement met en ligne une nouvelle version du site. Sur le serveur, il suit désormais un ordre fixe : construire l’image, appliquer les migrations, puis seulement remplacer le site qui tourne.
</Promesse>

<Callout type="warning">
Le code et la base doivent évoluer ensemble. Toute mise à jour qui contient un dossier dans `prisma/migrations/` exige un `prisma migrate deploy` en production **avant** que le nouveau code ne serve des requêtes. Le symptôme d’un oubli est toujours le même : une erreur Prisma qui parle d’une colonne ou d’une table qui « n’existe pas ».
</Callout>

## Et maintenant : faire entrer l’utilisateur dans le système

La donnée est modélisée, les relations sont structurées, le typage est généré, et le serveur sait lire et écrire de façon cohérente. Il manque une chose : rien de tout cela ne sert tant qu’un utilisateur ne peut pas agir sur ce modèle. Comment crée-t-il un compte, modifie-t-il ses informations, envoie-t-il une intention au serveur ? Et comment s’assurer que cette intention respecte le modèle ?

C’est le rôle des formulaires, et beaucoup de projets se trompent en les traitant comme une simple couche d’interface. Un formulaire est le point de contact entre l’intention humaine et la structure du système. Il ne part pas de zéro : il reprend les contraintes du modèle dans des schémas de validation partagés par le navigateur et le serveur, et produit des données que le serveur peut écrire sans les retraduire, sous la garde des types générés par Prisma. Sans ce socle, chaque formulaire devient un cas particulier, avec ses champs définis à la main, ses validations bricolées et ses types approximatifs ; avec lui, le frontend et le backend parlent déjà le même langage.

<Callout type="info">
Un bon formulaire ne « collecte » pas des données : il traduit une intention en une structure conforme au modèle, et ce modèle vient de Prisma.
</Callout>

Viendra ensuite le transport : faire circuler une structure typée du formulaire au serveur, sans perte de cohérence ni types redéfinis. C’est le rôle de tRPC, mais tRPC n’est pas un point de départ. Commencé avant le modèle, les relations et le typage, il ferait circuler des types sans qu’on sache d’où ils viennent : une architecture « magique ». La suite du parcours suit donc l’ordre du modèle : les formulaires pour capturer l’intention, tRPC pour transporter la donnée, l’authentification pour sécuriser les accès.
