## Pourquoi tout commence par le modèle

Quand on découvre une stack moderne, on a souvent envie d’aller vite.  
De voir quelque chose s’afficher. De faire répondre une route. De connecter rapidement le frontend au backend, et sentir que “ça marche”.

On pense immédiatement à construire une API, afficher des données, créer des formulaires, connecter le frontend au backend. C’est compréhensible. Mais dans un projet structuré, cette approche est une erreur, parce qu’elle saute une étape fondamentale : la définition du modèle de données.

Une application ne commence pas par des routes. Elle ne commence pas non plus par une interface. Elle commence par une question beaucoup plus simple, mais beaucoup plus structurante : **qu’est-ce que notre système manipule réellement ?**

Dans ce projet, cela signifie des membres, des groupes, des sessions, des disciplines, des cours, des stages, des documents — et surtout des relations entre toutes ces entités. Ces éléments existent déjà, quelque part : dans la base de données. Mais à ce stade, ils ne sont encore que des tables. Ils sont stockés, ils sont reliés… mais ils ne sont pas encore compréhensibles par le reste de l’application.

C’est précisément ici que Prisma entre en jeu.

Prisma ne sert pas uniquement à interroger la base. Il joue un rôle beaucoup plus structurant : il transforme la base de données en un modèle typé exploitable côté TypeScript. Autrement dit, il fait passer le système d’un état où la donnée est brute, où les relations sont implicites, et où le backend doit “deviner” la structure… à un état où les entités sont explicites, les relations modélisées, et les types réellement présents dans le code.

Ce moment est un point de bascule.

Parce que c’est ici que la donnée cesse d’être simplement stockée, et devient un langage partagé entre toutes les couches de l’application.

Sans cette étape, le backend bricole ses types, le frontend redéfinit des structures, les incohérences apparaissent — et la duplication s’installe. Pas immédiatement. Pas de façon spectaculaire. Mais progressivement, à chaque évolution du modèle.

Avec Prisma, le modèle est centralisé, les types sont générés, et la cohérence devient structurelle.

<Callout type="info">
Dans ce projet, Prisma n’est pas un simple ORM.

👉 c’est la source de vérité du modèle de données côté TypeScript

Tout ce qui suit — formulaires, tRPC, authentification — s’appuie sur ce socle.
</Callout>

## Avant de commencer : les mots de cette partie

Cette partie parle de base de données dès sa première page, et les mêmes mots reviennent dans chaque chapitre. Nous les fixons ici, une fois pour toutes, chacun avec un exemple du projet. Les chapitres suivants s’appuieront sur ces définitions sans les répéter.

### La base, la table, la ligne

- Une **base de données** est le programme qui garde les données du site et sait les retrouver vite. Dans le projet, c’est **PostgreSQL** : un conteneur Docker sur la machine du développeur, un autre sur le serveur du club. Le site lui parle par le réseau, avec des **requêtes** écrites en **SQL**, le langage des bases relationnelles : `SELECT` lit, `INSERT` ajoute, `UPDATE` modifie, `DELETE` supprime.
- Une base **relationnelle** range ses données en **tables**, une par sorte de chose : `User` pour les membres, `Course` pour les créneaux de cours. Chaque élément est une **ligne** de sa table (un membre, un créneau) ; chaque information d’une ligne est une **colonne**, ou **champ** (`email`, `beginTime`). Toutes les lignes d’une table ont les mêmes colonnes.
- Une colonne a un **type** (texte, entier, date, booléen vrai ou faux, JSON) et elle est **obligatoire** ou **nullable** : `null` veut dire « pas de valeur ».

### Identifier et relier

- La **clé primaire** identifie une ligne, de façon unique et définitive : c’est la colonne `id`, marquée `@id`. Dans le projet, c’est souvent un **cuid** (une chaîne générée, comme `clx3f…`), parfois un entier qui s’incrémente.
- Une **relation** relie deux tables. La ligne d’un créneau ne recopie pas sa discipline : elle garde l’identifiant de celle-ci dans `disciplineId`, une **clé étrangère**, qui pointe vers une ligne de `Discipline`. La base refuse une clé étrangère qui ne pointe vers rien.
- Une relation est **un-à-plusieurs** (*one-to-many* : une discipline a plusieurs créneaux, un créneau n’a qu’une discipline) ou **plusieurs-à-plusieurs** (*many-to-many* : un membre est dans plusieurs groupes, un groupe réunit plusieurs membres). La seconde passe par une table intermédiaire, la **table de jointure**, dont chaque ligne relie une ligne de chaque côté.
- Une **contrainte d’unicité** (`@unique`) interdit que deux lignes aient la même valeur dans une colonne : deux comptes ne peuvent pas avoir la même adresse. C’est la base qui la vérifie, quel que soit le code qui écrit.
- Un **index** (`@@index([status])`) est une table de recherche que la base tient à jour pour retrouver vite les lignes d’après une colonne. Il ne change pas les données, seulement la vitesse des lectures.
- Une **énumération** (`enum Day { MONDAY … SUNDAY }`) est un type qui n’accepte qu’une liste fermée de valeurs.
- Une **jointure** lit plusieurs tables liées en une seule requête : un créneau **avec** sa discipline.

### Prisma, et ce qu’il ajoute

- Un **ORM** (*Object-Relational Mapping*) fait correspondre les tables à des objets du langage : au lieu d’écrire du SQL, le code écrit `prisma.course.findMany({ where: … })`, et l’ORM fabrique la requête. **Prisma** est l’ORM du projet.
- Le **schéma** (`prisma/schema.prisma`) décrit toutes les tables dans le langage de Prisma. Un **modèle** (`model Course { … }`) y décrit une table.
- Le **client généré** est le code TypeScript que Prisma produit à partir du schéma : les fonctions pour lire et écrire, et les types qui vont avec.
- Le **seed** (« la semence ») est un script qui remplit une base vide avec des données de démonstration.
- Une **migration** est un fichier SQL qui fait passer la base d’une version du schéma à la suivante (ajouter une colonne, renommer une table). Une **transaction** regroupe plusieurs écritures en une seule : soit elles réussissent toutes, soit la base les annule toutes.

### 1.1 — Pourquoi Prisma est installé à la racine

Dans ce projet, le dossier `prisma/` vit à la racine du workspace. Ce choix est loin d’être anodin. Il signifie que le schéma de données n’appartient pas à une seule application, ni à un seul package technique. Il appartient au système dans son ensemble.

Ce placement raconte déjà quelque chose d’important.

Le modèle de données n’est pas caché dans `apps/web`, parce qu’il ne concerne pas seulement l’interface.  
Il n’est pas non plus enfoui dans `packages/backend`, même si le backend est celui qui consomme directement le client Prisma.

👉 Il est placé à la racine parce qu’il représente une couche plus fondamentale.

Une couche sur laquelle toutes les autres vont venir s’appuyer.

### 1.5 — Le client Prisma : brancher le schéma au backend réel

Une fois Prisma installé et configuré, encore faut-il éviter un piège très classique : créer le client n’importe où, n’importe comment. Dans une application qui recharge souvent en développement, ou dans un backend structuré en plusieurs modules, ce genre d’improvisation finit vite par produire de l’instabilité.

Dans ce projet, le client Prisma est centralisé dans `packages/backend/src/prisma.ts`.

Pourquoi tant de soin pour une seule ligne de création ? Parce que chaque `PrismaClient` ouvre son propre **pool de connexions** à PostgreSQL : un petit groupe de connexions gardées ouvertes et réutilisées d'une requête à l'autre. En développement, le rechargement à chaud de Next.js réévalue les modules à chaque modification de fichier. Sans ce rangement dans `globalThis`, chaque sauvegarde ouvrirait un nouveau pool, sans fermer l'ancien, jusqu'à épuiser les connexions que PostgreSQL accepte. En production, le module n'est évalué qu'une fois : la dernière ligne n'y sert à rien, et elle est donc limitée au développement.

Une seconde précaution vit ailleurs : `@prisma/client` est déclaré comme paquet externe au bundle serveur, dans `next.config.ts`, pour que tout le code du serveur partage le même module. Le chapitre « Next.js et next.config.ts » l'explique.

Là encore, le point n’est pas seulement technique. Il est architectural. Centraliser le client Prisma, c’est reconnaître que l’accès aux données est une dépendance transversale du backend. Cela évite que chaque module s’organise dans son coin et renforce l’idée que Prisma n’est pas une petite dépendance utilitaire, mais une colonne vertébrale technique.
