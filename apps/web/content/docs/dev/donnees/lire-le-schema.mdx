> **Précédemment.** Prisma vit à la racine du monorepo, configuré par `prisma.config.ts`, et le backend n’a qu’un client. Nous savons où vit la donnée et par quoi elle est décrite.

## 2 — Un fichier qui décrit un système

Nous avons installé Prisma et vu où il s’insère dans le monorepo. Le vrai point d’entrée de Prisma n’est pourtant pas une commande : c’est le fichier `schema.prisma`, et il mérite d’être lu avec plus de soin que ne le font la plupart des tutoriels.

### 2.1 — Un changement de perspective : on ne lit pas un fichier, on lit un système

À la première ouverture, on est tenté de lire `schema.prisma` comme une liste de modèles : un `User`, une `Session`, un `MemberGroup`, quelques relations. Cette lecture montre vite ses limites, parce que le fichier n’est pas une collection de tables : c’est une **description complète du système métier**.

Chaque modèle représente une entité réelle du domaine, chaque champ porte une contrainte, chaque relation impose une manière de structurer la donnée. Sans s’en rendre compte, on lit déjà l’architecture du système : lire le schéma, c’est comprendre l’application avant d’avoir vu une seule route.

<Callout type="info">
Un bon schéma Prisma se lit comme un diagramme de domaine, pas comme un fichier technique.
</Callout>

### 2.2 — Les blocs fondamentaux du schéma

Avant d’entrer dans les modèles, regardons la structure globale du fichier, non pour la mémoriser, mais pour voir ce qu’elle sépare. Un `schema.prisma` contient trois sortes de blocs, qui distinguent trois responsabilités :

- le `datasource` : **le lien au réel** (la base de données) ;
- le `generator` : **la transformation en code** (le client généré) ;
- les `model` : **la description du système**.

/>

Trois réglages du `generator` méritent un mot, parce qu’ils ne sont pas ceux d’un projet minimal :

- `previewFeatures = ["relationJoins"]` active une fonction encore marquée « en aperçu » par Prisma : quand une requête demande une entité **avec** ses relations, Prisma la lit en une seule requête SQL, par une jointure, au lieu d’enchaîner plusieurs requêtes. Le chapitre 5 en montre un usage ;
- `engineType = "binary"` et `binaryTargets = ["native"]` décident de la façon dont Prisma exécute les requêtes : un petit programme séparé (le « moteur »), compilé pour la machine qui génère le client. Le client est généré **dans** l’image Docker (l’étape `pnpm prisma generate` du Dockerfile), donc pour la machine qui l’exécutera.

Le `datasource`, lui, lit l’adresse de la base dans la variable `DATABASE_URL`, comme `prisma.config.ts`. Le schéma ne contient jamais l’adresse elle-même : seulement le nom de la variable qui la porte.

### 2.3 — Le datasource : connecter le modèle au réel

Le bloc `datasource` indique à Prisma où se trouve la base, et surtout il relie le modèle à quelque chose de concret. Dans notre projet, c’est PostgreSQL, avec une adresse injectée par l’environnement. Prisma ne simule pas de base : les contraintes sont appliquées par une vraie base relationnelle, et les relations ne sont pas imitées par le code.

### 2.4 — Le generator : là où le modèle devient exploitable

Le bloc `generator` passe souvent inaperçu ; c’est pourtant là que se joue l’essentiel. Il demande à Prisma de produire, à partir du schéma, un client TypeScript qui connaît les entités, leurs relations et leurs contraintes, et qui expose tout cela sous forme de types. C’est ici que la promesse d’un code typé de bout en bout prend forme.

<Callout type="info">
Sans generator, Prisma resterait un DSL de base de données : un petit langage dédié (*domain-specific language*), qui décrit des tables et rien d’autre. Avec lui, il devient la source des types de tout le backend.
</Callout>

### 2.5 — Les modèles : là où le système prend forme

Un modèle Prisma ressemble à une table, mais il en dit bien plus. Prenons un modèle réel et court, celui d’une session de connexion :

<CodeExample
  language="prisma"
  filepath="prisma/schema.prisma"
  filename="schema.prisma"
  snippetStart="/// Session de connexion, stockée en base."
  snippetEnd="(fin du bloc)"
  snippetHighlight="7,9,14,16"
  snippetTitle="Le modèle Session"
  fullFileTitle="Voir le fichier complet"
/>

Ce bloc court contient déjà une part du système :

- une identité (`id`) ;
- une contrainte (`expiresAt` est obligatoire : une session sans fin de validité n’existe pas) ;
- une relation (`userId`) ;
- un lien explicite (`user`), avec ce qui se passe quand le membre est supprimé (`onDelete: Cascade`).

Ce n’est pas seulement une structure : c’est une décision d’architecture.

#### 🔎 Dans le projet : un schéma qui se commente lui-même

Le schéma du projet décrit la base entière : une cinquantaine de modèles et une vingtaine d’énumérations, rangés en sections (`USER & AUTH`, domaine du club, contenus, médias…). Pour comprendre une fonctionnalité, on commence par lire ses modèles : la plupart des règles métier y sont déjà visibles.

Une convention le rend lisible : chaque modèle et chaque champ porte un commentaire `///`, en français, qui dit ce qu’il représente et ce qui se passe quand on le supprime. Ces commentaires ne sont pas perdus pour le code : l’éditeur les affiche au survol d’un champ, et dans l’autocomplétion.

Ce commentaire contient déjà une bonne partie des chapitres suivants : comment un membre est créé, ce qui fait de lui un instructeur ou un administrateur (une appartenance à un groupe, jamais un champ du membre), et ce que sa suppression bloque, efface ou détache. D’autres commentaires signalent ce qui est inutilisé ou fragile (« ⚠ Inutilisé », « Candidat à suppression ») : le schéma dit la vérité sur l’état du code, y compris ses dettes.

#### 🔎 Lire un modèle du projet : `MediaAsset`

Pour s’entraîner sur un modèle plus fourni, prenons celui qui décrit un fichier de la médiathèque. Voici sa forme, sans ses commentaires ni ses champs secondaires :

  title="Un modèle réel, réduit à sa structure"

  codeJson='"model MediaAsset {\n  id               String   @id @default(cuid())\n  fullPath         String   @unique\n  mimeType         String\n  originalFileName String\n  displayName      String?\n  bytes            Int\n  appRoot          String\n  status           String\n  categoryId       Int?\n  disciplineId     Int?\n  uploaderUserId   String?\n  createdAt        DateTime @default(now())\n  updatedAt        DateTime @updatedAt\n\n  category       Category?            @relation(fields: [categoryId], references: [id])\n  discipline     Discipline?          @relation(fields: [disciplineId], references: [id])\n  uploader       User?                @relation(\"UserMediaUploads\", fields: [uploaderUserId], references: [id], onDelete: SetNull)\n  pageReferences PageMediaReference[]\n  galleryItems   GalleryItem[]\n  memberDocument MemberDocument?\n\n  @@index([status])\n}"'
/>

<DocsTable columnsJson='["Élément","Ce qu’il dit"]' rowsJson='[["@id @default(cuid())","Identifiant texte généré, impossible à deviner. Les entités éditoriales simples (Discipline, Category) utilisent plutôt un entier autoincrémenté."],["fullPath @unique","Deux lignes ne peuvent pas désigner la même clé de stockage ; c’est sur ce champ que s’appuient les upsert (une seule requête qui crée la ligne si elle n’existe pas, et la met à jour sinon)."],["displayName String?","Le ? rend le champ facultatif (NULL en base, null en TypeScript)."],["@updatedAt","Prisma tient la date à jour à chaque modification."],["@relation(fields, references)","La clé étrangère et le champ qu’elle vise ; le champ de relation (category) n’existe pas en base, il sert aux requêtes."],["MediaAsset? / MediaAsset[]","Le côté opposé d’une relation : 0 ou 1, ou une liste."],["@@index([status])","Un index pour les filtres fréquents par statut."]]' />

`uploaderUserId` est facultatif, et la relation `uploader` porte `onDelete: SetNull` : c’est ce qui permet au commentaire de `User` d’annoncer qu’un média reste quand son téléverseur est supprimé. Le schéma ne se contente pas de dire une règle, il la fait respecter par la base.

`status` est un `String`, pas une énumération : les valeurs autorisées (`pending`, `published`) sont garanties par le code (les schémas Zod des procédures), et le commentaire du champ le dit. Une énumération Prisma est préférée quand l’ensemble des valeurs est stable ; ici, il a évolué plusieurs fois.

<Promesse vers="dev/api/valider-l-entree" section="Où vit la validation ?">
Un **schéma Zod** décrit la forme qu’une donnée doit avoir (« une chaîne parmi `pending` et `published` »), et la vérifie au moment où elle arrive, avant toute écriture. Une **procédure** est une fonction du serveur que le navigateur appelle par son nom. Il suffit ici de savoir que la règle existe, et qu’elle vit dans le code plutôt que dans la base.
</Promesse>

### 2.6 — Les relations : là où tout est déjà en place

On prend souvent les relations pour un détail technique ; ce sont elles qui en racontent le plus. Dans notre projet, les liens entre `User`, `Session`, `MemberGroup` et `MemberGroupMembership` définissent déjà l’authentification, les droits sur les espaces de groupe et qui est administrateur. Avant même d’avoir écrit une route, la logique de sécurité du système est visible.

<Callout type="info">
Pour comprendre un système, regardez ses relations avant ses routes.
</Callout>

### 2.7 — Ce que Prisma génère réellement

Une fois le schéma écrit, Prisma génère un « client ». Le mot est trompeur : il ne produit pas seulement des fonctions, mais une projection complète du modèle dans le code. Par exemple :

<CodeSnippet
  language="ts"
  title="Requête Prisma typée automatiquement"
  filename="users.service.ts"
  kind="pattern"
  codeJson='"const user = await prisma.user.findUnique({\n  where: { id: \"cm1…\" },\n  include: {\n    memberGroupMemberships: { include: { group: true } },\n  },\n})"'
/>

Dans cet appel, `user` est typé, chaque adhésion et le groupe qu’elle désigne le sont aussi, et la structure entière suit le schéma. Aucun type n’est écrit à la main, rien n’est dupliqué : le type vient du modèle.

C’est pour cela que cette partie vient avant les autres. Quand nous arriverons à tRPC, aux formulaires ou à l’authentification, nous verrons des types circuler partout ; sans ce chapitre, tRPC semblerait magique, et les formulaires comme l’authentification sembleraient indépendants du reste. En réalité, tout repose sur ce modèle.

## Ce que nous venons de construire dans le Mouvement 1

Nous avons posé le cadre. Trois idées en sont ressorties :

- **Prisma a une place, et cette place compte.** Installer Prisma à la racine du monorepo, avec une configuration dédiée, ce n’est pas un détail d’outillage : c’est déclarer que le modèle de données est partagé par toutes les couches du projet, et pas seulement possédé par le backend.
- **Le `schema.prisma` n’est pas un fichier de configuration.** C’est une carte du système, dont chaque bloc a une fonction précise : le datasource relie au réel, le generator produit les types, les modèles donnent forme aux entités, les relations dessinent les chemins entre elles.
- **La cohérence part de la donnée, pas de l’API.** Tant que le modèle n’est pas explicite, le reste du projet doit bricoler des types. Une fois qu’il l’est, le typage devient structurel, et tout ce qui suit peut s’appuyer dessus sans redéfinition.

Lire la carte n’est pas encore lire le terrain. Le Mouvement 2 descend dans les modèles réels du projet (`User`, `Session`, `MemberGroup`, `MemberGroupMembership`) pour les lire comme une architecture, pas comme une liste d’entités.
