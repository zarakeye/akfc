> **Précédemment.** Une page est rendue sur le serveur : tous ses fichiers résolus en une requête, une URL publique pour chacun, des blocs qui lisent une table préparée. La route publique ne sert pourtant un fichier que s’il est placé.

## Les parcours du chapitre

Trois parcours traversent ce chapitre : l’enregistrement d’une page, qui recense ses fichiers ; le visiteur qui charge une image ; l’administrateur qui range la bibliothèque et se heurte au recensement.

## Pourquoi recenser 📋

Un contenu ne désigne ses fichiers que par leur identifiant, rangé quelque part dans un JSON. Pour savoir si un fichier est utilisé, il faudrait relire tous les contenus de toutes les entités et fouiller chaque bloc, chaque document de texte. Trois questions posent pourtant cette question à tout moment :

<DocsTable columnsJson='["Question", "Qui la pose", "À quel moment"]' rowsJson='[["Ce fichier peut-il être servi à un visiteur ?", "La route publique", "À chaque image chargée par un visiteur."], ["Ce fichier peut-il être jeté ?", "La corbeille", "Quand un administrateur range la bibliothèque."], ["Ce fichier peut-il repasser en attente ?", "Le changement de statut", "Idem."]]' />

La réponse est donc **précalculée** : une table relie chaque fichier à chaque contenu qui l’affiche.

```prisma
// prisma/schema.prisma (extrait)
model PageMediaReference {
  /// Identifiant CUID.
  id           String             @id @default(cuid())
  /// Fichier référencé.
  mediaAssetId String
  /// Type de contenu qui utilise le fichier (voir PageReferencerKind).
  pageType     PageReferencerKind
  /// Identifiant du contenu, en texte (les identifiants numériques sont
  /// …
  pageId       String
  // …
  mediaAsset   MediaAsset         @relation(fields: [mediaAssetId], references: [id], onDelete: Restrict)
```

Une ligne par fichier et par contenu. `pageType` dit **quelle colonne** (chapitre 1 : `SITE_PAGE`, `POST`, `DISCIPLINE`, `INSTRUCTOR_BIO`…), `pageId` **quelle ligne** — en texte, parce que certains contenus ont un identifiant numérique, d’autres un slug, d’autres un cuid. La relation vers le fichier est en `onDelete: Restrict` : la base refuse de supprimer un fichier encore recensé (partie « Données »).

Une table précalculée n’est utile que si elle est **juste**. Deux conditions : savoir extraire, sans en oublier, les fichiers d’un contenu ; et tenir la table à jour à chaque enregistrement, sans fenêtre où elle ment.

Si l’on ajoute un septième bloc au contrat sans écrire son `case`, ce bloc arrive dans le `default` avec son type, qui n’est pas `never` : **la compilation échoue**, avec le nom du bloc oublié. <DocsTable columnsJson='["Si…", "Alors…"]' rowsJson='[["Le contenu est écrit, puis le recensement échoue", "La page montre un fichier que la base croit libre : la route publique le refuse aux visiteurs, et la corbeille accepte de le jeter."], ["Le recensement est écrit, puis le contenu échoue", "La base croit affiché un fichier qui ne l’est pas : il ne peut plus être jeté, et il est servi au public sans raison."]]' />

Dans la transaction, les deux écritures réussissent ensemble ou échouent ensemble. Et la validation (« seulement des fichiers validés ») protège l’autre sens : on ne publie pas, en le posant dans une page, un fichier qu’un administrateur n’a pas validé.

<Callout type="warning">
Une procédure qui enregistre un contenu sans appeler `syncPageMediaReferences` ne provoque **aucune** erreur. Ses images s’affichent dans l’éditeur (route privée), et sont absentes pour les visiteurs. C’est arrivé avec la présentation courte des disciplines : la seule défense est de relire chaque procédure qui écrit une colonne de contenu.
</Callout>

Pour les contenus enregistrés avant l’existence d’une synchronisation, un **rattrapage** au démarrage du serveur recalcule les lignes ; il est idempotent, puisqu’une différence recalculée sur un état juste est vide. Celui des présentations d’instructeur applique en plus les règles du chapitre suivant.

## Ce qui s’appuie sur le recensement

**La route publique.** Un fichier n’est servi à un visiteur que s’il est validé, hors corbeille, et placé dans quelque chose de public : une galerie publique, ou un contenu recensé **et publié** :

C’est ce qui empêche un visiteur de charger un fichier validé mais jamais publié dans une page (une photo de groupe rangée pour plus tard). Un recensement seul ne suffit pas : un brouillon recense ses fichiers dès son premier enregistrement, et ils étaient servis à qui connaissait leur URL alors que la page répondait 404. `isPubliclyPlaced` parcourt donc les lignes de recensement du fichier et demande, pour chacune, si son contenu est publié :

Le `switch` est exhaustif sur `PageReferencerKind`, comme l’extraction l’est sur les blocs : un nouveau type de contenu recensé ne compile pas tant qu’on n’a pas dit ce que « publié » veut dire pour lui. Un cours n’a pas de date : il est publié avec sa discipline. Une page éditoriale (association, contacts, inscription) a son interrupteur ; une autre page de contenu (`/infos/…`, compléments des pages légales) n’en a pas et est publique.

L’administrateur lit par exemple « POST #42, galerie « Stage d’été » » : il sait quoi retirer d’abord. Une page ne perd jamais une image parce que quelqu’un a rangé la bibliothèque.

**Le changement de statut.** Repasser en attente un fichier affiché est refusé de la même façon (`assertStatusChangeDoesntUnpublishReferencedAssets`, partie « Stockage et médias ») : un fichier affiché ne devient pas, à l’insu de la page, un fichier que plus personne ne peut voir.

**La suppression.** La relation `onDelete: Restrict` fait refuser par la base elle-même la suppression d’un fichier recensé. C’est le dernier filet, si une procédure oubliait la vérification.

## À suivre

Jusqu’ici, un contenu est écrit par un administrateur, qui peut tout publier. La présentation d’un instructeur est différente : c’est le membre lui-même qui l’écrit, et ce qu’il y pose devient public. Le recensement, qui rend un fichier servi, devient alors une question de droits.
