> **Précédemment.** Tous les contenus du site sont une liste de blocs dans une enveloppe versionnée, décrite par un schéma Zod partagé. Le schéma refuse à l’entrée et répare à la lecture ; un bloc y désigne un fichier par son identifiant.

## Les parcours du chapitre

Deux parcours traversent ce chapitre : l’administrateur qui enregistre une page, le visiteur qui la lit. Chaque onglet en déroule les étapes relevées dans le code ; chaque étape mène à son explication plus bas.

## Un document dans le document

Le bloc `tiptap`, et la partie texte des blocs média-texte et texte enrobant, contiennent un **document ProseMirror**. ProseMirror est le moteur d’édition sur lequel est construit Tiptap, l’éditeur du projet. Il ne manipule pas du HTML, mais un arbre de **nœuds** typés :

<CodeSnippet
  language="json"
  title="Un document ProseMirror, tel qu’il est enregistré"
  codeJson='"{\n  \"type\": \"doc\",\n  \"content\": [\n    {\n      \"type\": \"heading\",\n      \"attrs\": { \"level\": 2 },\n      \"content\": [{ \"type\": \"text\", \"text\": \"Horaires\" }]\n    },\n    {\n      \"type\": \"paragraph\",\n      \"attrs\": { \"textAlign\": \"left\" },\n      \"content\": [\n        { \"type\": \"text\", \"text\": \"Cours le \" },\n        { \"type\": \"text\", \"text\": \"mardi\", \"marks\": [{ \"type\": \"bold\" }] },\n        { \"type\": \"text\", \"text\": \", voir le \" },\n        {\n          \"type\": \"text\",\n          \"text\": \"planning\",\n          \"marks\": [{ \"type\": \"link\", \"attrs\": { \"href\": \"/agenda\" } }]\n        }\n      ]\n    },\n    { \"type\": \"library-image\", \"attrs\": { \"mediaId\": \"cm9x…\", \"caption\": \"Le dojo\" } }\n  ]\n}"'
/>

Trois notions suffisent à le lire.

<DocsTable columnsJson='["Notion", "Ce que c’est", "Dans l’exemple"]' rowsJson='[["Nœud (node)", "Un élément de structure, qui peut en contenir d’autres (content).", "doc, heading, paragraph, text, library-image"], ["Marque (mark)", "Une mise en forme posée sur un morceau de texte, sans le découper en sous-nœuds.", "bold, link"], ["Attributs (attrs)", "Les propriétés d’un nœud ou d’une marque.", "level: 2, textAlign, href, mediaId"]]' />

C’est ce document qui est enregistré dans la colonne JSON, à l’intérieur du bloc. L’image de la bibliothèque y est un nœud `library-image` qui ne porte qu’un identifiant : l’URL viendra au rendu, comme pour les autres blocs.

## Du JSON au HTML

Pour afficher le document, le rendu le transforme en HTML avec `generateHTML`, une fonction de Tiptap. Chaque **extension** de l’éditeur (titre, paragraphe, lien, surlignage…) décrit comment son nœud ou sa marque s’écrit en HTML, dans une méthode `renderHTML`. `generateHTML` parcourt l’arbre et appelle, pour chaque élément, la méthode de son extension :

<CodeSnippet
  language="html"
  title="Le même document, en HTML"
  codeJson='"<h2>Horaires</h2>\n<p style=\"text-align: left\">Cours le <strong>mardi</strong>, voir le\n  <a href=\"/agenda\" rel=\"noopener noreferrer nofollow\">planning</a></p>\n<figure class=\"tiptap-library-image\"><img src=\"/api/media/public/r2/AKFC/…\" alt=\"Le dojo\" …><figcaption>Le dojo</figcaption></figure>"'
/>

Ce HTML est ensuite inséré dans la page par `dangerouslySetInnerHTML` :

D’ordinaire, React échappe tout ce qu’il affiche : une chaîne qui contient `<script>` s’affiche comme du texte. `dangerouslySetInnerHTML` désactive cette protection. Son nom est un avertissement : ce qu’on lui passe **doit** être sûr, parce que personne d’autre ne le vérifiera.

Le texte, lui, est sûr : les `renderHTML` de Tiptap ne fabriquent pas de chaîne HTML à la main, ils décrivent des éléments et des attributs que la bibliothèque écrit en échappant chaque valeur. Un texte `<script>` devient `&lt;script&gt;`. La question est ailleurs : dans les **attributs**.

## Ce que generateHTML recopie sans vérifier ⚠️

Quand on colle du HTML dans l’éditeur, chaque extension le relit avec des règles (`parseHTML`) qui écartent ce qu’elle ne reconnaît pas. Mais `generateHTML` part du **JSON** : les règles de lecture ne sont jamais appliquées. Ce que le JSON contient, l’extension le recopie.

Or le JSON n’est pas forcément produit par l’éditeur. Une procédure tRPC reçoit une requête HTTP, et une requête se fabrique sans navigateur. Voici un paragraphe qu’aucun éditeur ne produit, mais qu’une requête peut envoyer :

<CodeSnippet
  language="json"
  title="Un paragraphe fabriqué à la main"
  codeJson='"{\n  \"type\": \"paragraph\",\n  \"attrs\": { \"textAlign\": \"left; position: fixed; inset: 0; z-index: 99; background: url(https://ailleurs.example/faux.png)\" },\n  \"content\": [\n    {\n      \"type\": \"text\",\n      \"text\": \"Mettre à jour vos coordonnées\",\n      \"marks\": [{ \"type\": \"link\", \"attrs\": { \"href\": \"javascript:fetch(\u0027/api/…\u0027)\" } }]\n    }\n  ]\n}"'
/>

Trois effets, tous réels avant ce chapitre :

<DocsTable columnsJson='["Ce qui est envoyé", "Ce que le rendu en faisait", "Conséquence"]' rowsJson='[["textAlign avec du CSS à la suite", "L’extension d’alignement écrit style=\"text-align: …\" en recopiant la valeur.", "Le paragraphe recouvre toute la page (position: fixed), avec une image prise ailleurs : un faux écran du club."], ["La couleur d’un surlignage", "Recopiée de la même façon dans un style.", "Le même recouvrement, par un autre attribut."], ["Un lien javascript:", "Le lien est écrit tel quel.", "Un clic exécute du script sur le domaine du club, avec la session du visiteur."], ["Un type de nœud inconnu", "generateHTML lève une exception.", "La page entière tombe en erreur, pas seulement le bloc."]]' />

L’éditeur ne produit aucun de ces documents, et une page n’est écrite que par un administrateur. Mais la présentation d’un instructeur est écrite par un **membre** (chapitre 6), et « l’éditeur ne le produit pas » n’est pas une protection : le serveur reçoit ce qu’on lui envoie, pas ce que l’éditeur aurait envoyé.

<Callout type="warning">
Un contenu rendu en HTML brut est une **entrée utilisateur** jusqu’à preuve du contraire. On ne la valide pas en vérifiant qu’elle « a la bonne forme » (un objet), mais en ne gardant que ce qu’on sait rendre sans danger.
</Callout>

## Une liste blanche

Deux stratégies existent pour assainir. Une **liste noire** retire ce qu’on sait dangereux (`javascript:`, `position: fixed`…) ; elle échoue au premier cas qu’on n’a pas prévu (`JaVaScRiPt:`, une entité HTML, une autre propriété CSS). Une **liste blanche** ne garde que ce qu’on sait sûr ; un cas imprévu est retiré par défaut. Le projet utilise la seconde, dans `packages/contracts/src/page/richText.ts`.

D’abord, ce qu’est un lien sûr :

La fonction ne **filtre** pas l’objet reçu, elle en **fabrique** un nouveau. `textAlign` n’est gardé que s’il vaut exactement `left`, `center`, `right` ou `justify` ; un niveau de titre hors de 1 à 6 devient 2 ; une case à cocher est cochée seulement si `checked` vaut exactement `true`. Un attribut qui n’est pas nommé ici n’existe pas dans le résultat — y compris ceux qu’une future version de Tiptap ajouterait.

## Assainir à l’entrée, et à la lecture

Le schéma assainissant est branché là où le texte riche apparaît dans le contrat — le bloc `tiptap`, et la partie texte des blocs média-texte et texte enrobant :

```ts
// packages/contracts/src/page/blocks.v1.ts (extrait)
const tiptapBlockSchema = blockBaseSchema.extend({
  type: z.literal("tiptap"),
  content: richTextContentSchema,
});
```

Il agit donc partout où le contrat est appliqué, sans qu’aucune procédure ait à y penser :

**À l’entrée.** Chaque procédure qui enregistre un contenu valide son entrée avec `pageContentSchemaV1`. Ce qui est écrit en base est le document réécrit, jamais le document reçu.

**À la lecture.** `parsePageContentV1` (chapitre 1) lit avec le même schéma, donc avec la même transformation. Un contenu enregistré **avant** la règle est assaini au moment où il est affiché ; il n’y a pas de migration de données à écrire, et rien à oublier.

<Callout type="tip">
Un `transform` Zod fait d’un schéma un **traducteur** : la valeur qui en sort n’est pas « la valeur reçue, vérifiée », mais « la valeur qu’on accepte de manipuler ». Le reste du code ne voit jamais l’autre.
</Callout>

## Un seul rendu pour tous les blocs

Trois blocs rendent du texte riche (`tiptap`, `media-text`, `float-text`), et deux aperçus de l’éditeur le font aussi. Chacun avait sa propre copie de la liste des extensions et de l’appel à `generateHTML`. Cinq copies, qui avaient déjà divergé : les deux aperçus ne déclaraient pas le nœud `library-image`, et `generateHTML` levait dès qu’un texte contenait une image — l’aperçu entier tombait.

## Les commentaires : l’autre stratégie

Les commentaires des actualités sont aussi des documents ProseMirror, écrits par n’importe quel membre connecté. Ils n’utilisent **pas** `generateHTML` : un petit rendu React parcourt le document et ne fabrique que des éléments qu’il connaît.

Pas de HTML brut du tout : React échappe tout, et un lien n’est posé que si son adresse est sûre. La contrepartie est la pauvreté : paragraphes, gras, italique, liens. C’est suffisant pour un commentaire, pas pour une page.

Les deux sont des listes blanches ; elles diffèrent par l’endroit où elles s’appliquent. Quand le rendu doit être riche, on assainit la **donnée** ; quand il peut être pauvre, on écrit un **rendu** qui ne sait rien faire de dangereux.
