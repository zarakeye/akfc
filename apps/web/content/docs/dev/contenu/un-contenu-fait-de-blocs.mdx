> **Précédemment.** Les fichiers sont envoyés, rangés et validés dans la bibliothèque. Un fichier validé n’est pourtant servi à personne tant qu’il n’est posé nulle part : la route publique exige qu’il soit **placé** dans une page ou une galerie publique. Cette partie raconte ce qui le place.

Cette partie suit un contenu du début à la fin. Ce chapitre décrit son **format**. Les suivants montrent comment le texte riche est rendu sans danger, comment l’éditeur et le rendu se branchent sur ce format, comment un contenu affiché sait quels fichiers il montre, ce qui change quand l’auteur n’est pas un administrateur, et enfin les réglages qui n’appartiennent à aucune page.

## Des textes partout 📝

Le site affiche beaucoup de textes mis en forme : la page « L’association », la description de chaque discipline et sa présentation courte, le contenu d’un cours, la description, le programme et le résumé d’un stage, le contenu et le résumé d’un événement, les actualités, la présentation de chaque instructeur. Chacun mêle des titres, des listes, des liens, des images de la bibliothèque, parfois une galerie ou une liste de documents.

Il existe trois façons courantes d’enregistrer un tel texte.

Le projet a choisi la troisième. Le coût est payé une fois — un éditeur, un schéma, un rendu — puis partagé par tous les contenus.

## Un seul format pour tous les contenus

Tous ces textes sont écrits avec le même outil, le **constructeur de pages**, et enregistrés dans le même format : une liste ordonnée de **blocs**.

<DocsTable columnsJson='["Bloc", "Ce qu’il affiche"]' rowsJson='[["tiptap", "Du texte riche : titres, listes, liens, citations, code, cases à cocher, images de la bibliothèque dans le texte."], ["image-gallery", "Une galerie d’images, en grille, carrousel ou mosaïque, avec légendes."], ["audio-collection", "Une liste de pistes audio."], ["document-list", "Une liste de documents à télécharger."], ["media-text", "Un média (image, vidéo, avatar d’un membre ou logo du site) à côté d’un texte, sur deux colonnes."], ["float-text", "Une petite image que le texte enrobe, comme un portrait dans une présentation."]]' />

Chaque endroit qui accueille un tel contenu est une colonne JSON d’une entité : `SitePage.content`, `Post.content`, `Discipline.description` et `Discipline.summary`, `Course.content`, `Seminar.description`, `program` et `summary`, `Event.content` et `summary`, `User.instructorBio`. Un format unique permet d’écrire **une seule fois** l’éditeur, le rendu, la validation et le recensement des fichiers. Ajouter un type de bloc le rend disponible partout à la fois ; corriger le rendu d’un bloc le corrige sur toutes les pages.

## Le contrat, bloc par bloc

Le format est un **contrat** : un schéma Zod dans `packages/contracts`, importé par le front (l’éditeur, le rendu) comme par le backend (la validation à l’enregistrement). Les deux côtés ne peuvent pas diverger, puisqu’ils lisent le même fichier.

Cet `id` est celui du **bloc**, pas d’un fichier : il distingue deux blocs d’une même page. React s’en sert comme clé quand on réordonne les blocs ; sans lui, déplacer un bloc ferait reprendre à son voisin l’état de son éditeur (le curseur, la sélection).

La différence est voulue. Une alternance est une décision de mise en page, qui dépend de la position du bloc dans la page ; un portrait posé à droite d’un texte est un choix de l’auteur. Ce qui dépend de la position se **calcule** ; ce que l’auteur choisit s’**enregistre**.

## L’union discriminée

Les six schémas sont réunis en une seule union, discriminée par le champ `type` :

  fullFileTitle="Voir le fichier complet"

`z.discriminatedUnion` lit d’abord `type`, puis valide le bloc avec le seul schéma correspondant. Une simple `z.union` essaierait les six schémas l’un après l’autre et, en cas d’échec, rapporterait six listes d’erreurs ; ici l’erreur nomme le bon bloc, ou dit que `type` est inconnu.

Côté TypeScript, l’union donne le **rétrécissement** : dans `if (block.type === "image-gallery")`, le compilateur sait que `block.items` existe. Un `switch` sur `block.type` peut même être vérifié **exhaustif** — le chapitre 5 s’en sert pour qu’aucun bloc n’échappe au recensement des fichiers.

`PageBlockKindV1` est l’union des valeurs de `type` : `"tiptap" | "image-gallery" | …`. Le registre des blocs (chapitre 3) l’utilise pour exiger une définition par type.

## L’enveloppe versionnée

Un contenu n’est pas une liste nue, mais une liste dans une **enveloppe** qui porte un numéro de version :

Une évolution **compatible** — un champ facultatif en plus, un champ avec une valeur par défaut, un ancien format absorbé par un `preprocess` — reste en version 1. Une évolution qui **change le sens** d’un champ ferait une version 2 : un fichier `blocks.v2.ts`, une fonction qui convertit un contenu v1 en v2, et la lecture qui choisit le schéma d’après `version`. Sans numéro dans les données, on ne saurait pas, devant un contenu enregistré il y a deux ans, avec quel schéma le lire.

`emptyPageContentV1()` fabrique un contenu vide. C’est la valeur de départ d’un nouveau contenu, et le repli d’une lecture qui échoue.

## Des références, jamais des URLs 🔗

Aucun bloc ne contient l’URL ni le chemin d’un fichier, seulement son `mediaId`. La partie « Stockage et médias » a montré pourquoi : un fichier se renomme, se déplace, change de statut. Une URL enregistrée dans une page casserait au premier déplacement ; un identifiant ne bouge pas.

L’URL est donc **calculée au rendu**, à partir de l’identifiant, avec la route qui convient au lecteur (la route privée dans l’éditeur, la route publique pour un visiteur). Le chapitre 4 montre ce calcul ; le chapitre 5, comment la base apprend qu’un fichier est placé.

<Callout type="info">
Le même principe vaut pour l’avatar et le logo : on enregistre **qui** (« l’avatar de ce membre », « le logo du site »), jamais **quoi** (un fichier). Ce qui est enregistré ne vieillit pas.
</Callout>

## Lire un contenu enregistré

À l’enregistrement, le schéma **refuse** un contenu invalide : la procédure répond `BAD_REQUEST`, rien n’est écrit. À la lecture, la situation est inverse. Le contenu est déjà en base ; il peut dater d’un ancien format, avoir été écrit avant une règle, ou avoir été abîmé. Refuser ne servirait à rien : la page doit s’afficher.

La dernière étape est la plus importante. Une version antérieure rendait la page **entière** vide dès qu’un seul bloc était invalide. À l’affichage, c’était déjà une perte ; dans l’éditeur, c’était pire : l’administrateur ouvrait une page vide, ajoutait un paragraphe, enregistrait — et tous les autres blocs étaient effacés pour de bon.

<Callout type="warning">
Une lecture tolérante doit perdre **le moins possible**, et le dire. Un repli silencieux et total transforme une petite anomalie de données en perte définitive au premier enregistrement.
</Callout>

Le schéma sert donc deux fois : il **refuse** à l’entrée, il **répare** à la sortie. Le chapitre suivant montre qu’il fait aussi une troisième chose, pour le texte riche : il **assainit**.
