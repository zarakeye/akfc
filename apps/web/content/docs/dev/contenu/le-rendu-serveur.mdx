## Les parcours du chapitre

Deux parcours traversent ce chapitre : le visiteur qui lit une page de contenu, et celui qui parcourt les présentations des instructeurs, où le même rendu est appelé plusieurs fois.

## Le rendu, sur le serveur 🖥️

Une page publique est un composant **serveur** : il s’exécute sur le serveur, lit la base directement, et envoie au navigateur du HTML déjà construit. Le visiteur reçoit le texte et les balises `<img>` d’un coup, sans attendre un JavaScript qui irait chercher le contenu.

La page « L’association » fait quatre choses : décider si le visiteur peut la voir (publiée, ou aperçu d’un administrateur), lire la ligne, la passer au filtre de lecture, la confier au rendu.

## Des blocs qui restent synchrones

Pourquoi ne pas laisser chaque bloc chercher ses propres fichiers ? Deux raisons.

**Le nombre de requêtes.** Une galerie de trente photos ferait trente requêtes, une page de cinq galeries cent cinquante. Rassembler d’abord les identifiants, puis les résoudre en une requête (`WHERE id IN (…)`), fait toujours **une** requête, quel que soit le nombre de fichiers. C’est le problème dit « N+1 » : une requête pour la liste, puis une par élément.

**La simplicité des blocs.** Un composant serveur peut être asynchrone, mais chaque bloc deviendrait alors une petite page, avec ses lectures, ses erreurs et ses attentes. Ici, une `View` est un composant **ordinaire** : elle reçoit son bloc et une fonction qui lit dans une table déjà remplie.

Le patron se généralise : **rassembler** les besoins, **résoudre** en une fois, **distribuer** une fonction de lecture. Les composants restent simples et le nombre de requêtes ne dépend plus de la taille de la page.

Un fichier repassé en attente ou jeté **après** avoir été placé disparaît de la page au rendu suivant. La page ne casse pas : la `View` omet ce qui est `null`. En pratique, les deux cas sont rares, parce que l’enregistrement et la bibliothèque les empêchent (chapitre 5) ; le rendu ne compte pas dessus.

Le rendu public demande l’audience `public` (la valeur par défaut de `PageRenderer`). Une URL privée sur une page publique ne marcherait que pour un visiteur connecté qui a le droit de lire le fichier — c’est-à-dire, presque toujours, pour l’administrateur qui vérifie sa page, et pour personne d’autre. Ce défaut est invisible à celui qui teste connecté : l’affiche des vidéos en était l’exemple.

<Callout type="warning">
Une page publique se vérifie **déconnecté**, dans une fenêtre privée. Connecté, on voit ce que voit un administrateur, pas ce que voit un visiteur.
</Callout>

Une page a pourtant une raison de demander l’audience `admin` : le **brouillon**. Ses fichiers sont recensés dès son premier enregistrement, mais la route publique ne les sert pas tant que le contenu n’est pas publié (chapitre 5). La page d’un brouillon répond 404 à un visiteur ; pour un administrateur, elle s’affiche avec le badge « Page non publiée », et ses fichiers passent par la route privée :

```tsx
// apps/web/src/app/(public)/disciplines/[slug]/page.tsx (extrait)
const access = await draftAccess(isLive(discipline.publicationDate));
if (!access) notFound();
// …
<PageRenderer content={description} audience={audienceFor(access)} />
```

`draftAccess` rend `"public"` pour un contenu publié, `"preview"` pour un brouillon vu par un administrateur, `null` sinon. Les aperçus du tableau de bord rendent toujours en `admin`.

`?variant=large` demande la déclinaison de 1 200 pixels d’une image, fabriquée au besoin par la route (partie « Stockage et médias ») ; `&as=poster`, l’affiche d’une vidéo.

L’URL porte l’identifiant du membre, pas la clé du fichier : si le membre change d’avatar, l’URL ne change pas, et chaque page qui la montre suit. Le logo du site suit le même principe, avec une URL versionnée par la date de modification des réglages (chapitre 7).

<Callout type="info">
La route des avatars sert l’avatar de n’importe quel membre : un avatar est fait pour **représenter** son titulaire, à côté de son nom (un commentaire, l’auteur d’une actualité). Ce qui est interdit, c’est de le **poser** dans un contenu à sa place : un contenu ne montre que l’avatar de son auteur (chapitre 6).
</Callout>

## L’alternance, sans mutation

Les blocs média-texte alternent : le premier place son média à gauche, le deuxième à droite, et ainsi de suite, en ne comptant que les blocs média-texte. La façon naturelle d’écrire cela est un compteur :

```tsx
// Ce que le projet n’écrit PAS
let rank = 0;
content.blocks.map((block) => {
  const side = block.type === "media-text" ? (rank++ % 2 === 0 ? "left" : "right") : undefined;
  // …
});
```

Le **React Compiler** du projet l’interdit : un rendu ne doit modifier aucune variable extérieure, parce que le compilateur se permet de mémoïser, de réordonner ou de rejouer des rendus. Le côté est donc **calculé** à partir de la position :

## Ce que coûte une page

<DocsTable columnsJson='["Lecture", "Requêtes"]' rowsJson='[["La ligne de contenu (la page)", "1"], ["Tous les fichiers de la bibliothèque", "1, quel que soit leur nombre"], ["Tous les avatars", "1, quel que soit leur nombre"], ["Le logo", "1"]]' />

Quatre requêtes pour une page entière. Une limite reste : la page des instructeurs rend **un** `PageRenderer` par présentation, et chacun refait ses lectures — trois requêtes par instructeur, dont la ligne des réglages relue à chaque fois. Pour une dizaine d’instructeurs, c’est négligeable ; pour une centaine, il faudrait préparer les fichiers de toutes les présentations ensemble et les passer à chaque rendu.
