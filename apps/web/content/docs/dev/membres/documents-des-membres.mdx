> **Précédemment.** Le membre a son compte, son mot de passe et son profil. Le club peut maintenant lui transmettre des documents.

Le club diffuse des documents à ses membres : le compte rendu de l'assemblée générale pour tous, une attestation pour une seule personne, un planning pour un groupe. Les membres les retrouvent sur la page « Documents », les lisent dans un panneau d'aperçu, et l'entrée « Documents » du menu signale ce qu'ils n'ont pas encore lu.

## Une publication, pas une copie

Un document des membres est d'abord un fichier de la bibliothèque, rangé dans le finder comme les autres. Le publier ne le copie pas : cela crée une ligne `MemberDocument` qui pointe vers son `MediaAsset` et décrit sa diffusion.

```prisma
// prisma/schema.prisma (extrait)
model MemberDocument {
  /// Identifiant CUID.
  id           String     @id @default(cuid())
  /// Fichier publié (unique).
  mediaAssetId String     @unique
  /// Fichier (1–1, MediaAsset.memberDocument). Supprimer le fichier supprime
  /// la publication (CASCADE).
  mediaAsset   MediaAsset @relation(fields: [mediaAssetId], references: [id], onDelete: Cascade)

  /// Titre affiché. À défaut : nom affiché du fichier, puis son nom d'origine.
  title String?

  /// Diffusion : à tous, ou ciblée (voir DocumentAudience).
  audience DocumentAudience @default(ALL_MEMBERS)
  // …
}
```

Ce choix permet trois choses. Le fichier n'existe qu'une fois : le corriger dans le finder corrige le document des membres. Son nom, son format et son type viennent du `MediaAsset`, sans être recopiés. Et `mediaAssetId` est unique : un même fichier ne peut pas être publié deux fois, avec deux diffusions contradictoires.

La publication vit aussi longtemps que le fichier : la relation est en `onDelete: Cascade`. Un fichier supprimé de la bibliothèque ne laisse pas derrière lui un document fantôme dans la liste des membres. À l'inverse, retirer la publication ne touche pas au fichier.

## Qui reçoit le document

Un document a deux modes de diffusion :

- **`ALL_MEMBERS`** : tous les membres, y compris ceux qui adhèrent après la publication ;
- **`SPECIFIC`** : une diffusion ciblée, vers des **groupes** (`MemberDocumentGroup`), des **personnes** désignées nommément (`MemberDocumentRecipient`), ou les deux à la fois.

Les destinataires ne sont jamais recopiés dans une liste au moment de la publication. La question « ce document concerne-t-il ce membre ? » est posée à chaque lecture, par une seule condition Prisma :

```ts
// packages/backend/src/modules/memberDocuments/visibleTo.ts (extrait)
export function memberDocumentVisibleTo(userId: string) {
  return {
    OR: [
      { audience: "ALL_MEMBERS" as const },
      {
        audience: "SPECIFIC" as const,
        OR: [
          { recipients: { some: { userId } } },
          {
            groups: { some: { group: { memberships: { some: { userId } } } } },
          },
        ],
      },
    ],
  };
}
```

Un groupe est ainsi une liste de diffusion **vivante** : un membre ajouté au groupe « Bureau » reçoit les documents déjà adressés au bureau, et un membre qui en sort ne les voit plus. Aucune tâche de synchronisation n'est nécessaire, puisqu'il n'y a rien à synchroniser.

Toutes les procédures du membre (lister, compter, marquer lu, marquer non lu) passent par cette condition, et la route qui livre le fichier l'importe aussi : ce que le membre voit dans sa liste et ce qu'il peut ouvrir ne peuvent pas diverger. Un membre qui demande à marquer comme lu un document qui ne le concerne pas reçoit « Document introuvable », exactement comme si le document n'existait pas.

## Publier depuis le finder

Les administrateurs publient un fichier sans quitter la bibliothèque, par trois chemins : le menu contextuel d'un fichier (dans les quatre vues du finder), l'option « Rendre les PDF disponibles aux membres » du formulaire d'envoi, et le glisser-déposer dans ce même formulaire. Tous ouvrent la même boîte de dialogue, qui choisit la diffusion, et appellent la même procédure.

Le finder manipule des chemins, pas des identifiants de base. La procédure retrouve donc le fichier par son chemin :

```ts
// packages/backend/src/modules/memberDocuments/router.ts (extrait)
const asset = await ctx.prisma.mediaAsset.findFirst({
  where: {
    OR: [
      { fullPath: input.path },
      { fullPath: { startsWith: `${input.path}.` } },
    ],
  },
  select: { id: true },
});
```

La seconde condition tolère un chemin donné sans son extension, comme le reste du module média. La procédure refuse ensuite un fichier déjà publié (`CONFLICT`), et une diffusion ciblée sans aucun groupe ni aucune personne.

## Lu, non lu

Le suivi de lecture repose sur `DocumentReceipt`, une ligne par membre et par document :

<DocsTable columnsJson='["État","En base","Signalé au membre ?"]' rowsJson='[["Jamais ouvert","pas de ligne","oui"],["Ouvert","readAt = date d’ouverture","non"],["Re-marqué non lu","readAt = null","oui"]]' />

Aucune ligne n'est créée à la publication : un document adressé à deux cents membres n'écrit rien de plus en base. La ligne naît à la première ouverture de l'aperçu, par un `upsert` :

```ts
// packages/backend/src/modules/memberDocuments/router.ts (extrait)
await ctx.prisma.documentReceipt.upsert({
  where: { memberDocumentId_userId: { memberDocumentId: input.id, userId } },
  create: { memberDocumentId: input.id, userId, readAt: new Date() },
  update: { readAt: new Date() },
});
```

« Non lu » se compte donc comme « aucun reçu daté pour ce membre » (`receipts: { none: { userId, readAt: { not: null } } }`), ce qui couvre à la fois l'absence de ligne et la ligne remise à `null`. Le membre peut re-marquer un document comme non lu, pour garder le signal et y revenir plus tard.

### Ce qui est signalé, et à partir de quand

Le badge de l'entrée « Documents » ne signale pas tout l'historique. Un membre qui adhère en octobre ne doit pas trouver vingt documents « non lus » datant d'avant son arrivée. Les documents adressés à tous ne sont signalés qu'à partir du **1er janvier de l'année d'adhésion** :

```ts
// packages/backend/src/modules/memberDocuments/router.ts (extrait)
const yearStart = me?.memberSince
  ? new Date(Date.UTC(me.memberSince.getUTCFullYear(), 0, 1))
  : null;
```

Le début de l'année, et non la date exacte d'adhésion : un membre qui arrive après l'assemblée générale est quand même invité à lire son compte rendu. Les documents plus anciens restent dans la liste de la page ; les lire est une démarche volontaire, pas une alerte. Les documents personnels et ceux des groupes sont toujours signalés : ils ont été adressés à ce membre en particulier.

Le badge affiche un total **distinct** : un document qui atteint le membre par deux chemins (à titre personnel et par son groupe) ne compte qu'une fois. L'infobulle détaille le nombre par provenance : le club, chaque groupe, les documents personnels.

## Servir le fichier aux seuls destinataires

Un document des membres n'a pas d'URL publique, et aucune URL signée de stockage n'est donnée au navigateur. Il est servi par une route du site, `/api/media/member-document/[id]`, qui vérifie la session puis applique la même condition que les procédures :

```ts
// apps/web/src/app/api/media/member-document/[id]/route.ts (extrait)
const session = await getSessionFromRequest(req);
if (!session?.user) {
  return new NextResponse("Unauthorized", { status: 401 });
}
const userId = session.user.id;
// …
if (!doc) return new NextResponse("Not found", { status: 404 });
```

Un document qui existe mais ne concerne pas le membre répond 404, et non 403 : la réponse ne révèle pas qu'il existe.

Le fichier est ensuite lu dans le stockage et transmis par la route elle-même, sous la même origine que le site, avec `Cache-Control: private, no-store`. Deux raisons à ce choix plutôt qu'une redirection vers une URL signée. L'aperçu des PDF (pdf.js) télécharge le fichier en JavaScript, ce qu'une redirection vers un autre domaine bloquerait (CORS). Et chaque accès repasse par la vérification : il n'existe aucun lien qu'un membre pourrait transmettre à quelqu'un d'autre. Le paramètre `?download=1` sert le même fichier en pièce jointe, sous son nom lisible.

<Callout type="info">
Une seule règle de visibilité, posée à chaque lecture : la liste, le badge, le marquage et la livraison du fichier répondent tous à la même question, avec la même condition.
</Callout>

## À suivre

Les documents descendent du club vers ses membres. Certains groupes ont aussi besoin de travailler ensemble : déposer leurs propres fichiers, les ranger, les partager entre eux, sans voir ceux des autres groupes.
