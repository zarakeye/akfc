> **Précédemment.** Les disciplines, les cours, les stages et les événements sont les contenus du club, chacun avec sa façon de porter le temps. Les membres, eux, ont leur propre espace sur le site.

Cette partie suit un membre à travers les fonctions qui lui sont réservées. Ce chapitre commence par son arrivée : la création de son compte, sa première connexion, son profil et son avatar.

## Les parcours du chapitre

Trois cas d'utilisation traversent ce chapitre. Chaque onglet en déroule les étapes et ce qu'elles écrivent en base, relevé dans le code ; chaque étape mène à son explication plus bas, ou à la carte des entités, rejouée à cette étape.

<Parcours />

## Un compte créé par le club

Le site n'a pas d'inscription libre. Un membre s'inscrit au club auprès de la MJC, et c'est un administrateur qui lui ouvre un compte, avec au moins un groupe :

```ts
// packages/backend/src/modules/users/router.ts (extrait)
const password = generateStrongPassword();
const hash = await bcrypt.hash(password, 12);

user = await ctx.prisma.user.create({
  data: {
    email: input.email,
    password: hash,
    ...legal,
    memberGroupMemberships: {
      create: groupIds.map((id) => ({
        group: { connect: { id } },
        access: "EDITOR" as const,
      })),
    },
  },
  omit: { password: true },
});
```

Le mot de passe est **généré par le serveur** : 12 caractères mêlant majuscules, minuscules, chiffres et symboles, sans caractères faciles à confondre. Chaque membre reçoit ainsi un mot de passe robuste, qu'il soit ou non familier des règles qui le rendent difficile à deviner. Il peut le garder, ou le changer depuis son profil. L'administrateur ne le voit jamais, et seule son empreinte bcrypt est enregistrée ; `omit` la retire de la ligne renvoyée au navigateur de l'administrateur.

Le compte et ses groupes sont créés par une seule écriture imbriquée : un compte sans groupe ne peut pas exister, même un instant. L'e-mail de bienvenue part **après** la création ; un échec d'envoi n'annule pas le compte. Les comptes de démonstration (`@akfc.demo`) ne reçoivent pas d'e-mail, puisque leur adresse ne mène nulle part.

## Un mot de passe qui ne va qu'au membre

L'e-mail de bienvenue contient le mot de passe. Il doit donc aboutir dans la boîte du membre, et nulle part ailleurs. Or un e-mail circule : on y répond en citant son contenu, et un e-mail qui ne peut pas être remis revient à l'expéditeur sous forme d'avis de non-remise (un « rebond »), qui recopie souvent le message d'origine. Le site envoie depuis `noreply@`, et la boîte du club, `contact@`, garde la mémoire des échanges : il faut que cette mémoire ne contienne jamais de mot de passe.

Deux réglages de l'envoi y veillent :

```ts
// packages/backend/src/email/templates/welcomeEmailWithPassword.ts (extrait)
const message: SMTPTransport.Options = {
  from: mailFrom(shortTitle),
  to,
  // Pas de replyTo : une réponse citerait le mot de passe.
  // Rebond : en-têtes seulement (jamais le corps, donc jamais le mot de passe).
  // (Transmis seulement si le serveur SMTP annonce l'extension DSN.)
  dsn: { ret: "HDRS", notify: ["FAILURE", "DELAY"], orcpt: to },
  subject: `Bienvenue à l'${shortTitle} : ${WELCOME_SUBJECT_MARK}`,
  // …
};
```

- **Pas d'adresse de réponse.** Les autres e-mails du site indiquent `contact@` comme adresse de réponse. Celui-ci non : une réponse revient à `noreply@`. Le texte du message le dit, et donne l'adresse du club pour écrire.
- **Un rebond sans le message.** L'option `dsn` demande au serveur d'envoi, en cas d'échec, un avis qui ne contient que les en-têtes du message (`RET=HDRS`, extension DSN du protocole SMTP), donc pas le mot de passe.

Le reste est confié aux filtres de la boîte `noreply@`, dans la messagerie du club. Les avis de non-remise sont transférés à `contact@`, pour que les administrateurs vérifient l'adresse du membre. Un dernier filtre supprime toute réponse dont l'objet contient « ton compte est créé » : c'est la constante `WELCOME_SUBJECT_MARK`, qui ne doit pas changer sans que ce filtre change aussi.

La boîte du club garde malgré tout la trace de chaque création. Le site lui envoie un **avis sans mot de passe** : compte créé pour telle adresse, par tel administrateur, dans tels groupes, ou bien e-mail impossible à envoyer, avec l'erreur.

<Callout type="info">
Le partage des rôles est net : le site décide de ce que contient chaque message, la messagerie décide où va le courrier reçu par `noreply@`. Aucun des deux ne refait le travail de l'autre.
</Callout>

## La première connexion

Un compte naît avec `isFirstLogin` à vrai : le membre n'a pas encore complété son profil. Tant que c'est le cas, il est ramené sur la page d'édition de son profil. La redirection est faite par un petit composant client, placé dans le layout du site public :

```tsx
// apps/web/src/features/auth/FirstLoginRedirect.tsx (extrait)
useEffect(() => {
  if (!user?.isFirstLogin) return;
  if (pathname === "/profil/edit") return;
  router.replace("/profil/edit");
}, [user?.isFirstLogin, pathname, router]);
```

Il lit la session dans le store client, et ne redirige jamais depuis la page de destination elle-même : aucune boucle n'est possible. `replace` plutôt que `push` : le bouton « précédent » ne ramène pas sur la page dont le membre vient d'être redirigé. Le drapeau retombe quand le membre enregistre son profil.

### Relire la session après une écriture

Le store client contient la session lue au chargement de la page. Une server action modifie la base, mais pas ce store : après l'enregistrement du profil, il porterait encore `isFirstLogin` à vrai, et le membre serait aussitôt ramené sur le formulaire. Le formulaire relit donc la session avant de quitter la page :

```tsx
// apps/web/src/features/admin/users/forms/update-me/UpdateMeForm.tsx (extrait)
void useSessionStore
  .getState()
  .fetchSession()
  .then(() => router.push(back.href));
```

La même relecture met à jour le nom affiché dans le header.

<Callout type="info">
Toute donnée de la session affichée par le client (nom, avatar, état de la première connexion) doit être rafraîchie dans le store après l'écriture qui la change. Le serveur a la bonne valeur ; c'est la copie du navigateur qui retarde.
</Callout>

## Le profil, scellé sur son titulaire

Le formulaire du profil (prénom, nom, pseudo, présentation, téléphone, date de naissance) est envoyé par une **server action**. Elle ne reçoit aucun identifiant d'utilisateur : elle prend celui de la session.

```ts
// apps/web/src/features/admin/users/forms/update-me/updateMeForm.action.ts (extrait)
const sessionClient = await getSessionFromRequest();
const userId = sessionClient?.user?.id;

if (!userId) {
  return {
    status: "error",
    error: "Vous devez être connecté pour mettre à jour votre profil.",
  };
}
```

Une server action est un point d'accès public, que n'importe qui peut appeler avec les données de son choix. Si le formulaire envoyait l'identifiant du compte à modifier, il suffirait d'en changer la valeur pour modifier le profil d'un autre membre. En le lisant dans la session, l'action ne peut modifier qu'un seul profil : celui de la personne connectée.

Les données sont validées par un schéma Zod partagé (`updateMeFormSchema`, dans `packages/contracts`), utilisé à la fois par le formulaire pour afficher les erreurs pendant la saisie, et par l'action, qui ne fait jamais confiance au navigateur. Le chapitre sur les formulaires détaille ce montage.

## L'avatar, un envoi à part

L'avatar ne passe pas par le formulaire du profil. Il suit le circuit des fichiers vu dans la partie « Stockage et médias » : le navigateur demande une autorisation d'envoi, envoie l'image directement au stockage, puis fait enregistrer le résultat.

```ts
// packages/backend/src/modules/avatar/avatar.service.ts (extrait)
if (!path.startsWith(`${avatarFolder(appRoot, userId)}/`) || path.includes("..") || !isAvatarKey(path)) {
  throw new Error("Chemin hors de l'espace avatar de l'utilisateur.");
}
const head = await getR2Client()
  .send(new HeadObjectCommand({ Bucket: getR2Bucket(), Key: path }))
  .catch(() => null);
if (!head) throw new Error("Avatar introuvable : l'envoi n'a pas abouti.");
if (!(head.ContentType ?? "").startsWith("image/") || (head.ContentLength ?? 0) > AVATAR_MAX_BYTES) {
  await removeAvatarFile(path);
  throw new Error("Fichier d'avatar refusé.");
}
```

L'enregistrement ne croit pas le navigateur sur parole. Le chemin reçu doit se trouver dans le dossier d'avatars **de l'utilisateur connecté**, dérivé de son identifiant par le serveur. Le fichier doit exister réellement, être une image, et ne pas dépasser 10 Mo, ce que le serveur vérifie en interrogeant le stockage lui-même (`HeadObject`). Un fichier refusé est supprimé. Une fois le nouvel avatar enregistré, l'ancien fichier est effacé.

Un avatar est **public** : il s'affiche à côté d'un nom, y compris sur des pages que tout le monde peut lire (la page des instructeurs, par exemple). Il est servi par une route dédiée, `/api/media/public/avatar/[userId]`, qui prend un identifiant d'utilisateur et non un chemin de fichier. Elle ne peut donc servir rien d'autre qu'un avatar, alors qu'une route acceptant un chemin pourrait être détournée vers n'importe quel fichier.

## Le nom affiché

Partout où un membre apparaît (commentaires, réactions, demandes, fichiers des espaces de groupe), son nom passe par une même fonction :

```ts
// apps/web/src/features/social/userDisplay.ts (extrait)
export function formatUserName(u: DisplayUser): string {
  const full = [u.firstName, u.lastName]
    .filter((p): p is string => Boolean(p?.trim()))
    .join(" ")
    .trim();
  return full || u.pseudo || u.email || "Membre";
}
```

Le prénom et le nom, sinon le pseudo, sinon « Membre ». L'adresse e-mail n'est un recours que lorsque l'appelant l'a fournie, c'est-à-dire là où il a le droit de la voir : un administrateur, ou le membre lui-même sur sa propre page. Les données envoyées aux autres membres et aux visiteurs n'en contiennent jamais (voir le chapitre sur la frontière serveur / client).
