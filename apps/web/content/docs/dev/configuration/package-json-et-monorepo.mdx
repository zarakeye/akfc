> **Précédemment.** Le projet est installé, vérifié par `pnpm check`, et nous savons travailler avec. Avant d'entrer dans le code, regardons les fichiers qui disent à chaque outil comment le lire.

Cette partie passe en revue les fichiers de configuration du dépôt : ce qu'ils règlent, qui les lit, et ce qui casse quand on y touche. Elle commence par le plus central, le `package.json`, et par ce qu'il devient dans un **monorepo** : plusieurs paquets dans un seul dépôt Git.

## Un dépôt, quatre paquets

pnpm sait qu'il gère plusieurs paquets parce qu'un fichier, à la racine, le lui dit :

```yaml
# pnpm-workspace.yaml (extrait)
packages:
  - apps/*
  - packages/*
```

Chaque dossier de `apps/` et de `packages/` qui contient un `package.json` est un **paquet** du workspace. `pnpm install`, lancé une fois à la racine, installe les dépendances de tous les paquets d'un coup, dans un seul `node_modules` partagé.

Le **nom** d'un paquet est celui de son `package.json`, pas celui de son dossier. C'est lui qu'utilise l'option `--filter` : `pnpm --filter web build` lance le script `build` du paquet `@akfc/web`. Un nom à portée (`@akfc/backend`) peut être désigné sans sa portée tant qu'il n'y a pas d'ambiguïté : `pnpm --filter backend typecheck`, que lance `pnpm check`, vise `@akfc/backend`.

## Le package.json d'un paquet

Le plus court du dépôt montre tout ce qu'un paquet déclare :

```json
// packages/finder-core/package.json (fichier complet)
{
  "name": "@akfc/finder-core",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "imports": {
    "#*": "./src/*"
  },
  "exports": {
    "./*": "./src/*"
  },
  "scripts": {
    "typecheck": "tsc --noEmit"
  },
  "dependencies": {
    "@akfc/contracts": "workspace:*"
  }
}
```

`"workspace:*"` est propre aux workspaces pnpm : la dépendance n'est pas téléchargée du registre, c'est le dossier `packages/contracts` lui-même, relié par un lien symbolique dans `node_modules/@akfc/contracts`. Une modification de `contracts` est donc visible immédiatement par les paquets qui en dépendent, sans publication ni réinstallation.

Les paquets ne sont **pas compilés** séparément : il n'y a pas de dossier `dist/`. Leurs fichiers TypeScript sont lus tels quels par Next.js et par `tsc`, comme s'ils faisaient partie de l'application. C'est ce qui permet de modifier le backend et de voir le changement au rechargement suivant.

## Un seul mécanisme pour se joindre

Un import du projet a trois formes, et une seule règle pour chacune :

<DocsTable columnsJson='["Forme", "Exemple", "Ce qu’elle désigne"]' rowsJson='[["« # » + chemin", "#features/docs/ui/Callout.tsx", "Un fichier du MÊME paquet, depuis son dossier src (champ imports de son package.json)."], ["« @akfc/ » + paquet + chemin", "@akfc/backend/prisma.ts", "Un fichier d’un AUTRE paquet du dépôt, depuis son src (champ exports du paquet visé, et dépendance workspace:* chez l’importeur)."], ["Un nom de paquet npm", "zod, @prisma/client", "Une bibliothèque installée dans node_modules."]]' />

Le chemin nomme le fichier **avec son extension** (`.ts`, `.tsx`) : les champs `imports` et `exports` associent un motif à un chemin, sans deviner d'extension ni chercher un `index`. C'est exigeant, mais sans surprise : l'import dit exactement quel fichier il lit.

Ces deux champs sont un standard de Node, pas une option de TypeScript. TypeScript, Node, webpack (le build) et Turbopack (le serveur de développement) les lisent tous dans le même `package.json`, celui du paquet **qui contient le fichier importeur**. Il n'y a donc plus de liste d'alias à recopier d'un `tsconfig` à l'autre (chapitre suivant).

<Callout type="info">
**Avant**, le projet avait trois mécanismes pour la même chose : une quinzaine d'alias de `tsconfig` (`@features/…`, `@backend/…`, `@/…`, dont deux pour le même dossier et deux qui portaient le nom de vrais paquets npm, `@trpc/…` et `@types/…`), quelques imports par nom de paquet (`@workspace/finder-core/cart`), et les dépendances `workspace:*`. Un script a réécrit les quelque 2 200 imports concernés vers les deux formes ci-dessus.
</Callout>

## Les dépendances : où elles sont déclarées

La règle d'un monorepo : **chaque paquet déclare ce qu'il importe**. `zod` figure ainsi dans trois `package.json` (contracts, backend, web), `@trpc/server` dans deux, `react` dans celui du web seulement. pnpm n'installe pas trois copies : il en garde une dans son magasin et la relie là où elle est déclarée.

Ce n'était pas le cas au départ : le `package.json` de la racine portait l'essentiel des dépendances, et le code les trouvait grâce à la résolution de Node, qui remonte de dossier en dossier jusqu'à la racine. Rien n'empêchait alors un paquet d'importer une bibliothèque qu'il ne déclarait pas, et 34 dépendances n'étaient plus importées par personne (Material UI, Emotion, bcrypt doublé de bcryptjs, des extensions Tiptap, le paquet `fs` du registre…). Un relevé des imports de chaque paquet a remis chaque dépendance à sa place, et retiré les autres.

### dependencies et devDependencies

`dependencies` liste ce dont le code a besoin pour tourner, `devDependencies` ce qui ne sert qu'à le développer (types, linters, outils de build). Pour une application privée comme celle-ci, la différence est surtout documentaire : l'image de production installe tout, puis Next.js ne garde dans son build que ce que le code utilise réellement.

```dockerfile
# Dockerfile (extrait)
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
  pnpm config set store-dir /pnpm/store \
  && pnpm install --frozen-lockfile
```

### Les versions et le fichier de verrouillage

Dans un `package.json`, `"zod": "^4.1.12"` est une **plage** : toute version 4 à partir de 4.1.12. La version réellement installée est écrite, avec son empreinte, dans `pnpm-lock.yaml`, pour chaque paquet de l'arbre de dépendances. Ce fichier est versionné : tous les développeurs et le serveur installent exactement les mêmes versions.

`pnpm install` met le fichier de verrouillage à jour si un `package.json` a changé. `pnpm install --frozen-lockfile`, utilisé par le `Dockerfile`, refuse au contraire de le modifier et échoue si le fichier ne correspond plus aux `package.json` : la production n'installe jamais une version qui n'a pas été vue en développement.

<Callout type="warning">
Ajouter une dépendance se fait avec `pnpm --filter <paquet> add <dépendance>` dans le paquet qui l'importe (ou `pnpm add -w <dépendance>` pour l'outillage de la racine), qui met à jour le `package.json` **et** le fichier de verrouillage. Chaque chapitre de cette documentation donne la commande de chaque dépendance au moment où elle sert pour la première fois. Modifier le `package.json` à la main sans relancer `pnpm install` laisse les deux en désaccord, et la construction de l'image échoue.
</Callout>

### Forcer une version : overrides

Deux bibliothèques peuvent demander deux versions différentes d'une même dépendance. Pour l'éditeur de texte, deux copies de `@tiptap/pm` dans l'arbre cassaient l'éditeur : chacune croyait être la seule. Le champ `pnpm.overrides` impose une version unique à tout l'arbre :

```json
// package.json (extrait)
"pnpm": {
  "overrides": {
    "@tiptap/pm": "3.27.3",
    "@tiptap/core": "3.27.3"
  }
},
```

### Les scripts d'installation des dépendances

Certaines bibliothèques lancent un script à leur installation (compiler un binaire natif, télécharger un fichier). Depuis la version 10, pnpm ne les exécute plus par défaut : c'est une protection contre un paquet malveillant. Chaque exception se déclare dans `pnpm-workspace.yaml` ; le projet y range `sharp` parmi les scripts **ignorés**, ses binaires précompilés arrivant par des paquets séparés :

```yaml
# pnpm-workspace.yaml (extrait)
ignoredBuiltDependencies:
  - sharp
```

## Les scripts

Le champ `scripts` donne un nom court aux commandes du projet. `pnpm dev` lance le script `dev` du `package.json` le plus proche ; s'il n'existe pas, pnpm cherche une commande installée du même nom.

Les scripts de la racine délèguent souvent au paquet concerné, qui a les siens :

```json
// apps/web/package.json (extrait)
"scripts": {
  "dev": "next dev",
  "build": "next build --webpack",
  "start": "next start",
  "lint": "eslint . --max-warnings 0",
  "typecheck": "tsc --noEmit"
},
```

`postinstall` est un nom réservé : pnpm l'exécute de lui-même après `pnpm install`, comme `preinstall` avant. Les autres noms ne s'exécutent que lorsqu'on les appelle.
