> **Précédemment.** Le Dockerfile produit deux images : un migrateur, qui applique les migrations puis s’arrête, et le service, qui ne contient que ce qui s’exécute, sans un seul secret.

Ce chapitre décrit **un modèle** d’infrastructure : celui du projet, débarrassé de ce qui lui est propre (noms de machine, adresses, autres sites hébergés). Les noms de domaine sont des exemples (`example.org`) et aucun secret n’y figure. On peut le reprendre tel quel pour héberger le site, ou un autre projet bâti de la même façon.

## Les mots du serveur

- Un **serveur loué** (un *VPS*, serveur privé virtuel) est une machine Linux chez un hébergeur, joignable depuis Internet à une adresse fixe, sur laquelle on se connecte en SSH.
- Un **proxy inverse** est le serveur web placé devant les sites : il reçoit toutes les requêtes des visiteurs, s’occupe du HTTPS, et transmet chacune au conteneur du bon site selon le nom de domaine demandé. Ici, **Caddy**.
- Un **déploiement** remplace la version du site qui tourne sur le serveur par une nouvelle, sans perdre de données.
- Le **migrateur** est un conteneur lancé à chaque déploiement, avant le site : il applique les migrations en attente, puis s’arrête.
- Les **journaux** (*logs*) sont ce que le site écrit pendant qu’il tourne : démarrages, erreurs, tâches de la nuit. Sur un serveur, c’est le seul moyen de savoir ce qui s’est passé.

## Le schéma

Un visiteur ne parle qu’à Caddy, sur les ports 80 et 443. Caddy parle au site, sur le réseau `web` ; le site parle à la base, sur le réseau `internal`. La base n’a **aucun** port ouvert sur la machine, et le réseau `internal` n’a pas de sortie vers Internet : même un conteneur compromis sur ce réseau ne peut rien envoyer au dehors.

pgAdmin n’est pas servi aux visiteurs, et il est pourtant aussi sur le réseau `web`. Un réseau `internal` n’a pas de passerelle vers la machine : un port publié n’y mène nulle part. Pour que `127.0.0.1:5050` du serveur atteigne pgAdmin, il lui faut un réseau ordinaire. Il est sur `internal` pour joindre la base.

## Le dossier d’infrastructure

Tout ce qui décrit le serveur vit dans un seul dossier, par exemple `~/infra`. Il est **versionné dans un dépôt Git privé, distinct de celui du site** : le dépôt du site décrit le site ; celui-ci décrit le serveur, qui peut héberger plusieurs sites.

<Arbre racine="infra/" texte="
docker-compose.yml          # tous les services du serveur — versionné
.env                        # secrets du compose (mot de passe Postgres…) — tapé sur le serveur, jamais versionné
.gitignore                  # tout ignorer, puis ré-autoriser ce qui est connu et sans secret
caddy/Caddyfile             # les sites et leurs domaines — versionné
caddy/data/                 # certificats HTTPS — non versionné
postgres/data/              # les données de toutes les bases — non versionné, à sauvegarder
postgres/init/              # création des bases et des utilisateurs au premier démarrage — en modèle, sans mot de passe
pgadmin/data/               # réglages de pgAdmin — non versionné
apps/akfc/                  # un clone du dépôt du site, mis à jour par git pull — ignoré par le dépôt d’infrastructure
apps/akfc/.env              # secrets du site — tapé sur le serveur, jamais versionné
" />

Le `.gitignore` du dépôt d’infrastructure fonctionne **à l’envers** de l’habitude : il ignore tout (`*`), puis ré-autorise un par un les fichiers connus et sans secret (`!docker-compose.yml`, `!caddy/Caddyfile`…). Un fichier nouveau, un dump oublié, un `.env` de plus restent donc hors du dépôt tant qu’on ne les a pas autorisés. Un fichier qui doit contenir un mot de passe (un script de `postgres/init/`) est versionné en **modèle** (`.template`), le mot de passe remplacé par un repère ; le vrai fichier, lui, est ignoré.

Les données sont dans des **dossiers de la machine** montés dans les conteneurs (*bind mounts*), pas dans des volumes nommés : on les voit, on connaît leur chemin, on sait ce qu’il faut sauvegarder. Le dépôt restaure la configuration ; les sauvegardes, les données. Les deux sont nécessaires : après une panne de disque, un dépôt sans données redonne un serveur vide, des données sans dépôt un serveur qu’il faut redécrire de mémoire.

## Le compose du serveur

<CodeSnippet
  language="yaml"
  title="docker-compose.yml (modèle, dans le dossier d’infrastructure)"
  kind="pattern"
  codeJson='"name: infra\n\nservices:\n  caddy:\n    image: caddy:2\n    restart: unless-stopped\n    ports:\n      - \"80:80\"\n      - \"443:443\"\n    volumes:\n      - ./caddy/Caddyfile:/etc/caddy/Caddyfile:ro\n      - ./caddy/data:/data\n    networks: [web]\n\n  postgres:\n    image: postgres:17\n    restart: unless-stopped\n    environment:\n      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}\n    volumes:\n      - ./postgres/data:/var/lib/postgresql/data\n      - ./postgres/init:/docker-entrypoint-initdb.d:ro\n    healthcheck:\n      test: [\"CMD-SHELL\", \"pg_isready -U postgres\"]\n      interval: 5s\n      retries: 20\n    networks: [internal]\n\n  akfc-migrator:\n    build:\n      context: ./apps/akfc\n      target: migrator\n    restart: \"no\"\n    env_file: ./apps/akfc/.env\n    depends_on:\n      postgres:\n        condition: service_healthy\n    networks: [internal]\n\n  akfc:\n    build:\n      context: ./apps/akfc\n      target: runner\n    restart: unless-stopped\n    env_file: ./apps/akfc/.env\n    depends_on:\n      akfc-migrator:\n        condition: service_completed_successfully\n    networks: [web, internal]\n\n  pgadmin:\n    image: dpage/pgadmin4:9\n    restart: unless-stopped\n    environment:\n      PGADMIN_DEFAULT_EMAIL: ${PGADMIN_EMAIL}\n      PGADMIN_DEFAULT_PASSWORD: ${PGADMIN_PASSWORD}\n    ports:\n      - \"127.0.0.1:5050:80\"\n    volumes:\n      - ./pgadmin/data:/var/lib/pgadmin\n    networks: [web, internal]\n\nnetworks:\n  web:\n  internal:\n    internal: true"'
/>

Ce qui change par rapport au compose de développement :

- **`restart: unless-stopped`** : un conteneur qui s’arrête sur une erreur est relancé, et tous redémarrent avec le serveur. Sauf le migrateur (`restart: "no"`), qui doit tourner une fois par déploiement, pas en boucle.
- **`build`** au lieu d’`image` pour le site : le serveur construit lui-même les deux images du chapitre 3, à partir du clone, en choisissant l’étape (`target`). Il les construit pour sa propre architecture.
- **`depends_on` avec une condition** : le migrateur attend que la base soit `healthy` ; le site attend que le migrateur se soit **terminé sans erreur** (`service_completed_successfully`). Une migration qui échoue empêche donc le nouveau site de démarrer, et l’ancien continue de servir. Le migrateur n’est que sur le réseau `internal`, sans sortie vers Internet : rien de ce qu’il fait au lancement ne doit télécharger quoi que ce soit. C’est pourquoi son image télécharge pnpm **au build** (chapitre 3) : au lancement, `pnpm prisma migrate deploy` n’a besoin que de la base.
- **`env_file`** : les secrets arrivent au conteneur au démarrage, depuis un fichier du serveur. Dans ce fichier, l’hôte de la base est le **nom du service**, `postgres`, pas `localhost` : dans un conteneur, `localhost` désigne le conteneur lui-même.
- **`${POSTGRES_PASSWORD}`** : Compose remplace cette expression par la valeur du `.env` posé à côté de lui. Le fichier versionné ne contient que le nom de la variable.
- **Aucun port publié**, sauf ceux de Caddy et celui de pgAdmin, limité à `127.0.0.1`.
- **Des versions majeures, pas des versions exactes** : `caddy:2`, `postgres:17`, `dpage/pgadmin4:9`. En développement, les images sont figées au chiffre près (`seaweedfs:4.52`). Sur le serveur, on fige la version **majeure**, celle qui peut casser : une mise à jour corrective ou de sécurité arrive au prochain `docker compose pull`, sans qu’un `latest` fasse un jour passer Postgres de 17 à 18. Un changement de version majeure se décide, et pour Postgres il se prépare : les données d’une version ne se lisent pas avec la suivante.

👉 sur le serveur, on fige ce qui peut casser, et on laisse passer les correctifs

<Callout type="warning">
**Un port publié contourne le pare-feu.** Sur Linux, Docker écrit ses propres règles réseau, qui passent **avant** celles d’un pare-feu comme `ufw`. Un `ports: "5432:5432"` ouvre la base à Internet même si `ufw` n’autorise que 22, 80 et 443. D’où les deux règles de ce modèle : ne publier que ce qui doit l’être, et préfixer par `127.0.0.1` tout ce qui ne sert qu’à l’administrateur.
</Callout>

## Le proxy inverse

<CodeSnippet
  language="txt"
  title="caddy/Caddyfile (modèle)"
  kind="pattern"
  codeJson='"akfc.example.org {\n\treverse_proxy akfc:3000\n}"'
/>

Trois lignes par site. Quand le nom de domaine pointe vers l’adresse du serveur et que les ports 80 et 443 sont ouverts, Caddy obtient seul un certificat HTTPS (Let’s Encrypt), le renouvelle avant son expiration, et redirige le HTTP vers le HTTPS. `akfc:3000` est le nom du service du site et son port, résolus sur le réseau `web`. Héberger un second site, c’est un second bloc, et un second service dans le compose.

Après une modification du Caddyfile, Caddy relit sa configuration sans couper les sites en cours :

```bash
docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile
```

## Administrer la base

pgAdmin n’est pas exposé sur Internet : son port n’est publié que sur `127.0.0.1` **du serveur**. Pour s’en servir depuis sa machine, on ouvre un **tunnel SSH**, qui fait passer un port local par la connexion SSH :

```bash
ssh -L 5050:127.0.0.1:5050 utilisateur@serveur
```

Tant que la connexion est ouverte, `http://localhost:5050` sur la machine affiche le pgAdmin du serveur. L’accès est protégé par la clé SSH, en plus du mot de passe de pgAdmin. Dans pgAdmin, l’hôte de la base est, là encore, le nom du service : `postgres`.

<Callout type="info">
**Plusieurs sites, une seule base.** Quand plusieurs applications partagent le même Postgres, chacune ouvre ses propres connexions, et leur nombre total peut dépasser la limite du serveur. Un **pgbouncer**, placé entre les applications et Postgres sur le réseau `internal`, les regroupe. Ce n’est pas indispensable pour un site seul ; si on l’ajoute, Prisma doit le savoir (`pgbouncer=true` dans l’adresse de la base).
</Callout>

## Ce que nous devons savoir expliquer

Avant de passer à la qualité, nous devrions pouvoir expliquer :

- ce qu’est un proxy inverse, et ce que Caddy fait seul pour le HTTPS ;
- pourquoi deux réseaux, et ce qu’un réseau `internal` interdit ;
- pourquoi le dossier d’infrastructure est un dépôt privé à part, et pourquoi son `.gitignore` ignore tout par défaut ;
- pourquoi les données du serveur sont dans des dossiers de la machine, et ce qu’il faut sauvegarder ;
- comment le migrateur passe avant le site, et ce qui se passe si une migration échoue ;
- d’où viennent les secrets d’un conteneur, et pourquoi l’hôte de la base est `postgres` et pas `localhost` ;
- pourquoi un port publié contourne le pare-feu, et comment administrer la base par un tunnel SSH ;
- à quelle version figer une image de serveur.
